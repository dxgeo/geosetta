#+TITLE: Plan: A Columnar IR
#+AUTHOR: Daniel Okuniewicz Jr.

* A Columnar IR

** STATUS -- C0 through C6 done
C0's harness is built, and C1 (2026-11-02): the =table= module behind the
collection's private storage, its views, selections and edits, =--layout=,
and both property tests (§ MILESTONES, C1). C2 the same day: the tabular
spokes read into column blocks and write from either form (§ MILESTONES,
C2), and C3: GeoJSON reads into blocks, sealed by D-C13's rule, and
writes from views (§ MILESTONES, C3); C4: KML the same, after
=performance.org='s KML step 2 (§ MILESTONES, C4); C5: the hub is only
blocks, and D-C8's API is public (§ MILESTONES, C5). C6 (2026-11-05):
geometry in flat buffers, every attribute editable (D-C16), every writer
reading views and the hot readers writing coordinates; polygons faster
than C5 and points a few percent slower, accepted (§ MILESTONES, C6). Written 2026-10-28, after
=performance.org='s /Memory/ section measured where the hub's bytes go and
Mem1--Mem5 took the contained wins. What remains is the shape of the IR
itself, and that is this plan.

Revised the same day, after weighing what the row IR gives that a table
does not (§ ALTERNATIVES CONSIDERED) and how duckdb and polars handle
row-shaped work. The first draft's one dense table was never worse than
today per cell but could be far worse per collection on sparse input. The
collection is now a sequence of blocks, each its own small table (D-C10),
with filters and sorts carried as selection vectors (D-C11).

Revised 2026-10-29: edits go through an overlay, with column-sized and
per-block edits first-class (D-C12), compared against today's row edits in
§ IN-FLIGHT EDITS. Then the same day: a block is columns or shaped rows,
chosen by the reader as it seals (D-C13), and =--layout= lets the user force
one form (D-C14). The hybrid is the first form of the design to try.

Smoke-tested 2026-10-29 with a scratch prototype outside the crate (§ SMOKE
TEST): the memory estimates hold, a block's column order changed from
first-seen to modal (D-C4), and pure columns turned out worse than today on
ragged GeoJSON, which only the hybrid avoids.

Revised 2026-11-02: C1's on-demand conversion decided (D-C15). The storage
goes private behind accessors, and the pipeline converts once, by =&mut=,
to the form the target's writer reads.

Revised 2026-11-02, after C5: D-C6 decides C6's layout -- GeoArrow-shaped,
not conformant, for per-position Z and M, mixed types and collections -- and
that a block holds geometry columns, so multiple geometry columns
(=multi-geometry-columns.org=) build on it.

Revised 2026-11-05, after C6: a geometry is read in place through public
views (D-C17), for nazca's =Sink=.

Revised 2026-11-05: geometry edits through the API are never worse than
today's (D-C16). A block's geometry is flat or owned, the API hands out an
owned =Geometry= to edit, and C6 pins the edit contract before it changes
any storage, and stops after measuring if geometry is not worth it.

** WHY
The hub stores a collection as rows: =FeatureCollection { features:
Vec<Feature> }=, and each =Feature= owns =properties: Vec<(Rc<str>,
JsonValue)>=. A cell is 48 bytes: a 16-byte key pointer and a 32-byte value,
plus a heap allocation for every string. Measured (=performance.org=, the
probe):
| collection                          | IR held     | per row     |
|-------------------------------------+-------------+-------------|
| 100 000 mixed features, 4 props     | 33.2 MB     | 348 B       |
| 50 000 points × 200 typed props     | 484.8 MB    | 10 168 B    |
On the wide table geosetta peaks at 820--850 MB where duckdb peaks at
130--230 MB (=compare.py=, 2026-10-28), and every contained fix has been
taken. The row layout is the remaining cost, and it is paid twice more on
the way through: a Parquet read transposes columns into rows, and every
tabular write transposes them back (=schema::infer_columns=).

Columnar storage holds a number in 8 bytes, a boolean in a bit, and a string
as its own bytes plus an offset, with no allocation per cell. The wide
fixture's columns are a quarter each integer, float, string (=v12345_67=)
and boolean, so a row is about 50 × 8 + 50 × 8 + 50 × ~15 + 50 / 8 ≈ 1.6 KB:
*~80 MB for the table that is 485 MB today.* The narrow collection's
properties fall from ~200 bytes a row to ~25, leaving geometry as most of
what is left.

** THE GOAL
The hub is a table of blocks, each columns or shaped rows as its data
suits (D-C13). Every reader builds one, every writer reads one, and nothing
in between materializes =Feature=s -- with *every same-format guarantee
the row IR gives today kept exactly*. The equivalence corpus (C0) is
byte-identical before and after every milestone; this is a change of
representation, not of behaviour.

** WHAT A ROW IR GIVES THAT A TABLE MUST STILL GIVE
Each of these is a guarantee some format relies on today. A table that
loses one has changed behaviour, so each needs a home in the design:
1. *Absent is not null.* GeoJSON's ={"a": null}= and a feature with no =a=
   are different documents, and both come back as they went in.
2. *Each feature's own key order.* A GeoJSON feature writes its properties
   in the order it read them, whatever order its neighbours used.
3. *Duplicate keys in one feature.* The JSON model keeps them as separate
   members (=schema.rs='s =duplicate_key_in_one_row_keeps_the_first_value=);
   GeoJSON writes both back.
4. *A value's own type, per cell.* =1=, =1.0= and ="1"= in one column are
   three values. =JsonValue::Int= is exact to 64 bits; =1= and =1.0= are
   written differently.
5. *Nested values.* Arrays and objects are values (=Mixed=-only today).
6. *Per-feature natives.* GeoJSON's =id= and foreign members, a GeoPackage
   feature's carried fid, a KML feature's element. Almost always absent.
7. *Order is meaning.* =--sort-hilbert= reorders features; nothing else may.

** DECISIONS (proposed)
*** D-C1 -- the collection is a table; a row is a view
#+begin_src rust
pub struct FeatureCollection {
    len: usize,
    geometry: GeometryColumn,       // flat buffers (D-C6)
    columns: Vec<Column>,           // in a block, its modal key order (D-C4)
    shapes: RowShapes,              // D-C4: rows that deviate from column order
    natives: RowNatives,            // D-C7: sparse, row -> Box<Native>
    pub crs: Option<Crs>,           // unchanged
    pub name: Option<String>,       // unchanged
    pub schema: Vec<FieldDecl>,     // unchanged
    pub native: Option<Native>,     // unchanged
}
#+end_src
The four collection-level fields keep their meaning and stay public. The rest
is reached through methods (D-C8), so the layout can keep changing without
breaking callers again. Under D-C10 the five private fields move into each
=Block=, and the collection holds =blocks: Vec<Block>= in their place; the
decisions below describe a block's table, which is the whole collection's
when there is one block.

*** D-C2 -- a column is a typed buffer, a validity bitmap, and a presence bitmap
#+begin_src rust
pub struct Column { name: Rc<str>, data: ColumnData, valid: Bitmap, present: Option<Bitmap> }
enum ColumnData {
    Bool(Bitmap),
    Number { bits: Vec<u64>, is_int: Bitmap },  // D-C3
    Str { offsets: Vec<u32>, bytes: Vec<u8> },  // u64 offsets past 4 GiB
    Binary { offsets: Vec<u32>, bytes: Vec<u8> },
    Mixed(Vec<JsonValue>),                      // the escape hatch, D-C3
}
#+end_src
=valid= is null-ness; =present= is absence, and is =None= -- costing
nothing -- for a column every row holds, which is every column a tabular
source produces. Guarantee 1 is the two bitmaps being different.

Built with one buffer more than the sketch: =Null=, for a column whose every
cell so far is null or absent. It holds nothing, and takes the first real
value's buffer when one arrives (D-C3) -- the promotion is free, since every
slot it holds is a placeholder.

*** D-C3 -- a column's type is the narrowest that holds every value exactly
Built as the reader appends, by the same lattice =schema::Infer= uses today,
with one change: *integers and floats share a =Number= column*, each cell's
eight bytes holding an =i64= or an =f64= and =is_int= saying which. That
keeps guarantee 4 (=1= and =1.0= stay distinct, and an integer past 2^53
stays exact) without falling back to =Mixed= on the most common mixture
there is. Anything else that disagrees -- a string beside a number, any
array or object -- makes the column =Mixed=, which costs what a row cell
costs today, so the worst case /per cell/ is today's case, not worse. Per
collection it is not: a dense column holds a slot for every row, present or
not, and D-C10 is what bounds that.

A column that starts narrow and meets a value it cannot hold is *promoted*
once (=Bool= → =Mixed=, say), copying what it holds. A reader that knows its
types up front (Parquet, FlatGeobuf, Shapefile, GeoPackage's declarations)
never promotes.

*** D-C4 -- a row's shape is recorded only when it deviates
A row is /regular/ when its keys are its present columns in column order,
each once. A tabular source's rows always are; a GeoJSON file written by
any tool that writes a table is too. A row that is not -- keys in another
order, a key repeated -- gets an entry in =RowShapes=: its members in its
own order, each a column index or, for a repeat, the extra =(key,
JsonValue)= pair itself. Guarantees 2 and 3 live here, and a regular file
pays nothing for them. =RowShapes= is a sorted =Vec<(row, Box<Shape>)>= or
a map; profiling decides.

*A block's column order is its most common key order*, then any other keys
in first-seen order. First-seen was the first draft's rule, and § SMOKE TEST
measured what it costs: on the ragged fixture, row 0 was one of the shuffled
rows, so every ordinary row deviated from it -- 94% of rows irregular where
38% are, and 350 bytes a row against the modal order's 216. The order is
free to choose because nothing outside the block sees it: views give each
row its own order, and the collection's first-seen key order, which
tabular writers declare today (=infer_columns=), is kept beside the blocks
as metadata for D-C10's schema merge, so their output does not change.

*** D-C5 -- writers read columns, and =infer_columns= goes away
=schema::Column= (Mem3's borrowing column) was the table, reconstructed for
every write. With the table in the hub, a tabular writer reads the hub's
columns directly; =columns_for='s declaration matching moves onto the
table. The reconciliation =FieldDecl::type_for= does stays, against the
column's real type rather than an inferred one.

*** D-C6 -- geometry is flat buffers, GeoArrow-shaped but not conformant
Geometry is the other half of the memory story (=Position= is 48 bytes for
16 of XY, and an =Option<Geometry>= point 56), but it is independent of
properties and every format already reads and writes it per feature. C6
adds flat coordinate buffers as a block's sealed form, beside today's
=Vec<Option<Geometry>>= as its owned form (D-C16), which absorbs =performance.org='s "compact =Position=" item.

*The layout borrows GeoArrow's idea, not its spec.* Coordinates in one
buffer, structure in offset arrays, as GeoArrow has them; but the buffers are
private (D-C9), nothing hands them to Arrow, and geosetta takes no
dependency on =geoarrow-rs= or =arrow-rs= (the crate writes its own
Parquet). Where GeoArrow's layout would lose what =Geometry= holds today,
the layout departs from it:
- *Z and M per position.* GeoArrow fixes a column's dimension (XY, XYZ, XYM,
  XYZM). =Position= lets one point lack a Z or M that its neighbours have,
  which Shapefile's M no-data sentinel relies on. Z and M are each their own
  buffer, absent when no row has them, and carry a presence bitmap only when
  some position lacks one.
- *Mixed types in one block.* GeoArrow gives each type its own array and
  mixes them through a union of children. GeoJSON and KML columns are often
  mixed, so a block holds one type tag per row and one set of offsets
  (geometry → part → ring → coordinate) that every type uses, in row order,
  without the union's indirection. A block of only points needs no offsets.
- *Collections.* GeoArrow nests them as a union. They are rare here, so a
  =GeometryCollection= is kept whole, in a sparse side table as natives are
  (D-C7).

A block of one type in XY is laid out as GeoArrow's own array of that type,
so a writer of GeoArrow output (Arrow, or GeoParquet's native encoding
rather than WKB) would be cheap for the common case. Neither is in scope:
both change output bytes, and are features of their own.

*A block holds geometry columns, not a geometry column.* The type is
self-contained -- no block or view assumes there is exactly one -- so
=multi-geometry-columns.org='s extra columns are more of the same (§ DEPENDS
ON / RELATED).

*The API.* =Feature=, =from_features=, =push= and =set_geometry= keep the
owned =Geometry=. =FeatureRef::geometry()= returns a =GeometryRef<'_>= view
with =to_geometry()=, since nothing in the buffers is a =&Geometry=; this
breaks callers that match on the reference. =for_each_position_mut= keeps its
=&mut Position=, built and written back per coordinate.
=for_each_position_run_mut= cannot hand out a =[Position]= that does not
exist from a flat block; D-C16 decides what it hands out. It has no caller
outside its own unit tests (=tests/reproject_pipe.rs= uses
=for_each_position_mut=), so its signature is free to change. Editing
geometry through the API is D-C16's.

*** D-C7 -- per-row natives are a sparse side table
=Vec<(row, Box<Native>)>= sorted by row, or a map. Today's =Option<Box<Native>>=
per row is already 8 bytes a row for something nearly always absent; this
makes it nothing. A permutation (=--sort-hilbert=) carries them along.

*** D-C8 -- the public API: build and edit through methods, read through views
The route (a) story (=edit-composability.org=, =tests/public_api.rs=) is
read, edit, write, from outside the crate. It stays possible and gets
explicit:
- *Read:* =fc.len()=, =fc.row(i) -> FeatureRef<'_>= (=geometry()=,
  =properties()= iterating =(&str, Value<'_>)= in the row's own order,
  =get(key)=, =native()=), =fc.rows()=, and =fc.column(name) -> ColumnRef<'_>=
  for typed column access.
- *Build:* =FeatureCollection::from_features(Vec<Feature>)= and =push(Feature)=,
  with =Feature= kept as the owned row type it is today, so a caller building
  a collection by hand changes one line.
- *Edit:* =set(row, key, JsonValue)=, =remove(row, key)=,
  =set_geometry(row, ..)=, =retain(|row| ..)=, =permute(&order)=, and the
  column-sized and per-block edits of D-C12.
- =Value<'_>= is a borrowed cell (=Null=, =Bool=, =Int=, =Float=, =Str(&str)=,
  =Binary(&[u8])=, =Json(&JsonValue)=) with =to_owned() -> JsonValue=.

*This is a breaking release.* =fc.features= goes private in C1, behind the
stopgap accessors of D-C15; C5 replaces those with the views above, and
=Feature::properties= as a field of the collection goes. The intermediate
API is internal to the work and never released on its own. Nothing in the
workspace links geosetta (the three compose through a caller that links
them or through pipes, never a dependency, by =../architecture.org=), and
the published crate has no users who need a
break avoided; under 1.0 it takes the next minor.

*** D-C9 -- the API never exposes a whole buffer
Every accessor works by row index and column, never by "the whole buffer",
so how rows are split into blocks (D-C10) is invisible to callers and can be
retuned freely. The first draft held one chunk and left several for later;
D-C10 makes blocks the design from the start, which is also the seam
=streaming-progress.org= and a batched pipeline would build on. This plan
builds neither.

*** D-C10 -- the collection is blocks, each its own small table
#+begin_src rust
struct Block {
    len: u32,
    geometry: GeometryColumn,
    columns: Vec<Column>,   // only this block's keys, typed for its rows
    shapes: RowShapes,      // this block's irregular rows
    natives: RowNatives,    // this block's natives
}
#+end_src
A reader fills a block of /N/ rows, seals it and starts the next. Each block
has its own column set and its own narrowest types (D-C3); a column's type
may differ from block to block. This is the PAX layout -- rows partitioned,
columnar within a partition -- that Parquet row groups, Arrow record batches
and duckdb's row groups all use.

Why blocks rather than one table:
- *Sparse input.* One dense table gives every key a slot in every row. An
  OSM-style export -- 2 000 distinct tag keys, ~5 a feature, 100 000
  features -- is 2 000 × 100 000 slots: ~1.6 GB as =Number= columns, 32
  bytes a slot as =Mixed=, where rows hold ~5 cells a feature today. With
  blocks a key exists only in the blocks that use it, and a key absent from
  a whole block costs nothing. That restores "never worse than today"
  without a separate sparse column type (unless profiling the bad case says
  otherwise; § OPEN QUESTIONS).
- *Promotion is local.* A string reaching a numeric column promotes one
  block, not a million rows (§ RISKS), and the blocks around it keep their
  narrow type.
- *Raggedness comes in stretches.* Concatenated exports and multi-source
  files are irregular between stretches, not within them; a block-local
  column order makes each stretch regular inside its block, and =RowShapes=
  records only what deviates from its own block.
- *Parquet row groups map onto blocks* on read and write, one to one.
- *=Str= offsets stay =u32=*, since a block of text past 4 GiB is not a
  case to design for (§ OPEN QUESTIONS).

What it costs:
- A column is no longer one buffer: =fc.column(name)= walks blocks whose
  types may differ. =ColumnRef= hides that; a typed fast path handles it.
- Writers that declare one schema up front (FlatGeobuf's header, Shapefile's
  DBF, GeoPackage's DDL) need one for the collection: a merge of the blocks'
  column sets and types, metadata only, which replaces =infer_columns=
  (D-C5). Its order is the collection's first-seen key order, kept as
  metadata, not any block's column order (D-C4).
- Each block repeats its column names and headers; on a wide table with
  small blocks that overhead dominates. Block size is a tuning knob, with a
  few thousand to ~64k rows the usual range.

*** D-C11 -- filters and sorts are selection vectors
=retain= and =permute= (=--sort-hilbert=) record a =Vec<u32>= of the rows
to keep, in order, rather than moving every column, =RowShapes= and
=RowNatives= at once. A writer gathers through it; anything that must see
the result materialized (a column read with a fast path) gathers once and
drops it. A second =retain= or =permute= composes with the first instead --
mapping through the existing selection costs what building one does -- so
it gathers nothing (built that way in C1). This is duckdb's =SelectionVector= and polars'
=take=. A sort mixes rows from every block, so the gather builds new blocks,
whose shapes can be wider than the originals: a sorted ragged file keeps
less of its saving than an unsorted one (§ RISKS).

*** D-C12 -- edits go through an overlay; column-sized edits are first-class
A table makes the edit rows find cheap -- one cell -- the expensive one, and
the edit rows find expensive -- a whole column -- the cheap one. The edit API
leans into that rather than hiding it (§ IN-FLIGHT EDITS compares the two):
- *Cell edits are an overlay.* =set= and =remove= record =(row, key) →
  Some(JsonValue) | None= in a sparse per-block patch, sorted by row like
  =RowShapes=, which views read through. It is folded into the block when the
  block is next gathered or written, so a column promotes at most once per
  block however many edits reach it. This is duckdb's update segments. A row
  block (D-C13) needs none: it takes a cell edit in place, as today.
- *Column-sized edits skip the overlay.* =set_column(name, values)=,
  =map_column(name, |row, value| ..)= and =drop_column(name)= build or
  replace each block's buffer directly. This is polars' =with_columns=, and
  what a caller doing bulk attribute work should reach for.
- *Appends go to a tail block.* =push= fills an open block and seals it at
  the block size (D-C10), like duckdb's Appender.
- *Rows are addressed logically.* Row =i= is the i-th row after =retain= and
  =permute=. The overlay is keyed by physical row, and a logical index goes
  through the selection vector (D-C11) first; folding an overlay and
  gathering a selection are one pass.
- *Blocks can be edited one at a time.* =map_blocks(|block| ..)= runs over a
  collection already read. It is also the hook a streamed pipeline (D-C9)
  would run between reader and writer, with memory bounded by the block
  size; this plan builds no such pipeline.

Every edit gives the output the row IR gives after the same edit. A =set= of
a key the row has keeps its position; a new key goes last in that row's own
order, with a =RowShapes= entry when that is not its block's column order;
=remove= from a column with no =present= bitmap creates one; and =1= written
into a column of floats stays an integer. C1's dual storage is what tests it.

/As built in C1:/
- *The patch holds whole rows,* not =(row, key)= cells: an edited row's full
  property list, sorted by row. An edit is then the row IR's own edit to a
  =Vec=, so position, last-in-order and repeats hold by it, at one row copy
  per edited row. A row block still takes a =set= of a key the row has in
  place.
- *=remove= takes every occurrence* of the key, repeats included; =set=
  changes the first.
- *Column-sized edits run on the cell path.* =set_column=, =map_column= and
  =drop_column= are correct and tested, at about 50 ms per 20 000 rows in a
  debug build; replacing each block's buffer directly is the fast path C2's
  profile can ask for.
- *=fold=* re-seals the blocks an edit touched, and every block from the
  first =push= reached; =gather= applies the selection and folds everything.
  Neither runs at a size threshold yet.
- *=map_blocks= is not built:* it has no caller until a streamed pipeline
  or C5's public API.

*** D-C13 -- a block is columns or shaped rows, chosen as it seals
#+begin_src rust
enum Block { Columns(ColumnBlock), Rows(RowBlock) }
struct RowBlock {
    len: u32,
    geometry: GeometryColumn,
    shapes: Vec<Shape>,         // interned: a key list in order, repeats kept
    row_shape: Vec<u32>,        // row -> its shape
    starts: Vec<u32>,           // row -> its first value
    values: Vec<JsonValue>,     // every row's values, back to back
    natives: RowNatives,
}
#+end_src
=ColumnBlock= is D-C10's =Block=. A =RowBlock= is § ALTERNATIVES
CONSIDERED's shaped rows: every guarantee holds by existing, as it does
today; a cell is 32 bytes rather than 48; sparse and ragged input costs what
it holds; and a cell edit is local.

*Who chooses.* A reader that knows its types (Parquet, FlatGeobuf,
Shapefile, GeoPackage, CSV) fills column blocks and never seals rows. A
schemaless reader (GeoJSON, KML) fills a row block -- interning shapes is
natural while streaming -- and decides at seal: it transposes to columns
when the block is dense (present cells over rows × columns), regular (few
rows needing =RowShapes=) and narrow (few columns that would be =Mixed=), and
keeps rows otherwise. The transpose costs one block's worth of memory, once.
The thresholds come from profiling the C0 corpus. A gather (D-C11) builds
new blocks and chooses again for each.

What § SMOKE TEST settled about the mechanics:
- *A starting rule.* Columns when the block's density is at least 0.25 and
  at most a quarter of its rows deviate from its modal order; both are read
  off the row block's interned shapes, not its cells. On every fixture it
  picked the form an oracle (build both, keep the smaller) picked.
- *Transpose from shapes, never by cell.* Each shape maps once to its
  columns, so the transpose does no per-cell key lookup. The first
  prototype hashed every key and ran 3--9× slower.
- *Intern cheaply, and stop when shapes do not repeat.* A row whose keys
  match the previous row's reuses its shape without hashing, which made
  shaped rows cheaper to build than today's rows on regular input. On the
  sparse fixture every row's keys are its own, so interning bought 2%
  memory for 4× the build time; a block whose new-shape rate stays high
  should keep each row's keys inline instead.

*Who sees it.* No one outside the table. Views (D-C8) hide the form as they
hide block boundaries (D-C9). A tabular writer reads a column block directly
and transposes a row block a block at a time -- today's =infer_columns=,
bounded to one block; a row-shaped writer reads a row block as today and a
column block through per-column encoders chosen once per block (§
ALTERNATIVES CONSIDERED, duckdb and polars), with each column's key text
built once per block, a tile of 64 rows at a time (§ SMOKE TEST). A row
block's writer builds key text once per shape, for shapes that repeat. The
schema merge for writers that declare one up front (D-C10) takes both forms.

This is the "columns for tabular sources, rows for schemaless ones"
alternative made permanent at the block, behind views, where its objection
-- every consumer handling two forms -- does not reach. It also makes C3 and
C4 optional: GeoJSON and KML can read into row blocks and stop there until
profiling says columns pay.

*** D-C14 -- =--layout= lets the user force a form
=auto= (the default, D-C13's choice), =rows= or =columns= forces every block
a reader seals, and every block a gather builds, into one form. Output is
byte-identical under every setting: it is a memory and time setting only, and
is documented as one, so that no one reaches for =rows= to "preserve more".
- *Library first.* =read_features= takes no options today; the layout is a
  =ReadOptions= beside =WriteOptions=, landing in C1, where the equivalence
  runs need it.
- *Then the CLI.* =--layout= landed in C1 rather than C2, the first
  milestone in which a real conversion's layout changes, because the
  equivalence corpus drives the binary and C1's acceptance runs it under
  each layout (=LAYOUTS= in =bench/equiv.py=).
- *Forcing can be far worse than =auto=,* and the flag's documentation names
  both cases: =columns= on many-keyed sparse input brings back the dense
  slot per key per row that D-C10 exists to avoid, and =rows= on a wide
  tabular file brings back today's peak.
- *It does not change the editing API.* A caller forcing =rows= still edits
  through views and methods (D-C8, D-C12); =to_features= is the way to plain
  data. Two public APIs depending on a read option would be worse than either.

This follows duckdb and polars, which expose tuning settings
(=map_inference_threshold=, =sample_size=, =infer_schema_length=, the
streaming engine) rather than a layout switch; geosetta's finer knobs, the
D-C13 thresholds and the block size, stay internal until someone needs them.

*** D-C15 -- the storage is private, and the pipeline converts it once, by =&mut=
Until C5 a collection is rows or a table at the collection level (C1's
=Storage=), and a spoke not yet moved reads rows. Where that conversion runs
decides whether the migration costs anything on paths that do not need it.
#+begin_src rust
pub struct FeatureCollection {
    storage: Storage,            // enum Storage { Rows(Vec<Feature>), Table(Table) }
    pub crs: Option<Crs>,
    // ...
}
impl FeatureCollection {
    pub fn features(&self) -> Cow<'_, [Feature]>;      // borrows rows; converts a table, uncached
    pub fn features_mut(&mut self) -> &mut Vec<Feature>; // a table becomes rows, in place

*** D-C16 -- every attribute is editable, and no edit is worse than today's
Editing what was read, through the API, is a goal of the crate
(=edit-composability.org= route (a)), for every attribute of a feature --
its geometry, its properties, its native -- and of the collection, not a
cost the layout may raise. The collection's own fields (=crs=, =name=,
=schema=, =native=) are public data. A feature's attributes each had a
setter, but no way to make an edit the setters do not name -- rename a key
in its place, reorder, insert anywhere, edit a repeat -- and D-C6 alone
would have taken away the =&mut Geometry= a block of =Vec<Option<Geometry>>=
hands out. So every attribute gets an owned hatch, an edit as ordinary Rust
on the row IR's own types:
- *=edit_properties(i, |ps: &mut Vec<(Rc<str>, JsonValue)>| ..)=* -- a
  feature's whole list, in its own order with repeats, through the patch
  (D-C12), which already holds whole rows. A list left as it was, bit for
  bit (a float by its bits, so =-0.0= is not =0.0=), is not patched.
- *=edit_feature(i, |f: &mut Feature| ..)=* and
  *=for_each_feature_mut(|i, f| ..)=* -- geometry, properties and native
  together; a pass that changes a few rows patches those few.
- The setters stay, as the cheap calls for what they do: =set=, =remove=,
  =set_column=, =map_column=, =drop_column=, =set_geometry=, =set_native=.

For geometry, which C6 changes the storage of:
- *A block's geometry is flat or owned.* Owned is today's
  =Vec<Option<Geometry>>=; flat is D-C6's buffers. =GeometryRef= views
  either, so writers, the bbox, the R-tree and the Hilbert sort read one
  type. This is D-C13's move made for geometry: the worst a block can be is
  exactly today's.
- *Who chooses.* A block seals flat; =--layout rows= keeps every block
  owned (D-C14, still byte-identical). On a flat block, an edit to one
  geometry goes to an overlay (D-C12's patch, for geometry) and only when it
  changed the geometry bit for bit; a pass over every row makes each block
  owned while its rows are visited and flat again after, so the overlay
  never holds the collection twice over. A position edit keeps a flat block
  flat.
- *The API hands out owned geometry to edit:*
  - =edit_geometry(i, |g: &mut Option<Geometry>| ..)= -- a row's geometry
    as an owned value, written back after. =match=, push a ring, change the
    type: ordinary Rust, at one copy per edited row from a flat block, none
    from an owned one. This is GDAL's =GetFeature= / =SetFeature=.
  - =for_each_geometry_mut(|i, g: &mut Option<Geometry>| ..)= -- the same
    over every row, a block at a time, rebuilding each block once rather
    than through the patch (the geometry =map_column=).
  - =set_geometry(i, ..)= -- as today.
  - =for_each_position_mut= -- as today, and the fast path for edits that
    keep the shape, such as reprojection.
  - =for_each_position_run_mut= -- hands out =&mut [Position]= per run, as
    today: from an owned block directly, from a flat one through a scratch
    run written back after. Batch transformers keep the call; the strided
    =[[f64; 2]]= form waits for a caller who measures the copy.
- *Every edit is any edit.* A position edit that gives one position a Z or
  M its neighbours lack, or takes one away, holds as it does today: the flat
  block grows the buffer or the presence bitmap. Edits reach
  =GeometryCollection=s in the side table (D-C6) as they reach the rest.
- *The contract is pinned first* (C6 step 2): public-API tests that pass
  against today's storage and must pass unchanged after C6.

/Built 2026-11-05/, before any storage changes: =edit_geometry=,
=for_each_geometry_mut=, =edit_properties=, =edit_feature= and
=for_each_feature_mut= on the blocks as they are, and =tests/edits.rs= (C6

** HOW EACH FORMAT FITS
| format      | fit                | notes                                                                                                                                           |
|-------------+--------------------+-------------------------------------------------------------------------------------------------------------------------------------------------|
| GeoParquet  | native             | Columns on disk are columns in the hub: the transpose (Mem4) and =infer_columns= both disappear. A =Str= column can take a page's bytes nearly as-is. |
| Shapefile   | natural            | Fixed, typed DBF schema; every record has every field.                                                                                          |
| FlatGeobuf  | natural            | The header declares typed columns; a row's omitted cell is null (=edit-composability.org=), which is =valid=, not =present=.                    |
| CSV         | natural            | Rectangular. Types are inferred per value (=csv.rs='s =unwidened= gate), so a disagreeing column is =Mixed=.                                    |
| GeoPackage  | mostly             | Declared types, but SQLite stores any type in any column (=sqlite_altered.gpkg=), so a column meeting one is promoted. Row-shaped writes stay row-shaped (the =sqlite= encoder takes rows), built a row at a time from the table. |
| WKT         | trivial            | Geometry only.                                                                                                                                  |
| GeoJSON     | needs D-C3/D-C4    | Schemaless. Regular files get the whole saving; a ragged one keeps row blocks (D-C13), since columns alone can cost more than today (§ SMOKE TEST). |
| KML         | needs D-C3/D-C4    | Like GeoJSON: =<ExtendedData>= is per Placemark. Projection (=project.rs=) appends to columns; =place.rs= and reconcile read a row view. A KML feature's element is a per-row native (D-C7), and is its own cost (=performance.org=, KML steps 2--3). |

So *every format can be columnar*, but the schemaless two stay no worse
than today only through the hybrid. Two notes from D-C10: a GeoParquet row
group is a block, so the reader seals one per row group and the writer emits
one per block; and a sparse key costs nothing outside its blocks, where a
single dense table would cost a slot per key per row. Blocks are not enough
alone: § SMOKE TEST measured column blocks at 350 bytes a row on ragged
GeoJSON against today's 288, and at 64 KB a row on the many-keyed one.
Under D-C13 the schemaless two read into row blocks first, and a stretch
keeps columns only where it is regular enough to pay for them.

** IN-FLIGHT EDITS, ROWS AGAINST A TABLE
An edit between read and write is one of two things
(=edit-composability.org=). Through a pipe (route (b), =geosetta | jq |
geosetta=) the IR never sees it: the edit happens in the transit's text, and
the layout changes only how fast that text is read and written -- a
same-format tabular transit gains from C2, the GeoJSON transit =jq= needs
waits on C3, where the gain is smallest. A caller linking the crate (route
(a)) edits the IR itself, and there the layouts differ:
| edit                    | row IR today                         | table (D-C12)                                                |
|-------------------------+--------------------------------------+--------------------------------------------------------------|
| set an existing key     | overwrite in place                   | overlay entry; folded at write                               |
| add a key to a row      | =push=; order is the row's own       | overlay; at fold a new column, =RowShapes= if out of order   |
| remove a key            | =Vec::remove=                        | overlay tombstone; at fold clears =present= (creating it)    |
| retype a value          | free                                 | overlay holds a =JsonValue=; fold promotes one block         |
| add or replace a column | loop every row, a heap string each   | =set_column=: one buffer a block, no overlay                 |
| delete features         | =Vec::retain= moves features         | selection vector (D-C11)                                     |
| add features            | =Vec::push=                          | tail block                                                   |
| reorder                 | moves =Feature= structs              | selection vector, gathered at write                          |
| edit every feature      | =&mut= over the whole collection     | =map_blocks=, one block at a time                            |
| read after editing      | direct                               | through the overlay until folded                             |
| API                     | plain data: =&mut=, =match=, =clone= | methods and views; no =&mut= to a cell                       |
| guarantees under edit   | free by construction                 | each one code, tested against rows (C1)                      |
| memory while editing    | whole collection, 48 B a cell        | whole collection, columnar; bounded by a block once streamed |
Under D-C13 a row block edits as the middle column does, behind the same
methods. Rows win on scattered single-cell edits and on ergonomics: an edit is
ordinary Rust, and nothing it does can break a guarantee. The table wins on
edits the size of a column or of the collection, and is the only layout in
which an edit over every feature could run in bounded memory. Neither changes
route (b), which is the route a sibling crate has.

** RISKS
- *Scope.* 79 uses of =.features= in =convert.rs= alone, every spoke's
  reader and writer, the KML projection and reconcile. C1's dual storage is
  what lets each milestone be checked against the corpus on its own, so a
  regression is found in the milestone that made it; its accessors (D-C15) rewrite every
  one of those uses once, mechanically, by hand (the code is not
  =cargo fmt=-formatted).
- *Promotion cost.* A column that is narrow for a million rows and then
  meets a string would copy a million cells once in one table. D-C10 bounds
  it to one block, and =Mixed= from the start is today's cost.
- *Sparse input in one dense table.* Many keys each in few rows give a slot
  per key per row -- worse than today by orders of magnitude (D-C10). Blocks
  are the answer; the C0 many-keyed fixture is the test that they suffice.
- *A sort scrambles blocks.* =--sort-hilbert= draws each output block from
  rows of every input block, so its column set and shapes are the union of
  theirs; a sorted ragged file keeps less of its saving. D-C11 defers the
  gather to the write, but cannot undo the mixing.
- *A column's type varies by block.* Every typed fast path over a column
  must handle a block whose type is wider than the next one's. Testing this
  needs a fixture whose blocks disagree, which the stretch-ragged one is.
- *Block size.* Too small and per-block names and headers dominate on wide
  tables; too large and promotion and sparse costs return. Chosen by
  profiling the C0 corpus, and retunable later without callers noticing
  (D-C9).
- *GeoJSON's worst case.* A file with every feature's keys in a different
  order records a shape per row. As columns that is worse than today (§
  SMOKE TEST); as rows (D-C13) it is no worse, but the saving goes. The
  benchmark should include one.
- *Speed on wide GeoJSON.* § SMOKE TEST puts the hybrid's build at about
  +85 ms against a 600 ms wide read (+14%), which breaks the "no slower" bar
  as it stands. The figure is an upper bound -- the prototype copies parsed
  values a reader would move -- and =parquet→geojson= also loses today's
  transpose on read, so its net is unmeasured. The write side, first
  measured 10% slower, is closed in the probe: the tiled writer is level
  with a row writer that caches its keys. The probe escaped a =char= at a
  time, slower than the crate's writer, so how either compares with today's
  real writer is unmeasured until C3 builds one.
- *Editing ergonomics.* A caller used to =fc.features[i].properties.push(..)=
  writes =fc.set(i, key, value)=. Worth a migration note in the release.
- *Streaming ends the in-place accident.* A pipe-form in-place run
  (=geosetta a.fgb - | tool | geosetta - a.fgb=) is safe today only because
  every reader buffers its whole input before any writer opens
  (=edit-composability.org= § THE IN-PLACE HAZARD). Blocks are the seam a
  streamed pipeline would use (D-C9, D-C12's =map_blocks=); once a writer
  emits block 1 while block 2 is still being read, the final stage can
  truncate the file the first is reading. Atomic write-and-rename
  (=edit-composability.org= D4) must land before any streaming built on
  blocks does.
- *Two block forms, for good.* Every view, writer path and schema merge
  handles both (D-C13), and a per-row feature added later -- a new native, a
  new guarantee -- is built twice. The row form is the simpler of the two,
  and the three-way equivalence run (D-C14) catches a form that drifts.
- *The seal-time choice can be wrong.* Thresholds tuned on the corpus can
  pick columns for a block that promotes to =Mixed= throughout, or rows for
  one that would have paid. Either is no worse than the other form's cost,
  and =--layout= is the user's override.
- *A heavily edited collection reads through its overlay.* Every view of an
  edited block checks the patch first until it is folded (D-C12). Folding on
  a size threshold, not only at write, bounds it if profiling says to.
- *Row-shaped formats pay a conversion per row.* GeoPackage's SQLite writer
  and the GeoJSON and KML writers walk rows. That walk is over borrowed views,
  not materialized rows, so it costs time, not memory.

** OPEN QUESTIONS
/Revisited 2026-11-05, with C0--C6 built./ Six of the eight are answered
by what was built; two stay open.

- =RowShapes= and =RowNatives= as sorted vectors or maps: decide by
  profiling a ragged GeoJSON. Per block (D-C10), and never re-sorted under
  D-C11, a sorted vector is the likely answer.
  /Answered by C1:/ both are sorted vectors of the irregular rows.
- =Str= offsets: settled by D-C10 as =u32=. A block past 4 GiB of text is
  not a case to design for; if one ever appears, the reader seals the block
  early.
- Do blocks alone handle sparse input, or does a column also need a sparse
  form (=rows: Vec<u32>= beside its values) for a key that is rare /within/
  its blocks? Decide on the C0 many-keyed fixture.
  /Answered by C3: blocks alone./ The sparse fixture (20 000 rows, 2 000
  keys) seals as rows at 9 MB against the pin's 8, and no column has a
  sparse form. What it still costs is time, not memory: a tabular write
  from a sparse row block is 1.6× the pin's (=sparse → fgb=), at an eighth
  of its peak (§ MILESTONES, C3 and C5).
- D-C13's seal-time measures and thresholds: density, the share of
  irregular rows, the share of =Mixed= columns, or a combination. Decide on
  the C0 ragged, stretch-ragged and many-keyed fixtures.
  /Answered by C3:/ § SMOKE TEST's starting rule, kept. On the C0 fixtures
  it picks the smaller form everywhere but ragged, where it keeps rows at
  12% over columns; the other side of that threshold is ownorder, where
  columns cost more.
- Should D-C13's thresholds or the block size ever be user settings beside
  =--layout=, as duckdb's and polars' are? D-C14 assumes not until asked.
  /Open; nothing has asked./
- The block size, and whether it is a row count, a byte budget, or both.
  § SMOKE TEST saw little between 8 192 and 65 536 rows except at a stretch
  boundary, where the smaller block wasted less (88 bytes a row against
  113 on the stretch fixture).
  /Answered by C1, for now:/ a row count, 8 192, with an interning sample of
  1 024, carried by the table as =Sizes= so a gather re-seals under the
  same. Private (D-C9), so it can be retuned or become a byte budget
  without callers noticing.
- Does =Value<'_>= replace =JsonValue= in the public API anywhere, or only
  sit beside it? D-C8 assumes beside.
  /Answered by C5: beside./ Reads hand out =Value<'_>= (=get=,
  =properties()=, =map_column='s argument); edits take =JsonValue= (=set=,
  =set_column=, =edit_properties=). Whether that split is the one to
  release with is part of the public-API review before the breaking
  release.
- Should =FieldDecl= move onto =Column= (a column's declaration is a fact
  about the column), or stay matched by name as =columns_for= does?
  /Open./ =columns_for= still matches by name (=schema.rs=).

** ALTERNATIVES CONSIDERED
*** Keep the row IR
Memory aside, the row IR has real strengths, and each is a cost this plan
pays:
- *The guarantees are free.* A =Vec<(Rc<str>, JsonValue)>= keeps key order,
  duplicates, absent-vs-null, per-cell type and nesting by existing. The
  table rebuilds each one deliberately (=present=, =RowShapes=, =is_int=,
  =Mixed=, promotion), and each is a place byte-identity can break.
- *Edits are local.* Setting, removing or retyping one feature's key touches
  that feature. In a table it can promote a column or add one.
- *The public API is plain data*: build, match, clone and edit with ordinary
  Rust, no views or lifetimes.
- *Row-shaped formats fit it.* GeoJSON, KML and the SQLite encoder read and
  write a feature at a time with no transpose.
- *Reordering moves pointers*, where a table moves every column (D-C11 is
  the answer).
- *Sparse input costs only what it holds* (D-C10 is the answer).
- *It is built and passes the corpus.*
None of these reaches the wide-table gap, which is the reason for the plan;
D-C10 and D-C11 exist to keep the last two.

*** How duckdb and polars handle row-shaped work
Mostly by not doing it: both run on batches (duckdb's 2 048-value vectors,
~122k-row row groups; Arrow chunks), keep buffers immutable and append as
new chunks, record deletes and filters as bitmaps and selection vectors,
and fuse many edits into one pass through a query plan. Row-at-a-time
access exists and is discouraged (polars' =iter_rows=, duckdb's =INSERT=
loop versus its Appender). And part of their speed on JSON is giving up the
guarantees above: duckdb's =read_json= infers a =STRUCT= from a sample,
returns an absent key as =NULL=, fixes key order to the schema, keeps no
duplicates and widens =1= beside =1.0= to =DOUBLE=; past
=map_inference_threshold= distinct keys it stops making columns and uses a
=MAP= or raw =JSON=. Borrowed here: blocks (D-C10), selection vectors
(D-C11), and the threshold idea (§ OPEN QUESTIONS, sparse form). Not
borrowed: the normalization, which geosetta cannot do.

Where rows are still needed, what they do that geosetta can take (defaults
recalled, not re-checked against either engine's source):
- *Dispatch once per batch, not per cell.* Both choose a column's code path
  once per vector or chunk and run a loop that knows its type. Polars' NDJSON
  writer builds a serializer per column and steps them in lockstep. The
  GeoJSON, KML and SQLite writers can choose an encoder per column per block
  the same way, and § SMOKE TEST found that is not enough on its own: the
  first column writer was 14% slower than rows over 200 columns. The cause
  was not locality but the key: it escaped a column's name again for every
  cell. Building each column's key text once per block brought it level with
  rows, and writing a tile of 64 rows column by column, into one buffer per
  row, made it 7--9% faster than rows on the wide table and ~20% on the
  narrow one -- a lead a row writer caching its keys matches, so
  row-shaped writes are layout-neutral, not a columnar win.
- *A row layout where rows win.* duckdb's sort, hash join and hash aggregate
  convert columns to a row format (=TupleDataCollection=), work there, and
  convert back: storage is columnar, operators hybrid by design.
  =--sort-hilbert= is the same shape -- sort a compact key and row index,
  then gather once (D-C11).
- *A threshold past which columns stop.* =read_json='s =MAP= / =JSON=
  fallback, for too many keys or keys too rare, is the precedent for a block
  too irregular to be worth columns holding shaped rows (D-C13).
- *Immutable buffers, edits as new data.* Polars shares buffers by =Arc= and
  copies on write, and =with_columns= replaces a whole column; duckdb keeps
  updates as versioned segments beside the data. Neither makes a one-cell
  edit cheap, and both discourage it. A slow, correct =set= is the same
  trade (D-C8).
- *Types decided up front.* duckdb samples the first ~20k records, polars
  the first N rows, and a later disagreement is an error or a cast. Geosetta
  can do neither, but a seekable input can afford a first pass that fixes
  each column's type and so never promotes; stdin cannot.

What they get by dropping guarantees, which geosetta cannot borrow:
- *The normalization* above: one key order, no duplicates, absent read as
  null, =1= beside =1.0= widened. Much of their JSON speed is here, and it
  is what D-C2's two bitmaps, D-C3's =is_int= and D-C4's =RowShapes= pay
  for instead.
- *Sparse keys.* Polars pays a null slot per row; duckdb's =MAP= changes the
  output's type. Geosetta's answer has to be invisible -- shaped rows or a
  sparse column inside the IR, output unchanged.
- *Geometry.* Neither is a model: polars has no geometry type, and duckdb
  spatial has stored one serialized value per row, much like
  =Option<Geometry>=. GeoArrow (C6) is the columnar answer, and few engines
  hold it in memory yet.

So per-batch dispatch, sort-then-gather and a fallback threshold make the
hybrid defensible. Their speed on schemaless input is mostly the guarantees
they drop, so C3 and C4 should not be expected to reach it, and are better
decided after C2's numbers than before.

*** Shaped rows
Each feature keeps its own row, but its keys move into an interned /shape/
-- an ordered key list, duplicates included -- shared by every row with the
same keys: a row is =shape_id + Vec<JsonValue>=. A cell falls from 48 bytes
to 32 and the key pointers go; every guarantee stays as free as today,
edits stay local, sparse input costs what it holds. But values stay 32-byte
=JsonValue=s, so the wide table shrinks by about a third, not the ~6× of
columns. The cheapest real step, and a shape is exactly D-C4's regular row,
so it survives as D-C13's row block.

*** Columns for tabular sources, rows for schemaless ones, permanently
C1's =Storage= enum kept forever. Cheap for the tabular wins, but every
consumer of the hub handles both forms for good. Only as a migration step
at the collection level; D-C13 keeps the idea at the block, behind views,
where consumers see one form.

*** Converting from =&self= into a cached second form
C1's =Storage= converting lazily behind =&self=, the result kept in a
=OnceCell= or =OnceLock= beside the original. It lets every writer keep its
signature with no pipeline step, but:
- *The cache goes stale.* Every =&mut= path -- =reorder_hilbert=, the CRS
  override, =release_foreign_natives=, a caller's edit -- must invalidate or
  update it, and a miss leaves two forms that disagree silently.
- *=OnceCell= makes the collection =!Sync=*, a quiet API change; =OnceLock=
  avoids that at a small cost on every access.
- *The second form is hidden memory,* against the plan's goal, and it blurs
  what memprobe's /IR resident/ measures.
D-C15's single =&mut= conversion in =prepare= gets the same result with
none of these: the pipeline already holds =&mut= there and knows the target.

Holding both forms eagerly was the other route considered, and is worse
still: double the IR on every path.

*** Compact values within rows
A smaller =JsonValue= (inline short strings, a boxed nested case) under the
row layout. Contained and modest; stacks with shaped rows; does not reach
the wide-table gap.

*** Triples
=(row, key, value)= stored sorted: by row it is rows, by key it is columns.
Handles any sparsity, but every cell carries ~8 bytes of index, worse than
shaped rows on the wide table. Blocks cover the sparse case it is good at.

*** Literal diagonals
The sparse-matrix DIA layout stores cells along row-minus-column offsets,
which pays only when a column's index means something, as in a banded
matrix. Property columns have no order, so neighbouring features' keys have
no diagonal structure to exploit. The useful sense of "cutting both axes"
is D-C10's blocks.
