* Spatial Indexing: R-trees and Hilbert Ordering

** WHY — the shared payoff
Spatial ordering and indexing are a cross-cutting capability that several
outputs benefit from. Rather than one-off code per format, build shared
primitives once and reuse them:

- *FlatGeobuf* — its spatial index *is* a packed Hilbert R-tree. We currently
  write index-less files (=index_node_size = 0=) and skip the index on read.
  Writing it makes our FGB spatially queryable by GDAL / QGIS.
- *GeoParquet* — *this entry was written before GeoParquet 1.1 and is no longer
  the whole story* (corrected 2026-08-20). Hilbert row ordering still clusters
  nearby features so row-group bbox stats prune well, and the =geo= metadata
  bbox we emit is the coarse version. But 1.1 *does* define an index structure:
  the =covering= bbox column, a per-row =struct(xmin,ymin,xmax,ymax)= beside
  the geometry, which GDAL writes and this crate reads but cannot write — see
  milestone E.
- *GeoPackage* — has an optional RTree extension (SQLite's R*Tree) enabling
  =rtree_...= spatial queries. Hardest of the three (see milestone D).
- *General* — Hilbert-sorting features improves locality (smaller bboxes, better
  compression) regardless of format.

The common threads: a *per-feature bounding box* and a *Hilbert curve encoding*
(map a point to a 1-D distance) used to sort features spatially.

** SHARED PRIMITIVES (new =src/spatial/= module)
1. *Per-feature bbox.* We have =geometry::Bbox= over a whole collection; add a
   =Geometry::bbox() -> Bbox= (or a helper) for a single geometry.
2. *Hilbert curve.* A pure =hilbert(x: u32, y: u32, order: u32) -> u64= mapping
   integer grid coordinates to a Hilbert distance (the standard rotate/reflect
   bit algorithm). Feature grid coordinates come from quantizing the bbox center
   (or min) to =[0, 2^order)= over the dataset extent. FlatGeobuf uses a fixed
   16-bit resolution over the dataset envelope; match that so our index agrees
   with GDAL's.
3. *Hilbert sort.* Given features + the dataset extent, produce the permutation
   that orders features by Hilbert distance. This is a prerequisite for the FGB
   index (features must be stored in the same order as the index leaves) and the
   optional reordering for Parquet.

** MILESTONES (ordered)

*** A. Foundation — bbox + Hilbert primitives — *DONE*
=src/spatial.rs= (=hilbert=, =hilbert_bbox=, =hilbert_order=) plus
=Geometry::bbox()=. The Hilbert mapping uses FlatGeobuf's 16-bit convention;
unit-tested as a bijection on a small grid and for clustering locality.

*** B. FlatGeobuf packed Hilbert R-tree (write) — *DONE*
Implemented in =flatgeobuf/writer.rs=: features are Hilbert-sorted, the packed
R-tree is built bottom-up (=NodeItem= = 4 f64 bbox + u64 offset, root first down
to leaves) and written between header and features, with =index_node_size = 16=.
Indexed only when every feature has geometry (else index-less, input order).
Validated: GDAL reads our indexed =.fgb= and a bbox-filtered =ST_Read= returns
the correct subset; our own reader still round-trips (it skips an index whose
computed size must now match). The original design:
- Sort features by Hilbert value (A) and write feature data in that order.
- Build the *packed R-tree* bottom-up over the sorted features: leaves are one
  =NodeItem= per feature (=minX,minY,maxX,maxY= as 4 f64 + =offset= u64 = 40
  bytes), grouped =node_size= at a time (default 16) into parent nodes whose
  bbox is the union of their children; repeat to a single root. Node layout is a
  flat array, root level first down to leaves — the same layout our reader
  already computes the size of and skips.
- Leaf =offset= = the byte offset of the feature within the data section, so
  feature sizes must be computed before the index is written; sequence:
  encode features → offsets → build index → assemble
  =magic · header · index · features=.
- Set =index_node_size= in the header (16), not 0.
- Validate: GDAL / DuckDB read the file; a bbox-filtered =ST_Read= returns the
  right subset (exercises the index), and =*.fgb → our reader → *= still works
  (we already skip the index, and its computed size must now match).

*** C. GeoParquet spatial clustering (optional) — *DONE*
An opt-in =--sort-hilbert= flag reorders features by Hilbert locality before
writing (=convert::reorder_hilbert=, reusing A). Applied to the normal convert
path and the GeoPackage read/write paths. Off by default since it changes row
order; benefits GeoParquet clustering most (and compression) — a 50-point grid
writes in Hilbert order instead of row-major. No new on-disk index.

*** D. GeoPackage RTree extension (opt-in =--rtree=) — *DONE*
GPKG's index is SQLite's *R*Tree virtual table*, not a packed Hilbert R-tree:
=rtree_<t>_<c>= backed by shadow tables (=..._node=, =..._rowid=, =..._parent=)
with SQLite's own node blob format, plus registration in =gpkg_extensions= and
insert/update triggers. Implemented from scratch in =geopackage/rtree.rs= behind
an opt-in =--rtree= flag (index-less GPKG is valid, so it stays the default):
- We build a *packed* R-tree bottom-up over feature bounding boxes,
  Hilbert-ordered for leaf locality (reusing =spatial.rs=) — no incremental
  insertion needed. Node blob = 4-byte header (2-byte depth on the root, 2-byte
  cell count) + fixed 24-byte cells (8-byte rowid/child + four big-endian f32
  =minx,maxx,miny,maxy=). Coordinates are rounded *outward* on f64→f32 so every
  stored box still contains its geometry. Nodes are zero-padded to a fixed
  =1228=-byte size (SQLite reads node size from the root blob's length).
- The virtual table (=CREATE VIRTUAL TABLE … USING rtree=) and the
  GeoPackage-standard maintenance triggers are written as schema-only
  =sqlite_master= rows (=rootpage 0=); shadow tables are ordinary b-trees. This
  required teaching =sqlite.rs='s writer two things: schema-only master entries
  (=MasterEntry=), and a real multi-page =sqlite_master= b-tree rooted on page 1
  (the many trigger rows overflow a single page — the interior root now stays on
  page 1, which the reader already handled).
- Validated: =PRAGMA integrity_check= and =rtreecheck()= both pass; a bbox query
  through the index returns the same subset as brute force; DuckDB/GDAL reads
  every layer; append (upsert) re-indexes correctly; our own reader still
  round-trips (the virtual table's =rootpage 0= is skipped, shadow tables aren't
  in =gpkg_contents=).

*** E. GeoParquet covering-bbox column (write) — *NOT STARTED*
GeoParquet 1.1's =covering= member points at a per-row bbox struct
(=geometry_bbox= with =xmin=/=ymin=/=xmax=/=ymax= children) that readers use to
prune without decoding WKB. Real =ogr2ogr= output carries one;
=tests/fixtures/gdal_covering_bbox.parquet= is that file.

*Where this came from.* It is the one GeoParquet member left unhandled by
=same-format-fidelity.org='s M3 spoke, and it landed here because it is *not a
natives question*: under D4 it is /derived-capability/ — never replayed
verbatim, but *rebuilt when the source had one*, exactly like FlatGeobuf's
R-tree (milestone B) and GeoPackage's (milestone D). This plan already owns
that pattern for the other two spokes; it should own the third.

*Status today, measured:* the reader parses the covering column's paths and
uses them **only to exclude those columns from properties**
(=parquet/reader.rs=), then discards them. So a GeoParquet with an index goes
in and one without comes out — exit 0, no warning, and the schema loses five
entries (=geometry_bbox= plus its four children).

*The blocker, and it is real.* Writing one means emitting a *nested struct
column*, and =parquet/writer.rs='s schema is one flat level of optional leaves:
every column is a top-level `SchemaElement` with no group nodes and definition
levels of 0 or 1. The read side already understands nesting
(=arbitrary-geoparquet.org= 3c taught it definition levels through OPTIONAL
ancestors); the write side has never needed it. That asymmetry is the work.

*Sizing:* a small feature, not a spoke — one group node, four required leaves,
and the =covering= member in the =geo= metadata. Values come free from the
=Bbox= this crate already folds per geometry.

** CONTROL / DEFAULTS
- FGB with an index *requires* Hilbert-ordered features, so enabling the index
  reorders features. Decide: write the index (and thus reorder) by default for
  FGB, or gate behind a flag (e.g. =--index= / =--sort-hilbert=)? Reordering
  changes feature/row order, which is observable — a flag is safer; a sensible
  default is "index FGB, leave others as-is."
- Parquet/GPKG reordering should be opt-in since it changes row order.
- *The covering column (E) is not a reordering question* and should follow D4
  rather than this section's opt-in stance: rebuild it when the source had one,
  leave it absent when it did not. That is the same rule milestones B and D
  settled on, and it needs no flag.

** TESTING
- Hilbert unit tests (known mappings, bijection on a small grid).
- FGB: build with an index, have GDAL do a spatial (bbox) query and check the
  result set; confirm =PackedRTree= size matches what our reader skips.
- Cross-check reordered outputs still round-trip through the hub (geometry set
  unchanged, just reordered).

** OPEN QUESTIONS
- Default resolution/anchor for the Hilbert quantization (center vs min; 16-bit
  to match FGB vs higher) — match FGB for B; revisit for C/D.
- The GPKG R*Tree now ships opt-in (=--rtree=, milestone D). Revisit whether to
  flip it on by default once it has seen more real-world files — it doesn't
  change row order, so the main reason to keep it opt-in is caution over the
  from-scratch node format, which =rtreecheck()= and GDAL validation now cover.

  /Narrowed 2026-08-20, not answered./
  [[file:same-format-fidelity.org][same-format-fidelity.org]] D4 decided a
  *separate and smaller* rule that does not settle this one: an index is
  rebuilt when *the source carried one*, whether or not =--rtree= was passed,
  because a same-format run must not hand back a file measurably worse than it
  received. Today the source's R*Tree is destroyed unconditionally and rebuilt
  only on request — verified on a two-layer =.gpkg=.

  So the question left here is strictly the remaining one: *should a file that
  never had an index get one?* That is a defaulting decision about new
  capability, and it stays this plan's call.

  /Confirmed and assigned an owner, 2026-08-23./
  [[file:same-format-fidelity.org][same-format-fidelity.org]] D10 settles the
  R*Tree half of the carry-or-rebuild question -- *never carried, always
  rebuilt* -- which leaves the "rebuilt when the source had one" obligation
  above as an *unimplemented decision* rather than an open question. It is not
  waiting on an argument; it is waiting on code, and the code belongs to
  =same-format-fidelity.org= M3b, which is already rewriting the container
  around it.

  *The tell is in the warning's own wording.* =container.rs= tells a user whose
  source carried an index to "pass =--rtree= to rebuild it" -- that is, it
  detects the exact condition D4 says should rebuild automatically, and then
  asks the user to ask. Whatever this plan decides about files that never had
  an index, that sentence should stop appearing on a same-format run.
