** METHOD
Per =plans/README.org= § Sourcing a fixture from a real tool. Each entry is
marked with how it was established, because the confidence differs:
- /measured/ -- run against the release binary, output in this file.
- /code/ -- read from the reader/writer source, with a =file:line=.
- /unverified/ -- believed from the format spec, *not* yet confirmed against a
  real producer. Treat as a question, not a finding.

** THE CLASSES
From =same-format-fidelity.org= D4. Every member gets exactly one:
- *opaque* -- carry verbatim, understood by nothing.
- *identity* -- carry verbatim; names and ids that travel with their subject.
- *derived* -- never replayed. Split by risk: /derived-information/ (a stale
  one is dangerous) is *recomputed*; /derived-capability/ (a missing one is
  merely slower) is *rebuilt when the source had it*.

** A FINDING THAT PRECEDES THE TABLE -- two spokes are containers, not one
=same-format-fidelity.org= § THE DOMAIN OF THE RULE was written about
GeoPackage. *KMZ is a container on identical terms*, and nobody had said so.

A =.kmz= is a zip that may carry icons, overlays and referenced imagery beside
its =doc.kml=. Geosetta writes exactly one entry /(measured)/:

#+begin_src text
$ geosetta src.geojson made.kmz && unzip -l made.kmz
   doc.kml
#+end_src

So a source =.kmz= carrying =files/icon.png= loses it, and the surviving
=doc.kml= keeps its now-dangling reference. /Carried since 2026-10-28
(=same-format-fidelity.org= M3c): a =.kmz= written back keeps every entry./ Under container scope this is the
same obligation as =gpkg='s, at a fraction of the cost -- a zip's other entries
are already bytes, and =src/zip.rs= already reads the archive. *It should get
its own milestone beside M3b rather than being absorbed into the KML spoke*,
because the KML spoke is about an XML document and this is about an archive.

*** CSV -- /measured/
***Read § FIXED below before this entry's present tense misleads you: every
loss measured here was closed on 2026-10-21.*** The finding is kept as written
because the reasoning is what earned D17.

CSV has no metadata to lose, which is why =same-format-output.org= reasoned it
had nothing unmodelled. That reasoning was about *members*. The loss is the
*lexeme*: the reader infers a type per cell and discards the text it inferred
from, and the inference is not reversible.

#+begin_src text
$ cat t.csv
zip,big,money,flag,geometry
007,12345678901234567890,1.50,TRUE,"POINT (1 2)"

$ geosetta t.csv - --to fgb | geosetta - - --from fgb --to csv
zip,big,money,flag,geometry
7,12345678901234567000,1.5,true,POINT (1 2)
#+end_src

Four losses in one row, all silent:
- =007= → =7=. Leading zeros are *data* in this domain -- ZIP, FIPS, census
  tract, phone.
- =12345678901234567890= → =12345678901234567000=. Beyond =i64=, so it went
  through an =f64= and lost precision. This one is a wrong number, not a
  reformat.
- =1.50= → =1.5=, =TRUE= → =true=. Reformatting, but a same-format run promised
  not to.

*Class: opaque, per cell* -- but this is the one entry where the natives
channel is probably the wrong tool. *A cheaper fix exists and should be
considered first: infer a type only when re-rendering reproduces the input
exactly* (=render(parse(s)) == s=), and keep the cell as a string otherwise.
That resolves all four cases with no payload, no per-cell allocation, and no
IR change -- and it fails safe, since an un-inferred cell is still a correct
string property.

**** FIXED 2026-10-21 -- the cheap fix was the right one, and it caught two more
=infer_value= now gates every inference on that check, rendering through
=cell_text= so the reference is *this spoke's own writer* rather than a second
opinion about how a value is spelled. /Measured on =hand_hostile.csv=: all four
rows above come back byte-identical, and so do =" spaced "=, =København= and
="Zürich, CH"=./

*It caught two spellings this section never listed*, which is the argument for
a rule over the named-exception list this nearly became: =+7= → =7= and
=1e2= → =100= were both normalising silently, and neither is a leading zero or
a trailing one. /A third, =1.0= → =1=, is this spoke's alone: =Cell::Double='s
rendering drops the =.0= where the JSON serializer keeps it, so the gate
declines it here and the number model's "whole floats keep their =.0=" still
holds everywhere else./

*The gate decides per **column**, and a ZIP column is what forced that.* Read
per cell, =[007, 08001, 12345]= returns two strings and a *number* -- the third
ZIP typed differently from its own column because it happens to have no leading
zero. One refused cell now types the whole column as text. /The =csv -> csv=
run cannot tell the two readings apart, since both keep every cell's text; the
difference shows only in a per-feature-property target like GeoJSON, and in the
IR a library consumer holds./

*But only a **refusal** gates a column.* A plain =hello= beside a =7= has no
typed reading to refuse, so that column still returns =Int(7)= and
=String("hello")= -- an ordinary mixed column, settled downstream by
=schema::infer_columns= as it always was.

***Two losses remain and neither is the inference's choice.*** The *geometry*
column is WKT by definition, so it inherits that spoke's canonicalisation
(=POINT (1.50 2.00)= → =POINT (1.5 2)=, /measured/). And a column type is a
property of the column: =[9007199254740993, 1.5]= is typed =Double= because one
row is fractional, so the integer loses its low bits on the way out even though
its own text round-trips /(measured)/. Both are what
=Format::Csv.same_format_losses()= now says, in place of the two entries it
used to carry.

See [[file:same-format-fidelity.org][same-format-fidelity.org]] D17 for the
rule and for which spokes it does *not* reach.

*** WKT -- /measured/
Same lexeme story, plus one hard gap.

| input                       | returns                | note |
|-----------------------------+------------------------+------|
| =POINT (1.50 2.00)=         | =POINT (1.5 2)=        | lexeme |
| =POINT (1e2 3E-1)=          | =POINT (100 0.3)=      | lexeme, notation |
| =linestring z (...)=        | =LINESTRING Z (...)=   | case; canonical, arguably fine |
| =MULTIPOINT ((1 2), (3 4))= | =MULTIPOINT (1 2, 3 4)=| dialect form |
| =POINT EMPTY=               | *rejected*             | see below |

=POINT EMPTY= does not round-trip -- it fails to parse at all:

#+begin_src text
$ geosetta pr.wkt - --to geojson
geosetta: conversion error: wkt: expected '('
#+end_src

*This is the refusal carve-out working as designed* (=same-format-fidelity.org=
§ A refusal honours the rule): no silent loss, because no run. But =EMPTY= is
standard OGC WKT, so it is a real capability gap, and one file containing one
=EMPTY= geometry makes the whole conversion fail. /Unverified/: which real
producers emit it, and how often. Source a fixture before deciding whether to
support or keep refusing.

The =MULTIPOINT= row is the interesting one for the invariant: both forms are
valid WKT and geosetta normalises to the bare one. Under a strict reading that
is a same-format loss; under a reasonable one it is canonicalisation. *It needs
a ruling* -- see § QUESTIONS THIS RAISES.

*** FlatGeobuf -- /code/, =flatgeobuf/reader.rs=
The largest inventory, because FGB's header is rich and the reader defines
constants for five fields out of fourteen.

=mod header= declares =GEOMETRY_TYPE(2)=, =COLUMNS(7)=, =FEATURES_COUNT(8)=,
=INDEX_NODE_SIZE(9)=, =CRS(10)=. Everything else in the table is not read:

| field                   | class    | note |
|-------------------------+----------+------|
| =name(0)=               | identity | *fixed 2026-08-20* -- modelled as =fc.name=; the writer's =geosetta= constant is gone (defect 4) |
| =envelope(1)=           | derived-information | writer recomputes it already |
| =title(11)=             | opaque   | *carried 2026-08-20* |
| =description(12)=       | opaque   | *carried 2026-08-20* |
| =metadata(13)=          | opaque   | *carried 2026-08-20*; the one real tools populate |
| =has_t(5)= / =has_tm(6)=| --       | the T dimension; unmodelled by the IR entirely |

*** FlatGeobuf spoke -- DONE 2026-08-20
=FgbNative= (=src/native.rs=) carries the header's =title=/=description=/
=metadata=, the =Crs= sub-table's =name=/=description=/=code_string=, and each
column's =title=/=description=/=metadata=; =fc.name= models the header name.
/Measured/ on =gdal_hostile.fgb=, which is real =ogr2ogr= output: reading it
recovers =name = "cities"=, =metadata = {"GPKG_METADATA_ITEM_1":"<lineage>
surveyed 2019</lineage>"}= and =crs.name = "WGS 84"=; rewriting it puts all
three back, and *=ogrinfo= reads the result and reports the same three*, so the
vtable widening (=header::NUM_FIELDS= 11 → 14) did not break compatibility with
the reference implementation.

*One member deliberately not carried:* =Feature.columns(2)=, FlatGeobuf's
per-feature schema override. No observed tool emits one, and it is a *schema*
rather than a description -- if it ever needs support it belongs with
=FieldDecl=, not in the native.

*A trap for whoever does the next spoke.* =build_crs= used to open with
=match crs?=, which returns early when the collection has no CRS. That silently
dropped the whole =Crs= sub-table -- *including the natives inside it* -- for a
file whose only CRS content was a name. A test caught it; the fix is that the
natives count toward "is there anything worth recording".

The nested tables lose more, and this is the part that was not anticipated:
- *=Crs=*: reader knows =org(0)=, =code(1)=, =wkt(4)=. Discards =name(2)=
  (identity), =description(3)= (opaque), =code_string(5)= (identity -- the
  alphanumeric-code case =NamedCrs.code= exists for).
- *=Column=*: reader knows =name(0)= and =type(1)=. Discards =title=,
  =description=, =width=, =precision=, =scale=, =nullable=, =unique=,
  =primary_key=, =metadata= -- *nine fields of per-column schema*. A
  FlatGeobuf written by a tool that populates them round-trips through geosetta
  as a bare name/type pair.

  *Six of the nine are now modelled, not opaque* (2026-08-20): =width=,
  =precision=, =scale=, =nullable=, =unique=, =primary_key= become first-class
  IR under =same-format-fidelity.org= D1. =title=, =description= and =metadata=
  stay opaque natives.

  *Implemented 2026-08-20.* Both sides: =reader.rs= =read_decl= fills
  =FeatureCollection::schema= from slots 4--9, =writer.rs= =write_decl= puts
  them back. The slot indices were *hand-decoded from real =ogr2ogr= output*
  rather than read off the schema file, and the decode is worth recording
  because it is not what the field names suggest:

  | =.dbf= declaration | FlatGeobuf slots written by GDAL |
  |--------------------+----------------------------------|
  | =String (80.0)=    | =width(4) = 80=, nothing else    |
  | =Real (23.15)=     | =precision(5) = 23=, =scale(6) = 15=, *no =width=* |
  | =NOT NULL UNIQUE=  | =nullable(7) = 0=, =unique(8) = 1= |

  So a *numeric* field's length is a =precision=, not a =width= -- OGR's
  "width" and FlatGeobuf's =width= are different things for numbers, and
  =FieldDecl= follows FlatGeobuf's vocabulary because it is the only one of the
  four spokes that names all six. Also /measured/: GDAL writes =width: 0= for a
  GeoPackage =TEXT= column, so *zero means undeclared*, not a zero-wide field;
  reading it as a declaration would pin every downstream field to width 0.

  *This is the load-bearing entry in the whole inventory*, and it did not look
  like it. Because a native cannot cross a pipe (D5), FlatGeobuf's =Column=
  table is the *only* place a schema declaration can survive a transit and be
  edited by a middle stage -- which is what lets
  =geosetta a.shp - --to fgb | tool | geosetta - b.shp --from fgb= widen a
  =.dbf= field alongside the value that outgrew it. Every other route either
  loses the declaration or cannot be reached by an external tool.

Plus the null cell (defect 1), which is a reader bug rather than an unmodelled
member: the column survives in the header and the value is encoded by omission.

*Except that its second half /was/ an unmodelled member* /(found 2026-08-20,
reviewing defect 1 -- see =same-format-fidelity.org= § THE DEFECTS)./ Both
halves are *fixed* as of M4. Restoring the cell was the reader bug; keeping the
column's *declared type* was not, because =FieldDecl= had no type field and
=infer_columns= defaults an all-null column to =String=. So =Column.type(1)=
belonged in this inventory after all, alongside slots 4--9 -- a *tenth*
discarded =Column= field, missed because the reader visibly /does/ read it (to
decode values) and only dropped it when a column had no values left to
describe. It was the same missing affordance as GeoPackage's unread =BOOLEAN=
declaration, which is why the two defects shipped together.

*And nested objects are stringified* /(measured while building the fixtures)/.
A GeoJSON property =nested: {"deep":[1,2,{"k":"v"}]}= comes back through FGB as
the *string* ="{\"deep\":[1,2,{\"k\":\"v\"}]}"=. FGB's column types are
scalar (=Bool=/=Int64=/=Double=/=String=), so a structured value has nowhere to
go but a string -- and the reader does not parse it back. Class: opaque, and it
is the same lexeme problem as CSV once more, since the re-parse is what is
missing rather than the storage. GeoPackage keeps such values as JSON text too;
GeoParquet keeps them structured.

*** A discard the table missed entirely -- blob *values*, 2026-08-21
Every entry above answers "what does this reader fail to *model*". None asked
what a reader fails to *carry*, and that is where the worst loss in this
document was hiding: =geopackage/reader.rs= mapped =Value::Blob(_)= to
=JsonValue::Null=, so **a =gpkg -> gpkg= run destroyed every blob in the file**
while its =BLOB= declaration survived intact. FlatGeobuf skipped the payload
and yielded =Null= too; GeoParquet rendered hex text.

All three were *correct given the IR*: its property type is =JsonValue=, so
bytes had nowhere to live, and all three then rightly declined to *declare*
=Binary= -- a declaration whose values are destroyed is a promise the value
side cannot keep. The fix was the IR (=JsonValue::Binary=), not the spokes.

*The lesson for this document:* an inventory of unmodelled *members* does not
catch a destroyed *value*. The same blind spot appeared in the test suite the
same day -- see =same-format-fidelity.org= § The blob the schema check could
not see.

*** A second discard the table missed -- the *feature id*, 2026-08-25
/Found by pulling on =gpkg_metadata_reference=, the same way =last_change= was
found by pulling on its timestamp./

***A =gpkg -> gpkg= run renumbered every feature.*** Measured 2026-08-25 on a
=cities= layer holding fids =1, 9, 40=:

#+begin_src text
  geosetta gap.gpkg out.gpkg   ->  fids 1, 2, 3     <- the finding
  ogr2ogr  -f GPKG ogr.gpkg    ->  fids 1, 9, 40
  geosetta, after decision 27  ->  fids 1, 9, 40
#+end_src

***Fixed the same day it was found***, by decision 27. What follows is the
argument as it was made, because the classification is the durable part and
the two requirements it turns on will come up again for the metadata pair.

Silently: no warning fires, because nothing classifies the id at all.
=reader.rs:148= filters the rowid alias out of the properties it builds, and
=writer.rs:900= assigns =(i + 1)= to each row on the way out. The value is not
carried, not warned about, and not listed anywhere in this document.

**Why this document missed it, and the reason is structural rather than an
oversight.** The GeoPackage entry above has exactly two levels -- *layer* and
*container* -- and the feature id is at neither. It is a *feature*-level
member, and the inventory has no such level for this spoke, so there was no
row for it to be absent from. *The concept was never missing from the
document* -- the GeoJSON entry has a =level= column and lists =id= at
=feature= level, classed *identity*, which is the same member of the same kind
by the same name. It was the GeoPackage entry that had no shelf at that level,
which makes this a gap in one table rather than in the method. /Third time this
week in a different disguise:
=last_change= was missed because a timestamp reads as bookkeeping, the blob was
missed because the table asked what a reader fails to **model** and not what it
fails to **carry**, and this one was missed because the table has no shelf at
the level it lives on./

**The standard gives the column a stated purpose, which is what settles its
class.** Requirement 29 (OGC 12-128r19 § 2.1.6, read at pinned =fe83fdd=)
mandates the INTEGER primary key acting as a =rowid= alias, and the note
immediately under it says what it is *for*: /"The integer primary key of a
feature table allows features to be linked to row level metadata records in the
=gpkg_metadata= table by rowid values in the =gpkg_metadata_reference= table."/
So the id is an **externally referenced value with a meaning the standard
defines**, not an allocation detail -- the same argument that reclassified
=last_change=, which was the one column in =gpkg_contents= with a stated
meaning about the data.

/Stated precisely, because the =gdal_tiles.gpkg= lesson applies: nothing in the
standard requires a **writer** to preserve the values across a rewrite, so
renumbered output is conformant. That is not the question. =last_change= was
conformant either way too, and the value was still real./

*And =ogr2ogr= preserves them exactly*, which is producer practice and evidence
of what a consumer will expect -- never evidence of a requirement
(=same-format-fidelity.org= § THE ORACLE RULE). It is recorded because a user
moving between the two tools sees one preserve identity and the other not.

**Nothing in the tree could test this, and the reason is uncomfortable**: all
eleven =.gpkg= fixtures held feature ids that are dense =1..n=, so every one of
them round-tripped through the renumbering unchanged and the whole corpus was
blind to it. =sqlite_fid_gap.gpkg= was built for exactly that gap.

/That fact is also the containment result, and it was confirmed rather than
assumed: after the fix, the outputs for all eleven older fixtures are
byte-identical to the previous binary's./

**The channel already exists and already carries exactly this member for
another spoke.** =Feature::native='s own doc names /"a GeoJSON =id="/ as its
example of what it holds. What is missing is that =NativePayload::Gpkg= is
*collection-level only* by construction, so a per-feature form is the one
structural addition -- and D16 contains the cost, because a dense =1..n=
sequence is precisely what the writer emits anyway and so is **derived**, not
carried.

***The consequence that reaches an already-taken decision.***
=container-reconciliation.org= D5 refuses a user-table merge on the
=row_id_value= hazard -- a =gpkg_metadata_reference= row pointing at a rowid
that renumbering silently invalidates, with no foreign key for

confined to merging: this writer renumbers on the plain **one-container** path
as well, so the hazard is already live in shipped behaviour wherever a source

bitten yet./

*** GeoPackage spoke -- DONE 2026-08-21, extended 2026-08-24 and 2026-08-25
=GpkgNative= (=src/native.rs=) carries =gpkg_contents.identifier=,

this member came to be missing from the table above for as long as it was is

***=last_change= was missed by this inventory, and the way it was missed is the
lesson.*** The =gpkg_contents= row was surveyed for what it says *about* a
layer -- title, description -- and =last_change= reads as bookkeeping, so it was
never listed as a member at all. It is not bookkeeping: the standard defines it
as /"timestamp of last change to content"/, which is the one =gpkg_contents=
column with a stated meaning about the *data*. A =gpkg -> gpkg= run had been
overwriting it with a constant since the spoke shipped. /Found 2026-08-23 while
reading the normative text for a different question -- the timestamp in
=gpkg_metadata_reference=, which the standard pointedly leaves undefined./ /Measured/ on =gdal_hostile.gpkg=,
extended for this spoke (see =tests/fixtures/HOSTILE.org=): a =gpkg -> gpkg=
run now preserves the title =Bykerne — København og Zürich=, the description,
both column rows and the =price_range= domain -- and *=ogrinfo= reads all of it
back off our output*, reporting the same alternative names, comments and
domain, with =ogr2ogr= able to rewrite the result.

*Two members carried conditionally, which is the ruling this spoke adds.* Both
are cases where the *default the writer already produces* is indistinguishable
from the source, so carrying them would be recording the absence of content:
- =identifier= is dropped when it equals the table name. GDAL writes that for
  every layer it creates, so keeping it would put a payload on essentially
  every GeoPackage in existence, make =is_empty= permanently false, and -- the
  part that is a bug rather than noise -- *replay a stale title into a layer
  that had since been renamed*. An identifier equal to the layer name is
  *derived* under D4 and regenerated.
- =last_change= is dropped when it is the writer's own epoch sentinel
  (=1970-01-01T00:00:00.000Z=), on exactly the =identifier= reasoning: a value
  the writer regenerates anyway is not content. /Added 2026-08-24./

  **But the consequence differs from =identifier='s, and that is worth stating
  because the two rules look identical.** Every file *another* tool wrote has a
  real =last_change=, so an =ogr2ogr= GeoPackage now *does* construct a payload
  -- the outcome the =identifier= rule exists to prevent. The difference is what
  is being recorded: dropping an empty =description= avoids a payload that
  records the *absence* of information, while =last_change= is present and
  meaningful, and the alternative to carrying it is destroying it. /D3's "the
  common case costs nothing" is unharmed for *our own* output, which is what it
  was about./

  ***The payload change is contained, and that was measured rather than
  argued.*** Two release binaries -- this commit and its parent -- over
  =gdal_hostile.gpkg=, writing to identical paths in separate directories so
  that nothing differs by filename:

  #+begin_src text
    geojson  payload:SAME  stderr:SAME
    gpkg     payload:DIFF  stderr:SAME   <- the intended change
    fgb      payload:SAME  stderr:SAME
    csv      payload:SAME  stderr:SAME
    wkt      payload:SAME  stderr:SAME
  #+end_src

  So a native existing where none did before changes *nothing* outside the
  GeoPackage write path -- no warning fires that did not fire, and no other
  spoke's bytes move. The reason is structural rather than lucky:
  =payload_for(Format::X)= is format-tagged, so a =Gpkg=-tagged payload is
  invisible to every other spoke, and **no warning path reads =fc.native= at
  all**. /Cost of the payload itself: one =Option<String>= per *layer*, holding
  a 24-character timestamp. Not per feature./

  ***The residual risk is worth naming because it has already bitten once.***
  =is_empty()= is now effectively always false for a foreign GeoPackage, so any
  code using =native.is_some()= as a proxy for /"this file has unusual
  content"/ is now wrong for every =ogr2ogr= file.
  =an_identifier_that_only_repeats_the_layer_name_is_not_carried= used exactly
  that proxy and broke on this change -- loudly, which is the good case. The
  next such proxy may not have a test behind it.
- =description= is dropped when empty. =ogr2ogr= writes ='' = (not NULL), and
  so does this writer.

  *This deliberately does not follow =FgbNative='s "absent and empty are
  different" rule*, and the difference is worth stating because the next spoke
  will meet it: that rule holds for FlatGeobuf because its writer *omits* an
  absent field, so the distinction survives into the file. =gpkg_contents= is a
  row that is always written, so NULL and ='' = produce the same bytes and the
  distinction has nowhere to live.

*The constraints are container-scoped on disk but carried per layer*, because a
constraint no data column refers to describes nothing. Two layers sharing one
therefore each carry a copy, and the writer de-duplicates on the way out. A
=gpkg_data_columns= row whose column no longer exists is dropped on write --
decision 14's "an opaque member can also be derived", second instance, since
GDAL would otherwise report an alias on a field that is not there.

*A bug found by measuring rather than by reading the code.* The round trip
turned =price REAL= into =price FLOAT=: =decl_type= grouped =REAL= with =FLOAT=
as =Float32=, but =REAL= is 64-bit in both the GeoPackage spec's table 1 and
SQLite's storage classes. GDAL made it visible -- =Real (0.0)= going in,
=Real(Float32) (0.0)= coming out -- on a *same-format* run. It is defect 5's
shape in one more spelling, and it was sitting inside work M4 had already
declared complete; nothing but running the file through and comparing the two
=ogrinfo= outputs would have surfaced it. /Fixed 2026-08-21./

*Still not carried, and deliberately:* everything at container level below,
which is M3b's. The two Schema-extension tables are the exception that proves
the split -- they *live* in container-scoped tables but their rows are keyed by

*** GeoParquet spoke -- DONE 2026-08-20
=ParquetNative= (=src/native.rs=) carries every =key_value_metadata= entry
beside =geo=, plus the primary column's =geo.orientation=. /Measured/ on
=gdal_covering_bbox.parquet=, real =ogr2ogr= output: all three keys come back,

=ARROW:schema= is *not* like the others: it restates the file's own column
types, and an Arrow reader trusts it over the Parquet schema. Replaying a
stale one into a file whose columns a middle stage changed would hand back

except this member is opaque *and* derived at once. So =ParquetNative= records
the property column names it was read beside, and =replayable_metadata= drops
=ARROW:schema= (only) when they no longer match. Opaque keys like
=gdal:metadata= travel unconditionally.

*Still not carried: =covering=.* It is /derived-capability/ under D4 -- rebuilt
when the source had one -- and rebuilding it means *writing a nested struct
column*, which this writer cannot do at all (its schema is one flat level of
optional leaves). That is a self-contained piece of work, not a natives
question, and it is the last GeoParquet entry in this inventory. *Owned by*
[[file:spatial-index.org][spatial-index.org]] *milestone E*, which already
holds the same D4 rebuild-if-present rule for FlatGeobuf's and GeoPackage's
indexes.

*=version= is deliberately not preserved, and that is correct.* DuckDB writes
=1.0.0=; geosetta always writes =1.1.0= (=geo.rs:14=). That is not a loss --
the member describes *the file geosetta just wrote*, which genuinely is a 1.1.0
document. Recorded so it is not "fixed" into a bug by someone reading this
table quickly.

*Null result on =edges= and =epoch=.* Per =plans/README.org=, a null result is
information. Neither GDAL 3.13.2 nor DuckDB-spatial emitted either member in
any file produced for this pass, so no fixture exists to build against and a
from-spec implementation would be unverifiable.

*But do not close it the way =envelope.org= closed the GPKG XYM indicators.*
There the null result meant nothing consumes them either. Here the likely
producers -- geography-typed exports from BigQuery/Snowflake-style engines --
simply were not available to test, and =edges= is not decorative:
=edges: "spherical"= means the segments between vertices are great-circle arcs,
so reading one and writing geosetta's default (planar, by omission) would
*restate the geometry's meaning* while preserving every coordinate. That is
the GeoJSON-relabel failure mode, which the crate already warns about. It
belongs on the fixture hunt, not in the closed pile.

1. ~~*Is canonicalisation a loss?*~~ ***ANSWERED 2026-10-21: it is a loss
   exactly where the reader had a choice*** -- =same-format-fidelity.org= D17,
   and the CSV half is implemented the same day (§ CSV → FIXED).

   *Measuring the question first split it into three things it had been
   holding as one*, and only the first is the canonicalisation argument the
   entry was filed about:

   | what changed | example | ruling |
   |--------------+---------+--------|
   | *spelling only* -- the output denotes what the input did | =1.50= → =1.5=, =TRUE= → =true=, =point= → =POINT=, the MULTIPOINT dialect, CSV's optional quoting | a loss *where the reader chose to type an untyped cell*; accepted where the grammar forces a number |
   | *the value's identity* -- the text /was/ the data | =007= → =7=, =08001= → =8001= | always a loss, and a type-inference error rather than canonicalisation |
   | *a different value* | =12345678901234567890= → =12345678901234567000= | always a loss; never was a canonicalisation question |

   *So "two bugs or a whole class" was the wrong fork.* It is a class, and the
   class is drawn by **who decides the type** rather than by the format: a CSV
   cell and a KML =ExtendedData= value are untyped text, so typing them is the
   reader's decision and must be reversible; a JSON number and a WKT
   coordinate are numbers *by grammar*, so there is no un-inferred reading to
   fall back to and the spelling loss is declared instead of fixed.

   *A fourth instance was found while ruling it, and it had been declared
   inconsistently*: =geojson -> geojson= reformats numbers exactly as
   =csv -> csv= did (=1.50= → =1.5=, =[1.50,2.00]= → =[1.5,2.0]=, and the same
   past-=i64= precision), while =Format::GeoJson='s loss list named only =bbox=
   and geometry foreign members. One loss, two stories, in a warning a user
   reads. /The list now names it./

   ***The =Json=-column instance is ruled but deliberately not fixed here, and
   it is not the same fix.*** GeoParquet *parses* a =JSON=-annotated column
   (=push_json_embedded=), so ={"a": 1}= re-serializes without the space where
   GeoPackage and FlatGeobuf keep the text. Gating the parse the way
   =infer_value= is gated looks obvious and is not: the parse is also what
   makes the column's =DeclType::Json= declaration meaningful, and
   =Format::recast='s pinned table is written against the parsed reading. It
   wants its own measurement and belongs to the GeoParquet spoke. /It is the
   one place the three spokes still disagree about the same column./
2. *Does the T dimension exist?* FlatGeobuf has =has_t=/=has_tm=; the IR has
   =x, y, z, m=. If a real producer emits T, the invariant says geosetta must
   refuse the file rather than drop the dimension. /Unverified/ that any does.
3. ~~*Should derived-capability sidecars be rebuilt for Shapefile too?*~~
   ***ANSWERED 2026-10-21: no -- and investigating it found that the index
   sidecars were the least of it.***

   *The question as filed asked about a capability, and the same gap was
   leaking information.* Geosetta writes =.shp=/=.shx=/=.dbf= and a =.prj= when
   it has a CRS; **every other file already at the output basename survives the
   write and then describes the output.** Measured, all three:

   | sidecar left behind | what it does to our output |
   |---------------------+----------------------------|
   | =.prj= | a CRS-less CSV's degree coordinates came back as =NAD83 / UTM zone 18N= in *metres*, from =ogrinfo= and from =geosetta --print-crs= alike |
   | =.cpg= | one reading =ISO-8859-1= turned =København= into =KÃ¸benhavn= -- for GDAL **and for geosetta's own reader**, so correct bytes were written and corrupt text read back |
   | =.qix=/=.sbn= | an index describing different geometry. /Could not be made to produce a wrong answer from GDAL in any configuration tried -- including a 500-feature file whose stale index knew nothing of the new extent, and with the =.qix= touched newer than the =.shp=. Per § THE ORACLE RULE that is evidence about one consumer, not a guarantee./ |

   /=ogr2ogr -overwrite= has none of this: measured, it deletes the entire
   prior file set, =.qix= and =.prj= included. **That is the other coherent
   answer and not this project's** -- a conversion must not delete files nobody
   asked it to touch, so the output file set can legitimately be part ours and
   part somebody else's, and the user is *told* which./

   **So the ruling is three parts:**

   1. ***=.cpg= is written, always, saying =UTF-8=.*** It is the one member of
      the set whose right answer this writer always knows, and under
      no-deletion it is the only thing that stops a foreign =.cpg= from
      relabelling our text. /This also closes this section's own one-sided
      =.cpg= gap, where the reader honoured one and the writer emitted none./
   2. ***A surviving sidecar is warned about, naming what it will be read
      as.*** =.sbn=/=.sbx= cannot be written at all (proprietary; GDAL declines
      too) and =.prj= has nothing to say when the source carries no CRS -- OGC
      WKT has no spelling for "unknown" -- so the warning is the whole answer
      for those, not half of one.
   3. ***=.qix= and =.sbn= are still not written.*** D4's
      "rebuilt when the source carried one" is triggered **nowhere today**,
      GeoPackage included -- =main.rs= passes only =args.rtree= -- so extending
      an unimplemented rule to a second spoke before the first would be
      backwards. It belongs on =spatial-index.org= as one piece of work
      covering both spokes.

   *Two things the ranking in this section got wrong, both because the
   comparison with the reference was incomplete.* =.cpg= was ranked "below the
   width narrowing" on the grounds that =ogr2ogr= emits none either. True, and
   beside the point twice over: the stale-=.cpg= corruption above has nothing to
   do with symmetry, and **=ogr2ogr='s default output declares LDID =0x57= --
   ANSI/Windows-1252 -- while writing UTF-8 bytes** /(measured)/. So the
   reference *does* declare an encoding by default; it declares the wrong one
   through the other channel, and only writes a =.cpg= when given an explicit
   =-lco ENCODING==.

   *And one adjacent defect, filed not fixed:* =encoding_from_cpg= maps any
   unrecognised =.cpg= to Latin-1 **silently**. The common real case is
   =CP1252=, which differs from ISO-8859-1 in exactly the 32 bytes =0x80=--=0x9F=
   -- where Windows-1252 keeps the curly quotes, dashes, =€= and =…= that real
   attribute data is full of, and Latin-1 has C1 control characters. Under
   =lossy-conversion-warnings.org='s rule that approximation owes a warning,
   and the cheap fix is a 128-entry table per single-byte codepage (no
   dependency, no architecture change). /Multi-byte codepages -- Shift-JIS,
   GBK, Big5 -- are where this stops being cheap, and the defensible answer
   there is to refuse rather than approximate./
4. *Does =edges: "spherical"= need a refusal rather than a warning?* If a
   producer is found, geosetta reading spherical geometry and writing its
   planar default does not drop a member -- it *restates what the coordinates
   mean*, which is the GeoJSON-relabel failure mode. Under the invariant that
   argues for the refusal carve-out, not a native. Blocked on the fixture.
5. ~~*Is a narrowed schema a data loss or a schema loss?*~~ *Answered
   2026-08-20: a loss, and the fix is modelling rather than a native.* Column
   =width=/=precision=/=scale= (and =nullable=/=unique=/=primary_key=) become
   first-class IR under =same-format-fidelity.org= D1's exception, beside
   collection =name= -- four formats have real slots for them. The deciding
   argument was D5: a native cannot cross a pipe, so only a *modelled* field
   lets an external tool widen a declaration mid-flight alongside the value it
   lengthened. =ogr2ogr= preserves =String (80.0)= and =Real (24.15)= exactly,
   confirming the reference treats the declaration as information.
   *Implemented 2026-08-20* for the Shapefile and FlatGeobuf spokes -- see
   § Shapefile → FIXED for the re-measurement, and note that the =shp -> fgb
   -> shp= route now preserves the declaration *better than =ogr2ogr= does*,
   which reformats =24.15= to =23.15= on the same hop.
6. ~~*An unrecognised KML geometry yields a feature with no geometry,
   silently.*~~ *Answered 2026-08-20: warn and emit.* Name the element on
   stderr, keep the feature with =geometry: null=. Refusing was rejected --
   the =POINT EMPTY= parallel is weak, since WKT refuses because its *parser*
   cannot handle the syntax (incidental) whereas KML returns =None= by design,
   and one =<Model>= should not kill a 10,000-feature file. Note GDAL is
   *silent* here /(measured)/, so this is geosetta being deliberately stricter
   than the reference -- as it already is on M-drop and CRS relabel.

   /Re-measured 2026-10-22 and "the reference" is two behaviours: **LIBKML**
   keeps the Placemark with no geometry and says nothing, exactly as this crate
   does, while GDAL's **built-in =KML= driver drops the feature outright**,
   attributes and all. So the warning is stricter than one driver and the
   feature's survival is kinder than the other./

   /2026-10-23: **built**, as § GEOMETRY ELEMENT COVERAGE in =kml.org= rules
   it -- =<Model>= warns and emits, the other three are parsed. The warning is
   a write-side one since =kml-standard.org= K4: the =<Model>= is carried./

   /2026-10-22: **scoped, still unbuilt -- and the ruling turned out to be
   three pieces of work, one of them not a warning at all.** Re-measured
   first: =hand_hostile.kml='s =<Model>= Placemark comes back
   =geometry: null= with nothing on stderr, and so do a bare =<LinearRing>=
   and a =<gx:Track>= authored for the re-measurement./

   1. ***There is no arm to warn in.*** =parse_geometry= (=kml/reader.rs:115=)
      is driven by =find_map= over *every* child, so its =_ => None= is also
      how =<name>=, =<description>=, =<styleUrl>=, =<visibility>=,
      =<TimeStamp>= and =<ExtendedData>= are passed over -- a warning there
      warns about all of them. What it needs is a *positive list* of KML's
      geometry element names, split recognised/unsupported, which is D6's
      catch-all-free shape one level down. Ruled in
      [[file:kml.org][=kml.org=]] § GEOMETRY ELEMENT COVERAGE.
   2. ***A capability gap was hiding inside the warning question*** -- which
      is item 3's lesson in a second instance, found the same way. KML 2.2's
      =Geometry= substitution group is =Point=, =LineString=, =LinearRing=,
      =Polygon=, =MultiGeometry= and =Model=; this reader handles four, and
      reads =LinearRing= *only* inside a =<Polygon>= boundary
      (=kml/reader.rs:147=). So a =Placemark= holding a bare =<LinearRing>=
      is legal KML and comes back geometry-less /(measured)/ -- but unlike a
      =<Model>=, **the IR can hold it**, so the answer for that one is to
      parse it rather than to warn about it. /Answering the question as asked
      would have put a warning on geometry this crate can represent exactly,
      which § THE CLASSES would call a silent loss dressed as a report./

      ***And measured 2026-10-22 it is two of the four, not one***: GDAL's
      LIBKML driver reads a =<gx:Track>= as =LINESTRING Z=, so ***that is
      ruled the same way -- parse it*** (=<gx:MultiTrack>= to a
      =MultiLineString=), under the preference now stated crate-wide at
      =lossy-conversion-warnings.org= § THE COMPLEMENT: where a loss can be
      avoided by doing the work, the work wins over the report.

      So ***three of the four members of the silent hole are capability gap
      rather than loss***, and only =<Model>= earns the warning Q6 was filed
      about. /The measurement is tabulated in =kml.org= § What GDAL does./
      **What a track still loses is its per-vertex =<when>= series** -- one
      instant per vertex, which is not the same thing as a Placemark's own
      =<TimeStamp>= and needs its own loss-list entry. Its home is the KML
      native channel when =same-format-fidelity.org= M3 lands, *not* the =m=
      ordinate: writing times into =m= would relabel what the coordinates
      mean, which is the failure mode item 4 refuses for =edges=.

      /Also worth noting against item 2: a =gx:Track= is the first real
      producer of **per-vertex time** either question has turned up. Item 2
      asks whether anything emits FlatGeobuf's =has_t=; this is adjacent to
      it and not the same question./
   3. ***There is nowhere to put the message.*** Both of this crate's warning
      mechanisms are write-side, and =geometry: None= left by a =<Model>= is
      indistinguishable in the IR from a Placemark that legitimately has
      none, so no pre-write check can recover the fact. The read-time channel
      this needs is scoped at
      [[file:lossy-conversion-warnings.org][=lossy-conversion-warnings.org=]]
      § 2b, where **item 3's own =.cpg= warning is the second owed instance**
      -- so the channel serves two, which is the argument for building it
      rather than special-casing this spoke.

   /Also worth knowing before it ships: =xml.rs= strips namespace prefixes at
   parse, so a =gx:Track= reaches the warning as =Track=. Ship the local name
   with a test pinning the wart -- the fix is the verbatim-replay ruling the
   KML spoke is already gated on, not a one-off here./
