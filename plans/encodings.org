* Text Encodings, Across Every Spoke
** STATUS -- rescoped 2026-10-28 to every encoding; E1 built, E5 partly
/2026-10-28:/ ***Rescoped from "single-byte, refuse the rest" to every
encoding in a closed, named set*** -- § WHAT "EVERY ENCODING" MEANS. The old
scope stopped at single-byte codepages because multi-byte tables were judged
too expensive for a dependency-free crate, and refused the rest (the old
D-E3). That was a warning standing in for a parser, which is the trade this
project does not make: the tables are published data, the algorithms are
specified, and the cost is a few hundred KB of committed tables rather than
an architecture. D-E3 is overturned; § WHAT THIS OVERTURNS has the list.

The rescope was asked for because KML's remaining same-format losses
(=todo.org=, "KML's XML-layer losses") include writing a non-UTF-8 document
back in its declared encoding, and that needs an *encoder* for whatever the
declaration names -- not only a decoder for the few encodings someone guessed
were common.

Built so far:
- *The =.cpg= write side* (2026-10-21): Shapefile emits a =.cpg= declaring
  =UTF-8= -- [[file:shapefile.org][shapefile.org]] § THE SIDECAR POLICY.
- *E1* (2026-10-23): an approximated =.cpg= codepage warns.
- *E5, partly* (2026-10-23, with =kml-standard.org= K1): =xml::decode= takes
  bytes and honours a BOM, UTF-16's first-bytes pattern and the declaration,
  for UTF-8, UTF-16, US-ASCII and ISO-8859-1.
- *E8's write side* (2026-10-28): a non-ASCII zip entry name sets
  general-purpose bit 11 in both headers (=zip.rs= =name_flags=).

This plan was first asked for after
[[file:native-inventory.org][native-inventory.org]] § QUESTIONS item 3 turned
up silent text corruption, and it is deliberately *not* a Shapefile plan. The
encoding surface spans every spoke that reads or writes text.

** WHY THIS IS A PLAN AND NOT A FLAG
=--encoding= is the obvious shape and it is a small part of the work. Four
things make this bigger than a flag:

1. ***Half the spokes refuse non-UTF-8 input outright and half guess.*** Those
   are opposite failure modes needing opposite fixes -- a refusal needs a
   *remedy*, a guess needs a *declaration or a warning* -- and today the crate
   does each in places nobody chose deliberately.
2. ***One spoke declares its encoding in-band, and its declaration cannot be
   trusted.*** Shapefile's =.dbf= carries a language-driver byte that the
   reference implementation fills in *wrongly*; another carries the truth in a
   sidecar. Honouring the obvious one corrupts correct files (D-E2).
3. ***The crate takes no dependencies.*** Every table is data in this tree,
   checked against its published source (D-E4), and every algorithm is ours.
4. ***Same-format runs owe the source's encoding back.*** A =kml -> kml= or
   =shp -> shp= run over a Shift_JIS source must write Shift_JIS, so every
   decoder needs its encoder (D-E7).

** WHAT IS WRONG TODAY
Not "missing features" -- things that produce a wrong answer or no answer where
a right one was available.

*** 1. An unrecognised =.cpg= is approximated as Latin-1
/Warned since 2026-10-23 (E1); still approximated./ =dbf::encoding_from_cpg=
maps every codepage it does not recognise to =Encoding::Latin1Approximating=.

***The common real case is =CP1252=, which differs from ISO-8859-1 in exactly
the 32 bytes =0x80=--=0x9F=*** -- where Windows-1252 keeps the curly quotes,
en/em dashes, =€= and =…= that real attribute data is full of, and ISO-8859-1
has C1 control characters. So the approximation is wrong precisely on the
characters that distinguish the two encodings. It is also *not* an exotic
input: =ogr2ogr= declares Windows-1252 by default (D-E2's measurement). The
fix is E2's tables, which retire the approximation entirely.

*** 2. Four spokes refuse non-UTF-8 input with no remedy to offer
=csv.rs:28=, =convert.rs:55=/=:140= all end in
=Error::Convert("… is not valid utf-8")=, and =xml::decode= refuses any
declared encoding it has no table for. **The refusal itself is right** --
§ A refusal honours the rule, in
[[file:same-format-fidelity.org][same-format-fidelity.org]]: no silent loss,
because no run. But a refusal is only honourable when the user has somewhere to
go, and today there is nowhere: no flag, no fallback, no message naming one.

/The asymmetry is the tell that nobody chose this:/ a Shapefile carrying
Latin-1 text reads fine, and the *same bytes* in a CSV are refused.

*** 3. A =.dbf= with no =.cpg= is guessed at, silently
With no =.cpg=, each field is tried as UTF-8 and, failing that, decoded as
Latin-1. That is a guess rather than a declared encoding approximated, so E1
left it open. Under this plan the guess has a better fallback (Windows-1252,
which is a superset of Latin-1's printable range and what =ogr2ogr= declares)
and is owed a warning either way -- D-E9.

*** 4. Zip entry names are refused on read and mis-declared on write
/Found 2026-10-28, while rescoping./ APPNOTE 6.3.0 § 4.4.4 and Appendix D:
an entry name with general-purpose bit 11 *clear* is IBM CP437, and with it
*set* is UTF-8.

- *Read:* =zip.rs:144= never reads the flag, and refuses any name that is not
  valid UTF-8. An older =.kmz= with a non-ASCII entry name in CP437 is
  refused; one whose CP437 bytes happen to be valid UTF-8 is mis-decoded.
- *Write:* =write_local_header= and =write_central_header= write UTF-8 name
  bytes with the flag *clear* -- declaring CP437. Since M3c carries a source
  =.kmz='s entries, a non-ASCII entry name is now reachable, and a reader that
  follows the spec gets mojibake.

The write side is a one-bit fix (set bit 11 when a name is not ASCII); the
read side needs CP437, which E2 brings. This is E8.
/2026-10-28: the write side is fixed./ A carried =Zürich.png= now reads back
as itself in Python's =zipfile= and =bsdtar=, where it read as
=Z├╝rich.png= before. macOS's =unzip= still shows it mangled: that build has
no Unicode support, ignores bit 11, and converts any name from an MS-DOS
host -- which our "version made by" (=20=, host 0) declares -- out of CP437.
Python's own archives say host 3 (Unix) and pass through. The host byte goes
with the external attributes it defines, so it is
=same-format-fidelity.org= M3c's, not this plan's.

** WHAT "EVERY ENCODING" MEANS
"Every" has to be a closed, named set, or it is untestable. The set is:

1. ***The WHATWG Encoding Standard*** (=encoding.spec.whatwg.org=), every
   encoding in it:
   - UTF-8, UTF-16LE, UTF-16BE.
   - 28 single-byte encodings: IBM866; ISO-8859-2, -3, -4, -5, -6, -7, -8,
     -8-I, -10, -13, -14, -15, -16; KOI8-R, KOI8-U; macintosh; windows-874;
     windows-1250 through -1258; x-mac-cyrillic. (-8 and -8-I share a table.)
   - 7 multi-byte encodings: GBK, gb18030, Big5, EUC-JP, ISO-2022-JP,
     Shift_JIS, EUC-KR.
   - =x-user-defined= (trivial: high bytes to =U+F780=--=U+F7FF=). The
     =replacement= encoding is a WHATWG security device for the browser and
     maps to a refusal here.

   It is the right base because it is *what producers actually emit* -- it was
   written by measuring the web -- and because it specifies every decoder and
   encoder as an algorithm with error handling, not just a table.

2. ***The DOS OEM codepages WHATWG leaves out*** -- CP437, CP737, CP775,
   CP850, CP852, CP855, CP857, CP860, CP861, CP862, CP863, CP864, CP865,
   CP869. dBase files and zip entry names use them, and WHATWG keeps only
   IBM866. Sourced from Unicode's =MAPPINGS/VENDORS/MICSFT/PC/=.

3. ***True ISO-8859-1 and US-ASCII***, kept distinct from windows-1252 -- see
   D-E5 for why WHATWG's aliasing is not adopted.

4. ***UTF-32LE/BE***, because XML 1.0 Appendix F names them in its detection
   table and they need no table.

***Out of the set, and refused by name:*** EBCDIC codepages, UTF-7, the
ISO-2022 variants other than -JP, HZ, and anything else unlisted. Each refusal
names the encoding and says it is outside the supported set -- a refusal the
user can act on, not mojibake.

/The set grows by adding a table and a fixture, never by approximating./

** THE COST
- ***Single-byte:*** a 128-entry high-half table each; =0x00=--=0x7F= is ASCII
  in all of them. 27 WHATWG tables plus 14 OEM ones -- a few thousand lines
  of generated data. The encoder is the table inverted.
- ***Multi-byte:*** the WHATWG indexes -- =index-gb18030= (~24k entries) and
  =index-gb18030-ranges= (207 ranges), =index-big5= (~19k),
  =index-jis0208= (~7k), =index-jis0212= (~6k), =index-euc-kr= (~17k),
  =index-iso-2022-jp-katakana= (63). /Estimated, not yet measured:/ on the
  order of 200 KB as packed =u16=/=u32= arrays, and it lands in the wasm
  build too ([[file:../../wasm-plan.org][wasm-plan.org]]).
- ***Algorithms:*** most decoders are a lookup with a lead-byte state. The
  three with real logic are gb18030's four-byte ranges, ISO-2022-JP's
  escape-sequence state machine, and EUC-JP's JIS X 0212 path. Encoders need
  a reverse index, built lazily on first use rather than committed twice.
- ***UTF-16/UTF-32:*** no tables; surrogate handling only.

** DECISIONS
*** D-E1 -- the IR is UTF-8 only; decoding happens at the spoke boundary
Not really a choice -- =JsonValue::String= and =Cell::Str= hold Rust =String= --
but worth stating, because it is also the *right* design and should not be
"improved". A byte-level cell already exists for genuinely binary data
(=JsonValue::Binary=, 2026-08-21); text that cannot be decoded is an input
problem, not a value the IR should carry undecoded.

**Consequence:** every encoding question is a question about one spoke's
boundary, and no two spokes need to agree. That is what makes this plan
incremental. The *source's encoding*, where a same-format write owes it back,
travels beside the IR as the spoke's native state, not in it (D-E7).

*** D-E2 -- the =.dbf= language-driver byte is never trusted
/Decided 2026-10-21, on a measurement that reverses the obvious answer./

=dbf.rs:4= already calls the LDID byte "unreliable in practice" and the reader
ignores it, taking the encoding from =.cpg= alone. **That looks like a gap and
is a correct decision**, because:

#+begin_src text
  ogr2ogr default output:   LDID 0x57  (= ANSI / Windows-1252),  bytes are UTF-8
  ogr2ogr -lco ENCODING=…:  LDID 0x00  (= unknown),              bytes per .cpg
  geosetta output:          LDID 0x00  (= unknown),              bytes are UTF-8, .cpg says so
#+end_src

/All measured against GDAL 3.13.3./ ***So honouring LDID would decode the
reference implementation's own default output wrongly*** -- every
=ogr2ogr=-written UTF-8 shapefile would be mis-decoded as Windows-1252 by a
reader that believed the byte.

**This does not generalise to =.cpg=**, which is written by tools that mean it,
and is the channel Esri invented precisely because dBase has no UTF-8 LDID
value to put in the header.

*** D-E3 -- a refusal beats an approximation, outside the set
/Rescoped 2026-10-28./ Originally: "a multi-byte codepage is refused rather
than approximated", with multi-byte support out of scope. Now every encoding
in § WHAT "EVERY ENCODING" MEANS is decoded exactly, and the rule applies
only to what is outside the set: refuse, naming the encoding. **There is no
approximating path left in the crate** once E2 retires
=Latin1Approximating=.

*** D-E4 -- no dependency, so tables are data in this tree
A table is generated from a published mapping committed as a fixture, and a
test asserts the generated table reproduces its source entry for entry. A
published mapping committed as a fixture is a real oracle rather than a second
opinion. /This is the same shape as =tests/fixtures/esri_*_wkt1.tsv= and the
registry TSVs: authoritative data in the tree, compared against./

The generator is a script beside the =build_*_fixtures.sh= scripts, and its
output is committed Rust source -- no =build.rs=, so a build never runs it.

*** D-E5 -- WHATWG's labels and algorithms, but not its Latin-1 alias
WHATWG maps the labels =iso-8859-1=, =latin1=, =us-ascii= and =ascii= to
windows-1252, because that is what browsers did. **Geosetta does not adopt
that alias.** XML 1.0 and a =.cpg= mean true ISO-8859-1 when they say it, and
=dbf::Encoding= already keeps =Latin1= distinct from an approximation for
exactly that reason. Every other WHATWG label maps as WHATWG says.

The decoders and encoders follow WHATWG's algorithms, including its encoder
exclusions (Big5 never encodes HKSCS pointers below =(0xA1 - 0x81) × 157=;
Shift_JIS skips pointers 8272--8835; ISO-2022-JP encodes half-width katakana
as full-width). Where WHATWG's single-byte index and Unicode's vendor mapping
disagree -- windows-1252's =0x81=, =0x8D=, =0x8F=, =0x90=, =0x9D= are C1
controls in WHATWG and UNDEFINED in =CP1252.TXT= -- WHATWG is followed, so
every byte decodes.

*** D-E6 -- one shared module, every spoke through it
=src/encoding.rs= owns label lookup, decoding and encoding. =dbf::Encoding=
and the encoding half of =xml::decode= move onto it; =xml::decode= keeps only
XML's own detection (BOM, Appendix F's first bytes, the declaration) and
hands the bytes to the shared decoder.

#+begin_src rust
  pub(crate) enum Encoding { Utf8, Utf16Le, Utf16Be, Utf32Le, Utf32Be,
                             Latin1, Ascii, SingleByte(&'static Table), Gb18030, Gbk,
                             Big5, EucJp, Iso2022Jp, ShiftJis, EucKr, UserDefined }
  pub(crate) fn from_label(label: &str) -> Option<Encoding>;
  pub(crate) fn decode(bytes: &[u8], enc: Encoding) -> Result<Cow<'_, str>>;
  pub(crate) fn encode(text: &str, enc: Encoding) -> Result<Cow<'_, [u8]>, Unrepresentable>;
#+end_src

=decode= borrows when the input is already valid UTF-8 or ASCII under an
ASCII-compatible encoding. =Unrepresentable= carries the character and its
offset, so every spoke's refusal names both. =from_label= takes WHATWG labels
plus the =.cpg= spellings seen in the wild (=CP1252=, =ANSI 1252=, =1252=,
=65001=, =UTF8=, =OEM 437=), case- and separator-insensitively as
=encoding_from_cpg= does today.

*** D-E7 -- a same-format run writes the source's encoding back
/Decided 2026-10-28./ A =kml -> kml= run over a Shift_JIS document writes
Shift_JIS with the same declaration; a =shp -> shp= run over a CP1252 =.dbf=
writes CP1252 and keeps its =.cpg=. That is the same-format invariant applied
to bytes the document chose -- not a flag, and not a default the user has to
know about. The source's encoding is native state, held where the KML document
model and the =.dbf= reader already hold theirs.

A same-format run *with* =--to-encoding= writes what was asked, and that is a
conversion, not a loss: the text survives (old open question 4, answered).

*** D-E8 -- an unrepresentable character on write is refused
/Decided 2026-10-28, answering old open question 3./ A character the target
encoding cannot hold refuses the run, naming the character, the encoding and
where it was found (feature and property). The crate refuses a CRS it cannot
express; a =?= in a place name is the same kind of silent corruption. XML has
one more option, since a numeric character reference (=&#x4E2D;=) is valid in
*text and attribute values* under any encoding -- so KML escapes rather than
refuses there, which loses nothing. Element and attribute *names*, a =.dbf=,
CSV and WKT have no such escape and refuse.

*** D-E9 -- a =.dbf= with no =.cpg= falls back to windows-1252, warned
/Decided 2026-10-28, closing the question E1 left open./ Per field, UTF-8
first; a field that is not valid UTF-8 is decoded as windows-1252 rather than
Latin-1 -- the encoding =ogr2ogr= declares by default and a superset of
Latin-1's printable characters -- and the read warns, counted per cause, that
an undeclared encoding was guessed. A =--from-encoding= replaces the guess.

*** D-E10 -- two flags, one per side
/Decided 2026-10-28, answering old open question 2./ =--from-encoding= and
=--to-encoding=. A single =--encoding= is ambiguous exactly when both ends are
text, which is the case that matters. =--from-encoding= overrides every
in-band declaration (an XML declaration, a =.cpg=), because a user naming an
encoding is correcting a file that lied. =--to-encoding= for a spoke whose
format fixes UTF-8 (GeoJSON, FlatGeobuf, GeoParquet, GeoPackage) is refused,
naming the format's rule.

** MILESTONES
Ordered by what each unblocks. E1 is built; E2 is the foundation everything
else stands on.

*** E1 -- warn when a declared codepage is approximated
/***Built 2026-10-23.***/ =Encoding::Latin1Approximating= is the unrecognised
codepage, kept apart from a declared ISO-8859-1 (which is exact and silent).
The warning counts only values holding a non-ASCII byte, since ASCII is exact
under every codepage. Beside it, the same pass found a =.cpg= declaring UTF-8
over invalid bytes replacing them with U+FFFD silently; that warns too.

/Retired by E2/, for every codepage in the set: an approximation that no
longer happens has nothing to warn about. The U+FFFD warning stays.

*** E2 -- the shared module and every single-byte table
- =src/encoding.rs= per D-E6, with =from_label=, =decode=, =encode=.
- The 27 WHATWG single-byte tables and the 14 OEM ones, generated per D-E4.
- UTF-16 and UTF-32 move here from =xml.rs=; ISO-8859-1 and US-ASCII join them.
- =dbf::Encoding= is replaced; =encoding_from_cpg= becomes =from_label=; a
  =.cpg= outside the set is refused by name rather than approximated.
- =xml::decode= hands off to the shared decoder after its own detection, so
  every single-byte declaration reads. *Finishes E5 for single-byte.*

*** E3 -- every multi-byte decoder
/Rescoped 2026-10-28; was "refuse a multi-byte codepage"./ GBK and gb18030,
Big5, EUC-JP, ISO-2022-JP, Shift_JIS, EUC-KR, per WHATWG's decoder algorithms,
with the indexes generated per D-E4. Each malformed sequence is an error naming
the encoding and the byte offset -- WHATWG's "replacement" error mode is the
browser's, and silently inserting U+FFFD is the loss this plan exists to stop.
*Finishes E5.*

*** E4 -- =--from-encoding=, and BOMs, for every text spoke
=--from-encoding= per D-E10 at the four refusing call sites (=csv.rs:28=,
=convert.rs:55=, =convert.rs:140=, =xml::decode=) and into the =.dbf=
reader. A BOM is honoured by every text spoke, not only XML: stripped, and
used to choose UTF-8/16/32 when no flag is given. D-E9's no-=.cpg= fallback
and its warning land here.

*** E5 -- honour KML's own XML declaration
/***Partly built 2026-10-23, with =kml-standard.org= K1.*** =xml::decode=
takes bytes and decides by Appendix F: a BOM, then UTF-16's first-bytes
pattern, then the declaration's =encoding=. It decodes UTF-8, UTF-16 (both
byte orders, BOM or not), US-ASCII and ISO-8859-1 exactly. Any other declared
encoding is accepted over all-ASCII bytes and refused otherwise, naming the
encoding./ Finished by E2 (single-byte) and E3 (multi-byte); nothing else is
owed here. Appendix F's UTF-32 patterns join the sniff with E2.

*** E6 -- writing in an encoding other than UTF-8
Two halves:

1. ***Same-format write-back*** (D-E7). The KML document model already records
   spelling provenance (=kml-standard.org= D-K5); the declared encoding joins
   it, and =xml::write= encodes the document in it and writes the matching
   declaration. =shp -> shp= keeps the source =.cpg='s codepage. **This is the
   non-UTF-8 item of KML's XML-layer losses**, and removes it from
   =Format::Kml='s =same_format_losses= row.
2. ***=--to-encoding=*** (D-E10) for =.dbf= (declared in the =.cpg= this
   writer already emits), KML (declared in the XML declaration -- KML *does*
   have an in-band place, contrary to this plan's first draft), CSV and WKT
   (no declaration anywhere, so only ever written on request).

Unrepresentable characters per D-E8. =.dbf= truncation is measured in *bytes
of the target encoding*, so a multi-byte target changes where a value is cut,
and that warning has to count the encoded length.

*** E7 -- UTF-16 GeoPackage input
=sqlite.rs:116= refuses any database whose header text encoding is not 1
(UTF-8). SQLite permits 2 and 3 (UTF-16le/be). With E2's UTF-16 decoder this
is a per-column decode in the record reader rather than a refusal. /Still last
by evidence: no observed producer writes one./ Output stays UTF-8, which the
GeoPackage spec requires.

*** E8 -- zip entry names by their flag
/Added 2026-10-28; § WHAT IS WRONG TODAY item 4./
- *Write, first and alone:* set general-purpose bit 11 in both headers when a
  name is not ASCII. No table needed; it should not wait for E2.
  /Built 2026-10-28./
- *Read:* bit 11 set means UTF-8 (refused if invalid, as now); clear means
  CP437, from E2. Info-ZIP's Unicode Path extra field (=0x7075=), when
  present and its CRC matches the header name, takes precedence -- it is
  how producers that never set bit 11 carry a UTF-8 name.
- A carried entry's name keeps its original bytes and flag, so a =.kmz=
  written back is byte-faithful in its names (=same-format-fidelity.org= M3c).

** WHAT THIS OVERTURNS
- *The old D-E3* ("refuse a multi-byte codepage") and *the old E3* (its
  milestone) -- now decoded. =lossy-conversion-warnings.org= § OPEN
  CANDIDATES and =shapefile.org= § OPEN QUESTIONS cite E3 as a refusal.
- *The old § THE COST BOUNDARY*'s conclusion that multi-byte is where
  "support more encodings stops being free" and the answer is refusal. The
  cost is real and stated in § THE COST; the answer is the tables.
- *The old E6's claim* that KML has no in-band place to declare an output
  encoding. The XML declaration is exactly that.
- *Old open questions 2, 3 and 4* -- answered as D-E10, D-E8 and D-E7.

** OPEN QUESTIONS
1. *Does the table size need a Cargo feature?* /Lean no./ The crate has no
   features, and a dependency-free feature is allowed but would be the first.
   Measure the wasm build's size with E3's tables in it before deciding; ship
   unconditionally unless that number is a problem.
2. *Is a BOM-prefixed CSV biting anyone?* Unverified; E4 fixes it either way,
   and the fixture is cheap.
3. *Does a CSV or WKT source's guessed encoding travel to a same-format
   write?* With no declaration, =--from-encoding cp1252= on =csv -> csv=
   could mean "write it back in CP1252" (D-E7's spirit) or "I fixed the input,
   give me UTF-8" (D-E1's). /Lean: back in CP1252 -- the flag named the
   source's encoding, and D-E7 says a same-format run keeps it./

** TESTING
- ***A committed mapping per table, as an oracle*** (D-E4): the WHATWG
  =index-*.txt= files and Unicode's =VENDORS/MICSFT/PC/*.TXT=. Each generated
  table is asserted against its source entry for entry, both directions where
  WHATWG's encoder uses the whole index.
- ***Round trip, every encoding:*** decode then encode every byte sequence the
  index maps, and require the original bytes back -- except where WHATWG's
  encoder exclusions (D-E5) say otherwise, which are asserted as exclusions.
- *A fixture per encoding family*, through the spoke that can hold it: a
  =.dbf= + =.cpg= pair carrying bytes that distinguish the codepage (the
  =0x80=--=0x9F= range for CP1252 -- **a fixture using only =é= would pass
  under both encodings and prove nothing**), a Shift_JIS and a Big5 KML, an
  ISO-2022-JP KML (the stateful one), a CP437-named =.kmz= entry.
- *GDAL differential*: write a =.dbf= in a codepage, have =ogrinfo= read it,
  and require the text to match what =ogr2ogr= produces for the same input.
  Per § THE ORACLE RULE, evidence about what a consumer accepts, which is the
  right bar for an encoding. =xmllint --encode= is the same check for KML.
- *The refusal cases are tests too*: an encoding outside the set, malformed
  multi-byte input, an unrepresentable character on write. Each asserts the
  error *names the encoding*, and the last names the character.
- *Every new warning needs a mutation check* (D-E9's guess, the U+FFFD case).
  A warning nothing asserts quietly stops firing -- see =handoff.org= on the
  =last_change= sentinel that had no test behind it.
