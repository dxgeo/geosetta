* 3D/4D Geometry — Z (elevation) and M (measure) Ordinates

** GOAL
Let Geosetta carry a Z (elevation) and/or M (linear-referencing measure)
ordinate through the IR and every format spoke, instead of silently dropping
them on read the way three spokes already do today (see BACKGROUND). This is
=arbitrary-geoparquet.org='s milestone 6a, split out into its own plan
because — as that file itself flags — it's a genuine IR-scope decision, not a
decode-path addition: every one of the eight format spokes touches the
=Position= type this plan changes.

** STATUS
*M1 through M5 are DONE (all 2026-08-17).* Written up on request after
[[file:arbitrary-geoparquet.org][arbitrary-geoparquet.org]]'s 6a was

** BACKGROUND

*** Three spokes already receive Z-bearing input and silently discard it
Not hypothetical — found while scoping this plan:
- =src/geojson/mod.rs= (~line 300): the position parser's own doc comment
  says it plainly — *"extra ordinates (z/m) are skipped"*. RFC 7946 natively
  allows a 3-element =[lon, lat, elevation]= position; Geosetta reads it and
  throws the third number away.
- =src/kml/reader.rs=: =<coordinates>lon,lat,alt</coordinates>= is
  real, common KML (every =<Point>= with an altitude, every LIDAR/survey
  export) — =parse_coordinates= parses all three numbers but returns
  =Position= (today a 2-tuple), so altitude never reaches the IR.
- =src/shapefile/geometry.rs= (line 71): =PointZ=/=PolygonZ=/=PolyLineZ=/
  =MultiPointZ= shape types are rejected outright — *"unsupported shape type
  {other} (Z/M/MultiPatch out of scope)"*. A shapefile of building footprints
  or LIDAR-derived points with real elevation data fails to convert at all
  today, not just loses the Z.

*** What's dimension-agnostic already, for free
- *GeoPackage* (=src/geopackage/{reader,writer}.rs=): the writer already
  emits =flags: 0x01= (little-endian header ints, *no* envelope) and wraps
  plain WKB with no 2D-specific logic; the reader's envelope-skip already
  branches generically on =(flags >> 1) & 0x07= for the xy/xyz/xym/xyzm
  envelope byte counts (=reader.rs:202-208=). Once WKB itself carries Z/M,
  GeoPackage inherits it with no format-specific code — the same "no new CRS
  code needed" story Shapefile's =.prj= had for R2 name recovery.
- *CSV (WKT column)* inherits whatever the WKT codec does; no separate work.

** DESIGN

*** The IR change: `Position` becomes a struct, not a wider array
Today (=src/geometry/mod.rs:15=):
#+begin_src rust
pub type Position = [f64; 2];
#+end_src
Proposed:
#+begin_src rust
pub struct Position {
    pub x: f64,
    pub y: f64,
    pub z: Option<f64>,
    pub m: Option<f64>,
}
#+end_src
Every =Geometry= variant's *shape* stays exactly as it is today —
=Point(Position)=, =LineString(Vec<Position>)=,
=Polygon(Vec<Vec<Position>>)=, and so on. Nothing about ring/part/collection
nesting changes; only the leaf type widens. =bbox=/=extend_bbox=,
=for_each_position_mut=, and =for_each_position_run_mut= keep their existing
recursion structure untouched — only the leaf access (=p[0]=/=p[1]= indexing
today) becomes =p.x=/=p.y=/=p.z=/=p.m= field access.

*Alternatives considered and rejected:*
- =[f64; 4]= with a =NaN= sentinel for absent Z/M — rejected: conflates
  "ordinate absent" with a real numeric edge case, and =f64= comparisons/
  =min=/=max= (used throughout =Bbox::add=) handle =NaN= inconsistently. An
  =Option<f64>= makes "this geometry has no Z" a type-level fact instead of a
  magic-value convention every call site has to remember to check.
- A parallel =Geometry3D= enum alongside the existing 2D =Geometry= —
  rejected: doubles every match arm in every writer/reader (the actual bulk
  of this plan's work) instead of widening one leaf type. Every format that
  can express Z (all except CSV's raw columns and the pure-2D formats) would
  need two near-identical code paths instead of one dimension-aware one.
- Keeping =Position= 2D and adding a *separate* per-point Z/M side-channel
  (e.g. =Vec<Option<f64>>= parallel to each coordinate =Vec=) — rejected:
  every ring/part-splitting helper (=split_rings=, =flatten_rings=, KML's
  ring parsing, Shapefile's part arrays) would need to thread a second
  parallel structure through the exact same recursion =Position=-as-struct
  gets for free by keeping z/m *on* the position.

*** Z and M share the IR change; format-level *support* for each is scoped separately
Folding both =z= and =m= into =Position= now (rather than doing a Z-only
migration and a second M-shaped migration later) avoids paying the
mechanical "touch every =p[0]=/=p[1]= call site" cost twice. But real-world
prevalence differs sharply — Z (elevation) is common (LIDAR, survey,
building-footprint data); M (linear-referencing measure, e.g. highway
mile-markers) is comparatively rare and Geosetta has no evidence of a real
consumer today. So the milestones below build Z per format as the primary
target; M-specific format work (Shapefile's M-only shape types 21/23/25/28,
WKT's =M= keyword, FlatGeobuf's =m= vector) is flagged *stretch, not
required* per milestone rather than assumed — see OPEN QUESTIONS.

*** A source-breaking, but purely mechanical, call-site change
=for_each_position_mut=/=for_each_position_run_mut=
([[file:reproject-composability.org][reproject-composability.org]]'s public
seam for an external reprojection library) hands callers =&mut Position=/
=&mut [Position]=. Changing =Position= from =[f64; 2]= to a struct is
source-breaking for any caller indexing it positionally (=p[0]=/=p[1]=)
instead of by field. Checked directly against the one real external
consumer in this repo, =tests/reproject_pipe.rs='s
=composes_with_wbprojection_library= test: wbprojection's own API
(=Crs::transform_to(x: f64, y: f64, …) -> (f64, f64)=) takes and returns
plain =f64=s — it has *no* knowledge of =Position='s shape at all. The only
code that touches =Position= positionally is Geosetta's own four-line glue
closure (=p[0]=/=p[1]= read and write, lines 272-274/287/294) — a two-line
mechanical fix (=p.x=/=p.y=), not a capability loss. wbprojection keeps
reprojecting mid-flight identically once that's fixed; nothing about *its*
ability to compose through the seam changes. The real, narrower consequence:
wbprojection's =transform_to= is 2D-only (no Z in, no Z out), so a Z-bearing
point piped through it today would have Z pass through *untouched* by
default — correct per Geosetta's own "label, never reproject" posture, but
worth being explicit that wbprojection specifically has no way to apply a
vertical-datum shift even if a future version wanted to. Since =geosetta= is
published to crates.io, any external crate consuming this API the same
positional way as the old test code would need the same trivial fix — worth
a release-note mention, but not a functional regression for anyone.

*** M2 — WKB Z/M codec (`src/geometry/wkb.rs`) — *DONE (2026-08-17)*
The type-code convention was *confirmed against real fixtures before
committing*, not assumed — matching this project's established discipline
(see =geoscribe/handoff.org='s =usages=-stripping and embedded-newline
generator bugs, both found only once a real bulk oracle ran). Two live
conventions existed as candidates:
- *ISO SFA* (what GeoParquet's spec calls for): base type code +1000 for Z,
  +2000 for M, +3000 for ZM (e.g. =PointZ= = 1001).
- *EWKB* (PostGIS-native, not GeoParquet's): high bit flags
  (=0x80000000= Z, =0x40000000= M) plus an optional SRID.

*Confirmed via two independent real tools*, not just one:
=duckdb -c "LOAD spatial; SELECT hex(ST_AsWKB(ST_GeomFromText('POINT Z (1 2 3)')))"=
and Python/GDAL's =ogr.CreateGeometryFromWkt('POINT Z (1 2 3)').ExportToIsoWkb()=
both emit type code =1001= (=0xE9030000= little-endian) — *ISO SFA*, not
EWKB. (GDAL's *non*-ISO =ExportToWkb()= does emit the EWKB flag form
=0x80000001=, confirming that path exists but isn't what GeoParquet
producers use — worth knowing so a future session doesn't get the two GDAL
export methods confused.) Also verified the *nesting* convention:
=MULTIPOINT Z (0 0 0, 1 1 1)='s outer wrapper type code (1004) and each
embedded sub-point's own type code (1001) are *both* independently
Z-suffixed, and =GEOMETRYCOLLECTION Z (...)= behaves the same way — this
directly shaped the encoder's per-part dimension derivation (see below).

*Implementation*: =Position='s own =z=/=m= fields already carry
dimensionality per position (from M1), so the codec derives a geometry's
declared WKB dimensionality from its *first* position (=dim_of_first=/
=dim_of_rings=/=dim_of_geometry= — a =LineString=/=Polygon= gets one
dimension-suffixed header for the whole geometry, exactly matching how WKB
itself declares dimensionality once per geometry, not per point) rather
than threading it in from outside. =header=/=wkb_size=/=point=/=read_point=
(and every variant's encode/decode arm) became dimension-aware; each
=MultiPoint=/=MultiLineString=/=MultiPolygon= part gets its *own*
independently-derived dimension-suffixed header, matching the verified
nesting convention above. A position whose =z=/=m= the geometry's declared
dimensionality expects but which itself lacks (not a real case today — no
reader populates Z yet) falls back to =0.0= on encode rather than panicking,
since WKB has no per-point "no data" marker the way Shapefile's M does.

*Testing*: 16 new unit tests in =wkb.rs=, including — per this project's own
bar of not trusting a round-trip against *only* our own encoder — a test
that decodes *raw hex bytes captured directly from DuckDB and GDAL* (not
just re-encoded output) for =POINT Z=, =POINT M=, =POINT ZM=,
=LINESTRING Z=, and =MULTIPOINT Z=, plus round-trip coverage across every
=Geometry= variant at Z/M/ZM, the outer/inner nesting check, the
mixed-dimensionality fallback, and an EWKB-style-code rejection test. All
2D-only existing tests pass byte-identical (Dim::XY's offset is 0, so no
behavior change for any input without Z/M — matching M1's degraded-mode
bar). Full suite verified: =cargo test= 308 passed (299 baseline + 9 new)/4
ignored; =cargo test --features crs-registry= 322 passed (313 baseline + 9
new)/6 ignored; =cargo clippy --all-targets= clean both configs;
=tests/reproject_pipe.rs= (incl. =composes_with_wbprojection_library=)
unaffected.

*** M3 — GeoJSON (`src/geojson/mod.rs`) — *DONE (2026-08-17)*
Smallest change of any spoke, as predicted: RFC 7946 already allows a
3-element position natively. Both position parsers — the streaming reader's
=stream_position= *and* the tree reader's =position= (two independent code
paths that must agree, per =streaming_reader_matches_tree_reader=) — now
read a present third array element as Z instead of skipping it; a fourth+
element (M — RFC 7946 gives it no defined meaning in bare GeoJSON
coordinates, out of scope by spec, not by choice, as predicted) is still
parsed past but discarded. Both writers — the streaming =write_position=
and the =#[cfg(test)]=-only tree-model =position_to_json= (used to build
the reference =JsonValue= the byte-for-byte writer-equivalence test checks
against) — emit a third element when =z= is =Some=, omitted entirely
otherwise (so 2D output is unchanged, matching the degraded-mode bar). A
non-numeric third element now errors clearly on both paths (tightened from
the old behavior, which tolerated *any* JSON value there since it was
unconditionally skipped — not a real behavior loss since RFC 7946 requires
coordinates to be numbers).

*This is the milestone that makes M2's WKB codec capability actually
reachable end-to-end*, not just exercised by =wkb.rs='s own unit tests: a
real GeoJSON→GeoParquet→GeoJSON conversion through the actual CLI now
carries Z all the way through. Verified two ways:
- In-process: =z_bearing_geojson_round_trips_through_geoparquet= encodes a
  parsed Z position to WKB and decodes it back.
- *End-to-end through the real binary*, checked against two independent
  external tools: =cargo run -- z_in.geojson z_mid.parquet= then
  =cargo run -- z_mid.parquet z_out.geojson= round-trips
  =[-73.9857,40.7484,381]= byte-identical in the final GeoJSON, and the
  intermediate =.parquet= is independently confirmed as real 3D geometry by
  both =ogrinfo -al= (=POINT Z (-73.9857 40.7484 381)=) and DuckDB
  (=SELECT ST_AsText(geometry) FROM read_parquet(...)= → the same =POINT
  Z=) — not just Geosetta agreeing with itself.

*Known, expected gap (not M3's job, still open — see M8)*: the written
GeoParquet's own =geo= metadata still declares ="geometry_types":["Point"]=,
not the spec's =["Point Z"]= — confirmed via
=duckdb parquet_kv_metadata()=. GDAL/DuckDB both still correctly identify
the geometry as 3D by inspecting the WKB's own type code directly (which is
why the external-tool checks above passed despite this), so this isn't an
interop break today, just non-compliant metadata — M8's scope, unchanged by
M3.

5 new tests (Z round-trip through both readers, a 2D point still writes
with no third element, a 4th ordinate is tolerated-but-dropped, a
non-numeric Z errors, and the WKB round-trip above). Full suite: =cargo
test= 313 passed (308 baseline + 5)/4 ignored; =--features crs-registry= 327
passed (322 baseline + 5)/6 ignored; clippy clean both configs; doctests and
=reproject_pipe.rs= unaffected.

*** M4 — WKT text (`src/geometry/wkt.rs`) — *DONE (2026-08-17)*
The flagged ambiguity was real, confirmed empirically rather than guessed:
- DuckDB (=ST_AsText=) and GDAL's *ISO* export (=ExportToIsoWkt()=) both
  always emit an explicit =Z=/=M=/=ZM= keyword — =POINT Z (1 2 3)=,
  =POINT M (1 2 4)=, =POINT ZM (1 2 3 4)=, no ambiguity.
- GDAL's *plain, non-ISO* =ExportToWkt()= genuinely emits a bare
  =POINT (1 2 3)= — no keyword at all — for a 3D point (and silently
  *drops* M entirely rather than ever writing an unlabeled M-bearing
  tuple). This is the exact real-world ambiguity source the milestone
  flagged, and it settles the fallback unambiguously: an unlabeled extra
  ordinate is *always* Z in practice (never M), matching this crate's own
  WKB codec and GeoJSON reader conventions already, so no new inconsistency
  was introduced.
- Nesting convention also confirmed and implemented accordingly: a
  =MULTIPOINT Z=/=POLYGON Z='s members are bare tuples sharing the *outer*
  keyword (=MULTIPOINT Z (0 0 0, 1 1 1)=, no per-member repeat), but a
  =GEOMETRYCOLLECTION=='s members are complete, independent WKT geometries
  that each carry their *own* keyword (=GEOMETRYCOLLECTION Z (POINT Z (1 2
  3))=) — the parser threads a =dim= parameter down through
  =coord=/=coord_list=/=ring_list=/=multipoint=/=polygon_list= for the
  former, but =geometry_list= (GeometryCollection's member list) calls
  =self.geometry()= fresh per member with no outer =dim= passed in, since
  each member re-derives its own.

*Also implemented (not previously scoped in detail): the write side.* The
old encoder never looked at =Position::z=/=m= at all — =write_coord= only
ever wrote =x y=. =write_header= now emits the =Z=/=M=/=ZM= keyword (derived
from the geometry's first position, mirroring =wkb.rs='s =dim_of_first=/
=dim_of_rings=/=dim_of_geometry= helpers — kept as an independent copy in
this module rather than shared, matching every other format spoke's
self-contained style) before the coordinate list; =write_coord= appends =z=
then =m= when present. 2D output is byte-identical to before (=Dim::XY=
adds no keyword and no extra ordinates).

*Verified against real external tools, not just self-consistency*: beyond
matching DuckDB/GDAL's captured text byte-for-byte in unit tests (11 new
tests total), routed a real =POINT Z (-73.9857 40.7484 381)= through the
actual CLI — =geosetta z.csv z.geojson= then =geosetta z.geojson
z_back.csv= — confirming =381= survives the full CSV→GeoJSON→CSV round
trip (CSV is WKT's real consumer in this crate, per =csv.rs=), and
=ogrinfo -al= independently parses the written CSV's =WKT= column as real
=POINT Z= geometry, not just a string. Full suite: =cargo test= 321 passed
(313 baseline + 8)/4 ignored; =--features crs-registry= 335 passed (327
baseline + 8)/6 ignored; clippy clean both configs; doctests and
=reproject_pipe.rs= unaffected.

*** M5 — GeoPackage — mostly free — *DONE (2026-08-17), zero production code changed*
Confirmed, not just assumed: =gpkg_geometry= (=writer.rs=) really does just
call =to_wkb(g)= and wrap it in the 8-byte header with no dimension-specific
logic at all, and =strip_gpkg_header= (=reader.rs=) really does already
branch generically on the flags byte's envelope-size indicator (0/32/48/48/
64 bytes for none/XY/XYZ/XYM/XYZM, GeoPackage §2.1.3) before handing the
rest to =from_wkb=. So M2's WKB codec alone was enough — this milestone was
verification-only, no source change beyond two new tests.

*Verified end-to-end through the real CLI, cross-checked against two
independent tools*: =geosetta z_in.geojson z.gpkg= then =geosetta z.gpkg
z_out.geojson= round-trips =381= (elevation) intact; both =ogrinfo -al= and
DuckDB's =ST_AsText(ST_Read(...))= independently confirm the written
=.gpkg= holds real =POINT Z (-73.9857 40.7484 381)= geometry, not just
Geosetta agreeing with itself.

*A real, if narrow, pre-existing gap found while verifying this, not
introduced by M5*: =strip_gpkg_header='s envelope-size branch had *no* test
coverage at all before this milestone — this crate's own writer always
chooses "no envelope" (=flags = 0x01=), so the branch was reachable only
from external input. First attempt to source a real fixture — DuckDB
(=COPY ... TO 'x.gpkg' (FORMAT GDAL, DRIVER 'GPKG')=) and =ogr2ogr -f GPKG=
on a single =POINT Z= feature — found neither tool populated an envelope
(both chose =flags=0x01=, matching this crate's own default), so a
synthetic, spec-table-grounded test
(=strip_gpkg_header_skips_every_envelope_size_per_the_spec_table=, all five
indicator codes) was added as a stand-in. *Root cause turned out to be the
geometry, not the tool*: a =Point='s bbox is a single, degenerate
coordinate (no filtering benefit), so GDAL skips the envelope for it —
=ogr2ogr -f GPKG= on a real =LINESTRING Z (0 0 0, 10 10 10, 20 5 3)= (a
non-degenerate bbox) *does* populate one — =flags=0x05=, indicator 2 (XYZ,
48 bytes), envelope values =(0,20,0,10,0,10)= confirmed by hand-decoding
the raw file to match the geometry's true bounds exactly before trusting
it. (One red herring on the way there: a naive byte-search for the =b"GP"=
magic matched *first* inside SQLite's own 100-byte file header at a
coincidental offset, not the real GPB blob — resolved by searching past
byte 100 and cross-checking the recovered WKB's own bytes decode to the
expected coordinates.) Committed as
=tests/fixtures/gdal_linestring_z.gpkg= (106 KB, in line with the existing
=points.gpkg= fixture's 98 KB) with a dedicated test,
=reads_a_real_envelope_bearing_z_fixture=, reading it through the real
=read_layers= entry point (not just =strip_gpkg_header= in isolation) and
confirming the exact =LineString Z= geometry recovered. The synthetic
spec-table test stays too — it still covers XYM/XYZM, which no tool tried
here happened to produce — but indicator 2 (XYZ) is now real-fixture-backed
rather than spec-only.

Optionally *emitting* a Z-range envelope (the spec allows it; the writer
always chooses "no envelope") remains a non-goal *for this milestone*, but
is no longer a closed question: per a 2026-08-17 user decision, envelope
computation is scoped as its own plan in the =geoscribe= sibling crate —
=geoscribe/plans/envelope-computation.org= — under a broader charter that
=geoscribe= owns any metadata =geosetta= must *compute* rather than simply
carry through from a source (the same shape CRS resolution already has).
See that plan for the design and open questions (feature-flag naming,
default-on vs. opt-in, and the charter/identity implications of broadening
=geoscribe= past "CRS registry").

Full suite: =cargo test= 324 passed (321 baseline + 3)/4 ignored;
=--features crs-registry= 338 passed (335 baseline + 3)/6 ignored; clippy
clean both configs; doctests and =reproject_pipe.rs= unaffected.

**** M follow-up: closed a real test-coverage gap for M — *DONE (2026-08-17)*

Real new work, as scoped: unlike WKB's per-point interleaving, =.shp='s Z
variants (=PointZ=(11), =PolyLineZ=(13), =PolygonZ=(15), =MultiPointZ=(18))
store Z as a *separate trailing section* per record — =Zmin=, =Zmax=, then
one Z value per point in the same order as the existing X/Y array — a
genuinely separate codec path from M2's WKB work, not a reuse of it.

Shapefile"= output before implementing*, hand-decoded field-by-field with a
throwaway Python script rather than trusting the whitepaper alone: =PointZ=

fields per the spec); =PolyLineZ=/=PolygonZ=/=MultiPointZ= all share the

fixture GDAL wrote, the trailing M section was completely absent* (content
length matched the Z-only layout exactly, not the whitepaper's fixed
=PointZ={X,Y,Z,M}= description) — this settles M's optionality empirically
rather than by spec-reading alone.

*Scope cut, matching DESIGN's Z-primary lean*: M support (both the M-only
shape types 21/23/25/28 *and* the optional M section within a Z-shape) is
*not implemented this pass* — no real M-bearing fixture was available to
verify against (GeoJSON, this project's easiest source format, has no M
concept at all), and unlike M6's FlatGeobuf M (which was a free extra
vector once Z's mechanism existed), Shapefile's M needs its own no-data-
sentinel logic that would ship unverified against real bytes, breaking this
project's own verification bar. =read_parts='s trailing M bytes (when a
real file does carry them) are simply never touched — record boundaries
still come from the record header's own content-length prefix, so this is
safe, not a truncation bug. =MultiPatch=(31) stays explicitly out of scope,
unchanged (=geometry.rs='s existing comment already excluded it, and it's a
fundamentally different multi-surface shape with no =Geometry= variant to
decode into at all).

*Design: file-wide Z promotion, not per-geometry*. A =.shp= declares exactly
one shape type for the whole file — unlike FlatGeobuf's per-Geometry-table
independent =z= vector (M6), Shapefile has no per-record way to say "this
one lacks Z." So =write()= computes =has_z= once, file-wide (=geometry_has_z=,
=true= if *any* geometry carries Z), and promotes the *entire* file to the
Z-variant shape type when so — a mixed 2D/3D source (e.g. one GeoJSON
feature missing its third ordinate) still produces one valid, uniformly-
Z-shaped file, with the 2D feature's Z falling back to =0.0= per point
(=write_z_section=), the same convention =wkb.rs=/=flatgeobuf/writer.rs= use
for the same reason (no per-point "no data" marker for Z, unlike M's
sentinel). The file header's own Zmin/Zmax (bytes 68–83, previously always
=0.0=/=0.0=) now reflect the real range when =has_z= (=fold_z=, a small
independent traversal kept separate from the shared 2D-only =Bbox= type
rather than widening it — see OPEN QUESTIONS on why =Bbox= stays 2D-only).
=read_parts= gained a =has_z: bool= parameter shared between the 2D and Z
paths (=PolyLine=/=PolyLineZ=, =Polygon=/=PolygonZ=) rather than duplicating
the whole function, mirroring how =wkb.rs='s dimension-aware helpers avoid
duplicating per-variant encode/decode logic.

**** M follow-up: full M support, both within Z-shapes and the M-only shape types
Requested immediately after the Z-only landing above, once real M-bearing
fixtures turned out to be obtainable after all (see BACKGROUND below) —
removing the original reason M had been scoped out. Covers *both* halves
DESIGN's OPEN QUESTIONS had separately flagged: M riding alongside Z within
=PointZ=/=PolyLineZ=/=PolygonZ=/=MultiPointZ=, *and* the pure M-only shape
types =PointM=(21)/=PolyLineM=(23)/=PolygonM=(25)/=MultiPointM=(28) that the
original M7 landing deferred as "stretch, no fixture."

*BACKGROUND: how the fixture blocker actually got resolved.* GeoJSON (the
easiest source format used throughout this plan) has no M concept at all,
which is what made M feel unreachable during the Z-only landing. The fix:
GDAL's =ESRI Shapefile= driver can source geometry from a WKT column via
CSV + =-oo GEOM_POSSIBLE_NAMES=wkt=, and WKT natively supports =POINT M=/
=POINT ZM= etc. — so =ogr2ogr -f "ESRI Shapefile" out.shp in.csv -oo
GEOM_POSSIBLE_NAMES=wkt= produces real, oracle-quality M-bearing =.shp=
bytes on demand. This unblocks M fixture-sourcing for *any* future Shapefile
work, not just this one — worth remembering the next time a GeoJSON-only
sourcing habit makes a format feature look unreachable.

*Every byte layout confirmed against real =ogr2ogr=-written bytes before
implementing*, hand-decoded with Python, mirroring the Z landing's own
discipline:
- =POINT ZM (-73.9857 40.7484 381 12.5)= → shape type *11* (=PointZ=, not a
  separate "ZM" code — there isn't one), content 36 bytes = type+X+Y+Z+M.
  Confirms M rides on the *same* type code as Z-only, distinguished purely
  by content length, exactly like M7's original Z/no-Z finding.
- =POINT M (1 2 5)= (no Z at all) → shape type *21* (=PointM=), content 28
  bytes = type+X+Y+M — genuinely different from a Z-only =PointZ= (also 28
  bytes, but type+X+Y+*Z*): same byte count, different field, only the
  shape-type code disambiguates them.
- =LINESTRING ZM=/=POLYGON ZM=/=MULTIPOINT ZM= sources all wrote a full
  =Mmin=,=Mmax=,M-array trailing section — *confirmed via two independent
  tools*, not just =ogrinfo=: DuckDB's =ST_AsText(ST_Read(...))= read the
  same real =.shp= back as the identical =LINESTRING ZM (0 0 1 10,1 1 2
  20,2 0 3 30)=.

*Design*: =geometry_has_m= mirrors =geometry_has_z= exactly (file-wide OR
across every position); the file's final shape type is =z_variant(base)=
whenever =has_z= (M rides along regardless of =has_m=, matching the real
=POINT ZM= finding above), else =m_variant(base)= whenever =has_m= alone,
else =base= — extracted into one shared =dim_shape_type= helper used by
=encode_point=/=encode_multipoint=/=encode_parts= instead of three separate
inline conditionals. =write_m_section= mirrors =write_z_section='s shape
(Mmin, Mmax, then one =f64= per point) but differs in two ways matching
ESRI's own stated M semantics, neither guessed: a position missing M writes
the "no data" sentinel (=NO_DATA_M = -1e38=, per the ESRI Shapefile
Technical Description) rather than a =0.0= fallback, since M (unlike Z) has
an established no-data convention; and the header's own Mmin/Mmax
(=fold_m=) *skip* unmeasured points entirely rather than folding in the
sentinel, so one unmeasured point can't blow out the file's declared M
range — verified by =header_m_range_ignores_unmeasured_points=. On read,
=apply_m_if_present= detects the M section (for *any* shape family, Z or
not) purely from remaining content length, exactly mirroring how the Z-only
landing already disambiguated "M section present" — no shape-type-specific
special-casing needed. A nice consequence of that content-length-driven
design: =POINT=/=POINT_M= share one decode arm (M offset 20 only ever has
real bytes behind it for a genuine =PointM= record) and
=POLYLINE=/=POLYLINE_M= and =POLYGON=/=POLYGON_M= share =read_parts(...,
false)= outright — M's optionality was already the load-bearing mechanism,
so the M-only types needed no new parsing path, only new *type codes* that
route into the existing one.

*The one thing no external tool could exercise*: the per-point "no data"
sentinel firing *within* an otherwise M-bearing shape (one point measured,
another not, in the same geometry) — WKT has no syntax to express a
partially-measured geometry, so this is verified only by this crate's own
encoder/decoder agreeing with each other
(=a_point_with_no_m_within_an_m_bearing_file_round_trips_as_none_not_the_sentinel=),
the same bar the original M7 Z =0.0= fallback used for the same reason.

*Verified end-to-end through the real CLI*, via the CSV/WKT path since
GeoJSON can't carry M: a real =gdal_point_zm.shp= fixture through =geosetta

  Geosetta's own posture is "label, never reproject" (=crs.org=), consistent
  with passing Z through unexamined — the question was whether the
  =for_each_position_mut=/=for_each_position_run_mut= seam's contract should
  say so explicitly, rather than leaving it to be discovered by a future
  caller. Now documented directly on both methods (=geometry/mod.rs=,
  mirrored in =feature.rs='s =FeatureCollection= wrappers): =z=/=m= are
  handed to the callback exactly like =x=/=y=, unexamined; a purely
  horizontal backend (=wbprojection=, the one real integration this seam has
  today) is free to leave =z= untouched, matching Geosetta's own posture, and
  a caller wanting a full 3D transform (e.g. a vertical-datum shift) can
  read/rewrite =p.z= itself inside the closure — nothing in the seam
  prevents it. =m= is never a reprojection concern at all (a
  linear-referencing measure, not a spatial coordinate), stated so a future
  backend author doesn't wonder whether it needs one.
- *Breaking-change handling — resolved (2026-08-17): don't care, not yet
  stable.* =Position= changing from =[f64; 2]= to a struct is source-breaking
  for any external code indexing it positionally (confirmed harmless in
  practice for =wbprojection= itself — see DESIGN). Per a direct user
  decision, no compatibility shim (=Index<usize>=/=From<[f64;2]>=) is being
  added, and no semver-major-bump ceremony is needed either — =geosetta=
  hasn't reached a stable (1.0) release yet, so breaking changes to its
  public API are an accepted, unremarkable part of pre-1.0 development, not
  something requiring the mitigation this entry originally flagged. Revisit
  this stance if/when the crate approaches a 1.0 release.
- *3D bbox / GeoParquet covering-bbox column* — out of scope for the first
  landing (see M8); revisit once basic Z round-tripping is verified.
- *Spatial index stays 2D — explicit non-goal, not a gap.* The Hilbert
  curve/packed-R-tree primitives in =spatial.rs= (feeding FlatGeobuf's
  packed R-tree, =--sort-hilbert=, and GeoPackage's =--rtree=) operate on
  2D bbox pruning; nothing about Z changes their correctness or requires
  them to become Z-aware. Stated here so a future reader doesn't mistake
  this for an overlooked gap.
- *KML's =<altitudeMode>=, resolved by M9* — real =ogr2ogr -f KML=/=-f
  LIBKML= output for a 3D point carries no =<altitudeMode>= element at all,
  so M9 shipped Z-without-altitudeMode as its final answer, not a
  placeholder; =<altitudeMode>= itself stays unmodeled/dropped-on-read, same
  as KML's other presentation-layer elements.
