#+TITLE: Plan: Performance (read/write throughput)
#+AUTHOR: Daniel Okuniewicz Jr.

* Performance

** BENCHMARKS
=tests/perf.rs= drives the real =geosetta= binary end-to-end (whole-pipeline
timing, including process startup and file I/O). It generates a synthetic GeoJSON
FeatureCollection (mixed point/line/polygon, typed properties, fractional
coordinates), derives the binary inputs from it, and times each conversion
best-of-3, printing MB/s and features/s. Marked =#[ignore]= so a normal test run
stays fast:
#+begin_src sh
cargo test --release --test perf -- --ignored --nocapture
# GEOSETTA_BENCH_N sets the feature count (default 200_000).
#+end_src
End-to-end timing includes process start + file IO, so it is noisy for small
deltas; use a large =N= (≥400k) and read relative changes, not absolutes.

There are two =#[ignore]= benchmarks:
- =throughput= — the original mix (point/line/polygon, four typed properties),
  one conversion per read/write path. Good for geometry- and IO-bound changes.
- =wide_table= — =n= trivial points, each with =GEOSETTA_BENCH_COLS= (default 30)
  typed property columns. Geometry is negligible, so *property handling
  dominates*: it isolates the schema/columnar cost on write and the per-row
  property rebuild on read, which the four-property =throughput= mix hides.
#+begin_src sh
cargo test --release --test perf wide_table -- --ignored --nocapture
# GEOSETTA_BENCH_COLS sets the column count; double it to expose super-linear
# scaling in the column dimension.
#+end_src

** DONE — GeoJSON writer bypasses the JsonValue tree
The writer used to build a whole =JsonValue= tree (=geojson::to_json=) and then
serialize it — an =Array=/=Object= heap allocation per coordinate, ring, and
feature, plus a temporary =String= per number. Replaced with
=geojson::to_geojson_string=, which writes GeoJSON straight into the output
buffer (numbers formatted in place via =fmt::Write=), reusing the existing value
serializer only for property values. The old tree builder is kept =#[cfg(test)]=
as the reference the direct writer is asserted byte-for-byte against.

Result (N=400k, best-of-3): every =* → geojson= path roughly *2× faster*.
| conversion       | before      | after       |
|------------------+-------------+-------------|
| parquet→geojson  | ~0.82M ft/s | ~1.63M ft/s |
| fgb→geojson      | ~0.86M ft/s | ~1.83M ft/s |
| csv→geojson      | ~0.66M ft/s | ~1.09M ft/s |
| gpkg→geojson     | ~0.75M ft/s | ~1.39M ft/s |

Also: =JsonValue= number serialization now formats into the buffer instead of
allocating a temporary =String= per number (helps every JSON/GeoParquet-string
path), and the JSON string parser bulk-copies runs of ordinary bytes with one
=push_str= instead of a =char= at a time (helps string-heavy input).

** DONE — GeoJSON reader bypasses the JsonValue tree
=geojson::from_geojson_str= streams a FeatureCollection's =features= array
straight into the =Feature= IR: coordinates parse directly into =Vec<Position>=
(no 2-element =Vec<JsonValue>= per coordinate), driving the JSON =Parser=
primitives (now =pub(crate)=) by hand and dipping into =parse_value= only for
=properties= (arbitrary JSON). Member order is handled by dispatching on key,
with a =JsonValue= fallback if =coordinates= precede =type=. The rare, tiny
single-=Feature= / bare-geometry documents fall back to the tree reader. A test
asserts it agrees with =from_json(parse(..))= across geometry types, null
geometry, out-of-order members, z-ordinates, GeometryCollection, and
pretty-printed whitespace.

Result (N=400k): GeoJSON read ~*1.35× faster* (820k → 1.11M ft/s;
=geojson→wkt= 488→361 ms, =geojson→parquet= 520→374 ms, =geojson→fgb=
654→481 ms). Short of a full 2× because *properties still go through
=JsonValue=* — legitimate, since property values are arbitrary JSON — and the
benchmark features carry four properties each. Streaming simple scalar
properties directly is a possible further micro-opt, with diminishing returns.

** GOAL — ≥2× across the board (read + write)
The two GeoJSON-tree bypasses above already bought ~2× on =* → geojson= and
~1.35× on GeoJSON read. The remaining ceiling is on the *binary* paths
(GeoParquet / FlatGeobuf / GeoPackage) and, above all, on *wide tables*, where a
quadratic schema pass and pervasive per-row/per-cell allocation dominate. The
items below are ordered by expected payoff ÷ effort; 1–4 are contained and
low-risk, 5–6 are invasive. Each should be landed behind a =wide_table= /
=throughput= measurement, not assumed.

*** Measured baseline (the case for this work)
=wide_table=, N=40k, best-of-3, release, this machine — doubling the column
count isolates per-column scaling:
| conversion             | 30 cols     | 60 cols     | ratio | shape        |
|------------------------+-------------+-------------+-------+--------------|
| geojson→parquet (wide) | 169.7k ft/s | 55.0k ft/s  | 3.1×  | *quadratic*  |
| geojson→fgb (wide)     | 161.9k ft/s | 54.2k ft/s  | 3.0×  | *quadratic*  |
| parquet→geojson (wide) | 400.6k ft/s | 200.6k ft/s | 2.0×  | linear/heavy |
Doubling columns should ~halve per-feature throughput (2×) if the work is linear
per cell. The write paths degrade *3×*, i.e. super-linearly — the schema pass is
O(cols²). The read path degrades exactly 2× (linear) but is already heavy from
per-cell cloning. Both are addressed below.

*** DONE 1. =schema::infer_columns= was O(rows × cols²)  [write path]
=src/schema.rs=. Ran on *every* Parquet/FlatGeobuf write (both share the schema
pass). Had two quadratic-in-=cols= scans:
- key collection: =order.iter().position(|k| k == key)= — a linear scan over all
  known columns, per property, per feature.
- materialization: for each column it re-walked *all* features, and per feature
  did =.find(|(k,_)| *k == name)= — another linear scan over that row's
  properties, once per column.
Replaced with a single =O(rows × cols)= pass keyed by =HashMap<&str, usize>=
(first-seen order preserved via a parallel =Vec=), recording each row's value per
column (=Option<&JsonValue>=, borrowed from the features) and back-filling =None=
for columns a row omits; a second pass resolves each column type and
materializes. Duplicate keys within a row keep the first occurrence, matching the
old =find=-based lookup. All 107 tests pass.

(Superseded by item 7 below — that back-filling-every-row design was still
paying a real per-row constant factor even though the asymptotics were fixed.)

Result (=wide_table=, N=40k, best-of-3, release, with item 2 below):
| conversion             | 30 cols (before→after) | 60 cols (before→after) | col-doubling |
|------------------------+------------------------+------------------------+--------------|
| geojson→parquet (wide) | 170.9k → 310.0k ft/s   | 56.9k → 161.3k ft/s    | 3.0× → 1.9×  |
| geojson→fgb (wide)     | 166.6k → 291.0k ft/s   | 55.5k → 153.5k ft/s    | 3.0× → 1.9×  |
The quadratic is gone: write paths now scale ~linearly (1.9×) instead of 3.0× on
column-doubling, and absolute throughput at 60 cols is ~2.8× higher. The
=parquet→geojson= read path is unchanged (it doesn't call =infer_columns=) — see
items 3/5.

*** DONE 2. Release profile  [free, whole-project]
Added =[profile.release]= with =lto = true= and =codegen-units = 1= to
=Cargo.toml=. (=panic = "abort"= left off — the CLI reports errors via =Result=/
=eprintln!=, not panics, and abort would only affect genuine bugs.) Folded into
the item-1 measurement above; also lifts the 30-col write numbers and every
non-wide path a few percent, for a one-time compile-time cost.

*** DONE 3. Parquet read: stop copying every value twice  [read path]
=parquet_to_features= (=src/convert.rs=) used to rebuild row-oriented properties
with =col.values[row].clone()= — a second full copy of every value (strings
included) on top of what the reader already materialized. Now it seeds one
feature per row, then transposes by *consuming* =parsed.properties= and
*draining* each column's =Vec<JsonValue>= into the rows (=zip= + =push=), so
values move instead of being cloned; combined with the shared =Rc= key from item
5 below, the per-cell allocation on read is gone.

Result (=throughput=, N=400k, best-of-3; jointly with item 5):
| conversion      | before      | after       |
|-----------------+-------------+-------------|
| parquet→geojson | ~1.63M ft/s | 1.99M ft/s  |
| fgb→geojson     | ~1.83M ft/s | 2.29M ft/s  |
| csv→geojson     | ~1.09M ft/s | 1.27M ft/s  |
| gpkg→geojson    | ~1.39M ft/s | 1.73M ft/s  |
And =wide_table= =parquet→geojson=: 30 cols 434k→550k, 60 cols 214k→279k (~1.3×).

Reader-internal fusion (also done): the reader used to build =Vec<Option<T>>=
per column via =align()= and then re-walk it in =column_to_json=. Replaced the
=ColumnData= (typed =Vec<Option<T>>=) accumulator with a =ColumnSink= that, for
property columns, decodes *straight* into =Vec<JsonValue>= against the
present-mask (=push_json= / =push_json_strings= / =emit_ints=) — one pass, no
=Option<T>= intermediate. The geometry column keeps a raw-WKB (=Wkb=) sink via
the unchanged =align=. =column_to_json= and =empty_column= are gone.

Measured (=wide_table= =parquet→geojson=, 60 cols, N=40k, interleaved A/B to
cancel thermal drift): ~263k → ~274k ft/s, a consistent ~4%. Modest because the
cross-module double-copy removed above was the bigger cost; this also drops one
allocation + one pass per column, so the win grows with column count and lowers
peak memory.

*** DONE 4. =write_json_string= decoded char-by-char  [string-heavy writes]
=src/json/value.rs= iterated =s.chars()= — decoding UTF-8 to =char= and
re-pushing one at a time for every string written (every property key on GeoJSON
write, plus string values, CSV, WKT-in-CSV), and =format!='d a fresh =String= per
control char. Now it bulk-scans runs of "clean" bytes and =push_str='s the slice,
stopping only on a byte that must be escaped (=\"=, =\\=, or =< 0x20=) — the
mirror of the parser on read (=json/parser.rs=). Escape bytes are all ASCII, so
run boundaries fall on char boundaries; the =\u00XX= path writes hex digits
directly instead of allocating. A unit test locks the exact output (specials,
control chars, multi-byte UTF-8 passed through verbatim).

Result (=throughput= =fgb→geojson=, N=400k, four interleaved A/B pairs to cancel
thermal drift): consistently faster by ~5–6% (~2.07M → ~2.25M ft/s). =fgb→geojson=
is write-dominated (FGB read is the fastest reader), so this isolates the GeoJSON
writer; the gain scales with string length and how few bytes need escaping. Less
dramatic than the projected ~2× because the benchmark's keys/values are short —
long, clean text fields benefit most.

*** DONE 5. Share property keys instead of re-allocating per row  [systemic]
The IR stored properties as =Vec<(String, JsonValue)>= per =Feature=, so the
*same* column name was heap-allocated once per row. Keys are now =Rc<str>=
(=src/feature.rs=), shared across rows:
- *Columnar readers* (Parquet, CSV, FlatGeobuf, GeoPackage) intern each column's
  key *once* and clone the =Rc= (a refcount bump) per row instead of a fresh
  =String=.
- *GeoJSON reader* — keys are parsed per feature, so a small =KeyInterner=
  (=HashSet<Rc<str>>=, looked up by =&str= via =Rc<str>: Borrow<str>=) dedups
  repeated names across features: N×cols allocations become cols. Threaded
  through both the streaming and the tree/fallback paths.
=JsonValue::Object= keeps =String= keys (arbitrary nested JSON is unaffected);
only the top-level feature key type changed. =Rc= (not =Arc=) since the pipeline
is single-threaded. Measured jointly with item 3 (table above) — the ~1.2× on
every =*→geojson= read and ~1.3× on =parquet→geojson (wide)=. GeoJSON read held
the 4-property common case (no regression) and improved key-heavy reads.

*** 6. Parquet level decoding + WKB churn  [lower priority, contained]
- *DONE — level decoding.* =split_definition_levels= used to decode every
  definition level into a =Vec<u64>= (eight bytes per 0/1 level) and map it to a
  *second* =Vec<u64>= present-mask. Replaced the mask with a =Present= enum:
  =Present::All(n)= for the all-present case (what Geosetta always writes — a
  single RLE run of the max level, detected by =is_all_present_rle= *without*
  decoding), so neither allocation nor the per-row scan happens; only a page that
  truly contains nulls falls back to =Present::Mask(Vec<bool>)= (one byte per
  row, down from eight). =push_json= / =push_json_strings= / =align= special-case
  =All=. Measured (=throughput= =parquet→geojson=, N=400k, interleaved A/B):
  ~1.90M → ~2.09M ft/s, ~6%.
- *DONE — WKB churn.* =wkb::encode= started from =Vec::new()= and reallocated as
  it grew — one =Vec= per feature on every GeoParquet/GeoPackage write. Added
  =wkb_size= (exact byte length, mirroring the writer, unit-tested equal to the
  encoded length) and =Vec::with_capacity=, so the write never reallocs. Measured
  (=throughput= =geojson→parquet=, N=400k, interleaved A/B): ~1.01M → ~1.09M
  ft/s, ~7%. (FlatGeobuf uses its own geometry coding, not WKB, so this helps the
  Parquet/GeoPackage write paths.)
- *Parked — float formatting (dtoa).* Coordinate output goes through
  =write!(…, "{}", …)=, i.e. std's shortest-round-trip float formatter. A
  hand-rolled dtoa could add ~1.5–2× on coordinate-heavy GeoJSON write, but it is
  correctness-sensitive and the largest effort here (a Ryū/Grisu from scratch),
  for a throughput-only gain — deliberately left for later, if ever. Note this is
  *not* a dependency question: the current formatter is =std=, so there is no
  crate to remove; the only question is speed vs. maintenance/correctness risk.

*** DONE 7. =schema::infer_columns=: cut the per-row column sweep and the double =Null= write  [write path]
Item 1 fixed the asymptotics but item 1's own pass still had a real per-row
constant factor: after each row's properties, a =for col in raw.iter_mut()=
loop swept *every known column so far* to back-fill a =None= for the ones that
row didn't touch — =O(cols)= work every row regardless of how many properties
that row actually has. Profiling a 3M-row, 4-column =geojson→parquet= with
=sample= (macOS's built-in, no-sudo stack sampler — =dtrace=/=cargo flamegraph=
need root here) showed this single function eating ~19% of total wall time,
~47% of the write phase.

Rewrote as two passes, neither doing per-row work proportional to the *total*
column count:
1. Discover the column set + merge each column's type — no per-row value
   materialization.
2. Append each column's cells in row order as encountered; a column skipped by
   the current row is left alone, not eagerly padded. The gap is back-filled
   with =Null= lazily — only when that column is touched again, or once at the
   end if it never is. A fully dense table (every row has every key, the
   common case) costs exactly one push per cell and never touches a column
   it isn't writing to.

First attempt pre-sized every column to =vec![Cell::Null; n]= up front instead
of the lazy back-fill above — *wrong*: for dense data (no rows ever omit a
key) every cell then gets written *twice* (the eager =Null=, then the real
value), and =Cell= is ~4× the size of the =Option<&JsonValue>= item 1's raw
buffer held. Caught this because a wide-column benchmark (200 cols) got
measurably *slower*, not faster — the narrow 4-column case alone didn't reveal
it. The lazy version fixed it in both regimes. Added a duplicate-key-within-one-row
test (item 1's =find=-first-wins rule had no dedicated test).

Result: whole-process wall-clock at these scales was too noisy to trust (even
interleaved A/B, the machine was under load this session) — from-scratch/new
binaries, =sample=-based time-share (immune to absolute-clock drift, since it's
a ratio within one run) gave the reliable signal instead:
| fixture                | before (sample-ms) | after | total Δ | =infer_columns= Δ |
|-------------------------+--------------------+-------+---------+--------------------|
| 4 cols, 3M rows         | 2819               | 2660  | -5.6%   | -32.6%             |
| 30 cols, 200k rows      | 486                | 456   | -6.2%   | ~flat (noisy)      |
| 200 cols, 50k rows      | 868                | 744   | -14.3%  | -44.2%             |
Win grows with column count, as expected — the eliminated sweep was =O(cols)=
per row. =bench/compare.py=, which only ever used a 4-property fixture, was
extended with a =WIDE_N=/=WIDE_COLS= wide-column case to actually exercise this;
at 200 cols geosetta's margin over ogr2ogr/duckdb *widens* to 8–10× (vs 5–9× on
the narrow cases) — both external tools scale worse with column count too.

*** Deferred / profile-first
- =get()= on JSON objects is a linear scan; fine for small feature/geometry
  objects, but a feature with very many properties re-scans per lookup.
- The compression codecs (Snappy on write; ZSTD/GZIP/LZ4 on read) are untuned;
  profile a real workload before investing — they are unlikely to be the
  bottleneck next to the allocation costs above.
- Everything is fully materialized in RAM (whole file → =FeatureCollection= →
  whole output). True streaming is tracked separately in
  [[file:streaming-progress.org][streaming-progress.org]]; it is a memory-footprint concern more than a
  throughput one.
