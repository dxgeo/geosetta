- [ ] [[file:container-reconciliation.org][container-reconciliation.org]] —
  what happens to container content when the *destination* GeoPackage already
  has some. **Blocks =same-format-fidelity.org= M3b from closing**: M3b can
  carry a source container into a fresh file without it, and cannot claim to
  carry a container in general until it is settled. The collision is the
  *common* case, not the rare one — any two =ogr2ogr= GeoPackages both hold
  =gpkg_metadata= — so no "which wins" rule is right down both paths, and a
  real merge means renumbering AUTOINCREMENT ids, rewriting the foreign keys
  that point at them, recomputing =sqlite_sequence= rather than carrying it,
  and *building* indexes rather than re-packing them — which reopens D10.
  One requirement is due regardless of the merge question: carried content
  referencing an =srs_id= points into the source's numbering, which
  =resolve_srs= renumbers. Scoping only.

  /2026-08-23:/ **D2 is decided -- merge, and build the index** -- on § THE
  MEASUREMENT rather than on the argument that was on file, and *both* options
  moved when =ogr2ogr= was actually asked. Refusing a merge for indexed tables
  is out: **every** table that would need merging carries an index, so it would
  fire on every ordinary append. Building is in, and costs less than feared: no
  producer emits a non-=BINARY= index, so the collation machinery stays out of
  scope and § 5's refusal covers what does not fit. The same run overturned the
  plan's own § 3 -- ***=ge_tce= does not make a set either***, and three of the
  four registry keys have a nullable column, so merging two *plain* =ogr2ogr=
  files deduped nothing at all while =integrity_check= reported =ok=. What is
  left is ordinary work plus one piece of paper: the "same row" contract, now
  load-bearing for three tables rather than one. *That contract is written* --
  § 6 states identity per table, the three rules that decide it (a surrogate id
  is allocation; NULL equals NULL; a write-time stamp is provenance), what is
  recomputed rather than merged, and the step ordering §§ 2 and 3 cannot choose
  freely. It raised **D4** and **D5**, and *both are now decided*, along with
  **D3** -- so this plan has no open decisions left.

  - *D3 -- =srs_id= reconciliation is **M3b's**.* Not a placement preference in
    the end: this plan's gate says M3b can carry into a *fresh* destination
    without any of it, and =resolve_srs= renumbers on every write regardless,
    so the failure happens where there is one container and nothing to
    reconcile.
  - *D4 -- a tile collision with differing bytes is **refused**.* It fires only
    on a true overlap: adjacent pyramids union cleanly on =(z, x, y)=, which
    Requirement 54 makes the declared key.
  - *D5 -- a same-named user table is **refused**.* Decided, reopened, and
    re-decided on a hazard neither option had accounted for:
    =gpkg_metadata_reference.row_id_value= is normatively a rowid into the
    table but carries **no foreign key**, so merging renumbers rowids and
    every row-scoped reference rots *silently* -- past =integrity_check= and
    past =foreign_key_check=. The reopen-shape is filed for when a real case
    turns up.

  Next is =same-format-fidelity.org= M3b, which now owns § 1.

  /2026-08-24:/ **=gpkg_contents.last_change= is now carried** -- a member the
  inventory had missed entirely, because the row was surveyed for what it says
  *about* a layer and this reads as bookkeeping. It is not: the standard defines
  it as "timestamp of last change to content", and a =gpkg -> gpkg= run had been
  overwriting it with a constant since the GeoPackage spoke shipped. Carried
  only; the *stamp* half of the rule -- a fresh timestamp where there is nothing
  to carry -- is deliberately unbuilt, because it would spend byte-reproducible
  output on nearly every run and fixes nothing the carry does not.
