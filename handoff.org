** WHAT THIS WORK IS
It began as a request to make =geosetta= read a file, let *another program*
modify the feature collection, and write it back. That turned out to be
possible already, and the interesting question was why it is not *faithful*.
Chasing that produced a standing rule:

#+begin_quote
*Reading a format and writing the same format loses nothing.* A capability gap
in the target is a defence for dropping data; the target being the source's own
format is not.
#+end_quote

Everything else is consequence.

** THE EDIT LOOP, AND WHAT IT REQUIRES OF EVERYTHING ELSE
/Added 2026-08-22, from the question "a middle package should be able to modify

*** The frame is already settled -- =edit-composability.org= § THE TRANSIT COROLLARY
#+begin_quote
An edit loop is lossless end to end only when the transit format *is* the
endpoint format.
#+end_quote

Everything below follows from it. Any other recipe is *two cross-format
conversions* wearing a round trip's clothing, and each hop is independently
entitled to drop what its target cannot hold.

*** In-process and piped are opposite cases, and natives behave oppositely
The "middle package" is two different things, and conflating them is the
easiest mistake to make here.

- *In-process* -- a Rust consumer holding a =FeatureCollection= (reprojection
  via =for_each_position_mut=, vector math). **Natives survive**, because
  nothing is serialized, and D7 made the modelled types nameable so this
  consumer can read *and construct* declarations. This path works today;
  =tests/reproject_pipe.rs= exercises it against a real third-party
  reprojection crate.
- *Piped* -- an external process. **Natives die at the transit boundary by
  construction**; that is D5. A =GpkgNative= cannot cross a FlatGeobuf pipe.

*M3b widens that gap rather than closing it*, which is worth knowing before
starting it: afterwards =gpkg -> gpkg= in one invocation carries the whole
container, while =gpkg -> fgb -> tool -> fgb -> gpkg= still carries only the
layers. Not an argument against M3b -- an argument for why the deletion's
position is now worth reopening (§ THE SEQUENCING).

*** M3b needs a third class, because D4's two are not enough
D4 splits derived content two ways -- information *recomputed*, capability
*rebuilt if present*. Editing forces a third distinction, because container
content divides by *what it depends on*:

| class | example | rule |
|-------+---------+------|
| *independent* | =side_notes=, a user's own table | carry unconditionally; survives any edit |
| *layer-coupled* | =gpkg_metadata_reference= (keyed by =table_name=/=column_name=), triggers on feature tables, =gpkg_data_columns= | **validate against what is actually being written**, never replay blindly |
| *derived* | R*Tree, =gpkg_ogr_contents=, =gpkg_contents='s bbox | recompute, *never* carry |

The precedent for the middle row already exists and should be followed rather
than reinvented: decision 14 replays =ARROW:schema= only while the column names
still match, and decision 16 regenerates a member equal to what the writer
would emit anyway.

*** Invalidation has to be *computed at write*, not tracked
The obvious design is a dirty flag -- mark the collection modified, drop the
natives. **It cannot work, and the reason is structural rather than effort:**
=Feature::properties= and =FeatureCollection::schema= are *public fields*,
deliberately, because D7 needed a caller able to name and build them. A
consumer mutates them directly. There is no method call to intercept and no
setter to hook.

So validity must be derived at write time, by comparing each native against
what is actually being written. That is already what the crate does -- the
format tag in =payload_for=, the column-name gate on =ARROW:schema=, decision
16's "is this what the writer would emit anyway" -- but it has grown one member
at a time. *M3b is where it should become one explicit contract*, because
container content multiplies the number of members that need it.

*** Reprojection is the case that invalidates the most
Every bbox, every spatial index, and the CRS rows in
=gpkg_contents=/=gpkg_geometry_columns=/=gpkg_spatial_ref_sys=. A carried
R*Tree after a reprojection would be *wrong*, not stale -- **worse than
absent**, because a reader trusts it. D4 already says an index is rebuilt
rather than carried; editing is what makes that rule load-bearing instead of
merely tidy.

settling: the IR's own four column types are measurably too narrow, so

modelled field lets an external tool widen a declaration mid-flight alongside
the value that outgrew it. *Both are implemented*; the schema half lives in
=crate::FieldDecl= and =FeatureCollection::schema=.

** WHAT IS BUILT
- ***The feature id*** (/2026-08-25/, decision 27) -- a =gpkg -> gpkg= run
  preserves each feature's =INTEGER PRIMARY KEY= instead of renumbering it,
  carried on =NativePayload::GpkgFeature= and *only* where it differs from the
  dense =1..n= the writer emits anyway. Validated at write rather than replayed:
  ids that no longer strictly ascend are discarded and the layer is renumbered,
  because a duplicate is a malformed database. The R*Tree is built against the
  same ids. /Byte-invisible to all eleven pre-existing =.gpkg= fixtures, which
  is D16's containment measured rather than claimed./
- ***A user's own tables*** (/2026-08-25/) -- =side_notes=, =events=,
  =registry=, =tags=, =people= and their kind survive a =gpkg -> gpkg= run
  with their DDL verbatim, their rows, **their rowids**, their triggers and
  their indexes. The plainest member of the independent class, and the one
  M3b's survey predicted would need no new file-format work -- correctly.
  /Its indexes are re-packed from the source rather than rebuilt, which is why
  a =UNIQUE ... COLLATE NOCASE= key survives a crate that implements no
  collation: an index read in index order is already sorted./
- ***The container carrying channel*** (M3b's first half, /2026-08-24/) --
  =geopackage/carry.rs=. Independent container content is read out of a source
  =.gpkg= and re-emitted, which is the first part of *defect 3's fix* rather
  than another warning about it. Today it reaches the **tile pyramid**: the
  tile table verbatim with its rows, its autoindex, its =sqlite_sequence= mark
  and its six triggers, plus =gpkg_tile_matrix= whole and
  =gpkg_tile_matrix_set=. /Measured on =gdal_tiles.gpkg=: 80 tiles
  blob-for-blob, =gdalinfo -checksum= identical through the output, a second

12. *A column added by =ALTER TABLE= read back NULL instead of its default.*
    SQLite does not rewrite existing rows on =ADD COLUMN=; their records stay
    *short*, and the added column's value for those rows lives only as the
    =DEFAULT= in the DDL. =read_rows= padded short records with
    =Value::Null= and =parse_columns= discarded =DEFAULT= as a constraint
    keyword. /Measured:/ =sqlite3= and =ogrinfo= both report =B=; geosetta
    reported an empty cell -- **on every output format**, needing no
    same-format run to fire. Fixed by decoding the literal (text with =''=
    escapes, integers, reals, blobs, =TRUE=/=FALSE=) and padding with it.

    *Only literals are decoded, and that is sufficient rather than partial:*
    the sole path by which a default reaches a stored row is
    =ALTER TABLE ADD COLUMN=, and SQLite rejects a non-constant default there.
    An expression default can never apply to a short record.

13. *=gpkg_ogr_contents= is reported as destroyed content, and it is derived.*

    the loss list -- =gpkg_ogr_contents (2 rows)= -- but the table is

    did.*** The second message exists because =--rtree= is a **remedy**; a
    cache with no remedy and no information lost would be furniture on every

    derived too, including the *ten* =ogr2ogr= puts on =gpkg_tile_matrix= --

    rows beside them.

*The lesson these two add*, which is the type-vs-value one turned outward:
**the fixture set is only as wide as the tools that built it.** Every fixture
in the tree came from =ogr2ogr=, DuckDB, pyarrow or hand-authoring, so the
whole crate had been tested against the subset of SQLite that GDAL emits --
and a GeoPackage is a general SQLite database that anything may touch after
GDAL is done. Both bugs sat in the gap between "what our fixtures contain" and
"what the format permits", which is a gap no amount of testing the fixtures
can close. The new =sqlite_altered.gpkg= is the first fixture built by
reading the *format* for what it allows instead of the *tool* for what it
writes.

19. ~~***A =gpkg -> gpkg= run renumbers every feature, silently.***~~ **Found
    2026-08-25 and FIXED the same day**, by decision 27. =reader.rs:148= filters the =rowid= alias out of the
    properties it builds and =writer.rs:900= assigns =(i + 1)= on the way out,
    so feature ids are reissued dense from 1 on every write. Measured on a
    =cities= layer holding fids =1, 9, 40=:

    #+begin_src text
      geosetta gap.gpkg out.gpkg   ->  1, 2, 3
      ogr2ogr  -f GPKG ogr.gpkg    ->  1, 9, 40
    #+end_src

    No warning fires, because nothing classifies the id at all -- it is not
    modelled, not carried, and was not listed in =native-inventory.org=, the
    document whose whole job is enumerating what each reader discards.

    **The standard gives the column a stated purpose**, which is what makes
    this a loss rather than an allocation detail. Requirement 29 mandates the
    INTEGER primary key as a =rowid= alias, and the note under it says what it
    is for: linking features to row-level records in =gpkg_metadata= *by rowid
    value* through =gpkg_metadata_reference=. /Nothing requires a **writer** to
    preserve those values, so renumbered output is conformant -- the same
    posture as =last_change=, which was conformant either way and was still
    real information being destroyed./

    ***Why it reaches a decision already taken.***
    =container-reconciliation.org= D5 refuses a user-table merge specifically
    on the =row_id_value= hazard: a reference the DDL declares no foreign key
    on, so =foreign_key_check= cannot see it and =integrity_check= cannot
    either, because the file is not malformed -- merely lying. D5 attributes
    that hazard to merging. **It is already live on the plain one-container
    path**, which D5 treats as safe. The decision is not wrong; its stated
    scope is too narrow.

    /It has not bitten because an ordinary =ogr2ogr= file's metadata reference
    is =table=-scoped, not =row=-scoped -- measured on the same file. That is
    luck about producer practice, not a property of the code./

    **Nothing in the tree could have caught it.** All eleven =.gpkg= fixtures
    hold dense =1..n= ids, so every one round-trips through the renumbering
    unchanged. /The same fact is the containment result: carrying the id would
    be byte-invisible to the entire existing corpus./

    *The channel exists already.* =Feature::native='s doc names /"a GeoJSON
    =id="/ as its example, and the GeoJSON spoke carries that member today,
    classed *identity*. What is missing is that =NativePayload::Gpkg= is
    collection-level only by construction, so a per-feature form is the one
    structural addition -- with D16 containing the cost, since a dense =1..n=
    sequence is what the writer emits anyway and is therefore derived.

    ***FIXED by carrying it*** -- decision 27, taken by the project owner on
    the recommendation filed here. =NativePayload::GpkgFeature= is the
    feature-level variant the enum's =#[non_exhaustive]= was written for, and
    the shape above survived contact with the code exactly: the reader attaches
    an id only when it differs from the position, so `second` in the new
    fixture carries nothing while `cities` carries two of three.

    *One thing the filing did not anticipate.* A carried id is **layer-coupled**
    rather than independent, and had to be validated at write per decision 23 --
    delete a feature from the middle and the survivors' ids no longer describe
    them, which can duplicate an =INTEGER PRIMARY KEY= (a malformed database) or
    run backwards (unpackable into a b-tree). The whole layer falls back to a
    dense sequence when the carried ids do not strictly ascend. /Falling back
    per feature would hand back a set that is neither the source's numbering nor
    a fresh one./

    *And the R\*Tree had to be told.* =rtree::build= numbered its leaf entries
    by position too, so an index built beside a carried numbering would have
    pointed at rows that do not exist -- **which =integrity_check= does not
    object to**, because the shadow tables are well-formed and merely wrong.
    The ids are now computed once per layer and passed to both.

*The number model and Shapefile's decimals, 2026-08-21 -- code.* Two findings
that had been recorded rather than fixed. The first turned out to be a symptom.

=JsonValue::Number= was an =f64= plus an =is_int= flag, and an =f64= carries
integers exactly only to 2^53 -- so a *same-format* =gpkg -> gpkg= run turned
=9007199254740993= into =...992=, on a plain 64-bit =INTEGER= column. Past
=i64::MAX= the serializer's =as i64= saturated: =12345678901234567890= came
back =9223372036854775807=, a specific wrong number. **The flag was the tell**
-- it existed to remember what the representation had already thrown away.

Now =Int(i64)= and =Float(f64)=, so an integer never touches a double. One too
wide for an =i64= becomes =Float=: lossy, but honestly lossy, never a different
integer. Whole floats keep their =.0= (=1.0= stays =1.0=), which matches
=ogr2ogr= -- verified, including its coordinates, which it writes =[1.0,2.0]=.
That change immediately caught =geojson/mod.rs='s *two writers disagreeing*:
the direct writer formatted its own coordinates while the tree serializer went
through =JsonValue=. Both now call one =write_json_f64=.

*The sweep now uses values past 2^53*, because it did not before -- =Int64='s
representative value was small enough to survive a double. A sweep can be
exhaustive over *types* and still miss a whole class by being unadventurous
about *values*. That is the third variation on the same lesson in two days,
after the undeclared-column path and the type-vs-value blind spot.

=dbf.rs='s =DECIMALS= fallback went 6 → 15, matching the =15= in =ogr2ogr='s
=Real (24.15)= for an undeclared double. *The number's text is now
byte-identical to GDAL's; the field around it is not, and deliberately.*
/Measured on =1.23456789012345=:/ both write the digits =1.234567890123450=,
and geosetta writes them into an =N(17,15)= field where =ogr2ogr= writes
=N(24,15)= -- the difference is trailing pad, because this writer sizes a field
from the values it actually holds while GDAL uses a fixed default. That is the
same policy that makes an integer column =N(2)= here and =N(9)= there, it is
not part of this change, and the =24= was never the thing being matched.
*Whether that policy is the right one is now an open question* --
=same-format-fidelity.org= § OPEN QUESTIONS' first entry, and § OPEN QUESTIONS
WORTH KNOWING below.
Fifteen decimals push the fixed-point text past the 255-byte =.dbf= limit at
lower magnitudes, so the *fallback* is trimmed to fit (at =1e240= those
decimals are padding an =f64= never carried); a *declared* scale is left to
fail loudly, since that is the source stating a fact.

*D7, the public API, 2026-08-21 -- code.* D1 models the column schema in the IR

*The binary cell type, 2026-08-21 -- code.* The recast matrix asserted
*declarations*, and it was green while a =gpkg -> gpkg= run **destroyed every
blob in the file**: the =BLOB= declaration survived, so the types matched, and
=X'0102'= came back =NULL=. The GDAL cross-check missed it for the same reason
-- it diffed =ogrinfo -so=, which prints the schema and no values.

The cause was structural rather than careless. The IR's property type is
=JsonValue=, so bytes had nowhere to live; =geopackage/reader.rs= returned
=Null=, FlatGeobuf skipped the payload, GeoParquet rendered hex text, and all
three then *declined to declare* =Binary= -- correctly, since declaring a type
whose values are destroyed is a promise the value side cannot keep. So the fix
was the IR: =JsonValue::Binary(Vec<u8>)=, whose doc admits it makes the type's
name a slight lie and cites the precedent (=Number { is_int }= is not a JSON
distinction either). The compiler then enumerated the blast radius exactly as
D3 intends -- eight sites, each a writer that had to decide.

Two spokes gained a capability they already had on disk: FlatGeobuf's
=ctype::BINARY= was in the reader's table and unreachable from the writer,
which kept *its own duplicate of all fourteen constants* -- collapsed to one
shared table in the same pass. GeoParquet's unannotated =BYTE_ARRAY= is binary
in Parquet's own model and was being decoded as UTF-8.

=Date= also stopped degrading to text: FlatGeobuf has no =DATE= but has
=DATETIME=, which is what =ogr2ogr= writes for the same hop. And once the type
survived the transit, the *value* turned out not to -- =format_timestamp=
emitted no =Z=, so =gpkg -> parquet -> gpkg= turned =12:00:00+00= into an
unzoned =12:00:00=. =TIMESTAMP_MILLIS= is UTC by definition, so it emits the
designator now.

*The rule this bought*, and it belongs beside the undeclared-column one below:
**a type-fidelity test that never looks at a value can be perfectly green while
the values are being destroyed.** Three of those four bugs fell out of one
change -- adding a value comparison beside the type comparison, in both the
in-tree sweep and the GDAL check.

** REPRODUCING THE MEASUREMENTS
Every claim marked /measured/ was run against the release binary
(=target/release/geosetta=, workspace target dir -- note =geosetta/target/= is
a stale leftover and its binary predates =--crs=) and GDAL 3.13.2. The fixtures
are in the tree, so most re-run directly, e.g.:

#+begin_src text
geosetta tests/fixtures/gdal_hostile.gpkg - --to geojson --layer cities
geosetta tests/fixtures/hand_hostile.csv - --to fgb | geosetta - - --from fgb --to csv
#+end_src

*The D2 measurement (2026-08-23) needs files that are not in the tree*, because
it is about what a *producer* emits rather than about a fixture. It rebuilds in
four commands, and the last one is the oracle:

#+begin_src sh
  ogr2ogr -f GPKG a.gpkg roads.geojson   -nln roads
  ogr2ogr -f GPKG b.gpkg rivers.geojson  -nln rivers
  # every index in either file, with the collation of its first key column
  sqlite3 a.gpkg "SELECT tbl_name, name, sql IS NULL AS autoindex FROM sqlite_master WHERE type='index';"
  sqlite3 a.gpkg "SELECT name, coll, desc FROM pragma_index_xinfo('sqlite_autoindex_gpkg_extensions_1') WHERE key=1;"
  # the naive set-union, which dedupes nothing: 3 + 3 -> 6
  cp a.gpkg m.gpkg && sqlite3 m.gpkg "ATTACH 'b.gpkg' AS s; INSERT OR IGNORE INTO gpkg_extensions SELECT * FROM s.gpkg_extensions; SELECT count(*) FROM gpkg_extensions;"
  # what the answer should have been: 4, renumbered, foreign keys rewritten
  cp a.gpkg o.gpkg && ogr2ogr -f GPKG -update -append o.gpkg rivers.geojson -nln rivers
#+end_src

/The =pragma_index_xinfo= line is the one to keep: it is the only way to read an
autoindex's collation, since an autoindex has no =sql= text to grep./

*A trap in the append leg, which cost one wrong sentence in a commit message.*
The interesting row is the destination's *pre-existing*
=gpkg_metadata_reference= row, not the count of rows afterwards -- the new
layer's row is newly created, so its =timestamp= being the append time is
evidence of nothing. Read the destination before and after, and discriminate
the mechanism before generalising:

#+begin_src sh
  ogr2ogr -f GPKG -update -append d.gpkg b.geojson -nln rivers  # NEW layer: rewrites the old row's ts
  ogr2ogr -f GPKG -update -append d.gpkg a.geojson -nln roads   # EXISTING layer: leaves it alone
  ogrinfo d.gpkg roads -so                                      # read-only: leaves it alone
#+end_src

/It is a new metadata *record* that makes GDAL rewrite the whole table, not a
write to the file. Two of those three commands are what stop "GDAL refreshes
metadata on every write" from being written down as measured./

Three traps that already cost time once each:
- *Do not write fixtures through a shell heredoc.* It silently mangled
  =København= to =Ke\xe2\x88\x9a\xe2\x88\x8f...=. Write with explicit encoding
  and check the raw bytes.
- *=strings= defaults to a 4-character minimum*, which hid a 3-character
  column name and produced a wrong conclusion about FlatGeobuf's header. Use
  =strings -n 1= when decoding fixtures by hand.
- *=tests/fixtures/gdal_hostile.fgb= does not exercise column widths*, despite
  being the fixture the inventory cites for FlatGeobuf's =Column= table. It was
  written *from the GeoPackage*, which has no widths, so every column reads
  =String (0.0)=. To exercise them, write a fresh FGB from
  =gdal_hostile.shp=. The =0.0= is itself a useful case -- it is what proved
  that GDAL writes =width: 0= for "undeclared".

*The carrying measurement (2026-08-24)* runs entirely on fixtures in the tree,
and the third command is the one that matters -- a row count survives a carry
that mangles every payload, so the check has to be on the *pixels*:

#+begin_src sh
  geosetta tests/fixtures/gdal_tiles.gpkg /tmp/out.gpkg --to gpkg
  sqlite3 /tmp/out.gpkg 'PRAGMA integrity_check; PRAGMA foreign_key_check;'
  # the reference implementation reading our output, band by band
  gdalinfo -checksum tests/fixtures/gdal_tiles.gpkg | grep -i checksum
  gdalinfo -checksum /tmp/out.gpkg                  | grep -i checksum
  # a fixed point: writing our own output again changes nothing
  geosetta /tmp/out.gpkg /tmp/out2.gpkg --to gpkg && cmp /tmp/out.gpkg /tmp/out2.gpkg
#+end_src

/And the containment check, on the =0e33a40= precedent:/ a GeoPackage with **no
pyramid** must come out byte-identical to what the previous binary wrote, which
is what says the new channel costs nothing where it does not apply. Build the
parent commit's binary into a *separate* target directory before comparing --
see the second false start below.

*Two false starts on the payload-containment comparison (2026-08-24), both of
which read as findings.* Neither was a bug in the code. Both were bugs in the
measurement, and each was believed for a while before it was caught.
- *The first compared files that were never written.* =zsh= does not
  word-split unquoted expansions, so a list of format names held in a variable
  stayed a single word, every output collapsed onto one path, and the
  per-format files did not exist -- yet the comparison still reported a
  difference in every spoke. **The mechanism is worth knowing exactly:**
  =cmp= exits *2* for a missing file and *1* for a real difference, but the
  usual test is =if ! cmp -s a b=, which sees only /non-zero/ -- and =-s=
  suppresses the =No such file or directory= that would have given it away.
  /Loop over an array, not over an unquoted string; the =bash= idiom is
  silently wrong here./
- *The second used a stale release binary*, built before the change, and so
  showed the carry silently not working -- a clean, plausible negative result
  about code that was never run. See the note at the head of this section:
  =geosetta/target/= is a leftover, and even the workspace binary is only as
  new as the last =cargo build --release=.

/Both produce the shape of a finding rather than the shape of an error, which
is why they cost time: nothing in either run looks like a failed measurement./

being done, which is what made the error plausible.

** OPEN QUESTIONS WORTH KNOWING
Not blockers, but they will come up:
- *Where does the format-check deletion go now?* /Added 2026-08-22./ It is
  drawn last and is no longer forced there -- the duplicated-inventory-pass
  argument that put it there is spent. Argued in full in § THE SEQUENCING; the
  call turns on whether defect 3's destruction or *composability* is the
  priority, because per § THE EDIT LOOP no format has a lossless edit loop
  until the deletion lands.
- ~~*Does M3b carry an index, or rebuild it?*~~ **CLOSED 2026-08-23**, in two
  steps, and the question named more than two things. /Added 2026-08-22:/
  Carrying is far cheaper than it looks -- an index b-tree on disk is *already
  sorted*, so an in-order read re-packs without any comparison or collation
  logic, which is the expensive part of building one. But § THE EDIT LOOP says
  a carried index is *wrong* rather than stale once a middle stage has touched
  the geometry. The two pull opposite ways and the plan's M3b entry records
  both.

  *=same-format-fidelity.org= D10 dissolved the fork* by splitting it: an
  index's fate follows the *content class of the table it indexes*. An R*Tree
  over a feature layer is derived -- always rebuilt, and =rtree::build= already
  does it. An ordinary index over a table carried verbatim is carried verbatim.

  *=container-reconciliation.org= D2 answered the third case D10 exposed* -- a
  *merged* table, whose rows are in neither source's order and whose index
  therefore cannot be re-packed at all. **Build it.** Both sides of that fork
  moved once measured: refusing the merge fires on every ordinary append
  (every table that would need merging carries an index), and building needs no
  collation logic (no real producer emits a non-=BINARY= index). So the answer
  is *all three*, by content class: rebuild derived, carry carried, build
  merged.
- *Is canonicalisation a loss?* =MULTIPOINT ((1 2))= → =MULTIPOINT (1 2)=,
  =linestring= → =LINESTRING=. Decides whether the CSV/WKT lexeme problem is
  two bugs or a whole class. (=native-inventory.org= § QUESTIONS, item 1.)

  *A third instance arrived 2026-08-21 and it is not CSV/WKT*: GeoParquet
  *parses* a =Json= column, so ={"a": 1}= comes back as an object and
  re-serializes without the space. GeoPackage and FlatGeobuf keep the text --
  so this is also a *spoke inconsistency*, and settling the question settles
  which of the three is right. Measured; the values are otherwise unharmed
  (key order holds, and numbers are exact now that the number model is split).
- *Does the mixed-number column earn a warning?* A column holding an integer
  past 2^53 *and* a fractional value infers =Double=, and the integer loses its
  low bits. The loss is inherent -- do not try to make the value survive -- so
  the question is only whether it should be *said*. Argued both ways in
  =lossy-conversion-warnings.org= § AN OPEN CALL; fixture and an =#[ignore]=d
  test are in place, written to be rewritten around the warning.
- *=edges= / =epoch= in GeoParquet* -- no available tool emits either, so no
  fixture exists. *Do not close this as a null result* the way =envelope.org=
  closed the GPKG XYM indicators: =edges: "spherical"= would restate what the
  coordinates *mean*, which is a semantic corruption, not a dropped member.
- *Should a =.dbf= field be sized to the data or fixed per type?* This writer
  sizes from the values; =ogr2ogr= uses a fixed default per type (=String
  (80.0)=, =Integer (9.0)=, =Real (24.15)=) and ignores the data. *Not a rule
  violation either way* -- on a route that carries the declaration the source's
  width wins and no default is consulted -- so it is only about what to invent
  on a carrier-less hop. Both sides measured, and each has one hard number:
  fixed widths cost *6.5x the file* (9.7 MB against 1.5 MB on 50,000 rows of
  four ordinary columns, because dBase records are fixed-width), and GDAL's
  fixed =Real (24.15)= **silently writes a different number** for =1e240= --
  =1.00000000000000008388608e23=, off by ~10^217, at warning severity -- where
  this writer widens to =Real (255.13)= and keeps it. Argued in full, with the
  =max(fitted, gdal_default)= floor that is the likely shape of a decision, in
  =same-format-fidelity.org= § OPEN QUESTIONS. /Do not decide this from the
  ratchet complaint alone: =schema_drop_warning= already tells the user the
  declaration did not survive that hop./
- *Raster GeoPackages* -- container scope puts tile pyramids in the domain
  while geosetta is vector-only. Recommendation on file is to *reject* a
  populated tile container rather than silently drop the imagery.
