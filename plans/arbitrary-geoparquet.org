#+TITLE: Plan: Reading Arbitrary GeoParquet
#+AUTHOR: Daniel Okuniewicz Jr.

* Reading Arbitrary GeoParquet (files from DuckDB / GDAL / Arrow / pyarrow)

** GOAL
Extend the round-trip reader (see
[[file:reverse-roundtrip.org][reverse-roundtrip.org]]) so Geosetta can read
GeoParquet produced by other tools, not just its own output. This is where the
Parquet format's real surface area lives; the round-trip reader is the skeleton
we hang these features on.

** PRECONDITION
The round-trip reader is done: thrift =CompactReader=, footer/schema parsing,
single-page PLAIN + RLE decode, snappy decompress, WKB decode, GeoJSON
serialize, and the =(Parquet, GeoJson)= pipeline arm all exist and are tested
(=src/parquet/reader.rs=).

** EMPIRICAL FINDINGS (DuckDB, the primary real-world target)
Measured by writing GeoParquet with DuckDB's =COPY ... (FORMAT PARQUET)= and
inspecting =parquet_metadata= / =parquet_file_metadata=. These drive the
priorities below — they are facts about what real files contain, not guesses.

- *Dictionary encoding is not optional.* Every =BYTE_ARRAY= column, *including
  the geometry (WKB) column*, is written as =PLAIN_DICTIONARY=. Numeric
  (=INT64=, =DOUBLE=) and =BOOLEAN= columns stay =PLAIN=. → We cannot read a
  DuckDB geometry column at all without dictionary support. This is milestone 1.
- *Multiple row groups appear immediately.* 200k rows produced *2 row groups*,
  split at DuckDB's default of 122,880 rows/group. Any file "at scale" has more
  than one. → Milestone 1 must iterate row groups, not assume one.
- *Codecs seen:* =SNAPPY= (default, already supported), =ZSTD=, and
  =UNCOMPRESSED= (already supported). =GZIP= not emitted by DuckDB but common
  from other writers.
- *=format_version= is 1* → data pages are V1 (same as ours). DuckDB does not
  emit =DATA_PAGE_V2= by default, so V2 is a later, lower-priority item.
- *=primary_column= may differ* — DuckDB names it =geom=, GeoParquet version
  =1.0.0=. The round-trip reader already reads =primary_column= dynamically, so
  this already works.
- *Current behavior on a DuckDB file:* the reader fails cleanly (no panic) with
  =invalid parquet: truncated varint= — it hits the dictionary index stream and
  can't parse it. The failure is safe but the message is unhelpful; see
  "Clean errors" below.

Local tooling note (superseded): =ogr2ogr=/GDAL and =cs2cs=/PROJ are now on
=PATH= in the dev environment (=pyarrow=/=geopandas= still aren't). GDAL
fixtures are now generated directly — see the covering-bbox milestone below,
which a real =ogr2ogr -f Parquet= fixture surfaced.

** MILESTONE 1 — dictionary encoding + multiple pages/row groups — *DONE*
Implemented in =src/parquet/reader.rs=. Geosetta now reads DuckDB's default
GeoParquet: a 200k-row, 2-row-group file with =PLAIN_DICTIONARY= on the string,
INT64, and geometry columns decodes to all 200k features with values matching
DuckDB (verified across the row-group boundary). =UNCOMPRESSED= files read too;
=ZSTD= now fails with a clear "unsupported compression codec ZSTD" rather than a
cryptic varint error. A committed fixture (=tests/fixtures/duckdb_dict.parquet=)
covers the dictionary paths for INT64 / string / geometry plus a PLAIN boolean.

Original scope, all landed:

*** 1a. Richer column-chunk metadata
=parse_column_meta= currently keeps =physical=, =codec=, =data_page_offset=,
and the leaf =name=. Add:
- =dictionary_page_offset= (=ColumnMetaData= field 11, optional): when present,
  the chunk *starts here*, before =data_page_offset=.
- =total_compressed_size= (field 7): bounds the byte range of the whole chunk,
  so page iteration knows where the chunk ends.
- =num_values= (field 5): total values in the chunk, so page iteration knows
  when it has consumed them all.
- =encodings= (field 2) is informational; the authoritative per-page encoding is
  in each =DataPageHeader=.

*** 1b. Multiple row groups
=parse_file_metadata= currently keeps only the first row group. Change =Meta= to
hold =Vec<RowGroup>= where =RowGroup { num_rows, columns: Vec<ColumnMeta> }=.
=read_geoparquet= decodes each row group and *concatenates* columns across
groups in order. Total rows = sum of per-group =num_rows= (cross-check against
=FileMetaData.num_rows=).

*** 1c. Page iteration within a chunk
Replace the single =decode_column= (one page at =data_page_offset=) with a loop
over the chunk's byte range =[chunk_start, chunk_start + total_compressed_size)=,
where =chunk_start= is =dictionary_page_offset= if set else =data_page_offset=:
- Parse each =PageHeader= (already have =parse_page_header=; extend it to also
  return =page_type= (field 1) and the =DataPageHeader= / =DictionaryPageHeader=
  fields: =num_values= and the value =encoding=).
- =DICTIONARY_PAGE= (type 2): decompress body, PLAIN-decode into a *typed
  dictionary* (=Vec<Vec<u8>>= for =BYTE_ARRAY=, =Vec<i64>=/=Vec<f64>= etc.).
  Keep it for the chunk's subsequent data pages.
- =DATA_PAGE= (type 0): decode body per its =encoding= (see 1d), appending to the
  chunk's running column until the chunk's =num_values= are consumed.

*** 1d. Value-encoding dispatch on data pages
The page body for a flat OPTIONAL column is =[u32 deflen][RLE def levels][values]=
(same framing the round-trip reader already parses; repetition levels are absent
when max rep level is 0). Dispatch on the data-page =encoding=:
- =PLAIN= (0): the existing =plain_*= decoders.
- =PLAIN_DICTIONARY= (2) or =RLE_DICTIONARY= (8): the values section is
  =[1 byte bit_width][RLE/bit-pack hybrid of dictionary indices]=. Decode the
  indices and map each through the chunk's dictionary.
  - *Reuse* =decode_levels(data, bit_width, count)= — it already handles the
    general RLE/bit-pack hybrid at arbitrary bit width and stops at =count=. The
    dictionary index stream has no 4-byte length prefix (it runs to the end of
    the values section), which is exactly how =decode_levels= consumes it.

*** 1e. General RLE/bit-pack hybrid — already done
The round-trip reader's =decode_levels= already decodes both RLE and bit-packed
runs at arbitrary bit width (it was written general on purpose). Milestone 1
reuses it verbatim for dictionary indices; no new bit-unpacking code needed.

*** 1f. Clean errors for the unsupported
Where a page uses an encoding/codec/page-type we don't implement, return a
specific =Error::Parquet= naming it (e.g. "unsupported page encoding
DELTA_BINARY_PACKED") instead of failing deep in a varint read. This turns the
current opaque =truncated varint= into an actionable message.

*** Milestone 1 test strategy
- Fixtures generated with DuckDB, committed small under =tests/fixtures/=:
  - a dictionary-encoded file (low-cardinality string + geometry column);
  - a multi-row-group file, forced small with =COPY ... (FORMAT PARQUET,
    ROW_GROUP_SIZE 4)= so a handful of rows spans several groups.
- Assert our reader's output matches DuckDB's own =read_parquet= of the same
  file (row count, per-column values, geometry decoded from WKB).
- Unit-test the dictionary index path: build a dictionary + =RLE_DICTIONARY=
  index stream by hand and assert the mapped values.

** LATER MILESTONES (evidence-ordered)

*** 2. ZSTD codec — *DONE*
Implemented from scratch (RFC 8878) in =src/compress/zstd.rs=: a decoder with
FSE (tANS) entropy decoding, Huffman literals (direct and FSE-compressed
weights, 1- and 4-stream), and the sequence machine (predefined/RLE/FSE tables,
repeat offsets). Verified against =zstd= CLI vectors (raw / RLE / Huffman /
structured, levels 1–19) and DuckDB's ZSTD GeoParquet — the 200k-row file
decodes with values matching across the row-group boundary. Committed fixture:
=tests/fixtures/duckdb_zstd.parquet=.

Provenance: independent implementation from the RFC, not derived from Meta's
=zstd= sources; the format is an open standard and libzstd itself is dual
BSD/GPLv2. The =zstd= CLI is used only as a test oracle. Documented in the
module header.

*** 3. GZIP codec — *DONE*
Implemented from scratch in =src/compress/gzip.rs=: RFC 1951 DEFLATE =inflate=
(stored / fixed / dynamic Huffman, canonical-code decoding, length/distance
matches) plus the RFC 1952 gzip container (also tolerant of bare zlib or raw
DEFLATE). Verified against Python =gzip= vectors (text / repetitive /
incompressible / small, levels 1–9) and DuckDB GZIP GeoParquet, including a 200k
multi-row-group file. Committed fixture: =tests/fixtures/duckdb_gzip.parquet=.

*** 3b. LZ4 codec — *DONE*
=LZ4_RAW= (codec 7, what DuckDB/Arrow emit) implemented from the LZ4 block spec
in =src/compress/lz4.rs= — a small LZ77 sequence decoder (token, variable
literal/match lengths, 2-byte offsets, overlapping copies), no entropy coding.
Verified against DuckDB LZ4 GeoParquet (200k rows) and a committed fixture
=tests/fixtures/duckdb_lz4.parquet=. The legacy Hadoop-framed =LZ4= (codec 5)
still errors cleanly; Brotli remains unimplemented.

*** 3c. Nested-schema definition levels + the GeoParquet covering-bbox column — *DONE*
=parse_file_metadata='s schema handling used to match a column chunk to its
schema definition *by bare leaf name*, reading only that one element's own
=repetition_type= — correct for a flat schema (DuckDB's default shape, which
is all this reader had real fixtures for), silently wrong for anything
nested: a leaf's true definition level is the count of OPTIONAL/REPEATED
*ancestors* down to and including itself, not just its own repetition type.

This was invisible until a real =ogr2ogr -f Parquet= fixture hit it: GDAL
3.13 / Arrow 25 writes a GeoParquet 1.1 =geometry_bbox= "covering" column —
a per-row bbox struct (=xmin=/=ymin=/=xmax=/=ymax=) alongside the WKB
geometry, a spatial-pruning optimization. Its leaves are REQUIRED *within*
the struct but the struct itself is OPTIONAL, so their true definition level
is 1, not 0; reading it as 0 made the reader skip a real, present
definition-level section entirely and start parsing dictionary indices 4
bytes into what was still level data — surfacing as
=invalid parquet: zero-length level run=, a confusing symptom of a schema
bug, not page corruption.

Fixed in =src/parquet/reader.rs=:
- =SchemaNode= now reads =num_children= (thrift field 5, previously
  unparsed), and =flatten_schema= walks the file's flat pre-order
  =SchemaElement= list as the tree it actually encodes — root first, each
  group immediately followed by its children — accumulating definition
  level through every ancestor rather than reading one element in
  isolation.
- =ColumnMeta= now carries its full schema =path= (not just the last
  segment), matched against =flatten_schema='s leaves by full path — a bare
  name isn't unique once nesting is in play (two different structs could
  each have an =xmin=).
- A leaf under a REPEATED ancestor (a genuinely list-valued column — a
  harder problem needing repetition levels this reader still doesn't parse)
  is flagged =unsupported_repeated= and rejected with a clear
  =Error::Parquet= naming the column, instead of attempting to decode and
  misparsing the same way the bbox column did.
- =covering_bbox_paths= reads the =geo= metadata's =columns.<col>.covering.bbox=
  key (GeoParquet 1.1) and excludes those columns from =properties=
  entirely — they're an index optimization, not real feature data, so they
  shouldn't surface as fake columns even once decodable.

Verified against a committed real fixture,
=tests/fixtures/gdal_covering_bbox.parquet= (=ogr2ogr -f Parquet= on a
3-point/2-property GeoJSON), plus unit tests for =flatten_schema= (flat
schema, nested-OPTIONAL-group inheritance, REPEATED detection) and
=covering_bbox_paths= in =parquet/reader.rs='s test module. Also fixed a
stale doc comment while in there: it claimed ZSTD/GZIP were unsupported
codecs, but =decompress= already handles them (only LZO, BROTLI, and
Hadoop-framed =LZ4= remain genuinely unimplemented).

*** 4. Additional physical / logical types — *DONE*
Done:
- =INT32= (4-byte LE) and =FLOAT= (4-byte IEEE) widen into the i64 and f64
  columns respectively, surfacing as ordinary JSON numbers, in both PLAIN and
  dictionary encodings (fixture =tests/fixtures/duckdb_int32_float.parquet=).
- =DATE= (INT32 days) and =TIMESTAMP_MILLIS= / =TIMESTAMP_MICROS= (INT64) render
  as ISO 8601 strings, read from the schema's =converted_type= (DuckDB writes
  it, so no need to parse the =logicalType= union). Verified against DuckDB
  read-back including sub-second micros (fixture =tests/fixtures/duckdb_dates.parquet=).
- =INT96= (legacy 12-byte Impala/Hive timestamp: 8-byte nanos-of-day + 4-byte
  Julian day, both little-endian) renders as an ISO 8601 string at full
  nanosecond precision (=format_int96=, keeping day and time-of-day arithmetic
  separate rather than summing into one nanoseconds-since-epoch =i64=, which
  would overflow outside ~1677-2262). No =converted_type= marks it — the
  physical type alone means "timestamp," matching every real writer.
- =FIXED_LEN_BYTE_ARRAY= decodes in both PLAIN and dictionary encodings, keyed
  by the schema's =type_length= (newly parsed, =SchemaElement= field 2, threaded
  through =SchemaNode=/=LeafInfo=/=ColumnMeta= alongside =converted_type=). A
  plain (non-=DECIMAL=) column renders as lowercase hex text — the fallback for
  a raw-bytes value with no more specific logical meaning, since the IR has no
  raw-bytes value type.
- =DECIMAL= on =INT32=, =INT64=, and =FIXED_LEN_BYTE_ARRAY= (=BYTE_ARRAY=-backed
  decimal is implemented too, sharing the same big-endian-bytes-to-=i128= path,
  though no real fixture exercises it — pyarrow only emits it for =INT32=/
  =INT64=/=FLBA=). Always renders as an exact base-10 string (=format_decimal=,
  scale read from the schema's newly-parsed =scale= field), never a JSON
  number — =f64= can't hold 38 significant decimal digits without loss, and a
  =DECIMAL= column exists specifically to avoid that loss.
- =JSON= logical type: a =BYTE_ARRAY= column annotated =JSON= is parsed and
  embedded as a real =JsonValue= rather than re-stringified into a JSON string
  of a string, falling back to a plain string on a parse failure.

Verified against a real fixture generated with pyarrow (now available in the
dev environment via =uv=), in both PLAIN and dictionary-encoded forms
(=tests/fixtures/pyarrow_types_{plain,dict}.parquet=, generated with
=store_decimal_as_integer=True= and =use_deprecated_int96_timestamps=True= so
all three =DECIMAL= physical encodings and the legacy =INT96= timestamp are
exercised end to end), plus unit tests for the pure formatters
(=format_int96=, =format_decimal=, =be_bytes_to_i128=, =to_hex=) and the
dispatch wiring itself. Writers that emit *only* the modern =logicalType=
union (not the legacy =converted_type=) would still need that union parsed —
DuckDB and pyarrow both write =converted_type=, so no real file has forced
this yet.

*** 5. DATA_PAGE_V2 — *DONE*
Not emitted by DuckDB by default, but pyarrow (now available in the dev
environment via =uv=) writes it with =data_page_version="2.0"=, which unblocked
this.

=DataPageHeaderV2= (=PageHeader= field 8) is parsed in
=parse_data_page_header_v2=: =num_values=(1), =encoding=(4),
=definition_levels_byte_length=(5), =repetition_levels_byte_length=(6), and the
thrift-optional =is_compressed=(7, default =true=) — read directly off the
field header's type nibble (=BOOL_TRUE=/=BOOL_FALSE=), since the compact
protocol encodes a bool's value *in the header*, not as a following byte
(=num_nulls=(2)/=num_rows=(3) are skipped: =num_values=, nulls included,
already gives the page's row count for any non-repeated column — the only
kind that reaches a page read at all, since a genuinely REPEATED column is
rejected earlier at the =unsupported_repeated= check in =read_geoparquet=,
before its pages are ever touched).

Rather than a parallel V2 decode path, =decode_data_page_v2_body= *bridges*
V2's on-disk shape into V1's — =[u32 rle_len][RLE levels][values]=, what
=split_definition_levels= already parses — so every consumer from
=decode_data_page= onward needs zero V2-specific code:
- V2's definition-level RLE stream has *no* 4-byte length prefix (the length
  is already in the header) — synthesized here so the reassembled body still
  matches V1's shape. Skipped entirely for a REQUIRED column (=max_def_level
  == 0=), matching how V1's own body has no level section at all in that
  case — miss it and a bare 4-byte zero-length prefix gets prepended even to
  values that should start immediately, silently corrupting every REQUIRED
  column.
- Unlike V1 (whose whole page body, levels included, is one compressed
  blob), V2 only ever compresses the *values* section — decompression is
  applied to =comp[def_levels_byte_length..]= alone, gated by =is_compressed=,
  never to the levels.
- =repetition_levels_byte_length != 0= (a genuinely list-valued/REPEATED
  column) errors clearly rather than misreading — reachable only if the
  earlier =unsupported_repeated= schema check and this page ever disagreed,
  which would itself be a bug worth surfacing loudly.

Verified against a real pyarrow fixture
(=tests/fixtures/pyarrow_data_page_v2_{plain,dict}.parquet=, both PLAIN- and
dictionary-encoded, =data_page_version="2.0"=) with a REQUIRED non-nullable
column (=max_def_level == 0=, the case above), an OPTIONAL column with a real
null pattern, and geometry.

*** 6. Geometry variation — *6a, 6b, 6c all DONE*
- WKB with Z / M / ZM (3D/4D) — extend =wkb::decode= and the =Geometry= model,
  or project to 2D with a documented note. Was a genuine IR-scope decision
  (does =Geometry=/=Position= grow a Z, touching every writer, or does the
  reader silently drop it), not just a decode-path addition, so it was
  scoped out into its own plan: [[file:zm-geometry.org][zm-geometry.org]].
  *That plan's all nine milestones are now DONE* (2026-08-17) — =Position=
  grew =z=/=m= fields, and every format spoke either carries both fully
  (WKB, WKT/CSV, GeoPackage, FlatGeobuf, Shapefile, GeoParquet) or has no
  way to represent M by its own spec (GeoJSON, KML/KMZ — Z-only there,
  correctly, per that plan's own scoping).
- *6b — DONE (as a clean rejection; real multi-geometry decode/write is now a
  separate plan).* The =geo= metadata may list multiple geometry columns or a
  non-CRS84 CRS — read =geo= rather than assuming defaults.

  Non-CRS84 CRS via =geo= metadata already worked before 6b:
  =parquet::geo::parse_crs= (=src/parquet/geo.rs=) reads
  =geo["columns"][primary_column]["crs"]=, not a hardcoded default — that's
  the exact mechanism =crs.org='s WKT→PROJJSON translation round-trips
  through already. There is no CRS-reading gap in the classic =geo=-metadata
  path; only the native-logicalType path needed new CRS plumbing (6c's
  =parse_native_geometry_crs=).

  *What 6b actually implemented: detecting multiple geometry columns declared
  via =geo["columns"]=.* Per the GeoParquet spec, every key in that object
  names a geometry column, not just =primary_column=. =geo_geometry_columns=
  (=src/parquet/reader.rs=) now parses every key of =geo["columns"]= into
  =Meta::geo_geometry_columns: Vec<String>=, and =read_geoparquet='s
  per-column loop rejects a second column named there with a clear
  =Error::Parquet= (mirroring 6c's existing native-tag collision error)
  instead of falling into the ordinary property path and failing on
  "invalid utf-8" the way it used to.

  Verified against two *real* fixtures, no synthetic metadata needed for one
  of them: =tests/fixtures/duckdb_multi_geometry.parquet= — DuckDB's spatial
  extension (v1.5.4) genuinely writes multi-geometry-column GeoParquet
  (=CREATE TABLE t(geom GEOMETRY, geom2 GEOMETRY, ...)= → =COPY ... TO
  parquet=), so this fixture needed zero hand-authoring, contrary to this
  section's original assumption that no mainstream tool produces this shape.
  GDAL 3.13's Parquet driver, by contrast, confirmed *not* to support writing
  more than one geometry column (an OGR VRT with two =<GeometryField>=
  elements silently downgrades the second to a plain string property on
  write) — so DuckDB, not GDAL, is the real-world source here.
  =tests/fixtures/pyarrow_multi_geometry.parquet= is the semi-synthetic
  fixture this section originally anticipated (real WKB via pyarrow/shapely,
  hand-authored =geo= JSON, since pyarrow has no geometry concept), kept as a
  second, independent code path (no covering-bbox column, no dictionary
  encoding). Both fixtures are DuckDB-oracle-verified and covered by unit
  tests in =parquet/reader.rs=.

  *Actually decoding a second geometry column* (rather than rejecting it) —
  keeping it in the =Feature= IR and round-tripping it through GeoParquet
  write, with a text fallback for every other target format — is scoped
  separately in
  [[file:multi-geometry-columns.org][multi-geometry-columns.org]], since it
  needs an IR change (=Feature= currently holds exactly one geometry) and
  isn't just a reader-side fix.
- *6c — DONE:* some writers use Parquet's native =GEOMETRY=/=GEOGRAPHY=
  logical type (=SchemaElement.logicalType=) instead of, or alongside, the
  =geo= key/value convention — GDAL 3.13's Parquet driver supports writing it
  (=-lco USE_PARQUET_GEO_TYPES=YES/ONLY=; pyarrow 25 cannot write it, only
  GDAL can, as of this writing). The physical encoding is unchanged (still
  plain =BYTE_ARRAY= WKB), so this was purely a *detection* gap, not a new
  decode path.

  =parse_geometry_logical_type= (=src/parquet/reader.rs=) parses
  =SchemaElement.logicalType= (field 10, a thrift union) looking for member
  17 (=GeometryType=) or 18 (=GeographyType=) — *both field IDs confirmed by
  reading a real =ogr2ogr=-produced file's raw thrift bytes*, since
  parquet-format's docs don't tabulate them plainly. When found, the same
  parse also reads the member's own field 1, =crs= — a raw PROJJSON string,
  confirmed the same way against an =EPSG:3857= fixture (absent means the
  format default, OGC:CRS84, empirically confirmed against a WGS84 fixture).
  =SchemaNode=/=LeafInfo=/=ColumnMeta= each grow =is_geometry=/=geometry_crs=
  fields, following the same plumbing pattern milestone 4 established for
  =type_length=/=scale=.

  In =parse_file_metadata=, the native tag fills in whatever the =geo= metadata
  left unset — never overrides it: if =geo= didn't name a =primary_column= and
  exactly one schema leaf is native-geometry-tagged, its name becomes the
  geometry column (recovering a *non*-default-named geometry column, e.g.
  GDAL's =GEOMETRY_NAME=shape=, with no =geo= key to name it at all); if the
  CRS is still unresolved, the primary column's native =crs= is parsed via the
  new =parquet::geo::parse_native_geometry_crs= (refactored to share
  =parse_crs='s PROJJSON→=Crs= lifting rather than duplicate it). A *second*
  native-geometry-tagged column that isn't the chosen primary is rejected with
  a clear error in =read_geoparquet= (Geosetta's =Feature= IR has room for one
  geometry per feature; silently misdecoding WKB as a text property, or
  silently dropping real geometry data, would both be worse than failing
  loudly) — true multi-geometry support is
  [[file:multi-geometry-columns.org][multi-geometry-columns.org]]'s job, not
  6c's.

  Verified against two real =ogr2ogr -f Parquet -lco USE_PARQUET_GEO_TYPES=ONLY=
  fixtures (=tests/fixtures/gdal_native_geometry_custom_name.parquet=, a
  non-default =GEOMETRY_NAME=shape= column with the default WGS84 CRS and *no*
  =geo= key at all; =gdal_native_geometry_3857.parquet=, the default column name
  with an =EPSG:3857= CRS carried only in the native =crs= field) plus a unit
  test for =parse_geometry_logical_type= itself, hand-encoding the union shape
  with the crate's own =CompactWriter= rather than raw bytes.

*** 7. Nested/repeated (list-valued) columns — *DONE (list of scalars; structs/nested lists still rejected)*
The §3c fix taught the reader to compute definition levels correctly for any
column nested under an OPTIONAL group (=flatten_schema='s tree walk), and to
detect a REPEATED ancestor. This milestone decodes the common case of that —
a single-level list of scalars — instead of just detecting and rejecting it;
a list of structs or a list nested inside another list still gets the same
clear =Error::Parquet= reject as before (see "What was actually implemented"
below for exactly which shapes qualify).

**** Concrete example
A property that's an array — a GeoJSON feature with
="tags": ["park", "historic"]= — written by a tool that gives it a
native Parquet list type instead of falling back to a JSON string (which is
what Geosetta's own writer does for any array/object property value — see
=schema.rs='s =infer_columns=, used by every one of Geosetta's own format
writers). GDAL does this for its =StringList=/=IntegerList= OGR field types;
so does pandas/geopandas via Arrow's list type. Parquet represents a list
with its standard 3-level encoding:
#+begin_src text
optional group tags (LIST) {
  repeated group list {
    optional binary element (STRING);
  }
}
#+end_src
The middle =list= group is REPEATED: for a single row it can appear zero
times (empty list), once, or many times. That's a fundamentally different
shape from §3c's =geometry_bbox= (OPTIONAL — each row has *at most one*
value at that path); decoding a REPEATED column needs *repetition levels* —
a second value alongside each definition level saying "does this value
start a new row, or continue the same row's list as the previous value" —
which is how the reader would tell where one row's list ends and the next
row's begins within Parquet's flat, columnar stream of encoded values.
=parquet/reader.rs= doesn't parse repetition levels at all today; only
definition levels.

**** Where this connects to the write side (already solved, no new design needed)
Once a list's elements are decoded, they don't need a new representation of
their own — they slot into the IR's existing =JsonValue::Array= and flow
through the *same* universal fallback every array-valued property already
uses, regardless of format: =schema.rs='s =infer_columns= treats any
=JsonValue::Array=/=JsonValue::Object= property as JSON text (line ~71:
"Arrays/objects can only be represented as JSON text"), so it gets
serialized to a JSON string and written into whichever text-shaped column
each target format has (Shapefile =.dbf= =Character=, GeoPackage =TEXT=,
FlatGeobuf =ColumnType::String=, a CSV cell, another GeoParquet
=BYTE_ARRAY=). This is exactly what already happens today for a
GeoJSON-sourced array — =convert.rs='s test fixture has a feature with
="tags": ["a", "b"]=, and =read_recovers_geometry_and_properties= confirms
it comes back out as the string =["a", "b"]= after a GeoParquet round trip.
So this milestone is read-side only: decode the list into a =Vec<JsonValue>=
(=JsonValue::Array=), hand it to the property sink as one cell the same way
every other decoded value is, and the existing write path takes it from
there with zero changes. No format gets special-cased, including Shapefile —
it's already in the same "flatten to text" boat as every other format for
array-valued properties, list-typed source column or not.

**** What was actually implemented
- *Structural detection, not just the =LogicalType=/=ConvertedType= tag*
  (=flatten_schema=, =src/parquet/reader.rs=): every leaf now carries a
  =max_rep_level= (count of REPEATED ancestors, mirroring =max_def_level='s
  existing accumulation) and a =list_eligible= flag, computed by walking the
  schema tree and tracking whether every REPEATED ancestor along the path had
  *exactly one child* — a REPEATED group with more than one child is a list
  of structs (each element has several fields; one leaf's column chunk alone
  can't decode a row's elements from it) and =max_rep_level >= 2= is a list
  nested inside another list; both are real Parquet shapes but harder
  problems this reader still declines, with the same clear
  =Error::Parquet("... is a nested/repeated (list-valued) column, which is
  not supported yet")= as before (=ColumnMeta::unsupported_repeated= now
  means specifically "repeated *and* not list-eligible," not "repeated at
  all"). Both the standard 3-level =optional group tags (LIST) { repeated
  group list { optional binary element } }= shape and the legacy bare
  =repeated binary tags= (2-level, no wrapping group) qualify as eligible.
- *Repetition-level parsing* (=split_list_levels=, a =read_prefixed_levels=
  helper shared with its definition-level section): reuses =decode_levels=
  verbatim, exactly as scoped, for both the rep and def sections of a V1 page
  body (=[u32 len][RLE rep]?[u32 len][RLE def][values]=). V2's separate
  =rep_levels_byte_length= header field — previously hard-rejected in
  =decode_data_page_v2_body= as "not supported" — is now bridged into the
  same prefixed shape rather than erroring.
- *Row grouping* (=group_list_values=): groups the chunk's flat,
  across-all-pages repetition levels, definition levels, and already-decoded
  per-occurrence values (reusing =decode_values=, the same PLAIN/dictionary
  dispatch every ordinary column already goes through — a list column's
  values are decoded exactly the same way, just at occurrence granularity
  instead of row granularity) into one =JsonValue= per row: =Null= for an
  absent list, =Array= (possibly empty) otherwise. The threshold between
  "list absent," "list present but empty," and "a real element" is a single
  new per-leaf number, =list_group_def_level= (the definition level achieved
  *at* the REPEATED ancestor itself) — computed once during the schema walk,
  reused directly rather than re-deriving it per row.
- *Correct row-counting across page boundaries* — the one real subtlety
  beyond the original sketch: a REPEATED column's page =num_values= counts
  *occurrences* (list elements plus one marker per empty/null row), not
  rows, so the ordinary column path's "stop once =rows_done >= rg_rows="
  loop doesn't apply, and nothing guarantees a single row's elements stay
  within one physical page. =decode_list_column= uses the column chunk's own
  =ColumnMetaData.num_values= (newly parsed, thrift field 5) — the
  chunk's total occurrence count — as its stopping bound instead, so a row
  split across a page boundary still gets all its elements; grouping into
  rows happens once, after every page in the chunk is read, not per-page.
- *Property naming*: a list column's decoded value is keyed by the *outer*
  list property's name (=tags=), not the innermost leaf's own bare name
  (=element=, always the same for the standard 3-level shape) — an
  easy-to-miss bug this session's fixtures caught immediately (every
  decoded list surfaced under the property key "element" until fixed).

**** Testing — done against real fixtures from two independent tools
- =tests/fixtures/duckdb_list_column.parquet= — DuckDB =LIST(VARCHAR)=, 3
  rows (a 2-element list, a present-but-empty list, a 1-element list),

  milestone 7 and §3c's nested-OPTIONAL-group definition levels together,
  from an independent tool.
- Unit tests for the primitives directly, hand-built byte streams, no full
  file needed: =split_list_levels_parses_rep_then_def_then_values= and two
  =group_list_values_*= tests covering multi-element/empty/null-element rows
  and the whole-list-null-vs-present-empty distinction — mirroring
  =decode_levels_single_rle_run=/=decode_levels_bit_packed='s existing style,

- End-to-end, the milestone's actual completion bar: decoding each fixture
  confirms =parsed.properties=' =tags= column matches the source row for
  row, then converting through the real CLI (=geosetta in.parquet

** ROBUSTNESS / VALIDATION
- Bounds-check every offset and length from the footer before slicing (the
  round-trip reader already does; keep it up as new offsets like
  =dictionary_page_offset= are added).
- Treat the file as untrusted input: no panics on malformed data; return
  =Error::Parquet= with context. Fuzz the thrift + page decoders.
- Optional statistics, page indexes, bloom filters: skip safely (=CompactReader::skip=
  already handles unknown fields).
