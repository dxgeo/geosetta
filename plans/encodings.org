* Text Encodings, Across Every Spoke
** STATUS -- scoping only (2026-10-21)
Nothing here is built. The *write* side's one settled question was answered the
day this file was written -- Shapefile emits a =.cpg= declaring =UTF-8=, see
[[file:shapefile.org][shapefile.org]] § THE SIDECAR POLICY -- and that is the
whole of what exists.

This plan was asked for after [[file:native-inventory.org][native-inventory.org]]
§ QUESTIONS item 3 turned up silent text corruption, and it is deliberately
*not* a Shapefile plan. The encoding surface spans every spoke that reads or
writes text, and the per-spoke picture is uneven in a way no single flag fixes.

** WHY THIS IS A PLAN AND NOT A FLAG
=--encoding= is the obvious shape and it is about a fifth of the work. Three
things make this bigger than a flag:

1. ***Half the spokes refuse non-UTF-8 input outright and half guess.*** Those
   are opposite failure modes needing opposite fixes -- a refusal needs a
   *remedy*, a guess needs a *warning* -- and today the crate does each in
   places nobody chose deliberately.
2. ***One spoke declares its encoding in-band, and its declaration cannot be
   trusted.*** Shapefile's =.dbf= carries a language-driver byte that the
   reference implementation fills in *wrongly*; another carries the truth in a
   sidecar. Honouring the obvious one corrupts correct files (measured below).
3. ***The crate takes no dependencies.*** Which codepages are supportable is
   therefore a real scoping question with a sharp cost boundary, not an
   import. See § THE COST BOUNDARY.

** WHERE EVERY SPOKE STANDS TODAY
All /code/, read 2026-10-21, with the two measurements marked.

| spoke | input | output | notes |
|-------+-------+--------+-------|
| GeoJSON | **refused** unless UTF-8 (=convert.rs:44=) | UTF-8 | RFC 7946 § 11 *requires* UTF-8, so the refusal is conformant -- but a user's Windows-authored file is still unreadable |
| CSV | **refused** unless UTF-8 (=csv.rs:28=) | UTF-8 | /the sharpest gap:/ CSV has no encoding story at all, and a CP1252 export is the single most common real-world text file in this domain |
| WKT | **refused** unless UTF-8 (=convert.rs:92=) | UTF-8 | ASCII in practice; lowest priority |
| KML / KMZ | **refused** unless UTF-8 (=kml/mod.rs:30=) | UTF-8 | *and the declaration that would have helped is thrown away* -- see § THE THREE THINGS, item 3 |
| Shapefile =.dbf= | =.cpg= honoured; **anything unrecognised silently becomes Latin-1** (=dbf.rs:52=) | UTF-8, declared in =.cpg= /(2026-10-21)/ | the only spoke with an in-band declaration, and the only one that can hold non-UTF-8 text |
| GeoPackage | **refused** unless the header says UTF-8 (=sqlite.rs:116=, =encoding != 1=) | UTF-8, stamped (=sqlite.rs:1940=) | SQLite allows UTF-16; a UTF-16 =.gpkg= is refused rather than decoded |
| FlatGeobuf | UTF-8 by FlatBuffers | UTF-8 | no encoding surface |
| GeoParquet | UTF-8 by the =UTF8= logical type | UTF-8 | no encoding surface |

*A BOM is stripped for XML only* (=xml.rs:75=). CSV, WKT and GeoJSON do not
strip one, so a BOM-prefixed CSV's first header name silently carries =U+FEFF=.
/Unverified whether that is biting anyone; it is cheap to fix and belongs to
E4./

** THE THREE THINGS THAT ARE ACTUALLY WRONG TODAY
Not "missing features" -- things that produce a wrong answer or no answer where
a right one was available.

*** 1. An unrecognised =.cpg= is approximated as Latin-1, silently
=dbf::encoding_from_cpg= maps *every* codepage it does not recognise to
=Encoding::Latin1=. =dbf.rs:42= documents this as "an approximation documented
as a known gap" -- and documents it *in the source*, where no user reads it.

***The common real case is =CP1252=, which differs from ISO-8859-1 in exactly
the 32 bytes =0x80=--=0x9F=*** -- where Windows-1252 keeps the curly quotes,
en/em dashes, =€= and =…= that real attribute data is full of, and ISO-8859-1
has C1 control characters. So the approximation is wrong precisely on the
characters that distinguish the two encodings, which is the worst possible
place for it to be wrong.

It is also *not* an exotic input: =ogr2ogr= declares Windows-1252 by default
(§ DECISIONS D-E2's measurement).

**This is a live instance of the crate's own standing rule**, filed at
[[file:lossy-conversion-warnings.org][lossy-conversion-warnings.org]]
§ OPEN CANDIDATES. The warning is owed whether or not a table is ever written,
and owed *first* -- it is E1.

*** 2. Four spokes refuse non-UTF-8 input with no remedy to offer
=csv.rs:28=, =convert.rs:44=/=:92= and =kml/mod.rs:30= all end in
=Error::Convert("… is not valid utf-8")=. **The refusal itself is right** --
§ A refusal honours the rule, in
[[file:same-format-fidelity.org][same-format-fidelity.org]]: no silent loss,
because no run. But a refusal is only honourable when the user has somewhere to
go, and today there is nowhere: no flag, no fallback, no message naming one.

/The asymmetry is the tell that nobody chose this:/ a Shapefile carrying
Latin-1 text reads fine, and the *same bytes* in a CSV are refused. Same crate,
same domain, opposite answers.

*** 3. For KML, the declaration we need is the one we discard
=xml.rs='s =skip_processing_instruction= skips the whole =<?xml …?>= prolog
unread, so a document declaring =encoding="ISO-8859-1"= has stated its encoding
and had the statement thrown away -- and is then refused by =from_utf8= a layer
further out, for being exactly what it said it was.

**Worse, the layering makes it unfixable in place**: =xml::parse= takes =&str=,
so the bytes are already decoded before the parser could read a declaration
about how to decode them. E5 is therefore a small *restructuring* (bytes in,
prolog sniffed, then decode) rather than a table.

** THE COST BOUNDARY -- single-byte is cheap, multi-byte is not
The dependency-free constraint makes this the plan's real scoping axis, and it
falls in a convenient place.

- ***Single-byte codepages: a 128-entry =char= table each.*** =0x00=--=0x7F= is
  ASCII in every one of them, so only the high half needs mapping. Windows-1252,
  CP437, CP850 and ISO-8859-15 cover nearly every real dBase file and nearly
  every Windows-authored CSV. A few hundred lines of table, no architecture
  change, and *reversible* -- a single-byte encoder is the same table inverted,
  which is what makes E6's write side cheap once E2 exists.
- ***Multi-byte codepages: thousands of entries each.*** Shift-JIS, GBK, Big5,
  EUC-KR. Tens of KB of source per codepage, plus stateful decoding for some.
  **This is where "support more encodings" stops being free**, and the answer
  is *refusal rather than approximation* (E3) -- a silent mojibake answer is
  worse than no answer, which is this crate's position everywhere else.

/UTF-16 sits oddly across that line: it is multi-byte but needs no table at
all, just surrogate handling, and a BOM makes it detectable. It is the one
multi-byte encoding E4 could plausibly include./

** DECISIONS
*** D-E1 -- the IR is UTF-8 only; decoding happens at the spoke boundary
Not really a choice -- =JsonValue::String= and =Cell::Str= hold Rust =String= --
but worth stating, because it is also the *right* design and should not be
"improved". A byte-level cell already exists for genuinely binary data
(=JsonValue::Binary=, 2026-08-21); text that cannot be decoded is an input
problem, not a value the IR should carry undecoded.

**Consequence:** every encoding question is a question about one spoke's
boundary, and no two spokes need to agree. That is what makes this plan
incremental.

*** D-E2 -- the =.dbf= language-driver byte is never trusted
/Decided 2026-10-21, on a measurement that reverses the obvious answer./

=dbf.rs:4= already calls the LDID byte "unreliable in practice" and the reader
ignores it, taking the encoding from =.cpg= alone. **That looks like a gap and
is a correct decision**, because:

#+begin_src text
  ogr2ogr default output:   LDID 0x57  (= ANSI / Windows-1252),  bytes are UTF-8
  ogr2ogr -lco ENCODING=…:  LDID 0x00  (= unknown),              bytes per .cpg
  geosetta output:          LDID 0x00  (= unknown),              bytes are UTF-8, .cpg says so
#+end_src

/All measured against GDAL 3.13.3./ ***So honouring LDID would decode the
reference implementation's own default output wrongly*** -- every
=ogr2ogr=-written UTF-8 shapefile would be mis-decoded as Windows-1252 by a
reader that believed the byte. The current UTF-8-probe-then-fallback is
*better* than the in-band declaration, which is not a sentence one expects to
write.

**This does not generalise to =.cpg=**, which is written by tools that mean it,
and is the channel Esri invented precisely because dBase has no UTF-8 LDID
value to put in the header.

*** D-E3 -- a refusal beats an approximation
The project's existing position (§ A refusal honours the rule), applied here:
E3 turns today's silent Latin-1 mojibake for a multi-byte codepage into a
stated refusal. **E1 and E3 together are the whole correctness story**; E2 and
E4 are capability on top of it, and could never land at all without this plan
having made the crate honest first.

*** D-E4 -- no dependency, so tables are data in this tree
A hand-written table is testable against a published mapping (§ TESTING), and a
published mapping committed as a fixture is a real oracle rather than a second
opinion. /This is the same shape as =tests/fixtures/esri_*_wkt1.tsv= and the
registry TSVs: authoritative data in the tree, compared against./

** MILESTONES
Ordered by what each one costs against what it fixes. E1 and E3 are
*correctness*; everything after is capability.

*** E1 -- warn when a declared codepage is approximated
/***Built 2026-10-23.***/ =Encoding::Latin1Approximating= is the unrecognised
codepage, kept apart from a declared ISO-8859-1 (which is exact and silent).
The warning counts only values holding a non-ASCII byte, since ASCII is exact
under every codepage: an unrecognised =.cpg= over all-ASCII text says nothing.
Beside it, the same pass found a =.cpg= declaring UTF-8 over invalid bytes
replacing them with U+FFFD silently; that warns too. /Not warned, and still
open: with no =.cpg= at all, a field that is not valid UTF-8 is decoded as
Latin-1 -- a guess, not a declared encoding approximated, so it is a
different question from E1's./

The smallest unit of work in this plan and the only one owed under an existing
rule. =encoding_from_cpg= knows it is approximating; it must say so.

#+begin_src text
  warning: shapefile: src.cpg declares CP1252, which this build approximates as
    ISO-8859-1 — the bytes 0x80–0x9F decode differently (curly quotes, dashes,
    €). (plans/encodings.org)
#+end_src

*No tables, no flags, no new types.* It also makes E2 visible as a fix rather
than a silent behaviour change, which matters for a crate whose output people
diff.

***It does need somewhere to say it, and that does not exist yet*** /(noted
2026-10-22)/. Both of this crate's warning mechanisms are write-side, and this
loss happens on **read** -- =shapefile::read='s =cpg= argument is consumed
there and the approximation is invisible by the time the IR holds the text.
The channel is scoped at
[[file:lossy-conversion-warnings.org::*2b. The read side -- OWED, and owed twice][=lossy-conversion-warnings.org= § 2b]],
where E1 is one of **two** owed instances -- the other being
=native-inventory.org= § QUESTIONS item 6's unrecognised KML geometry. /So E1
is still the smallest unit of work in this plan, and it is no longer the
smallest unit of work *outright*: whichever of the two is built first pays for
the sink, and =shapefile::read= is one of the three read entry points it has
to reach./

*** E2 -- single-byte codepage tables, read side
Windows-1252 first, on the strength of § THE THREE THINGS item 1. Then CP437
and CP850 (DOS-era dBase), and ISO-8859-15 if a fixture turns up. Each is a
128-entry =[char; 128]= plus an arm in =encoding_from_cpg=; =Encoding= grows a
variant per codepage and =decode_text= gains one lookup.

/Retire the Latin-1 catch-all as each table lands -- not before, since Latin-1
remains the right answer for a codepage with no table and E1 now says so./

*** E3 -- refuse a multi-byte codepage rather than approximating it
=.cpg= naming Shift-JIS, GBK, Big5, EUC-KR or any other multi-byte codepage
errors instead of silently producing mojibake. **Pairs with E1 and should ship
with or before E2**: once the crate distinguishes "approximated" from
"supported", the multi-byte case is visibly in neither category.

*** E4 -- =--encoding= on input, for the spokes that refuse today
The capability users will actually ask for: read a CP1252 CSV, a Latin-1 KML, a
Windows-authored GeoJSON. Decodes at the boundary into the UTF-8 IR (D-E1), so
no spoke's internals change -- the flag replaces =std::str::from_utf8= with a
decode step at four call sites.

*Also the natural home for the BOM handling* that only XML does today, and for
UTF-16 input, which needs no table.

/Blocked on nothing but E2's tables, since the flag and the tables are the same
lookup from opposite directions./

*** E5 -- honour KML's own XML declaration
/***Partly built 2026-10-23, with =kml-standard.org= K1.*** =xml::decode=
takes bytes and decides by Appendix F: a BOM, then UTF-16's first-bytes
pattern, then the declaration's =encoding=. It decodes UTF-8, UTF-16 (both
byte orders, BOM or not), US-ASCII and ISO-8859-1 exactly. Any other declared
encoding is accepted over all-ASCII bytes and refused otherwise, naming the
encoding -- so a declared Windows-1252 file with curly quotes is refused rather
than guessed at. What remains is E2's tables, which turn those refusals into
reads./

Requires =xml.rs= to take bytes rather than =&str=, sniff the prolog it
currently discards, decode, and *then* parse -- a small restructuring of the
layering described in § THE THREE THINGS item 3. Worth doing after E4 because
it then reuses E4's decoder, and because an explicit =--encoding= should
override a declaration either way.

/Note that =skip_processing_instruction= must keep skipping the prolog for
*parsing* purposes; E5 reads it before parsing begins, not during./

*** E6 -- =--encoding= on output
Write a =.dbf=, CSV, WKT or KML in a target codepage. A single-byte encoder is
E2's table inverted, so the mechanism is nearly free; **the design question is
the lossiness story**, and it is not optional. A character the target codepage
cannot hold must warn or refuse under
[[file:lossy-conversion-warnings.org][lossy-conversion-warnings.org]] -- and
unlike most of that plan's cases, this one is *per value*, which is the shape
its § 2 post-write mechanism exists for.

Shapefile already has somewhere to declare the result: the =.cpg= this writer
now emits. CSV, WKT and KML have *nowhere* -- no in-band declaration and no
sidecar convention -- so output in a non-UTF-8 codepage is undeclarable for
three of the four targets, which is an argument for keeping E6 behind an
explicit flag and never inferring it.

*** E7 -- UTF-16 GeoPackage input
=sqlite.rs:116= refuses any database whose header text encoding is not 1
(UTF-8). SQLite permits 2 and 3 (UTF-16le/be), so such a file is refused rather
than decoded. /Last in the order: no observed producer writes one, and the
refusal is honest. Listed so it is not rediscovered as a bug./

** OPEN QUESTIONS
1. *Which codepages earn a table?* Windows-1252 is settled by the evidence.
   CP437/CP850 are plausible-but-unmeasured -- **source a real fixture before
   writing either table**, per § THE ORACLE RULE's spirit: a table written for
   a codepage nobody emits is untested code that looks tested.
2. *One =--encoding= flag, or one per side?* A pipeline has two ends, and
   =--crs= already set a precedent for an input-side-only flag with an explicit
   name. =--from-encoding= / =--to-encoding= is the honest spelling if E6 lands;
   a single =--encoding= is friendlier and ambiguous exactly when both sides are
   text.
3. *On output, does an unrepresentable character warn or refuse?* The crate
   warns for =.dbf= truncation and refuses for a CRS it cannot express. A
   character has a cheap lossy rendering (=?=) and an expensive honest one (a
   refusal naming the character and the codepage). /Lean refusal: a =?= in a
   place name is the kind of silent corruption this whole body of work exists
   to stop./
4. *Does an =--encoding= on input interact with the same-format invariant?*
   Reading CP1252 and writing UTF-8 is a *conversion* of the text, not a loss
   of it -- the information survives. But =shp -> shp= with a CP1252 source
   would come out UTF-8 with a different =.cpg=, which is a byte-level change
   to a same-format run that loses nothing. /Probably fine; stated because the
   invariant's wording says "information", and this is the case that tests
   whether the wording means it./
5. *Is a BOM-prefixed CSV biting anyone?* Only XML strips one today. Cheap to
   fix in E4; unverified whether it has ever mattered.

** TESTING
- ***A committed mapping file per codepage, as an oracle.*** The Unicode
  Consortium publishes authoritative =CP1252.TXT=-style mappings; commit the
  one for each table and assert the in-tree table reproduces it entry for
  entry. That makes the table *checked against its source* rather than against
  someone's reading of it -- the =esri_*_wkt1.tsv= pattern applied to
  encodings.
- *A fixture per codepage*, round-tripped through the spoke that can hold it:
  a =.dbf= + =.cpg= pair carrying the bytes that distinguish the codepage from
  Latin-1 (the =0x80=--=0x9F= range for CP1252, not just accented ASCII --
  **a fixture using only =é= would pass under both encodings and prove
  nothing**).
- *GDAL differential*: write a =.dbf= in a codepage, have =ogrinfo= read it,
  and require the text to match what =ogr2ogr= produces for the same input.
  Per § THE ORACLE RULE, that is evidence about what a consumer accepts, not
  about what the standard requires -- which is the right bar for an encoding.
- *The refusal cases are tests too* (E3, E7): assert the error *names the
  codepage*, since an unnamed refusal leaves the user with nothing to act on.
- *E1's warning needs a mutation check.* A warning nothing asserts is a warning
  that quietly stops firing -- see =handoff.org= on the =last_change= sentinel
  that had no test behind it.
