#+AUTHOR: Daniel Okuniewicz Jr.

* Convention: Lossy Conversions Must Warn, Never Silently Succeed

** STATUS -- standing rule, in effect (2026-08-17)
Not a milestone plan with an end state — a written-down *policy* this
project already partly followed (=crs.rs='s CRS-downgrade warnings existed
before this doc did) and now applies deliberately, going forward, to every
format-capability gap. Prompted by a real mistake: M8
([[file:zm-geometry.org][zm-geometry.org]]) initially shipped GeoParquet's
=geo= metadata never emitting an =" M"=/=" ZM"= suffix, reasoning from
DuckDB's writer alone that the *spec* had no M vocabulary — wrong, caught
only when a user asked "is it that GeoParquet doesn't do it, or DuckDB
doesn't do it?" and the actual spec text said otherwise. That mistake was
about a *declared-metadata* gap (the summary string undersold what the WKB
bytes already carried correctly); this doc is about the different, worse
case — an actual *silent data drop* — and exists so the next such gap gets
caught by a warning firing automatically, not by a user's follow-up
question.

** THE RULE
Any format conversion that would silently drop, truncate, or degrade
information the source actually carries — because the target format has no
way to represent it — must emit a =warning: ...= to =stderr= (suppressed
only by =--quiet=) instead of just succeeding. The conversion still
*proceeds*: Geosetta is a format translator, not a validator, and refusing
to convert at all would be worse than a loud, honest downgrade. The bar is
*loud*, not *blocking*.

This applies retroactively (existing gaps found and not yet warned-about
are bugs, not accepted debt) and prospectively (every new format spoke or
new IR field must ship its capability gaps' warnings in the same pass as
the feature itself, not as a follow-up).

** THE TWO EXISTING MECHANISMS -- extend these, don't invent a third
Two shapes already exist in this codebase; a new gap should fit one of
them, not grow a bespoke path. As of the *generalization pass* below, both
funnel through the same two shared =main.rs= functions rather than each
growing its own wrapper — see § GENERALIZED COLLECTION.

*** 1. Pre-write predictive check (preferred when the answer doesn't depend on the actual encoding)
A pure function taking the source data and the target =Format=, returning
=Option<String>= — =None= when nothing is lost, =Some(warning)= otherwise.
Five real instances now. Four are each just an entry in
=main.rs='s =collect_conversion_warnings= (see below) rather than its own
wrapper-function pair; the last keeps the shape but not that collector, for a
reason it states:
- [[file:crs.org][=Crs::downgrade_warning(&self, target: Format) ->
  Option<String>=]] (=crs.rs=) — CRS-loss warnings, the original instance
  this pattern is named after.
- =FeatureCollection::m_downgrade_warning(&self, target: Format) ->
  Option<String>= (=feature.rs=) — the M-ordinate case this doc was
  originally written for.
- A narrower =Crs::downgrade_warning= branch (=crs.rs=) for FlatGeobuf/
  GeoPackage's alphanumeric-authority-code case (e.g. IGNF's =LAMB93=) —
  found and closed in the same pass as the M-ordinate warning, once the
  general question ("what else silently drops today?") was actually asked
  instead of stopping at the one case named in the request. Both
  =flatgeobuf/writer.rs= and =geopackage/writer.rs= already had *tested*
  behavior for this (=alphanumeric_code_is_dropped_but_org_and_wkt_survive=,
  =alphanumeric_code_falls_back_to_a_synthetic_srs_id=) with *zero* runtime
  warning until this pass — a gap that had been sitting there, known and
  tested, since =projjson-to-wkt.org='s era.
- =geopackage::container_drop_warnings(bytes, label, written, carried, rtree)
  -> Vec<String>= (=geopackage/container.rs=) — *defect 3's warning*, added
  2026-08-21. /The =carried= parameter arrived 2026-08-24: the survey subtracts
  what =carry.rs= puts back, because a warning whose job is to name what a
  rewrite loses must stop naming content the moment it survives./ Same pure-function-of-the-source shape, but it takes the
  container's *bytes* and no target =Format=, so it cannot be an entry in
  =collect_conversion_warnings= and is called directly from
  =run_geopackage_write= instead.

  *The deviation is the interesting part, and it is not laziness.* The other
  three report a *capability gap in the target*: the target format has no slot,
  so =(source, target)= is the whole question. This one's target is GeoPackage,
  which represents user tables, =gpkg_metadata= and R*Trees perfectly well —
  the loss is in *this crate's writer*, which rewrites the file from the tables
  it knows how to build. So the question is not "can the target hold this" but
  "does the container hold anything this writer does not reproduce", which only
  the bytes can answer. Anyone tempted to fold it into the collector for
  symmetry should note that doing so requires the collector to take a container,
  which the other three have no use for.

- =geopackage::metadata_drop_warnings(existing, new_layers, carried) ->
  Vec<String>= (=geopackage/writer.rs=) — added 2026-08-25, and **the first
  warning in this crate about content carried in *part***.

  /The others answer "does this survive at all". This one answers "how much of
  it", because a carried =gpkg_metadata= pair can lose *some* of its
  references: one naming a layer the write does not produce is dropped while
  the document it named is kept./

  ***Two things about its shape are load-bearing and neither is obvious.***
  First, it takes the **destination bytes**, not just the layers the caller
  passed: =write_layers= upserts =new_layers= over whatever the destination
  holds, so an append produces a layer set the caller never named, and both now
  compose it through the same =compose_layers=. /Getting this wrong made it
  claim "3 of 3 metadata references could not be carried" about three
  references the same run then wrote -- caught in review before it shipped./
  Second, it lives in =writer.rs= rather than beside the other container
  warning, because it must evaluate **exactly the rule the write evaluates**
  (=retained_references=) rather than a second copy of it.

  /Both properties got stronger on 2026-10-13 without this warning changing a
  line, which is the payoff for the second one. =container-reconciliation.org=
  § 3 merges the destination's container into the =Carried= handed to the
  write, so this call now reasons about the **merged** metadata pair -- the
  destination's documents and references included -- rather than the source's
  alone. The neighbouring container warning gained the merged
  =reproduced_names()= on the same terms, and stopped naming the destination's
  content as destroyed because it no longer is./

  *Why it earns a message at all*, against § THE RULE's noise bar: the two
  neighbouring precedents disagree, and the distinction between them is the
  test. =gpkg_ogr_contents= is reported *silently* because it is derived and
  nothing is lost; the R*Tree earns a message because =--rtree= is a
  **remedy**. A dropped reference has no remedy and *does* lose information --
  the combination neither precedent covers.

  =container_drop_warnings= returns =Vec<String>= rather than =Option<String>= because it reports two
  losses of *different kinds*: content destroyed outright, and — separately —
  a spatial index not rebuilt, which is D4-derived and has a one-flag remedy
  (=--rtree=). Folding them into one message would either bury the remedy or
  imply the index is unrecoverable.

- =FeatureCollection::decl_recast_warning(&self, target: Format) ->
  Option<String>= (=feature.rs=) -- *the declared type* the target cannot hold,
  added 2026-08-21. Ordinary entry in =collect_conversion_warnings=; the
  interesting part is what it does *not* fire on.

  *It is stated against a widening relation, not equality.* =DeclType::admits=
  says whether one declaration can hold everything another can, so a Shapefile
  writing every integer as its single numeric field type is silent (dBase's
  design, nothing lost) and so is a GeoPackage writing =UInt16= as =MEDIUMINT=.
  It fires only on a genuine narrowing or degradation -- a =DateTime= becoming
  text, a =Binary= column becoming a string. Without that relation every check
  would have to hand-wave which recasts are acceptable, and reviewers would
  disagree case by case.

  *The relation is deliberately narrow, and =String= admits nothing.* Text
  holds the bytes of a =DateTime=, a =Date=, a =Json= or a =Binary= and holds
  none of their meaning; a relation that called that lossless would define
  defect 5 out of existence.

*** 2. Post-write actual-outcome collection (when the loss is only knowable during real encoding)
A writer returns its warnings alongside its bytes, collected as the actual
encoding happens (field-name collisions, fixed-width truncation — things a
pure pre-check can't predict without redoing the writer's own work).
- =shapefile::writer::Encoded { warnings: Vec<String>, ... }= (=dbf.rs='s
  field-name/value truncation) — =main.rs='s =write_shapefile_to_path=
  prints them via the same shared =print_warnings= the pre-write checks
  use (see below), same =--quiet= gate.

** GENERALIZED COLLECTION -- one place to add a check, one place to print
Adding the M-ordinate warning alongside the existing CRS one meant
copy-pasting =warn_crs_loss=/=warn_crs_loss_layers= almost verbatim into
=warn_ordinate_loss=/=warn_ordinate_loss_layers= — identical =--quiet=
gate, identical =eprintln!= loop, identical =BTreeSet= de-dup for the
layers variant, the only difference being which check function got called.
With more format spokes (and more capability gaps) planned, that
per-warning-type wrapper-function-pair was real, and growing, duplication —
so it was collapsed once a second real instance made the pattern
undeniable and a third was explicitly expected.

*What's shared now (=main.rs=)*:
- =collect_conversion_warnings(fc: &FeatureCollection, target: Format) ->
  Vec<String>= — runs every registered pre-write check (§1) against one
  collection, in order, returning whichever fired. *A new check is one
  line added here* — no new wrapper function, no new call sites to
  remember.
- =collect_layer_warnings(layers: &[(String, FeatureCollection)], target:
  Format) -> Vec<String>= — the same de-duplicating fan-out
  =warn_crs_loss_layers= used to do alone, now built once on top of
  =collect_conversion_warnings= and shared by every check.
- =print_warnings(warnings: &[String], quiet: bool)= — the =--quiet= gate
  and =eprintln!= loop, shared by *both* mechanisms (§1 and §2): the
  three =main.rs= call sites use =print_warnings(&collect_conversion_warnings(...),
  ...)=/=print_warnings(&collect_layer_warnings(...), ...)=, and
  =write_shapefile_to_path= calls =print_warnings(&encoded.warnings, quiet)=
  directly for its post-write =Encoded.warnings=.

*What deliberately stayed independent*: the check functions themselves
(=Crs::downgrade_warning=, =FeatureCollection::m_downgrade_warning=) were
*not* forced through a shared trait or a common input shape. They happen
to both take =(&self, target: Format)= today, but that's coincidental, not
fundamental — a future check (a property-schema limit, a geometry type a
target can't represent) might need a different shape entirely (a column
list, a single =&Geometry=, …). Generalizing the *collection-and-printing
boilerplate* removed real, measured duplication; generalizing the *checks
themselves* into one interface would have meant guessing a shape for cases
that don't exist yet — the same over-abstraction =geoscribe='s own charter
scrutiny (see =architecture.org=) warns against. Add new checks as their
own naturally-typed functions; only the boilerplate around them is shared.

** KNOWN GAPS THIS RULE HAS ALREADY CLOSED
- GeoJSON/KML/KMZ silently dropping M when converting from an M-bearing
  source — [[file:zm-geometry.org][zm-geometry.org]]'s M7/M8 work landed
  full M *support* everywhere it can exist; this doc's warning is what
  fires for the two spokes (GeoJSON, KML/KMZ) where M *can't* exist by
  spec, so the user finds out at conversion time, not by diffing output.
- FlatGeobuf/GeoPackage silently substituting a dropped/synthetic id for an
  alphanumeric authority code (=crs.rs=, this pass).
- *A source's column schema dropped on the way to a target that does not
  carry it* -- =FeatureCollection::schema_drop_warning=, added 2026-08-20 with
  the modelled column schema (=same-format-fidelity.org= D1). Mechanism 1, one
  line in =collect_conversion_warnings=.

  *This is a gap this rule created and then closed in the same pass*, which is
  worth naming because it is the shape future spoke work will keep producing:
  before the declarations were *read*, nothing was dropped, because nothing was
  recovered. Raising the IR ceiling turns a member the crate never knew about
  into a member it knowingly discards, and the second is exactly what this rule
  governs. Expect the same the next time a spoke starts modelling something.

  Two things it deliberately does. It is *silent when the source declared
  nothing*, which is every GeoJSON/CSV/WKT/KML input and so the overwhelming
  majority of runs -- the noise test in § THE RULE. And its predicate,
  =Format::carries_column_schema=, is a statement about *this crate's
  implementation*, not about the formats' specs, unlike =supports_m= beside it:
  GeoPackage and GeoParquet both have somewhere to put a declaration and
  neither is wired up, so both warn today and must move when M3/M3b lands. The
  doc comment says so, so the two reasons a target can appear in that list do
  not blur together.

** OPEN CANDIDATES -- known, not yet warned, lower priority
Found while scoping this doc; not fixed in this pass because each is a
narrower or lower-real-world-impact case than the two above. Listed so the
next pass through this area doesn't have to rediscover them:
- KML's =<altitudeMode>= is never modeled at all (see
  [[file:zm-geometry.org][zm-geometry.org]]'s M9 OPEN QUESTIONS) — arguably
  out of scope for *this* rule specifically, since it's dropped uniformly
  on *read*, not conversion-target-dependent the way every case above is;
  a pre-write predictive check has nothing to compare against for it.
- GeoParquet's full 3D covering-bbox (6-element =[xmin,ymin,zmin,xmax,ymax,zmax]=
  vs. the 4-element 2D form this crate writes) is a *tightness* loss
  (spatial pruning is less effective), not a data loss — real DuckDB/GDAL
  output confirms the gap exists, but it doesn't fit this rule's "the
  source's information is gone" bar. Explicitly out of scope, not an
  oversight (see M8's own section in =zm-geometry.org=).
- Shapefile's M-only shape types' rarer stretch cases (already implemented,
  per =zm-geometry.org='s M7 follow-up) and =MultiPatch=(31) (never
  modeled, no =Geometry= variant exists to decode into) — not conversion
  losses in the sense this rule covers.

** AN OPEN CALL -- the mixed-number column, and whether it earns a warning
/Raised 2026-08-21, deliberately not decided./

A column holding *both* an integer past 2^53 and a fractional value infers as
=Double=, so the integer loses its low bits: =9007199254740993= arrives as
=...992=. /Measured; fixture =tests/fixtures/hand_mixed_number.geojson=, and
=convert.rs='s =a_mixed_number_column_loses_precision_above_2_53= states it./

*The loss is inherent and must not be "fixed".* The column is a double because
something else in it was fractional, and no format this crate writes holds both
exactly -- GDAL's =OFTReal= does the same. So the only question § THE RULE can
ask is whether it should be *said out loud*.

*The argument against is this document's own noise bar.* It fires only for a
genuinely mixed column *and* an integer above 2^53. Every other check here
guards something a user routinely hits; this one may not, and a warning nobody
ever sees is a maintenance cost with no reader.

*The argument for is that the rule is written without an exception for rarity*,
and the loss is exactly the kind it names: information the source carries,
silently degraded, on a run that reports success.

Whoever settles it: the shape is a fifth entry in =collect_conversion_warnings=,
and the ignored test is written to be rewritten around it.

** OWED WARNING -- a WKT-bearing CRS written to GeoParquet loses its dialect
/Added 2026-08-20, decided./ Reclassified in from
[[file:same-format-fidelity.org][same-format-fidelity.org]], which had it filed
as a round-trip-fidelity defect until the file was actually checked.

*The loss.* GeoParquet's only CRS channel is PROJJSON. Writing a collection
whose CRS carries WKT text converts it and *discards the original*:

#+begin_src text
$ geosetta base.fgb x.parquet          # base.fgb's CRS is verbatim WKT2
wrote x.parquet (2063 bytes)           # silent
$ grep -c PROJCRS x.parquet
0
#+end_src

Convert that GeoParquet onward to any WKT-dialect target and the definition
comes back as *WKT1*, because =projjson_to_wkt= renders WKT1 by construction --
which is the deliberate, documented choice of
[[file:projjson-to-wkt.org][projjson-to-wkt.org]] § Output dialect, not a bug:
=NamedCrs.wkt= is a single slot that FlatGeobuf, GeoPackage and Shapefile's
=.prj= all read as WKT1/ESRI text.

*Why it is owed a warning.* This is the ordinary shape this rule already
covers -- a capability gap in the target -- and it belongs with
=Crs::downgrade_warning='s existing per-target arms. The identity survives
(=EPSG:28356= both sides), which is exactly why it is easy to miss and why it
went unnoticed until an in-place edit destroyed the original it could have been
compared against ([[file:edit-composability.org][edit-composability.org]] § THE
IN-PLACE HAZARD).

*Decided 2026-08-20: the dialect is information.* The alternative -- that the
identity is the whole of it and a dialect change is a rendering detail -- was
weighed and rejected, because [[file:crs-definition-output.org][crs-definition-output.org]]
established that a definition passes through *verbatim*, and a user who
supplied WKT2 via =--crs= and gets WKT1 back has lost the thing that contract
promised. A third option, warning only where the text was user-supplied rather
than synthesized from an authority code, was rejected as needing text
provenance the IR does not track.

*Shape.* A pre-write predictive check (§ mechanism 1) on the =Format::Parquet=
arm of =Crs::downgrade_warning=, firing when the CRS carries WKT and the target
is GeoParquet. Note it must *not* fire when the CRS reached the IR as PROJJSON
in the first place -- there is no dialect to lose then, and a GeoParquet →
GeoParquet run must stay silent.

** OPEN QUESTION -- does the unmodelled-member warning belong on cross-format runs?
/Consolidated here 2026-08-20./ This question was being carried in three
places at once -- =same-format-output.org= § OPEN QUESTIONS (deferred),
=edit-composability.org= D3, and implicitly by
=same-format-fidelity.org='s asymmetry -- which is how one question gets two
different answers. It lives here, because this doc owns what a *warning* must
say; the other three link to it.

*The question.* A reader discards what the IR does not model -- a GeoJSON
feature =id=, a collection =name=, foreign members. On a *same-format* run
that loss is indefensible and =same-format-fidelity.org= closes it outright,
so no warning is owed. On a *cross-format* run the same members are dropped
just as silently, and the target may or may not have been able to hold them.
Is a warning owed there?

*For:* the loss is identical and equally silent. A =.geojson= → =.fgb= user
losing their =id=s is no happier that the target had nowhere to put them.

*Against:* the target's incapacity is a genuine defence, and it is the exact
defence this rule already accepts everywhere else (=Crs::downgrade_warning=,
=m_downgrade_warning=). Warning anyway would either fire on almost every
conversion -- becoming noise the way § THE RULE warns against -- or need
hedging into uselessness.

*What would settle it:* the M1 inventory in
[[file:same-format-fidelity.org][same-format-fidelity.org]], which classifies
every unmodelled member per spoke. Until that exists the question is being
argued over a set nobody has enumerated. Two of the three classes may answer
differently -- an *identity* member (=id=, =name=) has a plausible claim to a
cross-format warning; an *opaque* one (a vendor foreign member) almost
certainly does not, since no target but its own could ever hold it.

*Do not answer it before M1.* The temptation is to settle it while writing one
of the plans that touches it, which is what produced three copies.

** HOW TO APPLY THIS TO FUTURE WORK
When adding a new format spoke, a new IR field, or discovering an existing
capability gap:
1. Ask, explicitly, "does every other current target actually represent
   this, or does at least one silently degrade it?" — the M8 mistake
   happened specifically because this question was answered by checking
   *one* tool's behavior instead of the actual capability.
2. If a gap exists, write the pre-write predictive check (§1) unless the
   loss is only knowable during actual encoding, in which case use the
   writer-returns-warnings shape (§2).
3. For a §1 check: add one line to =main.rs='s =collect_conversion_warnings=
   calling it. That's the whole wiring step — it already reaches all three
   =main.rs= entry points (single-file convert, GeoPackage fan-out read,
   GeoPackage fan-out write) through =collect_conversion_warnings=/
   =collect_layer_warnings=, so there is no longer a way to wire a new
   check into only *some* of them by mistake (the exact failure mode this
   note used to warn about, before the collection was generalized — see §
   GENERALIZED COLLECTION). For a §2 check: have the writer collect into
   its own =Encoded.warnings=-shaped field and call =print_warnings= on it
   where the writer's bytes get written.
4. Test both the *positive* case (the warning fires, with the right target
   named) and the *negative* case (a target that legitimately supports the
   feature stays silent) — mirroring this doc's own two new tests
   (=feature::tests::m_downgrade_warning_fires_only_for_m_incapable_targets_with_real_m=,
   =crs::tests::wkt_targets_warn_for_an_alphanumeric_code_even_with_wkt_present=).
5. Verify the warning's wording against what actually happens, not what
   you'd expect to happen — end-to-end through the real CLI, the same
   verification bar every other plan in this repo uses.
