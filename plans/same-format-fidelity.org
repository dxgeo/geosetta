This plan proposes a standing invariant for the crate, and the one mechanism
that can deliver it without the IR growing into a union of all nine spokes:

#+begin_quote
*Reading a format and writing the same format loses nothing.* A capability gap
in the target is a defence for dropping data; the target being the source's own
format is not.
#+end_quote

It is a *rule* plan, like
[[file:lossy-conversion-warnings.org][lossy-conversion-warnings.org]], not a
feature plan. Its milestones are a mechanism and a bug list; its real output is
a line every future spoke has to hold.

It also *gates* [[file:same-format-output.org][same-format-output.org]], and
inverts part of that plan's scope -- see § SEQUENCING.

** THE RULE, STATED PRECISELY
Two halves, and the second is what makes the first affordable:

1. *Same-format runs are information-lossless.* =geosetta a.f b.f= produces a
   file carrying everything =a.f= carried.
2. *Cross-format runs drop only what the target genuinely cannot record*, and
   warn when they do -- unchanged, and already the crate's rule
   ([[file:lossy-conversion-warnings.org][lossy-conversion-warnings.org]]).

The asymmetry is deliberate and is the whole point. =same-format-output.org= §
THE FIDELITY PROBLEM had already isolated the reasoning and stopped one step
short of drawing this conclusion: on a cross-format run, dropping a GeoJSON
=id= has a defence, because the target may have no slot for it. On a
same-format run "the target can't hold it" is provably false -- the target *is*
the source's format, and the source held it. This plan makes that observation
binding.

** WHY THE RULE IS RIGHT -- what the reference implementation promises
Per =plans/README.org= § Sourcing a fixture from a real tool, checked against
GDAL 3.13.2 before designing. The fixture was built to be as hostile as GeoJSON
allows: a collection =name=, a collection-level *foreign member*, both
=bbox=es, a feature =id=, a *feature-level* foreign member, a nested property
object, and an explicit =null= property.

*** Same format: GDAL loses nothing
#+begin_src text
$ ogr2ogr -f GeoJSON og.geojson exotic.geojson
$ cat og.geojson
{"type": "FeatureCollection", "name": "roads",
 "myExtension": { "vendor": "acme", "v": 2 }, "bbox": [ 0, 0, 10, 10 ],
 "features": [
 {"type":"Feature","id":42,"featureForeign":"keep-me",
  "properties":{"n":"a","nested":{"deep":[1,2,{"k":"v"}]},"nil":null},
  "bbox":[0.0,0.0,10.0,10.0],"geometry":{...}}]}
#+end_src
Every member survived, including the two foreign ones GDAL has no model for.

*** Cross format: GDAL drops exactly what the target cannot hold
The same input through a GeoPackage detour and back:
#+begin_src text
$ ogr2ogr -f GPKG mid.gpkg exotic.geojson && ogr2ogr -f GeoJSON back.geojson mid.gpkg
$ cat back.geojson
{"type": "FeatureCollection", "name": "roads",
 "myExtension": { "vendor": "acme", "v": 2 }, "bbox": [ 0, 0, 10, 10 ],
 "features": [
 {"type":"Feature","properties":{"n":"a","nested":{"deep":[1,2,{"k":"v"}]},
  "nil":null},"geometry":{...}}]}
#+end_src
Collection-level =name=, =myExtension= and =bbox= survived; the *feature-level*
=id=, =bbox= and =featureForeign= did not.

*** The asymmetry is the mechanism showing through
That split is the finding, and it is worth more than either result alone. GDAL
is not modelling =featureForeign= semantically -- if it were, it would have
carried it through the GeoPackage as easily as it carried =myExtension=.
It is holding an *opaque, driver-keyed* blob per feature and replaying it only
into the driver that produced it. Cross the driver boundary and the blob is
dropped, because nothing else knows what it means.

*** And the mechanism is legible on disk, not merely inferred
The GeoPackage written during the detour above carries it in plain text, in
=gpkg_metadata=:

#+begin_src xml
<MDI key="NATIVE_DATA">{ "name": "roads", "bbox": [ 0, 0, 10, 10 ],
                         "myExtension": { "vendor": "acme", "v": 2 } }</MDI>
<MDI key="NATIVE_MEDIA_TYPE">application/vnd.geo+json</MDI>
#+end_src

An opaque payload -- the source's own GeoJSON text, unparsed -- beside an
explicit *format tag*. That is § THE MECHANISM's =Native { format, payload }=,
already deployed, with =NATIVE_MEDIA_TYPE= doing exactly what D1's tag does.
The feature-level natives died on the detour and the collection-level ones did
not because only the latter had somewhere in the target to be written down.

So the rule this plan proposes is not an aspiration someone might reach; it is
what the reference tool already implements, down to the shape of the record.
§ THE MECHANISM adopts it deliberately rather than by convergence.

** WHAT "LOSSLESS" DOES NOT MEAN
Three carve-outs, all needed for the rule to be checkable rather than
rhetorical.

*** Information, not bytes
Byte-preserving pass-through is =cp=, and =same-format-output.org= D2 already
rules it out: a same-format run is a re-encode through the IR, never a copy.
Even GDAL is not byte-preserving here -- it emitted =0.0= where the input had
=0=, and reordered the members. Equivalence is defined at the IR level plus the
replayed natives (§ TESTING), not on the file.

*** A refusal honours the rule
Where a reader *hard-rejects* input it cannot model rather than silently
dropping it, the invariant is satisfied -- there is no lossy run, because there
is no run. Geosetta already does this in two places, both currently filed as
gaps in =plans/todo.org=: GeoParquet's list-of-structs / nested-list columns,
and a second geometry column
([[file:multi-geometry-columns.org][multi-geometry-columns.org]]).

*Name this explicitly so it is not "fixed" into a violation later.* The
tempting next step on both is to decode what is understood and drop the rest;
under this rule that trades a loud refusal for a silent loss, which is the
wrong direction. If they gain support, they gain it fully or they keep
refusing.

*** The invariant binds an invocation, not a pipeline
/Added 2026-08-20, after it caused a misfiling./ The rule covers one
=geosetta= run whose input and output formats match. It says *nothing* about a
sequence of runs whose net effect is a round trip.

This is not pedantry; it is the distinction that decides where a bug lives.
=edit-composability.org= § THE IN-PLACE HAZARD overwrites a =.fgb= via a
GeoParquet transit and loses the CRS dialect. That looks like a same-format
round trip and is not one: both hops -- =fgb= → =parquet= and =parquet= → =fgb=
-- are cross-format, and each is entitled to drop what its target cannot hold.
The loss is real and owed a warning, but by the *other* rule
([[file:lossy-conversion-warnings.org][lossy-conversion-warnings.org]]), and no
amount of same-format fidelity would have prevented it.

*The consequence for editing pipelines is sharp.* An external-edit loop is
lossless end to end only when the transit format *is* the endpoint format --
=geosetta in.fgb - --to fgb | tool | geosetta - out.fgb --from fgb=. Any other
transit is two cross-format conversions wearing a round trip's clothing. That
is a further, and stronger, reason
[[file:same-format-output.org][same-format-output.org]] is a prerequisite for
[[file:edit-composability.org][edit-composability.org]] rather than a
convenience, and it is what D5 is really protecting.

*** The IR ceiling is what is being raised, and it bounds the promise
Until the natives channel exists, "lossless" can only mean "lossless with
respect to the IR" -- and the IR is =geometry + properties + crs=
(=src/feature.rs=), so =id=, =name=, both =bbox=es and every foreign member die
at *read* time, before any writer is chosen. That is precisely the ceiling
§ THE MECHANISM raises. It is stated here so the rule is not read as already
satisfied by any format whose spoke happens to be tidy.

** THE DOMAIN OF THE RULE
/Decided 2026-08-20./ Two questions about what the invariant ranges over, both
settled deliberately and one of them against the recommendation that was on the
table. Recorded together because they compound: each widens the promise, and
they interact at exactly one place (§ The collision).

*** It binds the whole container, not just the layer
A =.gpkg= is not a collection; it is a database holding layers, a non-spatial
user table or two, =gpkg_metadata=, extension registrations, R*Tree indexes and
triggers, and possibly raster tiles. The invariant covers *all of it*.

*The alternative was to bind the layer* and give the container its own narrower
promise, on the grounds that preserving arbitrary SQLite content makes geosetta
a SQLite-preserving editor. That was recommended and *not* taken. The reasoning
for the wider choice, recorded so it is not re-opened by whoever meets the cost:
a user's =.gpkg= is one file, and a rule that silently exempts most of what is
in it is not the rule this plan set out to state. "Same format loses nothing"
that quietly means "loses nothing in the layer" is the kind of hedge § THE RULE
exists to remove.

*What it costs, plainly.* =run_geopackage_write= rewrites the whole file, so
everything it does not model is destroyed on write -- measured, and now defect 3
below. Satisfying the invariant means either copying unmodelled SQLite objects
structurally (their =sqlite_master= SQL text carries triggers, views and indexes
verbatim, which is mechanical but means the writer re-emits SQL it never parses)
or not rewriting at all. The second is a genuine option here and would change
the answer to the in-place question in
[[file:edit-composability.org][edit-composability.org]] D4 as well; it is worth
weighing on this plan rather than assumed away.

*The classification still does the work.* Container content sorts into D4's
three classes as cleanly as feature content does, which is what keeps the
obligation bounded rather than open-ended:
- *Derived* -- R*Tree tables and their triggers, =gpkg_ogr_contents= feature
  counts, =gpkg_contents= bboxes. Recomputed, never replayed. =--rtree= already
  builds the first from scratch.
- *Identity* -- layer names, =gpkg_contents= =identifier=/=description=.
- *Opaque* -- user tables, =gpkg_metadata=/=_reference=, =gpkg_extensions=,
  =gpkg_data_columns= and its constraints, QGIS-style =layer_styles=, views and
  triggers. Carried verbatim, understood by nothing.
So the Gpkg spoke's native payload has a mechanical definition -- *every object
in =sqlite_master= this crate did not itself write, plus every row of the
=gpkg_*= registry tables it does not populate* -- rather than an open-ended one.

*** It covers any file this crate reads without rejecting
Not merely geosetta's own output. The weaker scope was rejected as barely
covering the motivating case: the files users care about round-tripping were
written by QGIS, GDAL, DuckDB and Esri, not by this crate. It is also what makes
§ A refusal honours the rule load-bearing rather than a technicality -- under
this scope, "we read it" *is* the promise, so a reader that cannot be faithful
must decline instead.

The cost lands on the arbitrary-GeoParquet path, where a DuckDB- or GDAL-written
file carries key/value metadata, column statistics and row-group structure that
the reader currently walks past. M1 must inventory those the same way it
inventories GeoJSON's foreign members.

*** The collision -- where the two decisions meet
The two choices intersect at raster GeoPackages, and the intersection needs an
answer M1 cannot dodge. Geosetta is vector-only, but a =.gpkg= may carry tile
pyramids. Under *container* scope those tiles are in the domain; under *any
readable file* scope, geosetta does not get to keep reading such a file and
quietly drop them.

So one of two things must be true, and it should be chosen rather than
discovered: either the Gpkg reader *rejects* a file whose tile tables are
populated (the carve-out, and cheap), or those tiles are opaque natives carried
verbatim (faithful, and much less cheap). *Recommend rejecting*, and saying so
in the error -- a vector tool declining a raster container is a defensible
sentence; silently returning a =.gpkg= with the imagery gone is not.

*Decided 2026-08-23, and the recommendation above was not taken -- see D8.*
Tiles are *carried*; nothing is rejected. Both halves of the framing above
failed once the case was measured rather than argued: the refusal was drawn at
the *reader*, where nothing is lost, and "much less cheap" turned out to be
false under the three-class contract, which makes a tile pyramid the *easiest*
class rather than the hardest. /The paragraph above is left standing because
what it got wrong is instructive -- it is the same wrong-layer mistake as the
R*Tree warning that named layers it was not writing./

*The state it was decided out of was worse than "silently returning a =.gpkg=
with the imagery gone", which is what this section assumed today's behaviour
was.* Defect 3's warning did not even *name* the tile table: it was excluded
from the survey as though it were a layer. That is =handoff.org= § BUGS FOUND
entry 14, found while taking this decision and fixed the same day.
** WHAT VIOLATES THE RULE TODAY
Two kinds. The first kind is small, confirmed, and needs no new machinery.

*** THE DEFECTS that are bugs the moment the rule is adopted
Each was measured, and each was traced to the side that is actually wrong --
which in both of the first two is *not* the side the symptom suggests.

/Was four until 2026-08-20; defect 5 was found while reviewing defect 1 and is
the largest of them. Defect 6 arrived 2026-08-23. **The count came out of this
section's name at the same time**, on the precedent of "THE NINE DECISIONS" --
a heading that states a total is a heading that expires, and this one had
already been renamed once./

1. ~~*FlatGeobuf drops a null property cell.*~~ *FIXED 2026-08-20 (M4)*, both
   halves: =decode_properties= now yields every header column in header order,
   an omitted cell coming back =Null=, and the column's declared type rides in
   =FieldDecl::ty= so it no longer re-infers as =String=. /Verified/ on the
   original measurement -- an =allnull= column survives a round trip, and
   =geosetta='s GeoJSON output for a null-bearing FlatGeobuf is now identical
   to =ogr2ogr='s. The analysis that led there is kept below, because the
   second half of it was missed for most of a day.

   The wire is innocent: FGB encodes
   properties as sparse =[u16 col_index][value]= pairs
   (=flatgeobuf/writer.rs:343=), so a null is encoded by omission and *the
   column still stands in the header* -- confirmed by decoding the header,
   where an all-null column is present by name. The *reader* materializes only
   the columns a row carries, so an omitted cell returns as an absent key
   rather than a null one.

   /Re-measured and re-scoped 2026-08-20, after the FlatGeobuf spoke./ Still
   reproduces, and it is *two* losses rather than one. The plan previously
   called this a "one-sided fix in =flatgeobuf/reader.rs=", which names the
   right file and understates the size.

   *Loss 1 -- the cell.* A property null in *every* row has no key in any
   feature, so =infer_columns= never sees it and the column is gone. Its
   neighbours survive only because some other row happens to carry a value,
   which is why this is invisible in any fixture where every column has at
   least one value -- most of them.

   *Loss 2 -- the type, and this one is not in =reader.rs='s gift.* Fix the
   cell and an all-null column still comes back *=String=*: with no values to
   infer from, =infer_columns= falls back to =ColumnType::String= (the
   "columns whose values were all null default to String" line). The reader
   /knows/ the real type -- it reads =Column.type(1)= in order to decode
   values at all -- but [[*D1 -- opaque passthrough, never semantic modelling -- with one named exception][=FieldDecl=]]
   models =width=/=precision=/=scale=/=nullable=/=unique=/=primary_key= and
   *not type*, so there is nowhere in the IR to put it. /Measured/ against a
   real =ogr2ogr= FlatGeobuf carrying an all-null =Integer= column (built from
   a =.csv= + =.csvt=, since no GeoJSON input can declare one):

   #+begin_src text
   on disk:       cnt: Integer (0.0)
   GDAL fgb->fgb: cnt: Integer (0.0)    preserved
   geosetta:      column absent entirely
   #+end_src

   *The unset-vs-null question is settled, and it is not a fork.* An earlier
   draft of this entry held that restoring an omitted cell as null diverges
   from GDAL, which maps FGB omission to OGR /unset/ -- true of =ogrinfo='s
   *display* convention and misleading about everything else. =ogr2ogr=
   converting such a file to GeoJSON writes =null= for every declared column
   in every feature, turning sparse input rectangular. More to the point,
   *this crate already made the choice four times over* /(measured, one input
   through each spoke)/:

   | via         | result                                            |
   |-------------+---------------------------------------------------|
   | GeoParquet  | =null= for every column in every feature           |
   | GeoPackage  | identical                                          |
   | CSV         | identical                                          |
   | Shapefile   | rectangular, =""= for strings (dBase has no null)  |
   | FlatGeobuf  | *keys absent* -- the outlier                       |

   Every rectangular spoke materializes every column for every feature, and
   the first three are byte-identical to GDAL's own output. FlatGeobuf is
   alone because it is the only format that is rectangular in its *header* and
   sparse in its *rows*. And =schema::materialize= already collapses =None=
   and =JsonValue::Null= to the same =Cell::Null=, so the IR has no /unset/ to
   protect. Restoring the null is not a new policy; it ends an inconsistency.
2. ~~*GeoPackage loses booleans.*~~ *FIXED 2026-08-20 (M4)*: the reader parses
   each column's declared SQL type out of the table DDL and a declared
   =BOOLEAN= holding =0=/=1= comes back as a boolean. Also a reader defect,
   and the writer is spec-correct: =geopackage/writer.rs:449= declares the
   column =BOOLEAN= and =:459= stores 0/1, which is what the GeoPackage spec
   requires of SQLite. The declared type is on disk and unread --
   =geopackage/reader.rs= has no notion of a declared column type at all,
   mapping storage classes straight to JSON. Fix reads the declaration.

   *Defects 1 and 2 are the same bug wearing two formats* /(found 2026-08-20,
   reviewing defect 1)/. Both are *a declared column type sitting on disk,
   unread, because the IR will not hold one*: GeoPackage declares =BOOLEAN=
   and the reader sees only SQLite's =INTEGER= storage class; FlatGeobuf
   declares =Integer= and the reader cannot keep it once the column has no
   values to re-infer from. Neither closes by reading harder -- both want the
   same affordance, a *declared type on =FieldDecl=*, which is also its
   natural home: FlatGeobuf's =Column.type(1)= is slot 1 of the very table
   whose slots 4--9 =FieldDecl= already models. This is a better reason for
   M4 to ship them together than "both are free-standing", which is how they
   were paired before anyone noticed they share a fix.

   *The precedence rule that comes with it*, mirroring =declared_or=: *the
   declaration wins where the data is silent; the data wins where it
   contradicts.* An all-null =Integer= column returns =Integer=; a column a
   middle stage has filled with strings is not forced back into an integer
   and truncated. Same reasoning that made a declared width a floor and never
   a ceiling -- a stale declaration may not destroy a value a later stage
   produced.

3. *A GeoPackage same-format run destroys most of the container.* Measured on
   a =.gpkg= carrying two feature layers, a plain non-spatial user table,
   dataset metadata and R*Tree indexes, run through =geosetta g2.gpkg g2.gpkg=
   -- the one same-format path that works today, and in place:

   #+begin_src text
   before: roads  extra  side_notes  gpkg_metadata  gpkg_metadata_reference
           gpkg_extensions  gpkg_data_columns  gpkg_ogr_contents
           gpkg_tile_matrix(_set)  rtree_roads_geom*(4)  rtree_extra_geom*(4)
   after:  roads  extra  gpkg_contents  gpkg_geometry_columns
           gpkg_spatial_ref_sys
   #+end_src

   Exit 0, no warning. =ogr2ogr= on the same input kept all of it. The two
   feature layers survive; the user's own table does not.

   Unlike defects 1--2 this one *does* need the mechanism (§ THE DOMAIN OF THE
   RULE), so it could not ship with M4. /(This sentence read "unlike defects
   1--3" until 2026-08-21, which made it exempt itself; it always meant the two
   defects M4 shipped.)/ But it is a silent data drop under the rule that is
   *already* in effect
   ([[file:lossy-conversion-warnings.org][lossy-conversion-warnings.org]]), so
   the warning is owed now regardless, and
   [[file:same-format-output.org][same-format-output.org]] M3's same-file
   refusal would independently stop the in-place form of it.

   *The warning shipped 2026-08-21; the fix is still M3b's.*
   =geopackage/container.rs= surveys the container about to be rewritten and
   reports, per § THE RULE, what will not survive it. The measurement above,
   re-run against =tests/fixtures/gdal_hostile.gpkg=, now says so out loud:

   #+begin_src text
   warning: writing a GeoPackage rewrites the whole file, and this writer
   reproduces only the feature layers and the tables they require -- so the rest
   of tests/fixtures/gdal_hostile.gpkg is not carried: gpkg_ogr_contents
   (2 rows), side_notes (1 row), gpkg_metadata (1 row), gpkg_metadata_reference
   (1 row); 2 empty tables; 14 other schema objects (triggers, views, indexes).
   The layers themselves are written in full.
   warning: tests/fixtures/gdal_hostile.gpkg carries an R*Tree spatial index on
   cities and second; the output is written without one -- pass --rtree to
   rebuild it.
   #+end_src

   *Three things it does deliberately*, each of which is D4 doing the work
   § THE DOMAIN OF THE RULE predicted it would:
   1. *The index is a separate warning, not an item in the first.* It is
      *derived*, so it is not destroyed content but content not rebuilt, and it
      has a one-flag remedy the first message would bury.
   2. *An R*Tree's =gpkg_extensions= registration is not counted as a loss.*
      Its rows travel with the index they declare, so counting them would
      report one loss twice -- which the first draft did, until our own
      =--rtree= output was fed back in and warned about the very table it had
      just written. Rows registering any *other* extension are a real loss and
      are named. This is why the survey counts =gpkg_extensions='s rows rather
      than reporting its existence, alone among the tables.
   3. *Layers are out of scope entirely.* The warning is about the container
      *around* the layers, which also keeps =--layer= out of it: a deliberately
      selected subset must not read as an accidental loss.

   *It is silent on every GeoPackage this crate writes itself*, which is the
   § THE RULE noise bar -- a warning that fires on the common case teaches
   users to ignore it. Pinned by
   =a_container_this_crate_wrote_itself_says_nothing= and four siblings in
   =geopackage/container.rs=.

   *The one thing to know before M3b edits it:* =container.rs='s =REPRODUCED=
   is a *statement about the writer* -- the tables =writer::build= emits
   unconditionally. A new always-emitted table has to be added there in the
   same pass, or this starts warning about content that in fact survives. Its
   module doc says so; this is the second place, because the coupling is the
   kind that goes unnoticed until it is wrong.

4. ~~*FlatGeobuf discards the collection's name.*~~ *FIXED 2026-08-20* with the
   FlatGeobuf spoke (M3). =flatgeobuf/writer.rs= wrote the constant string
   =geosetta= into the header's =NAME= slot -- a first-class field the format
   provides precisely for this -- and the reader never read it back. Now the
   writer writes =fc.name= (and *nothing* when there is none, rather than
   inventing one), the reader models it, and =main.rs= consults it before
   falling back to the input's file stem.

   *This does not on its own close the layer-duplication failure* in
   [[file:edit-composability.org][edit-composability.org]] D4. /Measured after
   the fix:/ the loop still appends a =layer= table, because the *GeoPackage*
   reader does not set =fc.name= from the table name, so the FGB it writes has
   no name to carry. That half lands with the GeoPackage spoke.
5. ~~*Every spoke narrows a declared column type to the IR's four.*~~

   than a tidiness question: the source stated a fact about its own schema and
   the output does not repeat it.

   /Measured, geosetta's output against =ogr2ogr='s, table by table:/

   | table | what is missing from this writer's DDL |

   casualty, and no test in the tree looks at it. A conformance validator

   requires is a file making a weaker promise than its format allows.

   *It was gated on the same work as D10*, and that is the useful part: fixing

*** The structural violation: everything the IR never modelled
The rest is the ceiling. =same-format-output.org= enumerated it for GeoJSON

*** Defect 5 was a class, not a list -- the recast matrix, 2026-08-21
Defect 5 closed with M4 across all four declaring spokes, and then *three more
instances of it shipped anyway*: =REAL= read back 32-bit (found by the
GeoPackage spoke), GeoPackage writing every unsigned width as the same-width
*signed* spelling, and a =DateTime= carrying ISO 8601's =Z= degrading to text on
the GeoParquet writer's parse side. None was a hard problem. All three survived
because *every test that touched the type surface was an example test* -- one
type someone thought of -- while the surface itself is eight =match= tables (a
reader and a writer for each declaring spoke) over sixteen =DeclType= variants
and some forty on-disk spellings.

*What was built instead of a fourth example.*
1. *=DeclType::admits=* -- the widening relation. Derived from =int_range= for
   integers, so a new width joins the order by declaring its range. Deliberately
   narrow: =String= admits *nothing*, because text holds the bytes of a
   =DateTime= and none of its meaning, and a relation that called that lossless
   would define this defect out of existence.
2. *=Format::recast(DeclType)=* -- what each format turns each type into. A
   *ninth* statement of a mapping that lives in eight places, which is only safe
   because a test proves it matches all eight (below). Its doc says so, at
   length, because the temptation to consult it without maintaining it is the
   whole risk.
3. *=FeatureCollection::decl_recast_warning=* -- the fourth entry in
   =collect_conversion_warnings=, firing only where =admits= fails.
4. *The sweeps.* =every_declared_type_survives_or_is_admitted= runs all sixteen
   types through all four declaring formats and asserts the real answer equals
   =Format::recast='s, then that the result either admits the original *or
   warns*. Its sibling =an_undeclared_column_never_acquires_a_narrower_declaration=
   covers the path the =REAL= bug actually lived on -- an *undeclared* double,
   written =REAL=, read back as =Float32=. The declared path was closed the
   whole time, so no amount of declared-only testing could have found it. **This
   is the lesson worth keeping: a self-round-trip over declared values is not
   sufficient, because a writer never emits the spelling it cannot read.**
5. *Four inbound tables*, one per declaring reader, asserting what each on-disk
   spelling *means* rather than that it parses. =geopackage/reader.rs= now
   states, with the spec citation, that =REAL= is eight bytes.
6. *=tests/gdal_types.rs=* -- the differential check, =#[ignore]=d. It does not
   hardcode GDAL's vocabulary, which would only move the guess; it compares GDAL
   reading the input against GDAL reading our output. That is precisely the
   procedure that found both bugs, written down so it runs on demand rather than
   when someone thinks of it.

*** The blob the schema check could not see -- 2026-08-21
The recast matrix above asserts *declarations*. It was green while a
=gpkg -> gpkg= run **destroyed every blob in the file**: the =BLOB= declaration
survived intact, so the types matched on both sides, and =X'0102'= came back
=NULL=. The GDAL cross-check missed it for the same reason -- it diffed
=ogrinfo -so=, which prints the schema and no values.

*The cause was one line and the reason behind it was structural.*
=geopackage/reader.rs= mapped =Value::Blob(_) => JsonValue::Null=, with the
comment "non-geometry blobs have no GeoJSON representation" -- true, and the
wrong conclusion: the IR's property type is =JsonValue=, so a blob had nowhere
to *live*, and returning `Null` was the only option the type system offered.
FlatGeobuf did the same thing (decode the length, skip the payload, yield
=Null=) and GeoParquet rendered hex text. All three then *declined to declare*
=Binary=, correctly, because declaring a type whose values are destroyed is a
promise the value side cannot keep.

*The fix was the IR, not the spokes.* =JsonValue::Binary(Vec<u8>)= --
acknowledged in its doc comment as making the type's name a slight lie, with
the precedent cited: =Number { is_int }= is not a JSON distinction either, and
exists for the same reason. The compiler then enumerated the blast radius
exactly as D3 intends -- eight sites, every one a writer that had to decide
what it does with bytes.

*Two spokes gained a capability they already had on disk*: FlatGeobuf's
=ctype::BINARY= (14) had been in the reader's constant table and unreachable
from the writer, which kept *its own duplicate copy of all fourteen constants*
-- collapsed to one shared table in the same pass, since two tables of magic
numbers for one on-disk enum is precisely the shape the =REAL= bug came in.
GeoParquet's unannotated =BYTE_ARRAY= is binary in Parquet's own model (text
carries =UTF8=); it was being decoded as a UTF-8 string, which both rejected
genuine binary outright and gave the ones that happened to decode a =String=
declaration.

*And =Date= stopped degrading to text.* FlatGeobuf has no =DATE=, but it has
=DATETIME=, and that is what =ogr2ogr= writes for the same hop /(measured: a
GeoPackage =DATE= column arrives in FlatGeobuf as =DateTime=)/. Still a recast
-- a date is not an instant -- so it still warns, but temporal beats text.

*A datetime stopped losing its time zone.* Once the type survived the transit,
the *value* turned out not to: =format_timestamp= emitted no =Z=, so a
=gpkg -> parquet -> gpkg= round trip turned =12:00:00+00= into an unzoned
=12:00:00=. =TIMESTAMP_MILLIS= counts from the Unix epoch and *is* UTC, so the
designator is now emitted.

*What this cost, and the rule it bought.* Three of those four were found by one
change: adding a *value* comparison beside the type comparison, in both the
in-tree sweep (=a_value_survives_wherever_its_declared_type_does=) and the GDAL
check. **A type-fidelity test that never looks at a value can be perfectly
green while the values are being destroyed.** That belongs beside the
undeclared-column lesson above; both are cases where the obvious test shape has
a blind spot exactly where the bugs were.

*Two findings recorded rather than fixed*, because both are policy calls rather
than defects: a =Json= column round-trips through GeoParquet as a *parsed
object* rather than its original text, which is not byte-preserving (a source
with ={"a": 1}= loses the space) and is an instance of the open canonicalisation
question in =native-inventory.org= § QUESTIONS; and Shapefile rounds an
undeclared double to =dbf.rs='s =DECIMALS= fallback of 6, silently, where GDAL
uses 15.

*** The number model -- 2026-08-21
Found by pulling on what looked like a canonicalisation question. A =Json=
column round-trips through GeoParquet as a *parsed object*, so its text is not
byte-preserved; that part is genuinely § QUESTIONS' open canonicalisation
issue and is left alone. But measuring it turned up the real problem
underneath, which is not about JSON at all:

#+begin_src text
  gpkg -> gpkg, a plain INTEGER column:
    9007199254740993  ->  9007199254740992
#+end_src

=JsonValue::Number= was an =f64= plus an =is_int= flag. An =f64= carries
integers exactly only to 2^53, so *a same-format run silently changed a 64-bit
integer* -- a type both GeoPackage and GeoParquet define as 64-bit and neither
could round-trip. Past =i64::MAX= the serializer's =as i64= saturated, so
=12345678901234567890= came back =9223372036854775807=: a *specific wrong
number* rather than a nearby one.

*The flag was the tell.* =is_int= existed to remember something the
representation had already discarded. The fix is two variants -- =Int(i64)= and
=Float(f64)= -- so an integer never touches a double: the parser goes straight
to =i64=, =materialize= uses =as_i64=, and the GeoPackage and GeoParquet
readers hand back =Int= directly. A JSON integer too wide for an =i64= becomes
=Float=: lossy, but *honestly* lossy, and never a different integer.

*Whole floats keep their =.0=*, which is what makes the split visible in
output: =1.0= stays =1.0= instead of collapsing to =1=. That matches =ogr2ogr=
/(measured: it round-trips ={"whole_float":1.0,"real_int":7}= unchanged, and
writes coordinates as =[1.0,2.0]=)/. It also immediately caught
=geojson/mod.rs='s two writers disagreeing -- the direct writer formatted its
own coordinates while the tree serializer went through =JsonValue= -- so both
now call one =write_json_f64=, and =direct_writer_matches_tree_serialization=
is what holds them together.

*The sweep now uses values past 2^53*, because it did not before: every
declared type through every declaring format, and the =Int64= case was small
enough to survive a double. A sweep can be exhaustive over *types* and still
miss a whole class by being unadventurous about *values*.

*** Shapefile's decimal fallback -- 2026-08-21
=dbf.rs='s =DECIMALS= was 6, so an undeclared double lost everything past six
decimal places, silently: =1.23456789012345= was written =1.234568=. =ogr2ogr=
writes =Real (24.15)= for the same input. Now 15 -- the reference
implementation's answer, and about as many decimal digits as an =f64= carries
meaningfully. /Measured after: the number's text is byte-identical to =ogr2ogr='s
(=1.234567890123450=); only the field *width* differs -- =N(17,15)= here
against =N(24,15)= there, the difference being trailing pad -- because this
writer sizes the field to the data where GDAL uses a fixed 24, and a declared
=precision= still wins over both. Whether that sizing policy is the right one
is now § OPEN QUESTIONS' first entry; it is not part of this change./

*One consequence had to be handled rather than accepted.* Fifteen decimals make
the fixed-point text longer, so the 255-byte =.dbf= limit arrived at lower
magnitudes -- values around =1e239= that used to write began to error. The
fallback is now *trimmed to fit*: =1e240= is 241 characters before the decimal
point and an =f64= carries ~17 significant digits, so those decimals were
padding, never information. A *declared* scale is left alone to fail loudly,
because that is the source stating a fact.

*** Three narrowings survive, all pinned by name in the sweep
Every one is a genuine capability gap rather than a mapping bug: =Binary= degrades everywhere
but GeoPackage (the *IR* has no byte-level cell, so binary arrives as hex text);
FlatGeobuf has no =DATE=; dBase has no JSON, timestamp or blob field type. A new
entry cannot appear in that list without someone editing it.

*Measured after, through GDAL:* every one of the twelve GeoPackage declared
types survives =gpkg -> gpkg= with =ogrinfo= reporting identical field types,
and a transit through FlatGeobuf or GeoParquet changes *exactly* the columns
=Format::recast= predicts and the CLI warned about -- no more, and no fewer.

** THE ARCHITECTURAL BILL -- and why the obvious approach is wrong
The obvious way to satisfy the rule is to teach the IR the missing members:
=Feature.id=, =FeatureCollection.name=, per-feature =bbox=. *Rejected*, and the
reason is the one thing this plan most needs to record, because the idea will
recur.

*Semantic modelling makes the IR the union of every spoke's expressiveness.*
The IR is shared by all nine formats. Model =id= and every one of the nine
writers must decide what to do with it; then the next format arrives with
=.dbf= field widths, or a Parquet row-group layout, or GeoPackage's extension
rows, and either the IR grows again -- touching all nine spokes -- or that
format is silently exempt from the rule. Cost grows as formats × members, in
exactly the dimension the hub-and-spoke design exists to keep flat
([[file:../../architecture.org][../../architecture.org]] § WHY THIS STRUCTURE
HELPS: "whole files fit in working context").

Worse, most of these members have *no cross-format meaning to model*. A =.dbf=
field width is not a fact about a feature; it is a fact about how one format
stores it. Promoting it to the IR asserts a generality it does not have.

** THE MECHANISM -- one opaque, format-tagged channel
Adopt GDAL's shape (§ WHY THE RULE IS RIGHT). The IR grows *one* field, not one
per member:

#+begin_src rust
/// What a reader recovered but the IR does not model, kept verbatim and
/// tagged with the format that produced it.
pub struct Native {
    pub format: Format,
    pub payload: NativePayload,
}

// on Feature:            pub native: Option<Native>,
// on FeatureCollection:  pub native: Option<Native>,
#+end_src

The contract, in three lines:
- A *reader* stashes what it did not model, verbatim, tagged with its own
  =Format=. It stashes nothing when it modelled everything -- =None= is the
  common case.
- A *writer* replays the payload *if and only if* =native.format == self=.
- On a mismatch it ignores the payload and warns through the existing
  discipline. A mismatch is not an error; it is an ordinary cross-format run.

*Why the tag is load-bearing.* It is what makes the channel unable to corrupt a
cross-format run: a GeoJSON foreign member can never leak into a FlatGeobuf
writer, because the writer never looks at a payload that is not its own. The
GeoPackage-detour experiment is the evidence that this is the right boundary --
GDAL's feature-level natives died on exactly that line.

*Why adding a format stays cheap.* A new spoke populates and consumes its own
payload variant and touches no other spoke. The rule costs each format the
knowledge of its own format, which it necessarily already has.

** DECISIONS

*** D1 -- opaque passthrough, never semantic modelling -- with one named exception
§ THE ARCHITECTURAL BILL. The IR keeps meaning *only* what all nine formats
share; everything else rides in a payload the hub never inspects.

*The exception, and it is a real one: the collection's name* (decided
2026-08-20). It earns modelling on the test D1 otherwise refuses, because four
spokes have a *first-class slot* for it rather than a foreign-member bag --
GeoJSON's =name=, FlatGeobuf's header =NAME=, GeoPackage's table name and
=gpkg_contents.identifier=, and Shapefile's filename. A member that four
independent format specs each chose to model is not a quirk of one wire format,
which is the whole basis for keeping things out of the IR.

It is also the member whose absence is *actively corrupting files today*:
=flatgeobuf/writer.rs:181= writes the constant =geosetta= into FlatGeobuf's
name slot, so a layer name cannot survive an FGB transit, and
[[file:edit-composability.org][edit-composability.org]] D4 measures the
consequence -- a GeoPackage edit loop silently duplicating its layers instead
of replacing them.

*And the column schema* -- =width=, =precision=, =scale=, =nullable=,
=unique=, =primary_key= (decided 2026-08-20). Same test, four slots:
Shapefile's =.dbf= field descriptor, FlatGeobuf's =Column= table, GeoPackage's
column declarations, GeoParquet's =ARROW:schema=.

The reason it *must* be modelled rather than carried opaquely is D5. A native
does not cross a pipe, so a Shapefile-tagged width payload never reaches a
middle stage; but a *modelled* field rides in the transit's own first-class
slot, which means an external tool can *read and update the schema mid-flight*:

#+begin_src text
geosetta a.shp - --to fgb | tool | geosetta - b.shp --from fgb
#+end_src

The tool widens =width: 80= to =120= alongside the value it lengthened, and the
Shapefile writer honours the declaration it was handed. No native could do
that.

*This also retires a fourth D4 class that was briefly proposed and is not
needed.* The concern was that replaying a declared width verbatim could
truncate data a caller had lengthened, which argued for a "declared minimum"
class carrying =max(declared, required)=. It does not arise: a single geosetta
invocation cannot lengthen a property value (=--sort-hilbert= reorders,
=--crs= relabels, =--rtree=/=--envelope= build indexes, =--layer= selects), so
a verbatim width is still valid at write time by construction. The one place it
*can* arise -- a route (a) caller mutating between =read_features= and
=write_features= -- is already covered: =dbf::write= truncates at a char
boundary *and warns* (=dbf.rs:207--216=), and errors where truncation cannot
safely paper over the loss. *D4 stays at three classes.*

*=bbox= is* not *the same case*, though it looks like one: it too appears in
several formats, but it is *derived*, so D4 recomputes rather than models it.

*A third member joins the exception, 2026-08-20: the column's declared type.*
It passes the same two tests the width did. Four spokes give it a first-class
slot (FlatGeobuf's =Column.type(1)=, GeoPackage's column declaration,
Shapefile's =.dbf= field type, GeoParquet's =ARROW:schema=), and it must cross
a pipe for the same D5 reason -- a type that rode as a native would be
invisible to the middle tool that just changed a column's values. It arrived
by a different route than the width, though, and the route is worth recording:
not from the inventory, but from *defects 1 and 2 turning out to need the same
thing* (§ THE DEFECTS). An all-null FlatGeobuf column re-infers as =String=
without it, and a GeoPackage =BOOLEAN= has nowhere to be remembered. See M4.

*** D2 -- the payload is an enum, not =Box<dyn Any>=
Forced, not chosen: =Feature= and =FeatureCollection= derive
=Debug, Clone, PartialEq= (=src/feature.rs=), and =dyn Any= satisfies none of
them. A small enum with one variant per format that needs a payload keeps all
three derives, keeps the compiler enumerating the blast radius on change (the
advantage =architecture.org= names), and costs one match arm per spoke.

Payload contents are the spoke's business -- raw =JsonValue= for GeoJSON,
whatever FlatGeobuf's unmodelled header fields want. =Rc= where cloning would
otherwise be expensive; the IR already uses it for property keys.

*** D3 -- =None= when nothing was unmodelled, so the common case costs nothing
The channel must not add a per-feature allocation to a wide table that had no
foreign members. A reader populates =Some= only when it actually discarded
something. This keeps the =performance.org= wide-table benchmarks honest and
should be asserted there, not assumed.

*** D4 -- classify natives; do not replay derived data blindly
The most dangerous thing this mechanism could do is faithfully replay a
=bbox= that stopped being true. Three classes, and each spoke's inventory
assigns every member to one:

- *Opaque* -- foreign members, vendor extensions, =.dbf= field widths. Replay
  verbatim. Nothing in geosetta can or should interpret them.
- *Identity* -- feature =id=, collection =name=. Replay verbatim, and they
  survive reordering because they travel with their feature (=--sort-hilbert=
  permutes features, not their natives).
- *Derived* -- never replayed, because replaying is how derived data goes
  stale. But *what replaces it splits by risk profile*, not by derivedness
  (decided 2026-08-20):
  - *Derived information* -- both =bbox=es, =gpkg_contents= extents. A missing
    extent is a real loss and a *stale* one is actively dangerous:
    =envelope.org= records that GDAL *trusts* a cached GeoPackage envelope on
    the spatial-filter path, so a wrong one silently drops features that really
    intersect the query box while unfiltered reads look perfect.
    *Always recomputed* from the geometry actually being written. Already
    correct today -- verified that =gpkg_contents= bboxes survive a
    =gpkg= → =gpkg= run intact.
  - *Derived capability* -- the R*Tree and its triggers, =gpkg_ogr_contents='s
    feature counts. Losing these costs query speed, not data, and any tool can
    rebuild one. *Rebuilt when the source carried one*, whether or not
    =--rtree= was passed.

  The capability rule is deliberately narrower than "turn =--rtree= on by
  default": it restores what the input had and says nothing about a file that
  never had an index, which is
  [[file:spatial-index.org][spatial-index.org]]'s own open question and stays
  there. The machinery is already in place and already validated --
  =geosetta r1.gpkg r2.gpkg --rtree= rebuilds the index for *every* layer from
  scratch, =rtreecheck()= returns =ok= on the result, =ogrinfo= reads it back,
  and =gpkg_extensions= is recreated to register it. What is missing is only
  the trigger: today the source's index is destroyed unconditionally and
  rebuilt only on request.

This class matters most under
[[file:edit-composability.org][edit-composability.org]], where the whole point
is that a middle stage changed the geometry between read and write.

*** D5 -- the natives channel does not cross the pipe
A native payload lives in the IR, in one process. It does not survive
=geosetta ... - | tool | geosetta - ...= unless the transit format is the same
format *and* its own natives are replayed into the stream -- which, for a
same-format transit, is exactly what D1's contract delivers, and is one more
reason =same-format-output.org= is a prerequisite rather than a nicety.

Stated as a decision because the alternative -- a side-channel carrying natives
around the middle tool -- is Route 3 from =edit-composability.org= wearing a
different hat, and is rejected for the same reason: no external tool would know
what to do with it.

*** D7 -- the caller D1 and D5 argue for must be able to *name* the types
/Decided 2026-08-21, after the argument turned out never to have been checked./

D1 models the column schema in the IR rather than carrying it as a native, and
D5 explains why: a native does not cross a pipe, so *only a modelled field lets
an external tool widen a declaration mid-flight alongside the value that
outgrew it*. Both are arguments about a **caller**. Neither had ever been run
from where a caller stands.

*What was actually true.* =Feature::properties= is a public field of type
=JsonValue=; =FieldDecl::ty= is a public field of type =DeclType=; and both
types lived in =pub(crate)= modules, so **neither could be named outside this
crate**. A consumer could read a declaration and could not construct one. They
could read a feature's properties and could not build a feature that had any.
The library was a read-and-convert API whose documentation described an
edit-in-the-middle API.

The tell was found by accident: adding =JsonValue::Binary= on the same day was
a new variant on a public enum -- normally a breaking change for every
downstream =match= -- and it broke nothing, because there were no downstream
matches possible.

*The decision.* Export =JsonValue= and =DeclType=, both =#[non_exhaustive]=.
- *Exported*, because a modelled field a caller cannot name is a native with
  extra steps, and D1's whole cost is justified by that caller.
- *=#[non_exhaustive]=*, because both vocabularies are explicitly open --
  =DeclType='s own doc says there is no =Decimal= or =List= "because no spoke
  this crate reads declares one today", and four spokes are unbuilt. External
  code must carry a wildcard arm; adding a variant stays non-breaking.
- *Inside the crate the attribute does nothing*, which is what makes it safe
  here: every exhaustive match the recast suite depends on (=hub=,
  =sql_type_for=, =representative_value=, =position_of=) keeps its compile-time
  completeness guarantee. The binary is a separate crate but never matches on
  either type.

*What stayed internal, and why that is not the same wart.* =ColumnType=, =Cell=
and =Column= are the writer-side materialization, reachable from nothing
public once =DeclType::hub= and =FieldDecl::type_for= are demoted to
=pub(crate)= -- which they now are, since both take or return types that stay
internal and neither means anything to a consumer. Exporting them later is
non-breaking; exporting them now would commit to a shape that is a writer
detail.

*The enforcement is =tests/public_api.rs=*, and it has to live in =tests/=:
an integration test compiles as a *separate crate*, so it sees the API a real
dependent sees. A unit test inside =src/= cannot check this property at all,
because inside the crate everything is nameable -- which is precisely why the
gap survived this long. It builds a collection by hand, and it runs D5's own
scenario: read, widen a declaration in the middle, write, and confirm the
widened declaration reaches the file.

*** D6 -- the rule binds new spokes, and the enforcement is the fixture registry
/Decided 2026-08-20./ =format.rs='s module doc splits a new format's
obligations into "the compiler catches these" and "nobody catches these." The
fidelity obligation goes in the *first* list -- which an earlier draft doubted
was possible.

*Not* via a =Format::native_members() -> &'static [&'static str]= constant.
That was the obvious candidate and it is a claim, not a mechanism: an impl
returning =&[]= is simultaneously the correct answer for a spoke that genuinely
discards nothing and the exact shape of having forgotten, so it enforces a
*declaration about* the property rather than the property.

*The mechanism is an exhaustive match in the test harness*, with no catch-all
arm:

#+begin_src rust
fn hostile_fixture(f: Format) -> Fixture {
    match f {
        Format::GeoJson => ...,
        Format::Parquet => ...,
        // no `_ =>` arm: a new variant fails to compile the test suite
    }
}
#+end_src

The round-trip test iterates it and asserts real losslessness (§ TESTING). A
new spoke cannot build the suite without supplying a fixture, and cannot pass
without actually being faithful. The =&[]= ambiguity has nowhere to arise --
there is no empty fixture that passes a losslessness assertion for a format
that loses things.

*This pattern also fixes a live instance of the failure mode.*
=format.rs='s own =display_name_uses_each_format_s_own_spelling= pins all nine
spellings from a hand-written *array literal*, so a tenth variant compiles,
passes, and is silently uncovered -- the precise staleness D6 exists to prevent,
already present next to the rule. It converts to the same exhaustive-match
shape and should, in this plan rather than filed separately: leaving a working
example of the anti-pattern beside the new rule is how the rule gets read as
optional.

*** D8 -- a tile pyramid is carried, and no file is rejected for holding one
/One consequence, found 2026-08-23 while scoping the carrying channel: a tile
pyramid carries =srs_id= *references* -- in its =gpkg_contents= row and its
=gpkg_tile_matrix_set= row -- and =resolve_srs= renumbers, handing out
synthetic ids from 100000 in layer order. So carrying a pyramid is not purely a
byte move: those references have to be rewritten into the new numbering, or
=fk_gc_r_srs_id= makes =foreign_key_check= say so. See
[[file:container-reconciliation.org][container-reconciliation.org]] § 1./

/Decided 2026-08-23, overturning the recommendation in § The collision./

That section left one of two things to be chosen: the Gpkg *reader* rejects a
file whose tile tables are populated (recommended, "cheap"), or tiles become
opaque natives carried verbatim ("faithful, and much less cheap"). *Neither
half of that framing survived measurement.*

**The refusal was drawn at the wrong layer.** The loss is on the *write* path:
=run_geopackage_write= rewrites the container, and a =gpkg -> geojson= read
destroys nothing at all. Rejecting at the reader punishes the one path that was
never lossy -- a user extracting a vector layer out of a mixed container gets
refused over imagery they were not touching. *This is defect 3's warning
mistake in another place*: the R*Tree message named layers that were not being
written (=handoff.org= § WHAT CHANGED, 2026-08-21 review, item 1), because the
guard sat where it could *see* the content rather than where the damage was.
A carve-out, if one is ever wanted, belongs on the write path.

**And "much less cheap" does not survive the three-class contract.** Tiles are
*independent* content by that classification -- they depend on no layer, and no
middle-stage edit can invalidate them. A tile table is an ordinary rowid table
with a BLOB column, so carrying one is the same operation as carrying
=side_notes=, with no raster-specific code anywhere. Under the contract M3b has
to build regardless, *the raster case is the easiest class, not the hardest.*

*What it does cost, stated so nobody discovers it:* memory. =read_rows= decodes
a table to =Vec<Vec<Value>>=, so a large pyramid is held decoded and re-encoded.
That is true of any large carried table and is not specific to imagery; it is an
argument for streaming a carried table someday, not for refusing this one.

*Does this make geosetta a raster tool?* No, and the distinction is worth
keeping sharp: it reads no tile, decodes no image, and answers no question about
one. It *preserves bytes it did not understand*, which is exactly what D1's
opaque channel does for every other format. The rule in § THE RULE asks for
nothing less.

*** D9 -- =run_geopackage_write= keeps rewriting; the question is closed
/Decided 2026-08-23. The conclusion is the one § MILESTONES M3b already leaned
to; the argument is not, and the argument is why this is now closed rather than
"expect it to reopen"./

The recorded reasoning was cost: in-place mutation asks =sqlite.rs= for
free-list management and page reuse, which is harder file-format work than
anything in it. True, and *not the load-bearing reason.*

**In-place makes preservation the default and destruction the exception, which
is backwards for editing.** It would faithfully preserve =gpkg_ogr_contents=,
every R*Tree, and =gpkg_contents='s bbox across an edit that invalidated all
three -- decision 23's failure mode written into the architecture rather than
merely risked by it. A rewrite forces every object through an explicit
classification, which is precisely M3b's job. Given the three-class contract,
the design where *carrying is a decision* beats the design where *carrying is
an omission*.

So cost and correctness agree here, which is the comfortable case, and the
question should stop being carried as open.

*Note what this does not concede.* The risk people attach to rewriting -- a
truncated file when the write fails partway -- is real and is answered
separately by =edit-composability.org= D4's committed atomic write-and-rename,
which needs no file-format work at all.

*** D10 -- an index's fate follows the content class of the table it indexes
/Decided 2026-08-23. It dissolves the "carry or rebuild an index" question in
=handoff.org= § OPEN QUESTIONS by splitting it: that question named one thing
and meant two./

***This decision holds for carrying and is superseded for merging -- read
[[file:container-reconciliation.org][container-reconciliation.org]] § 4 and D2
before relying on it.*** /Added 2026-08-23, the same day it was taken;
resolved the same day./ Everything below rests on one fact: *an index on disk
is already sorted*, so it can be re-packed without ever comparing two keys.
**That fact does not survive a merge.** Combine two containers' rows for one
table and the result is in neither source's order, so the index has to be
*built* rather than re-packed.

*The challenge was answered by measurement, and it cut both ways.* That plan's
D2 is now **decided: build**. Two things it found, neither visible from here:
**every** table that would need merging carries an index, so refusing on one is
not the bounded escape it read as -- and *no real producer emits an index this
crate would struggle to build*, because across six GDAL files and
=spec_conformant.gpkg= every index is an autoindex on =BINARY= ascending key
columns.

**So the sentence below that says "no comparison semantics, no collation logic"
splits.** No *collation* logic: that stays out of scope, and a merge of a table
whose index declares one this crate does not implement is refused. Comparison
semantics: the type ordering plus =BINARY= is *in* scope for merging -- which
is the same capability defect 6 already obliged for the registry tables this
crate builds itself, so it extends shipped work rather than opening an axis.
**Carrying is unchanged: re-pack, and construct nothing.**

**The R*Tree.** The cost argument recorded for carrying -- that building needs
SQLite's comparison semantics and its collations -- *does not apply to it at
all*. R*Tree shadow tables are ordinary rowid *table* b-trees, already
writable, and =rtree::build= already constructs a complete index from a
=FeatureCollection= (a bbox per feature, Hilbert order, pack). There is no
trade to weigh: rebuilding is implemented and cheap, and =handoff.org= § THE
EDIT LOOP says a carried one is *wrong rather than stale* once geometry has
been touched. **Never carried. Always rebuilt.**

**Ordinary SQLite indexes**, including the implicit =sqlite_autoindex_*=. These
are not geometry-derived, so the edit-loop argument does not reach them -- and
here "an index on disk is already sorted, so an in-order read re-packs without
comparing two keys" is both true and load-bearing.

*The two resolve into one rule*, which is the part worth carrying forward:

| what the index indexes | fate |
|------------------------+------|
| a feature layer (R*Tree) | *derived* -- rebuild, never carry |
| an independent table carried *verbatim*, same rows and same rowids | *carry it verbatim* -- it is exactly as valid as the table |
| anything rewritten, or layer-coupled | does not arise: this writer emits its own constraint-free DDL |

**The scope that falls out is much tighter than the question implied:** read
index b-trees and re-pack them; *never construct one from unsorted keys*. No
comparison semantics, no collation logic -- the expensive half of the warning
in § MILESTONES M3b gap 1 is out of scope entirely, because an index is only
ever carried for a table whose rows and rowids were carried unchanged.

*And the half nobody had noticed: this makes index b-trees mandatory.* SQLite
creates a =sqlite_autoindex_*= b-tree for every =UNIQUE= and every non-INTEGER
=PRIMARY KEY=. A table carried with its DDL verbatim and no index behind it is
a *malformed database*. /Measured, on a file whose DDL was rewritten to declare
=UNIQUE= with no autoindex present:/

#+begin_src text
  SELECT                  -> works
  PRAGMA integrity_check  -> database disk image is malformed
                             wrong # of entries in index sqlite_autoindex_notes_1
  INSERT                  -> malformed (11)
#+end_src

*Reads work, which is why no round trip would have caught it.* Two things kept
it hidden and both are the fixture lesson again: this writer *strips
constraints from its own DDL* (it emits =gpkg_contents (table_name TEXT NOT
NULL, ...)= where GDAL writes =table_name TEXT NOT NULL PRIMARY KEY, identifier
TEXT UNIQUE, ... CONSTRAINT fk_gc_r_srs_id FOREIGN KEY ...=), so it has never
needed an autoindex; and the only user table in the fixture set,
=side_notes(id INTEGER PRIMARY KEY, note TEXT)=, is the one shape that needs
none either. =PRAGMA integrity_check= on this crate's output is =ok= today.

*What this turned up, and it is not M3b's -- it is bigger:* the registry DDL
this crate emits deviates from the specification's own definitions, in five of
the six tables it writes. That is **defect 6**, filed in § THE DEFECTS the same
day with the table-by-table measurement. It was briefly filed as an open
question and should not have been: conformance is not a matter of taste.

*So the scope boundary this decision drew needs one more line, because defect 6
crosses it.* "Re-pack only, never construct" is right for *carried* content,
and it is not sufficient for content this writer *builds*:

| the index is for | how it is produced | what it needs |
|------------------+--------------------+---------------|
| a feature layer's R*Tree | rebuilt by =rtree::build= | already implemented |
| a *carried* table (a user's own) | *re-packed* from the source's own b-tree, in order | no comparison logic at all |
| a table this writer *builds* (=gpkg_contents=, =gpkg_geometry_columns=, ...) | *constructed* from keys it just wrote | ordering rules -- but only its own |

**The construction case is far smaller than the general one, and the reason is
that this writer controls both sides.** The general fear -- SQLite's full
comparison semantics, =BINARY=/=NOCASE=/=RTRIM= collations -- applies to
arbitrary user DDL. The registry tables' specified DDL declares *no =COLLATE=
clause anywhere*, so their keys sort under =BINARY=, which is =memcmp= over
UTF-8 bytes; and the keys are table names and constraint names this writer
produced itself. What is actually needed is the type-class ordering
(NULL < INT/REAL < TEXT < BLOB) plus =memcmp=, over a few dozen short rows.

*A user table declaring =COLLATE NOCASE= on a =UNIQUE= column never reaches
this path*, because its index is carried rather than constructed -- which is
the rule at the top of this decision doing its job.

** SEQUENCING -- this inverts part of =same-format-output.org=
That plan currently scopes closing the fidelity gap *out*, and ships a warning
describing it instead ("This one warns about the gap; it does not close it",
D3: "the warning ships with the deletion, not after it").

Under this rule that ordering is backwards, for a reason that is not a matter
of taste: *the warning would be permanent furniture describing a bug.* The
crate does not write pending state into user-facing text, so the message cannot
say the loss is temporary -- it would simply assert, indefinitely, that a
same-format run drops =id=s. That is a promise this plan exists to break.

*DECIDED 2026-08-20: land the natives channel before deleting the format
check.* Two alternatives were weighed and rejected: shipping the deletion
first with M2's warning (fastest unblock, but =Format::unmodelled_members='s
nine constants become dead code the moment natives replace them with real
handling), and a hybrid shipping the deletion alongside GeoJSON-only natives
(limits the throwaway to eight constants, but leaves eight spokes warning
about a loss the crate has already decided is a bug). Neither pays for
splitting the inventory pass in two.

Note one argument that was *withdrawn* rather than upheld, so it is not
re-litigated from the record: an earlier draft claimed M2's warning could not
be phrased honestly because the crate does not write pending state into
user-facing text. That conflates two things. "GeoJSON feature ids are not
preserved" is a statement of current fact, not pending state, and deleting it
later would be ordinary. The decision rests on the duplicated inventory pass,
not on the warning being unsayable.
=same-format-output.org='s M1 stays exactly as designed and simply follows M2
here. Its M2 warning then narrows to what it was always meant to cover --
genuine cross-format capability gaps -- and its § OPEN QUESTIONS entry asking
whether the same-format warning needs its own =--quiet= escape hatch dissolves,
because on a same-format run there is nothing left to warn about.

Defects 1--2 in § THE DEFECTS are independent of all of this and should not
wait for any of it. Defect 3 is the container, so it travels with M3b; defect 4
travels with D1's =name= modelling.

    had just lengthened. This is the one-line form of the "declared minimum"

  =ogrinfo= reports the same title, description, alternative names, comments
  and domain off our output, and =ogr2ogr= rewrites the result. The identifier
  was the same shape as *defect 4* -- =gpkg_contents(identifier)= was hardcoded

  source*, and both new here:
  1. *A member equal to what the writer would emit anyway is derived, not

     =description= only when non-empty. GDAL writes =identifier = table_name=
     for every layer it creates, so the alternative is a payload on every
     GeoPackage in existence and an =is_empty= that is never true -- and, the
     part that is a bug rather than noise, a *stale* title replayed into a
     layer that had since been renamed. This is decision 14 ("an opaque member
     can also be derived") reached from the other direction: there the member
     was derived from the *columns*, here from the layer's own name.
  2. *=FgbNative='s "absent and empty are different" rule does not generalize.*
     It holds for FlatGeobuf because that writer *omits* an absent field, so
     the distinction reaches the file. =gpkg_contents= is a row always written,
     so NULL and ='' = are the same bytes and the distinction has nowhere to
     live. Stated because the rule reads like a general one and is not.

** THE ORACLE RULE -- what =ogr2ogr= is and is not evidence of
/Added 2026-08-23, out of defect 6. It is short because it is a rule, not an
argument, and it should be applied before the next differential check is
written./

This crate leans on GDAL as a second opinion throughout, and that is right --
=tests/gdal_types.rs=, the =ogrinfo= diffing that caught the =REAL= bug, the
=ogr2ogr= rewrite check. **But agreement with a reference implementation is not
conformance to a standard**, and defect 6 is what happens when the two are
treated as one thing: four measured deviations in =ogr2ogr='s GeoPackage
output, three of which this crate had inherited by checking against it.

| question | the right oracle |
|----------+------------------|
| What does a real producer *emit*? | =ogr2ogr=, DuckDB, pyarrow -- a member a real tool writes is a member that really occurs |
| Can a real consumer *read what we wrote*? | =ogr2ogr=, =ogrinfo=, DuckDB |
| Is a b-tree *well formed*? | =sqlite3= -- =PRAGMA integrity_check= |
| **What does the format /require/?** | **the standard's own text, and nothing else** |

*The failure mode is specific and worth naming:* a differential test cannot see
a deviation the two implementations *share*, and the cheapest way to end up
sharing one is to build the reference file with the tool you are checking
against. Every GeoPackage fixture in this tree came from =ogr2ogr=, so the
whole fixture set was blind to exactly this class.

*** The rule now has a fixture behind it -- /2026-08-23/
=tests/fixtures/spec_conformant.gpkg= is a GeoPackage built by =sqlite3= from
the annexes' normative SQL, with **no GDAL at any point in its provenance**,
not even as a base file. =build_spec_fixtures.sh= transcribes the DDL
mechanically from the =.adoc= sources at a pinned commit, so the independence
is auditable rather than asserted, and it starts from an empty file rather than
=cp gdal_hostile.gpkg= the way =build_sqlite_fixtures.sh= does.

=writer.rs='s =the_registry_ddl_is_what_the_standard_says= compares *whole
normalised DDL* per table against it. That is the part that matters, and not
only because it is stricter than the substring assertions beside it: the
standard's clause is a SHALL in *both* directions -- /"SHALL have **only** the
specified columns and table constraints"/ -- and a substring assertion cannot
see an added column at all. **Confirmed by mutation** rather than by reasoning:
dropping =gdc_tn=, adding a spurious column and restoring =ogr2ogr='s
=NOT NULL= on =srs_id= are each caught by the new test, and the extra column is
*not* caught by the old one.

/Result: all six registry tables this crate emits match the standard exactly./
So the spec pass earlier the same day holds up under a check that does not
depend on anyone remembering what to assert -- which is the only reason to
trust it, given that what the spec pass was correcting was a fix that had been
checked the wrong way.

/The normative SQL is small and worth fetching rather than recalling:/ Annex C
of OGC 12-128r19, plus the extension annexes for the Schema and Metadata
tables. Source text at
[[https://www.geopackage.org/spec/][geopackage.org/spec]]; the =.adoc= files

- ~~*What should =gpkg_contents.last_change= hold on a =gpkg -> gpkg= run?*~~
  ***DECIDED 2026-08-23: carry it. Stamp only when there is nothing to
  carry.*** /Raised and decided the same day it was raised./

  **The rule, in one line: the stamp follows whoever last changed the content,
  and that is never geosetta.**

  #+begin_src text
    geosetta in.gpkg out.gpkg               passthrough  -> carry the source's value
    geosetta in.shp  out.gpkg               cross-format -> stamp: nothing to carry
    geosetta in.gpkg - --to gpkg | tool | … middleman    -> carry what the tool left
  #+end_src

  ***What collapses the rule to three cases is an invariant this crate already
  holds: geosetta never changes content.*** It does not reproject
  (=src/main.rs= module doc, =src/crs.rs=, and
  [[file:reproject-composability.org][reproject-composability.org]] -- a
  reprojection tool composes with it through a pipe or the mutation seam, and
  the transform happens *there*). So there is no "geosetta edited this" case to
  stamp for, and the only reason it ever writes a fresh value is that a
  cross-format source had none to give.

  /An earlier draft of this decision carried a fourth row --
  =geosetta in.gpkg out.gpkg --reproject= -- and it was wrong: that flag does
  not exist and by design will not. =--crs= is the nearest thing and it is
  *assign, not enrich*: it relabels a declared CRS without moving a
  coordinate, so it is not a content change under this rule./

  *So the classification is =independent=, not layer-coupled.* Carried
  unconditionally on a same-format run -- which under a complete M3b *is* a
  passthrough by construction, since that is what the rule in § THE RULE
  promises. It wants a =GpkgNative= field beside =identifier= and
  =description=, and nothing more.

  **And the middleman case works because of D5**, which is the non-obvious
  part: a native crosses the pipe when the transit format is the same format,
  which per the transit corollary is the only shape in which a GeoPackage edit
  loop is lossless anyway. So the tool's own stamp survives if it set one, and
  its staleness stays visible if it did not. *Geosetta manufacturing a
  timestamp there would launder the tool's omission rather than fix it* --
  which is why no middleman-detection is attempted, and it could not be:
  the second process has no baseline to diff against.

  *The cost, which is real and unasserted:* stamping on the cross-format path
  makes output non-reproducible across runs, which the fixed epoch buys today.
  No test in the tree depends on it. /If both are wanted later, the standard
  answer is a =SOURCE_DATE_EPOCH=-style pin, and that is a separate feature./

  /The original text follows./

  **** the entry as filed -- what should =gpkg_contents.last_change= hold?

  =src/geopackage/writer.rs= has =const LAST_CHANGE: &str =
  "1970-01-01T00:00:00.000Z"=, written for every layer on every run. It had no
  doc comment, no plan entry and no mention in =handoff.org=; it now has the
  first, and this is the second. **The effect is that this writer's output is
  byte-identical across runs**, which is worth having and is presumably why it
  is there -- /the reason was never recorded, so that is inference/.

  *It is conformant.* The standard's only requirement touching the value is
  that it be in DATETIME format, and Requirement 5 is about data types; the
  epoch is a well-formed ISO-8601 UTC string and the abstract test suite checks
  format alone.

  ***The question is what the rule says, not what the standard says.*** Unlike
  =gpkg_metadata_reference.timestamp=, which the standard leaves undefined,
  =gpkg_contents.last_change= is described as *"timestamp of last change to
  content"*. So it has a meaning, this writer does not carry it, and a
  =gpkg -> gpkg= run overwrites the source's value with a constant. Three
  readings, and they are not obviously distinguishable:

  1. *A loss* -- it is content the source held and the output does not.
     Then the natives channel should carry it, and the rule is violated today.
  2. *Derived* -- it describes the write rather than the data, like
     =gpkg_ogr_contents='s row count. Then it should be *recomputed honestly*,
     and a constant epoch is not that either.
  3. *Correctly ignored* -- a write-time stamp is provenance, which is exactly
     the argument =container-reconciliation.org= § 6 rule 3 makes for the
     *other* column. Then the only defect is that nothing said so.

  /Reading 3 is the tempting one and it is the one to be careful with:/ rule 3
  earned its conclusion from the standard declining to define
  =gpkg_metadata_reference.timestamp=. That argument is unavailable here,
  because the standard *did* define this one. **Do not carry rule 3 across by
  analogy** -- the two columns differ in exactly the respect the argument
  turned on.

  *Cheap to resolve and not yet resolved:* nothing measures what this crate
  does to a source =last_change= today, and no fixture asserts either
  behaviour.
- *Should a =.dbf= field be sized to the data, or fixed per type the way GDAL
  does?* /Raised 2026-08-21, measured both ways, deliberately not decided./

  This writer sizes every field from the values it holds; =ogr2ogr= uses a
  fixed default per type and ignores the data. Neither is a rule violation --
  on a route that *carries* the declaration (=shp -> fgb -> shp=) the source's
  own width wins and no default is consulted -- so this is only about what the
  writer should *invent* on a carrier-less hop, where =schema_drop_warning=
  already says the declaration was lost.

  | column       | =ogr2ogr=        | this writer      |
  |--------------+------------------+------------------|
  | ="ab"=       | =String (80.0)=  | =String (2.0)=   |
  | =7=          | =Integer (9.0)=  | =Integer (1.0)=  |
  | =2^53+1=     | =Integer64 (18.0)= | =Integer64 (16.0)= |
  | =1.5=        | =Real (24.15)=   | =Real (17.15)=   |

  *For fixed.* A width stops being a lie about the future: the complaint
  =native-inventory.org= calls the entry most likely to break a real workflow
  is an 80-character name field coming back one character wide -- it holds
  today's rows and cannot hold tomorrow's. Fixed defaults also stop the
  *ratchet*: today the schema is a function of the sample, so two subsets of
  one source produce two different schemas and every carrier-less hop
  re-narrows, which is felt by anyone appending to or unioning shapefiles. And
  an alternating geosetta/=ogr2ogr= pipeline would converge instead of
  drifting.

  *Against fixed, and both of these are measured.* dBase records are
  fixed-width, so every field pays its declared width on every row: a
  50,000-row table of four ordinary columns is *1.5 MB fitted against 9.7 MB
  fixed*, 6.5x. (Narrow columns are the best case for fitting; a table of long
  free text would show much less.) More seriously, **GDAL's own fixed width
  silently writes a different number**: =1e240= through =Real (24.15)= comes
  back =1.00000000000000008388608e23= -- off by ~10^217, at =Warning 1=
  severity -- where this writer widens to =Real (255.13)= and keeps it. That is
  precisely the desync =dbf.rs='s =Double= arm was fixed for, so a fixed policy
  would have to keep the widen-to-fit escape hatch anyway and could not simply
  delete the sizing pass. Fixed is also *both* too wide for typical data and
  too narrow for atypical: 80 wastes 78 bytes a row on a two-character column
  and truncates a 200-character value the current code sizes to hold.

  *And it does not restore what was lost.* A source declaring =String (120)=
  does not get 120 back from a fixed default; it gets GDAL's 80. Fixed widths
  substitute a better-shaped guess for the source's fact. The actual fix for
  that loss is a carrier, which D1 already supplies wherever one exists.

  *The shape a decision would most likely take*, if the append-after-narrow
  complaint is the real driver: a *floor* rather than a replacement --
  =fitted.max(gdal_default).min(255)= -- which buys the schema contract and
  keeps the large-magnitude correctness, while explicitly *choosing* the 6.5x
  rather than getting it by accident. A flag (=--dbf-widths=fit|gdal=) is the
  other shape, and this crate already ships =--rtree= as a policy flag.

  *What would settle it:* whether anyone has actually hit append-after-narrow,
  or whether it is an inferred risk. If inferred, =schema_drop_warning= already
  tells the user the declaration did not survive that hop, and inventing GDAL's
  number is a strictly noisier answer than saying so.
