** WHAT THIS WORK IS
It began as a request to make =geosetta= read a file, let *another program*
modify the feature collection, and write it back. That turned out to be
possible already, and the interesting question was why it is not *faithful*.
Chasing that produced a standing rule:

#+begin_quote
*Reading a format and writing the same format loses nothing.* A capability gap
in the target is a defence for dropping data; the target being the source's own
format is not.
#+end_quote

Everything else is consequence.

*Three later rulings extended D1*, all worth knowing before you design
anything, and *all three now implemented*. The third is =FieldDecl='s
*declared type* (M4) -- what lets an all-null FlatGeobuf column keep its type,
a GeoPackage =BOOLEAN= survive its reader, and a =DateTime= stop returning as
=String= (defect 5). Its vocabulary was the open question M4 opened by
settling: the IR's own four column types are measurably too narrow, so
=crate::DeclType= names sixteen, every one drawn from some spoke's own on-disk
vocabulary rather than invented for symmetry. The first two: collection =name=
and the *column schema* (=width=/=precision=/=scale=/
=nullable=/=unique=/=primary_key=) are **modelled in the IR**, not carried as
opaque natives. The reason is D5 -- a native does not cross a pipe, so only a
modelled field lets an external tool widen a declaration mid-flight alongside
the value that outgrew it. *Both are implemented*; the schema half lives in
=crate::FieldDecl= and =FeatureCollection::schema=.

** WHAT IS BUILT
- *The inventory*, all nine spokes, every entry marked /measured/ or /code/.
- *The natives mechanism and four spokes* -- GeoJSON (=id=, foreign members
  at three levels), FlatGeobuf (header/=Crs=/per-column descriptive members
  plus the header name), GeoParquet (every =key_value_metadata= entry
  beside =geo=, plus =geo.orientation=) and GeoPackage (the layer's
  =gpkg_contents= title/description and its =gpkg_data_columns= rows plus the
  constraints they name). See § STATUS in the fidelity plan.
- *The modelled column schema*, end to end for three spokes: a =.dbf= field's
  declared width survives =shp -> fgb -> shp= intact, and a middle stage can
  widen it. Losing a declaration to a target that does not carry one now warns.
- *Declared column types* (M4) -- =crate::DeclType= on =FieldDecl=, carried by
  *all four* declaring spokes: FlatGeobuf, GeoPackage, Shapefile and
  GeoParquet. An =Int16= stays an =Int16=, a =DateTime= stops becoming text, a
  GeoPackage =BOOLEAN= comes back a boolean, and an all-null column keeps both
  its existence and its type. GeoParquet needed no =ARROW:schema=: its own
  =converted_type= annotations carry every width and both temporal types.
- *Nine hostile fixtures* in =tests/fixtures/= (=gdal_hostile.*= produced by
  =ogr2ogr=, =hand_hostile.*= authored), each confirmed *readable by geosetta*
  before being committed. They fail the invariant by design -- they are the
  target, not a regression suite.

  *Two more joined them on 2026-08-21 and neither is hostile*, which is why
  =HOSTILE.org= now says so per entry: =gdal_types.gpkg= is a *specimen sheet*
  (one column per GeoPackage declared type, for the GDAL cross-check), and
  =hand_mixed_number.geojson= documents a single open case rather than testing
  anything. =gdal_hostile.gpkg= also *grew* -- the GeoPackage spoke needed
  layer-level members it did not carry.

*Everything below landed on 2026-08-21, after M3's GeoPackage spoke, and none
of it was planned work* -- each item was found by measuring the one above it:
- *Defect 3's warning* -- =geopackage/container.rs= surveys the container a
  =gpkg= write is about to rewrite and reports what will not survive. The

- *The recast matrix* -- =DeclType::admits= (the widening relation),

- *An exact integer model* -- =JsonValue::Int= / =Float=, after a same-format

  declaring spokes carry one as of M4, so =Format::carries_column_schema= has
  stopped shrinking and the four remaining =false= answers (GeoJSON, CSV, WKT,
  KML) are permanent -- those formats have no slot.
- *GeoParquet's =covering= bbox column*, the one member the GeoParquet spoke
  left unhandled -- a file with a spatial index goes in and one without comes
  out, silently. Now owned by =plans/spatial-index.org= *milestone E*, which
  already owns the same D4 "rebuild it when the source had one" pattern for
  FlatGeobuf's and GeoPackage's indexes. Blocked on the writer's flat schema:
  it has never emitted a nested struct column.
- *Defect 3* -- the only entry left in § LIVE BUGS. Note that section's
  numbering is *not* the plan's "five defects"; see its own note.
- The exhaustive-match fixture registry (D6).
- The format-check deletion, which is sequenced last.
- *One open call, deliberately not decided*: a column mixing an integer past
  2^53 with a fractional value infers =Double= and the integer loses its low
  bits. The loss is *inherent* -- inference has decided the column is
  fractional, and GDAL's =OFTReal= does the same -- so what is missing is a
  warning, not exactness. Whether it earns one against the noise bar is argued
  both ways in =lossy-conversion-warnings.org= § AN OPEN CALL. Fixture and an
  =#[ignore]=d test that *passes* and exists to be rewritten:
  =hand_mixed_number.geojson= and
  =convert.rs='s =a_mixed_number_column_loses_precision_above_2_53=.

/Warning work is no longer on this list./ It said "and any warning work" until

*Four =sqlite.rs= gaps are known and unclosed*, all found while scoping M3b on
2026-08-22 and all recorded in =plans/same-format-fidelity.org= § MILESTONES,
M3b. None is a silent data loss today; each is work M3b needs:
*index b-trees* (neither read nor written, which is also why =WITHOUT ROWID=

out of scope by construction: *WAL* is invisible to a reader that takes bytes
rather than a path, so an un-checkpointed GeoPackage reads as its last
checkpoint, silently.

*The list positions below are reading order, not defect numbers.* The canonical
numbering is =same-format-fidelity.org= § Five defects, and each entry names
its own identity in bold; entries with no such name are not one of the five at
all. This is worth stating because an earlier draft numbered these entries
1--5 and then referred to them as though they *were* the plan's numbers, which
made § THE SEQUENCING above -- where "defects 1--2" correctly means the
FlatGeobuf null cell and the GeoPackage boolean -- read as a contradiction of
this section. It never was one; the two lists were simply counting different
things. /Reconciled 2026-08-20./

1. ~~*A GeoPackage edit loop silently duplicates layers.*~~ *FIXED
   2026-08-20.* Not one of the five -- it belongs to =edit-composability.org=
   D4, which calls it *live bug 1*. The second cause was the one left: the
   GeoPackage reader did not set =fc.name= from the table name, so the FGB on
   the wire had no name to carry and the write-back landed in a new table
   called =layer=. One line in =geopackage/reader.rs='s =read_layers=, because
   =write_layers= already *replaces* a same-named layer rather than appending
   rows. /Verified on the original reproduction, both the pure-FGB and
   FGB-via-GeoJSON forms:/ one =bug1= table, and a middle stage that deletes a
   feature now has its deletion stick -- which was the real damage, since a
   delete silently became a no-op. Pinned by
   =an_edit_loop_that_deletes_a_feature_does_not_duplicate_the_layer=, which
   asserts on the surviving rows rather than the table name.
2. ~~*Shapefile narrows the schema.*~~ Also not one of the five -- it is the
   inventory's own finding, M1 § 3. *FIXED 2026-08-20* by D1's column
   schema. An 80-character =.dbf= field used to return sized to today's longest
   value; it now returns 80. Verified through a FlatGeobuf transit, which is
   the only route that carries it -- =shp -> geojson -> shp= and
   =shp -> gpkg -> shp= still narrow, and now warn.
3. *A =gpkg= → =gpkg= run destroys the container* around the layers: user
   tables, =gpkg_metadata=, =gpkg_extensions=, every R*Tree. This is
   *defect 3*, and after M4 it is *the only defect left* -- the destruction
   travels with the GeoPackage container (M3b).

   *No longer silent, as of 2026-08-21.* "Exit 0, no warning" was the original
   finding; the exit code is unchanged (§ THE RULE is loud, not blocking) but
   =geopackage/container.rs= now surveys the container being rewritten and
   reports what will not survive -- destroyed content in one message, and an
   R*Tree that will not be rebuilt in a second, since that one is *derived* and
   =--rtree= fixes it. Silent on any GeoPackage this crate wrote itself. The
   two things worth knowing before touching it: =REPRODUCED= is a statement
   about what =writer::build= emits and has to move when the writer does, and
   an R*Tree's =gpkg_extensions= rows are counted as part of the index rather
   than as a loss of their own. Both are written up in
   =same-format-fidelity.org= § Five defects, defect 3.
4. ~~*FlatGeobuf drops null cells*~~ -- *defect 1*, *FIXED 2026-08-20 (M4)*.
   It was *two* losses, not one, and the second was nearly missed: fixing the
   cell is necessary and not sufficient, because an all-null column then
   returns as =String= -- =infer_columns= has no values to infer from, and
   =FieldDecl= carried no *type*. Both halves landed together.

   *The unset-vs-null worry recorded here on 2026-08-20 was wrong and has been
   retracted.* It read =ogrinfo='s display convention as GDAL's data model.
   =ogr2ogr= itself writes an explicit =null= for every declared column in
   every feature on GeoJSON output, and -- decisively -- *GeoParquet,
   GeoPackage and CSV already do exactly that in this crate today*, with
   Shapefile rectangular too. FlatGeobuf is the lone outlier, being the only
   format rectangular in its header and sparse in its rows. There is no fork
   to settle. See =same-format-fidelity.org= § Five defects for the
   spoke-by-spoke measurement.
5. ~~*GeoPackage loses booleans*~~ -- *defect 2*, *FIXED 2026-08-20 (M4)*.
   The reader now parses the declared SQL type out of the table DDL, so a
   =BOOLEAN= storing =0=/=1= comes back a boolean. *It was defect 1's second
   half in another format* -- both were a declared column type on disk that
   the IR could not hold -- which is why M4 shipped them as one piece.
6. ~~*Every spoke narrows a declared column type to the IR's four*~~ --
   *defect 5*, /found 2026-08-20 while reviewing defect 1/, *FIXED the same
   day (M4) across all four declaring spokes* -- FlatGeobuf, GeoPackage,
   Shapefile and GeoParquet. It was the largest of the five:
   unlike defect 1 it needed no null to show itself, so it fired on most real
   =ogr2ogr= output. /Measured before/: =Integer(Int16)= returned
   =Integer64=, =Real(Float32)= returned float64, and *=DateTime= returned
   =String=* -- a temporal column silently becoming text. /Measured after,
   through GDAL:/ all three arrive intact across =parquet -> gpkg=,
   =parquet -> fgb=, =fgb -> gpkg= and =fgb -> parquet=. This is what
   re-scoped M4 around a vocabulary investigation -- the declared type has to
   carry the *source's* vocabulary, not the hub's.

group in the sequencing diagram, and *all three shipped together as M4* on

*** Four more, all found and fixed 2026-08-21 -- and none of them by reading
None was in the list above, none was hard, and every one broke the *same-format*
invariant. They are grouped because what found them matters more than what they
were: each fell out of measuring the fix for the one before it.

7. *A GeoPackage =REAL= column read back 32-bit.* =decl_type= grouped =REAL=
   with =FLOAT=; the spec and SQLite both make it 8 bytes. /Measured through
   GDAL:/ =Real (0.0)= in, =Real(Float32) (0.0)= out. Found while measuring the
   GeoPackage spoke's round trip. Fixed -- and note the fix *normalizes the
   spelling* rather than preserving it: a =REAL= column comes back =DOUBLE=,
   which GDAL reads identically. See the GeoPackage spoke's entry in § WHAT
   CHANGED IN EXISTING DOCS.
8. *Every unsigned width written as its same-width signed spelling.* =UInt32=
   was written =MEDIUMINT=. The value survived SQLite's dynamic typing and the
   *declaration* was a lie: **GDAL read =3000000000= back as =-1294967296=**.
   Found by the recast matrix, which (7) is what motivated building.
9. *Every blob destroyed on read.* =Value::Blob(_) => JsonValue::Null=, so a
   =gpkg -> gpkg= run replaced =X'0102'= with =NULL= while the =BLOB=
   declaration survived. Found by adding *value* assertions to a suite that
   had only ever compared declarations.
10. *64-bit integers routed through an =f64=.* =9007199254740993= came back
    =...992= on a same-format run; past =i64::MAX= the serializer saturated, so
    =12345678901234567890= became =9223372036854775807=. Found by pulling on
    what looked like a JSON canonicalisation question.

*The pattern worth carrying forward*, because it caught three of these four and
is not obvious: **the obvious test shape has a blind spot exactly where the
bugs are.** A self-round-trip misses a spelling the writer never emits (7). A
sweep over every *type* misses a class if its *values* are unadventurous (10).
And a check that compares declarations can be perfectly green while the values
are being destroyed (8, 9).

*** Two more, found and fixed 2026-08-22 -- by asking what =sqlite.rs= cannot do
Both were found while scoping *M3b*, by reading =src/sqlite.rs= for the gaps
M3b would have to close rather than by testing anything. Both turned out to be
live in shipped code, and *neither is reachable from any existing fixture* --
=ogr2ogr= writes neither construct, so every fixture in the tree is built out
of the subset of SQLite that GDAL happens to emit.

11. *One =WITHOUT ROWID= table silenced every defect 3 warning in the file.*
    Such a table is stored as an *index* b-tree; =walk_table= handles only
    table b-trees (=0x0d=/=0x05=) and errors on the page type. That =Err=
    propagated out of =survey=, and =container_drop_warnings= swallowed it on
    the documented reasoning that "every caller has already read this
    container" -- true of feature layers, false of a user table nothing else
    ever reads. /Measured on =gdal_hostile.gpkg= with one table added and
    nothing else changed:/ both warnings present with a rowid, *both absent*
    with =WITHOUT ROWID=, exit 0 either way. Defect 3 was returned to exactly
    the silence its warning shipped to end, one day after it shipped.

    Fixed by classifying rather than aborting: a table whose rows cannot be
    decoded is reported by name, without a count (=kv (rows not counted)=).
    Naming it without a number is the honest form -- the rows are real and this
    cannot count them.
12. *A column added by =ALTER TABLE= read back NULL instead of its default.*
    SQLite does not rewrite existing rows on =ADD COLUMN=; their records stay
    *short*, and the added column's value for those rows lives only as the
    =DEFAULT= in the DDL. =read_rows= padded short records with
    =Value::Null= and =parse_columns= discarded =DEFAULT= as a constraint
    keyword. /Measured:/ =sqlite3= and =ogrinfo= both report =B=; geosetta
    reported an empty cell -- **on every output format**, needing no
    same-format run to fire. Fixed by decoding the literal (text with =''=
    escapes, integers, reals, blobs, =TRUE=/=FALSE=) and padding with it.

    *Only literals are decoded, and that is sufficient rather than partial:*
    the sole path by which a default reaches a stored row is
    =ALTER TABLE ADD COLUMN=, and SQLite rejects a non-constant default there.
    An expression default can never apply to a short record.

*The lesson these two add*, which is the type-vs-value one turned outward:
**the fixture set is only as wide as the tools that built it.** Every fixture
in the tree came from =ogr2ogr=, DuckDB, pyarrow or hand-authoring, so the
whole crate had been tested against the subset of SQLite that GDAL emits --
and a GeoPackage is a general SQLite database that anything may touch after
GDAL is done. Both bugs sat in the gap between "what our fixtures contain" and
"what the format permits", which is a gap no amount of testing the fixtures

*The number model and Shapefile's decimals, 2026-08-21 -- code.* Two findings
that had been recorded rather than fixed. The first turned out to be a symptom.

=JsonValue::Number= was an =f64= plus an =is_int= flag, and an =f64= carries
integers exactly only to 2^53 -- so a *same-format* =gpkg -> gpkg= run turned
=9007199254740993= into =...992=, on a plain 64-bit =INTEGER= column. Past
=i64::MAX= the serializer's =as i64= saturated: =12345678901234567890= came
back =9223372036854775807=, a specific wrong number. **The flag was the tell**
-- it existed to remember what the representation had already thrown away.

Now =Int(i64)= and =Float(f64)=, so an integer never touches a double. One too
wide for an =i64= becomes =Float=: lossy, but honestly lossy, never a different
integer. Whole floats keep their =.0= (=1.0= stays =1.0=), which matches
=ogr2ogr= -- verified, including its coordinates, which it writes =[1.0,2.0]=.
That change immediately caught =geojson/mod.rs='s *two writers disagreeing*:
the direct writer formatted its own coordinates while the tree serializer went
through =JsonValue=. Both now call one =write_json_f64=.

*The sweep now uses values past 2^53*, because it did not before -- =Int64='s
representative value was small enough to survive a double. A sweep can be
exhaustive over *types* and still miss a whole class by being unadventurous
about *values*. That is the third variation on the same lesson in two days,
after the undeclared-column path and the type-vs-value blind spot.

=dbf.rs='s =DECIMALS= fallback went 6 → 15, matching the =15= in =ogr2ogr='s
=Real (24.15)= for an undeclared double. *The number's text is now
byte-identical to GDAL's; the field around it is not, and deliberately.*
/Measured on =1.23456789012345=:/ both write the digits =1.234567890123450=,
and geosetta writes them into an =N(17,15)= field where =ogr2ogr= writes
=N(24,15)= -- the difference is trailing pad, because this writer sizes a field
from the values it actually holds while GDAL uses a fixed default. That is the
same policy that makes an integer column =N(2)= here and =N(9)= there, it is
not part of this change, and the =24= was never the thing being matched.
*Whether that policy is the right one is now an open question* --
=same-format-fidelity.org= § OPEN QUESTIONS' first entry, and § OPEN QUESTIONS
WORTH KNOWING below.
Fifteen decimals push the fixed-point text past the 255-byte =.dbf= limit at
lower magnitudes, so the *fallback* is trimmed to fit (at =1e240= those
decimals are padding an =f64= never carried); a *declared* scale is left to
fail loudly, since that is the source stating a fact.

*D7, the public API, 2026-08-21 -- code.* D1 models the column schema in the IR
rather than carrying it as a native, and D5 says why: only a modelled field lets
an external tool widen a declaration mid-flight. Both are arguments about a
*caller*, and neither had ever been run from where a caller stands.

=Feature::properties= is a public field of type =JsonValue=; =FieldDecl::ty= is
a public field of type =DeclType=; both types lived in =pub(crate)= modules, so
**neither could be named outside this crate**. A consumer could read a
declaration and not construct one, read a feature's properties and not build a
feature that had any. The library was a read-and-convert API whose docs
described an edit-in-the-middle API.

was a new variant on a public enum -- normally breaking for every downstream
=match= -- and it broke nothing, because no downstream match was possible.

=FieldDecl::type_for= are demoted to =pub(crate)= (both name types that stay
internal); =ColumnType=/=Cell=/=Column= stay internal and are now reachable
from nothing public. *The enforcement is =tests/public_api.rs=, and it has to
live in =tests/=* -- an integration test compiles as a separate crate, so it
sees what a real dependent sees. A unit test in =src/= cannot check this
property at all, because inside the crate everything is nameable, which is
exactly why the gap survived this long.

*The binary cell type, 2026-08-21 -- code.* The recast matrix asserted
*declarations*, and it was green while a =gpkg -> gpkg= run **destroyed every
blob in the file**: the =BLOB= declaration survived, so the types matched, and
=X'0102'= came back =NULL=. The GDAL cross-check missed it for the same reason
-- it diffed =ogrinfo -so=, which prints the schema and no values.

The cause was structural rather than careless. The IR's property type is
=JsonValue=, so bytes had nowhere to live; =geopackage/reader.rs= returned
=Null=, FlatGeobuf skipped the payload, GeoParquet rendered hex text, and all
three then *declined to declare* =Binary= -- correctly, since declaring a type
whose values are destroyed is a promise the value side cannot keep. So the fix
was the IR: =JsonValue::Binary(Vec<u8>)=, whose doc admits it makes the type's
name a slight lie and cites the precedent (=Number { is_int }= is not a JSON
distinction either). The compiler then enumerated the blast radius exactly as
D3 intends -- eight sites, each a writer that had to decide.

Two spokes gained a capability they already had on disk: FlatGeobuf's
=ctype::BINARY= was in the reader's table and unreachable from the writer,
which kept *its own duplicate of all fourteen constants* -- collapsed to one
shared table in the same pass. GeoParquet's unannotated =BYTE_ARRAY= is binary
in Parquet's own model and was being decoded as UTF-8.

=Date= also stopped degrading to text: FlatGeobuf has no =DATE= but has
=DATETIME=, which is what =ogr2ogr= writes for the same hop. And once the type
survived the transit, the *value* turned out not to -- =format_timestamp=
emitted no =Z=, so =gpkg -> parquet -> gpkg= turned =12:00:00+00= into an
unzoned =12:00:00=. =TIMESTAMP_MILLIS= is UTC by definition, so it emits the
designator now.

*The rule this bought*, and it belongs beside the undeclared-column one below:
**a type-fidelity test that never looks at a value can be perfectly green while
the values are being destroyed.** Three of those four bugs fell out of one
change -- adding a value comparison beside the type comparison, in both the
in-tree sweep and the GDAL check.

*The one lesson worth carrying forward*, because it is not obvious and it cost
a day: **a self-round-trip over declared values is not sufficient.** The =REAL=
bug lived on the *undeclared* path -- the writer emits =REAL= for a plain

second implementation, will say.

** REPRODUCING THE MEASUREMENTS
Every claim marked /measured/ was run against the release binary
(=target/release/geosetta=, workspace target dir -- note =geosetta/target/= is
a stale leftover and its binary predates =--crs=) and GDAL 3.13.2. The fixtures
are in the tree, so most re-run directly, e.g.:

#+begin_src text
geosetta tests/fixtures/gdal_hostile.gpkg - --to geojson --layer cities
geosetta tests/fixtures/hand_hostile.csv - --to fgb | geosetta - - --from fgb --to csv
#+end_src

Two traps that already cost time once each:
- *Do not write fixtures through a shell heredoc.* It silently mangled
  =København= to =Ke\xe2\x88\x9a\xe2\x88\x8f...=. Write with explicit encoding
  and check the raw bytes.
- *=strings= defaults to a 4-character minimum*, which hid a 3-character
  column name and produced a wrong conclusion about FlatGeobuf's header. Use
  =strings -n 1= when decoding fixtures by hand.
- *=tests/fixtures/gdal_hostile.fgb= does not exercise column widths*, despite
  being the fixture the inventory cites for FlatGeobuf's =Column= table. It was
  written *from the GeoPackage*, which has no widths, so every column reads
  =String (0.0)=. To exercise them, write a fresh FGB from
  =gdal_hostile.shp=. The =0.0= is itself a useful case -- it is what proved
  that GDAL writes =width: 0= for "undeclared".

** THE ONE REAL GAP -- *RETRACTED 2026-08-20, it was a measurement error*
This section claimed *"this repository has no commits at all"* and recommended
an initial commit. Both were wrong, and the way they were wrong is worth
keeping.

=geosetta= has full history -- =git log= shows =2a12bab=, =a1c9bc1=,
=028314a= and back through the 0.2x releases. What actually happened is that
=git= was run from =geocore/=, which is *not* a repository: the search walked
up to =~/Projects=, which *is* one, has no commits, and holds every unrelated
project the user owns. So the "no commits" reading was true of a repo nobody
meant to look at.

*The trap, for whoever runs =git= here next:* =geocore/= is a bare workspace
directory containing two independent repos, =geosetta/= and =geoscribe/=,
inside an outer =~/Projects= repo that should almost certainly never be
committed to. *Always run =git= from =geosetta/= itself*, and check
=git rev-parse --show-toplevel= before staging anything -- a =git add -A= one
level up would sweep in =basin/=, =hen/=, =sphere2/= and a =.venv=.

The fidelity work described in this handoff /was/ uncommitted while it was
being done, which is what made the error plausible.

*The durable rule, since naming which commits exist is a claim that expires:*
**prefer =git log= / =git show= over this document wherever the two disagree.**
§ WHAT CHANGED IN EXISTING DOCS exists for work that has not reached a commit
yet, and which work that is changes every time someone commits -- so treat it
as a record of *what was done*, never as a statement about *what is committed*.

** OPEN QUESTIONS WORTH KNOWING
Not blockers, but they will come up:
- *Is canonicalisation a loss?* =MULTIPOINT ((1 2))= → =MULTIPOINT (1 2)=,
  =linestring= → =LINESTRING=. Decides whether the CSV/WKT lexeme problem is
  two bugs or a whole class. (=native-inventory.org= § QUESTIONS, item 1.)

  *A third instance arrived 2026-08-21 and it is not CSV/WKT*: GeoParquet
  *parses* a =Json= column, so ={"a": 1}= comes back as an object and
  re-serializes without the space. GeoPackage and FlatGeobuf keep the text --
  so this is also a *spoke inconsistency*, and settling the question settles
  which of the three is right. Measured; the values are otherwise unharmed
  (key order holds, and numbers are exact now that the number model is split).
- *Does the mixed-number column earn a warning?* A column holding an integer
  past 2^53 *and* a fractional value infers =Double=, and the integer loses its
  low bits. The loss is inherent -- do not try to make the value survive -- so
  the question is only whether it should be *said*. Argued both ways in
  =lossy-conversion-warnings.org= § AN OPEN CALL; fixture and an =#[ignore]=d
  test are in place, written to be rewritten around the warning.
- *=edges= / =epoch= in GeoParquet* -- no available tool emits either, so no
  fixture exists. *Do not close this as a null result* the way =envelope.org=
  closed the GPKG XYM indicators: =edges: "spherical"= would restate what the
  coordinates *mean*, which is a semantic corruption, not a dropped member.
- *Should a =.dbf= field be sized to the data or fixed per type?* This writer
  sizes from the values; =ogr2ogr= uses a fixed default per type (=String
  (80.0)=, =Integer (9.0)=, =Real (24.15)=) and ignores the data. *Not a rule
  violation either way* -- on a route that carries the declaration the source's
  width wins and no default is consulted -- so it is only about what to invent
  on a carrier-less hop. Both sides measured, and each has one hard number:
  fixed widths cost *6.5x the file* (9.7 MB against 1.5 MB on 50,000 rows of
  four ordinary columns, because dBase records are fixed-width), and GDAL's
  fixed =Real (24.15)= **silently writes a different number** for =1e240= --
  =1.00000000000000008388608e23=, off by ~10^217, at warning severity -- where
  this writer widens to =Real (255.13)= and keeps it. Argued in full, with the
  =max(fitted, gdal_default)= floor that is the likely shape of a decision, in
  =same-format-fidelity.org= § OPEN QUESTIONS. /Do not decide this from the
  ratchet complaint alone: =schema_drop_warning= already tells the user the
  declaration did not survive that hop./
- *Raster GeoPackages* -- container scope puts tile pyramids in the domain
  while geosetta is vector-only. Recommendation on file is to *reject* a
  populated tile container rather than silently drop the imagery.
