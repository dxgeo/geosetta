** THE GOAL
#+begin_quote
*Read either OGC KML version, detecting which one was given. Write the version
the user asks for; by default the source's own version on a =kml -> kml= run,
and KML 2.2 from any other format. Warn when the version changes.*
#+end_quote

So =geosetta a.kml b.kml= on a KML 2.2 file writes KML 2.2, and
=geosetta a.kml b.kml --kml-version 2.3= writes KML 2.3 and says so.

*Only the OGC standards.* Google's pre-OGC KML 2.0 and 2.1 are out of scope,
for reading and writing alike (D-K8).

** WHAT THE STANDARD IS -- measured against OGC 12-007r2
OGC KML 2.3, approved 2015, is the latest. Read from the published text
(=https://docs.ogc.org/is/12-007r2/12-007r2.html=) on 2026-10-22; section
numbers are that document's.

- *The namespace did not change.* "The namespace for KML 2.3 is unchanged" from
  =http://www.opengis.net/kml/2.2= (§5.2). The version lives only in the root
  =version= attribute (=kml:kmlVersionType=, *default =2.2.0=*, §7.1). A 2.2
  document is a 2.3 document in the same namespace. /=ogckml23.xsd= itself
  declares =default="2.2"= (line 767) -- the same version either way. And
  =ogckml22.xsd= declares *no* =version= attribute at all, so a 2.2 document
  carrying one is invalid 2.2 (measured 2026-10-23): a 2.2 write never adds a
  stamp, it only gives back one its source had./
- *Minor-version compatibility* (§5.2): new components are optional, nothing is
  removed (only deprecated), and "any schema components unrecognized by a KML
  application shall be gracefully ignored". Deprecated components (§5.3) stay in
  the normative schema -- =kml:Snippet= (replaced by =kml:snippet=),
  =kml:Metadata= (replaced by =kml:ExtendedData=, deprecated since 2.2).
- *Element order is no longer enforced* "as of version 2.3" (§5.6).
- *Extension everywhere.* The schema is XSD 1.1 and declares
  =<defaultOpenContent mode="interleave"><any namespace="##other"
  processContents="lax"/>= (§6.7.2.3, Annex D.3), so foreign-namespace elements
  may be interleaved at *any* depth. Every element also takes an
  =anyAttribute= from a foreign namespace (§6.7.2.4). Both sit beside the older
  =*SimpleExtensionGroup= / =*ObjectExtensionGroup= substitution points.
- *Coordinates and datum* (§6.2, Annex B): longitude, latitude, altitude;
  "altitude is measured from the vertical datum, which is the WGS84 EGM96
  Geoid" -- EPSG:5773, i.e. a compound of EPSG:4326 and EGM96 height.
- *=altitudeMode= changes what Z means* (§9.20): =clampToGround= is the default
  and "the altitude value is ignored"; =relativeToGround= is height above
  terrain. 2.3 adds =kml:seaFloorAltitudeMode= (§9.21) and =altitudeOffset=.
- *2.3 brought Google extensions into the standard*: =kml:Track= (§10.15),
  =kml:MultiTrack= (§10.16), =kml:Tour= and its primitives (§9.23--9.32),
  =kml:SimpleArrayData=/=SimpleArrayField= (§9.7, §9.12), =kml:LatLonQuad=
  (§11.4), =balloonVisibility=, =horizFov=, =duration=, =altitudeOffset=,
  =TimeStamp=/=TimeSpan= inside =Camera= and =LookAt=, and the seafloor
  altitude modes. /Not/ adopted, by a search of the text and confirmed against
  the schemas on 2026-10-23: =outerColor=, =outerWidth=, =labelVisibility=,
  =physicalWidth=, =ViewerOptions=, =rank=, and =Icon='s =x=/=y=/=w=/=h=.
  /=drawOrder= was listed here as adopted until 2026-10-23, and is not:/
  =gx:drawOrder= orders line strings, while =kml:drawOrder= belongs to overlays
  and was already in 2.2 -- two elements sharing a local name. See § WHAT THE
  SCHEMAS SAY.
- *2.3 added three things that are not Google adoptions*, found by the
  schema's own version assertions rather than the text: a =uom= attribute on
  =SimpleField= and =Data=; =MultiGeometry= inside =Create=; and every
  geometry inside =Delete=.
- *Scale*: 147 =kml:= components are defined. The reader today handles about
  ten.
- *Conformance*: three classes, CL1--CL3 (Annex A); the abstract test suite is
  OGC 14-068. /Whether an executable 2.3 suite exists is unverified./

** DECISIONS
Taken 2026-10-22. =same-format-fidelity.org= D18 is the crate-level summary.

*** D-K1 -- read both OGC versions, detected; refuse everything else
The reader identifies the version per § VERSION DETECTION and raises it into one
model. A pre-OGC namespace (2.0, 2.1), an unknown KML namespace or an unknown
=version= is *refused* with an error naming what was found, not guessed at --
the crate's convention everywhere else.

*** D-K2 -- the output version is the flag, else the source's, else 2.2
=--kml-version <2.2|2.3>= is a format-specific output flag like
=--rtree= and =--envelope=, with one difference: those are ignored for other
output formats, and this one is a *usage error* unless the output is
=kml=/=kmz=. Ignoring an explicit request about content would be a silent drop.

Resolution, in order:
1. =--kml-version=, if given;
2. the version recorded in the KML native (visible only through
   =payload_for(Format::Kml)=, so only after a KML read);
3. 2.2.

/Step 3 was 2.3 until 2026-10-23./ It changed on measurement, not preference:
2.3 renamed the =gx:= elements it adopted into the KML namespace, and no reader
measured reads those names (§ MEASURED IN A RENDERER). A non-KML source written
as 2.3 would carry its tracks as =kml:Track=, which Google Earth Web, GDAL LIBKML
and CesiumJS all accept as a Placemark with no geometry, silently. The same
track as 2.2 + =gx:= is read by all three. 2.3 stays fully supported -- read,
detected, modelled, and written on request -- and is still the model (D-K4),
since it holds everything 2.2 does. It is the *default* that moved. It is also
what this writer emitted before the plan: OGC's 2.2 namespace, no =version=, so
the default output does not change for anyone.

The library exposes a public =KmlVersion= enum, threaded to the KML writer the
way =rtree= reaches the GeoPackage writer. =#[non_exhaustive]=, for D7's
reason: a KML 2.4 would otherwise be a breaking change downstream.

*** D-K3 -- the same-format invariant holds unchanged
Because the default is the source's own version, and every version read is a
version written, =kml -> kml= is never an upgrade. KML needs *no* clause of its
own in =same-format-fidelity.org=: a 2.2 or 2.3 input comes back as it went in.

*A version does not cross a pipe.* =kml -> geojson | tool | -> kml= and
=kml -> fgb -> kml= both come back as 2.2, because the version rides in a native
and natives do not survive a pipe (=same-format-fidelity.org= D5). That is the
contract working, not a defect; the README must say so before someone files it.

*** D-K4 -- a typed 2.3 document model in the native; the IR is its projection
Option A or B ("raw names in =XmlElement=" or "carry byte ranges"), posed in
=handoff.org= § WHAT IS NOT BUILT, was the wrong question once the target became
the standard. Two facts settled it:

- 2.3 allows foreign content *inside* modelled elements (§6.7.2.3--4), so a
  side channel next to the IR would have to carry content from within the
  elements the IR projects. It cannot do that cleanly.
- A 2.2 source cannot be replayed byte for byte into a 2.3 output: its adopted
  =gx:= elements are respelled (D-K10). Everything in a KML namespace must be
  *parsed and transformed*.

So:
- The KML native holds a *typed model of the whole document*, in 2.3 terms,
  where every node has slots for its foreign attributes and foreign elements.
- The IR (=Feature=, =FeatureCollection=) is a *projection* of that model.
- The writer *reconciles*: projected members come from the IR (which a route
  (a) caller may have edited), everything else from the model. Precedent:
  =geopackage/reconcile.rs=.
- *Verbatim bytes survive only for content outside every KML namespace* --
  foreign elements and attributes, and comments. Those carry as source slices,
  the way =json::raw_at= slices PROJJSON out of =geo=.

*This does not breach D1.* D1 forbids the *hub* from modelling format
semantics; the model is the KML spoke's payload, opaque to the hub like every
other one. The only thing that reaches the IR is the projection.

*Per-feature content travels with its feature.* Folder membership is a
feature-level native (the folder path), so =--sort-hilbert= and edits do not
detach a Placemark from its folder -- the identity class of D4. A skeleton of
the document with numbered slots for the placemarks was rejected: it breaks the
moment a feature is added, removed or reordered.

*** D-K4a -- "typed" means an identified node tree, not a struct per type
/Decided 2026-10-23, before K3./ 2.3 defines 168 concrete elements and 81
complex types, and "a typed model" fits two designs that differ by thousands
of lines. Taken: *every element in a KML namespace is resolved to a closed enum
of the 2.3 vocabulary*, with the namespace it was spelled in recorded beside it,
and keeps its attributes, children, text and comments on a generic node; an
element in no KML namespace is carried as its source bytes. Rejected: one Rust
struct per complex type, with a typed field per child and attribute. Four
reasons:

- *The round trip has to survive invalid documents*, and real ones are:
  =hand_hostile.kml= is out of 2.2's order, gpslogger interleaves track
  children, a stampless =kml:Track= is invalid 2.3. Per-type structs need a slot
  for every misplaced or duplicated child; a node tree keeps what was there.
- *The transforms are tables*: respelling is keyed on (namespace, local name,
  parent) and 2.2's order is =ogckml22.xsd='s sequences. As tables they are
  transcribed from the schemas and checked against them, as the 23 version
  assertions were (K2).
- *Typed reading is needed only where something reads*: the projection
  touches about fifteen element kinds; the other ~150 are carried, reordered
  and respelled.
- *It is still typed where D-K6 needs it*: no raw name reaches the logic, so
  local-name matching cannot return.

/The cost/: the compiler does not check an element's structure. The XSD
oracle on every write (K5) checks it instead, and more thoroughly. /When this
would be the wrong call/: if the crate came to *build* rich KML from other
formats -- styles, views, regions, network links. It builds placemarks,
geometry, =ExtendedData= and time. Typed builders producing nodes can be added
for whatever it starts building, without redoing the model.

*** D-K5 -- spelling provenance is recorded, and the round trip is the test
Several source spellings map to one 2.3 construct. The model records which one
the source used, so a same-version write reproduces it:

| source spellings                                   | 2.3 construct       |
|----------------------------------------------------+---------------------|
| =earth.google.com/kml/2.2= vs =opengis.net/kml/2.2= | the KML namespace   |
| =Snippet= vs =snippet=                              | =kml:snippet=       |
| =gx:Track= vs =kml:Track= (and each adopted =gx:=) | the adopted element |
| =Metadata= vs =ExtendedData=                        | =kml:ExtendedData=  |
| absent =version= vs explicit =2.2.0=                | the version stamp   |
| no =xmlns= vs the OGC namespace (D-K13)            | the KML namespace   |

*The invariant*, for every supported version /v/: lowering the raised model of a
version-/v/ document back to /v/ gives that document back. Checked over one
hostile fixture per version.

*** D-K6 -- =xml.rs= becomes namespace-aware
Elements and attributes are identified by (namespace URI, local name), with
prefix bindings tracked in scope. The prefix as written is kept so output can
repeat it. Foreign attributes are kept, not stripped. Comments and their
positions are kept for the verbatim channel. The parser records element byte
offsets so D-K4 can slice foreign content.

=kml.org= § What the warning says called a =raw_name= on =XmlElement= "a
cosmetic gain". Under the standard it is a correctness fix: an extension element
whose local name is =Point= is read as a KML Point today.

*** D-K7 -- three warnings, kept separate
1. *The version changed*, one line, counted per construct:
   #+begin_src text
     warning: kml: input is KML 2.2; written as KML 2.3 (gx:Track→Track ×3, Snippet→snippet)
   #+end_src
   It fires only when =--kml-version= differs from the source *and* at least
   one construct was respelled. A run that changes only the =version= stamp
   is silent, because that is exactly what was asked for (open question 4,
   decided 2026-10-22). A conversion from another format has no previous
   version and says nothing.
2. *Lost on a downgrade* to 2.2 -- the ordinary lossy-conversion warning,
   naming each construct. Under the crate's fidelity-over-warning preference,
   the =gx:= equivalent is *written* wherever one exists; only what genuinely
   has none is reported.
3. *Cross-format losses* -- unchanged, =lossy-conversion-warnings.org=.

/No fourth warning about readers./ A 2.3 write whose adopted elements no
measured reader reads (§ MEASURED IN A RENDERER) says nothing about it. Nothing
is lost -- the output is the standard -- and =--kml-version 2.3= is only ever
an explicit request, so whoever made it has chosen the standard over what
readers support. Ruled 2026-10-23. The *version-changed* warning above still
fires on a 2.2 source written as 2.3, because that one reports a respelling.

*** D-K8 -- KML 2.0 and 2.1 are out of scope
Google's pre-OGC versions are neither read nor written; D-K1 refuses them by
namespace. Taken 2026-10-22, on two grounds:

- *They are not OGC standards*, and the goal is the standard.
- *Their consumers are going away.* Google deprecated the Maps JavaScript API's
  =KmlLayer= (effective 2026-04-30) and is discontinuing Google Earth Pro
  downloads. The *format* is not deprecated -- it is OGC's -- but the reason to
  write versions older than 2.2 is gone.

What this removes: a phased rollout (every version read is now a version
written, so there is no interim fallback), the sourcing of two undocumented
versions, and the hardest inverse D-K5's round trip would have needed -- 2.1's
schema-extended placemarks (believed, never sourced).
/If 2.0/2.1 input turns out common, reading it is additive: an upgrade-only
front end into the same model, with its own sourcing./

*** D-K9 -- =<Schema>= is a column declaration
=SimpleField= types (=string=, =int=, =uint=, =short=, =ushort=, =float=,
=double=, =bool=) declare columns, so reading every =SimpleData= as a string is
unfaithful. They map to =DeclType=, and =Format::carries_column_schema= answers
=true= for KML -- a fifth declaring spoke under D1's column-schema exception.
=<Data>= (no =Schema=) stays untyped text, under D17.

*** D-K10 -- adopted =gx:= elements move with the version; the rest stay foreign
On a write to 2.3, each =gx:= element 2.3 adopted is written in the KML
namespace (=gx:altitudeMode= with a seafloor mode becomes
=kml:seaFloorAltitudeMode=) unless the source spelled it =gx:= and the run is
same-version (D-K5). On a write to 2.2 they lower back to =gx:=. Elements 2.3
did *not* adopt stay =gx:= foreign content, carried verbatim.

/Reopened and re-closed 2026-10-23, unchanged./ § ORACLES made this decision
conditional on one measurement -- whether Google Earth reads =kml:Track= -- and
it does not; nor do GDAL LIBKML or CesiumJS (§ MEASURED IN A RENDERER). The
rule did not change. The default did: D-K2's step 3 is now 2.2, so this rule
applies only when 2.3 is asked for, and then the standard's spelling is the
right one to write (open question 9). =gx:drawOrder= joins the non-adopted
group, carried verbatim.

*** D-K11 -- a Track's per-vertex data lives in the native only
/Decided 2026-10-22, answering open question 1./

A =Track= projects into the IR as =kml.org= § GEOMETRY ELEMENT COVERAGE already
ruled: =LineString Z= for =Track=, =MultiLineString Z= for =MultiTrack=. What
the IR cannot hold -- the =when= series, =angles=, per-sample
=SimpleArrayData= and an attached =Model= -- stays in the KML model in the
native. So:

- *=kml -> kml= is lossless*, whichever of 2.2 (=gx:=) and 2.3 (=kml:=) is
  written.
- *Cross-format drops the per-vertex data*, and warning 3 names what went
  (=Format::Kml='s loss list states it separately from a Placemark's own
  =TimeStamp=/=TimeSpan=, which is one instant per feature).
- *No IR change.* Rejected:
  - *the =m= ordinate* -- relabels a measure as time, and turns it into a
    =Double= in every spoke that writes =m= (=kml.org='s own reasoning);
  - *a T ordinate on =Position=* -- two spokes with a slot (KML, FlatGeobuf's
    =has_t=) is below D1's bar, FlatGeobuf leaves T's unit undefined, and
    angles and per-sample data would still have no home.

/Left open, and additive: copying the =when= and =SimpleArrayData= arrays into
array-valued properties so they reach other formats and survive a pipe. It
would need the writer to check array lengths against geometry an edit may have
changed. Nothing in D-K11 has to be undone to add it./

*** D-K12 -- the vertical datum is stated where it is true, and Z's meaning travels as properties
/Decided 2026-10-22, answering open question 2./

*It stays inside geosetta.* =Crs= is opaque, and the compound CRS has a code of
its own: *EPSG:9707, "WGS 84 + EGM96 height"* (=projinfo= gives
=COMPOUNDCRS[...]=; geoscribe's name table already lists it). *Stating* it needs
no other crate. *Transforming* heights is reprojection work, which is moving
from nazca to geoscribe (it holds the CRS database), and only the write side
needs it.

**Read.**
- A collection is =EPSG:9707= when every geometry carrying a Z -- each leaf of a
  =MultiGeometry= counted separately -- is =altitudeMode= =absolute=, the only
  mode in which Z is an EGM96 height (§6.2, §9.20). Otherwise it is
  =Crs::Wgs84=, and warning 3 names the vertical meaning left unstated.
- =altitudeMode=, =seaFloorAltitudeMode=, =extrude= and =tessellate= project
  as per-feature properties, *only when the source had the element*. Z values
  are kept as written in every mode -- a =clampToGround= Z is the source's
  statement, ignored for rendering, not absent. On write, the KML writer
  reconciles the elements from the properties (D-K4).

**Write.** From a source whose vertical datum is not EGM96 -- =EPSG:4979='s
ellipsoidal heights, say -- Z is written unchanged *with a named loss warning*:
the heights are now labelled EGM96 and are not. The transform is logged as a
cross-repo item in =geocore/todo.org=, against geoscribe's reprojection. It is
composed by a caller or a pipe, never by geosetta depending on geoscribe
(=architecture.org=
§ THE COMPOSITION MODEL), and the warning names that composition.

**Measured against GDAL 3.13.3 LIBKML, 2026-10-22** -- and it is a gap, not an
oracle (=same-format-fidelity.org= § THE ORACLE RULE):
- *Read*: Z kept verbatim in every mode; =altitudeMode=, =extrude=,
  =tessellate=, =visibility= exposed as fields; the SRS reported as 2D WGS 84,
  never vertical.
- *Absent elements*: =tessellate= and =visibility= read as =-1= and are omitted
  on write, which round-trips. =extrude= reads as =0= and is *written* as
  =<extrude>0</extrude>=, an element the source never had. Hence "only when
  present" above, with no sentinel.
- *Write*: no vertical handling at all. A point at Zürich with an EPSG:4979
  height of 500 m is written as =500=; its EGM96 height is =452.66=
  (=cs2cs EPSG:4979 EPSG:9707=), so GDAL places it ~47 m high, silently.

/Projected property names can collide with an =ExtendedData= key of the same
name -- the question =kml.org= § OPEN QUESTIONS already asks of
=name=/=description=, now with more members. A test case, not a design
decision, until a real file shows it./

*** D-K13 -- a document with no namespace is read as KML 2.2
/Decided 2026-10-22, answering open question 3./

Strictly, an un-namespaced =<kml>= is not KML: §5.2 defines every component in
the OGC namespace. In practice everything reads it -- measured 2026-10-22 on a
one-Placemark file: GDAL LIBKML, GDAL's built-in =KML= driver and geosetta
today all return the feature. Refusing it would be a regression.

So it is read as OGC 2.2, or as whatever a =version= attribute declares, and
D-K5 records that the namespace was absent. A same-version =kml -> kml= run
writes it back without one; a run to 2.3, or from another format, gets the
namespace. *No warning*: nothing is lost, and an informational line on every
such file would be noise, not a loss report.

*** D-K14 -- overlays with geography are features; the rest stay in the native
/Decided 2026-10-22, answering open question 5./

- *=GroundOverlay= → a =Polygon=*: its footprint from =LatLonBox= *with
  =rotation= applied*, or from =LatLonQuad= as written.
- *=PhotoOverlay= → a =Point=*, from its own =Point=.
- *=Icon= =href= → an =icon= property* on both.
- *=ScreenOverlay=* has no geography and stays in the document-level native.

The per-feature native records *which KML feature it was* and the exact
=LatLonBox= with its =rotation=, so a =kml -> kml= run writes a =GroundOverlay=
back as one, not as a Placemark. If an edit leaves a footprint that is no longer
a rotated box, the writer emits =LatLonQuad= (=gx:LatLonQuad= when writing 2.2).
From another format, a polygon is a Placemark: nothing says it was an overlay.

*Measured against GDAL 3.13.3, 2026-10-22* (=ov.kml=, one of each overlay):
LIBKML returns a =GroundOverlay= as =POLYGON Z= with an =icon= field and
*ignores =rotation=* -- a box rotated 15° comes back unrotated, so the footprint
is not where the image is. It *drops* =PhotoOverlay= and =ScreenOverlay=. The
built-in =KML= driver drops all three.

/The plane of the rotation -- ***measured 2026-10-23: the ground.***/ §11.3.3
says =rotation= turns the overlay "about its center, in decimal degrees ...
counterclockwise", with 0 at north, but not whether the corners rotate in
degree space or on a local metric plane. The two differ away from the equator.
Google Earth Web turns it *on the ground*, counter-clockwise: at 60°N all four
corners of a 45° turn land on the ground-plane prediction, and the
degree-space prediction is ~80 km off (§ MEASURED IN A RENDERER). So the reader
computes the footprint by scaling longitude offsets by cos(latitude of the
centre), turning, and scaling back. Its docs say so, and cite this measurement.

/What the measurement could not separate/: a local metric plane and Web
Mercator put those corners 1.7 km apart, about 3 pixels at the zoom that
showed the whole overlay. ***Separated 2026-10-28: the local plane*** (§
MEASURED IN A RENDERER, *The rotation plane, at scale*) -- open question 10,
decided. The reader's model is the renderer's.

/A 2008 claim to the contrary/ -- "GE draws GroundOverlays by rotating them on
the lat/lon plane", from a member of Google's KML developer group, not Google --
does not describe current Earth Web. It is the source of the degree-space
corner formula that circulates online, so expect to meet it.

*** D-K15 -- a feature's time projects as GDAL-named properties, verbatim
/Decided 2026-10-22, answering open question 6./

=TimeStamp/when= projects as a =timestamp= property, and =TimeSpan= as =begin=
and =end= -- GDAL LIBKML's names, so a file GDAL wrote comes back to KML with
its times. The value is *the source's text*. A column is declared a date-time
only when every value in it is a full =xsd:dateTime=, which is D17 applied per
column, as for CSV. KML's time type (§16.11) also admits =xsd:date=,
=gYearMonth= and =gYear=, and those stay text. On write, the KML writer
rebuilds =TimeStamp=/=TimeSpan= from the properties (D-K4).

This is one instant or interval *per feature*. A =Track='s per-vertex =when=
series is D-K11's and stays in the native.

*Measured against GDAL 3.13.3, 2026-10-22* (=t.kml=):
| source                           | LIBKML reads                   | writes back |
|----------------------------------+--------------------------------+-------------|
| =2026-10-22T14:30:00Z=           | =timestamp= DateTime           | same |
| =2026-10-22T09:30:00-05:00=      | =timestamp=, offset kept       | same |
| =<begin>2026-01=                 | =2026/01/01 00:00:00=          | =2026-01-01T00:00:00= -- *widened* |
| =<end>2026-03-15=                | =2026/03/15 00:00:00=          | =2026-03-15T00:00:00= -- *widened* |
| =<when>1997=                     | *nothing -- the value is lost* | -- |

*** D-K16 -- the document model stays crate-private
/Decided 2026-10-28, answering open question 11./

=KmlNative='s =document= and =KmlFeatureNative='s contents stay
=pub(crate)=. A library caller sees a KML document through the IR, and edits
it there. This is a ruling, not a deferral, so the difference from the other
spokes' natives -- whose contents are public -- is not an oversight.

- *The IR is the one edit surface* (D-K4). The writer reconciles the IR
  against each feature's stored element; a public model would be a second
  way to change the same member, and the writer would need a rule for which
  edit wins.
- *The model carries invariants a caller could break silently.* A feature's
  =Address= is a path of child indices into the skeleton: a caller adding or
  removing a folder's children would send features to the wrong container,
  or to the default one, with no warning -- the spoke's fidelity guarantee
  made the caller's problem. The other natives are flat members with no such
  coupling, which is why they can be public.
- *The surface would be large and unstable*: the node tree, the 168-variant
  vocabulary generated from the schemas, the spellings, the skeleton and the
  addresses. A regenerated vocabulary or a later KML version would break
  callers; K4's own rework of the addressing would have.
- *No caller needs it.* nazca and geoscribe read no native, and none has been
  asked for.

/If a caller needs to see what the IR does not hold/ -- styles, folder names,
network links -- the additive step is a read-only accessor returning the
skeleton as KML text: no new types, no invariants exposed, stable however the
model changes. Making the tree itself public stays the last resort, and would
need =#[non_exhaustive]= on the vocabulary.

** VERSION TRANSFORMS
*** 2.2 ⇄ 2.3 -- sourced
- Version stamp.
- =Snippet= ⇄ =snippet=; =Metadata= → =ExtendedData= (upward only; 2.3 still
  admits =Metadata= as deprecated, so a same-version run keeps it).
- Each adopted =gx:= element ⇄ its =kml:= form (D-K10). /The =gx:= spellings of
  =horizFov=, =duration= and =altitudeOffset= are confirmed (2026-10-23)/:
  same local name, same parents, in =kml22gx.xsd=, =ogckml23.xsd= and Google's
  KML reference. The full mapping is § WHAT THE SCHEMAS SAY.
- =gx:Track='s children must be *grouped* -- every =<when>=, then every
  =<gx:coord>=, then every =<gx:angles>=: =kml22gx.xsd= declares them as a
  =sequence=. 2.3 declares =kml:Track='s as =xs:all=, which also admits
  interleaving. So lowering an interleaved 2.3 track to 2.2 must regroup it,
  and the writer should emit the grouped order in both versions, since it is
  the only order both accept. /An interleaved =gx:Track= is reported not to
  draw in Google Earth Pro -- gpslogger issue 1335./
- Expected lossless in both directions, because =gx:= covers what 2.3 adopted.
  Each claim is a test, not an assumption, and every transform gets a fixture
  before it is implemented, per README.org § Sourcing a fixture from a real
  tool.

** MILESTONES
- *K1 -- =xml.rs=*: namespace resolution, prefixes kept, foreign attributes
  kept, comments kept, byte offsets, UTF-16 and declared encodings. D-K6.
  ***Built 2026-10-23.*** Every element and attribute carries its namespace
  URI and its prefix as written; declarations are attributes in the xmlns
  namespace, scoped to their element, and an unbound prefix is kept with no
  namespace rather than refused. Comments and processing instructions keep
  their position among an element's children (=XmlElement::misc=), and those
  around the root are on =XmlDocument=. Each parsed element records its
  source =span=. =xml::decode= takes bytes: BOM, UTF-16's first-bytes pattern,
  then the declared =encoding= -- UTF-8, UTF-16, US-ASCII and ISO-8859-1
  exactly, any other only over all-ASCII bytes (=encodings.org= E5). The
  namespace-blind =child=/=children_named= are gone, so local-name matching
  cannot come back by accident. Measured on a 35 MB, 200,000-Placemark file:
  0.36 s before, 0.38 s after.

  *Applied to today's reader at once*, since leaving it on local names would
  have kept the bug D-K6 names: =kml/reader.rs= matches KML by namespace
  (OGC 2.2, Google's 2.0--2.2, or none), so an extension's =<x:Point>= is no
  longer read as a Point, and does not descend into extension subtrees. A
  root in a non-KML namespace is refused with the namespace named -- D-K1's
  refusal, early, because matching by namespace would otherwise read such a
  file as empty, silently. Google's 2.0/2.1 are still *read*; refusing them
  stays K2's, with the version detection it belongs to.
- *K2 -- versions*: detection per § VERSION DETECTION, =KmlVersion=, the version
  in the native, =--kml-version=, the refusal of 2.0/2.1, and warning 1.
  Needs the read-time warning channel
  (=lossy-conversion-warnings.org= § 2b) -- the source version is a read fact.
  /Built 2026-10-23./ ***K2 built 2026-10-23.*** =KmlVersion= is public and
  =#[non_exhaustive]=; =NativePayload::Kml(KmlNative)= records the detected
  version and the namespace and =version= stamp as written. Both the =.kml= and
  =.kmz= writers read a native tagged either way, since the two hold one
  document; a =.kmz='s provenance is its first entry's, the one it is written
  back as. Resolution is D-K2's: =--kml-version= (a usage error for any other
  output, and with =--print-crs*=), else the native's version, else 2.2. The
  library form is =convert::write_kml_features=. Every write validated:
  geosetta's 2.2 output against =ogckml22.xsd= under =xmllint=, its 2.3 output
  and a 2.3 round trip against =ogckml23.xsd= under =xmlschema='s XSD 1.1.

  /Warning 1 is built as nothing, correctly./ It fires only when a version
  change *respells* a construct, and today's writer emits no construct that
  2.2 and 2.3 spell differently -- a track is written as a =LineString=, its
  per-vertex data already reported at read. It gains its first respelling with
  K5's writers, which is where it belongs. The same holds for D-K7's warning 2.
- *K3 -- the model*: the typed 2.3 document model with extension slots, raised
  from 2.2 and 2.3. Geometry group first (=LinearRing=, then =Track=/
  =MultiTrack=, =Model= carried), then features and containers, ids, styles,
  =Schema=/=ExtendedData=, time, views.
  ***Built 2026-10-23, as D-K4a's node tree*** -- =src/kml/model.rs=. Under
  that design the element-by-element order above collapses: the whole
  vocabulary is raised at once, and the order it lists becomes the order K4
  *reads* the model in. What is there:
  - =KmlElement=, all 168 concrete 2.3 elements, with =from_name=/=name= and one

    145 elements are a subset, so 2.3's vocabulary is the model's. Two pairs

  - =Node=/=KmlDocument=, =raise= and a same-version =write=. Foreign content is
    its source slice; a name in a KML namespace that 2.3 does not define is

  - *D-K5's invariant at the XML level*: writing a raised document parses to
    the document it came from. Tested over every =.kml= fixture, every entry of
    GDAL's layered =.kmz=, and a hand-built document with comments, PIs,
    foreign elements and attributes, and a =gx:Track=.

  order table and the version transforms are K5's./
- *K4 -- projection and reconcile*: the IR as a projection; IR wins for
  projected members on write; =Schema= → =DeclType= (D-K9).
  ***Step 1 built 2026-10-23: Placemarks, and the same-version write.***
  - *The reader parses straight into the model* (=model::parse=, through a
    =Builder= the XML parser now takes), so a large document never exists as
    an =XmlElement= tree beside its model. =document::split= takes each
    projected feature out, with its address -- the container's path and its
    slot among the container's other children -- and the comments just before
    it; the rest is the collection's skeleton, in =KmlNative=. Each feature's
    element is a new =NativePayload::KmlFeature(KmlFeatureNative)=.
  - *Only containers hold features*: the root, =Document= and =Folder=. A
    Placemark inside a =NetworkLinkControl='s =Update= is an instruction to
    another document and stays in the skeleton -- before this it became a
    feature.
  - *The writer reconciles* (=kml/reconcile.rs=), when the source was KML or a
    single-document KMZ and the output is its own version. An unedited
    feature is written exactly as read; an edited one has only what changed
    rewritten -- =<name>=, =<description>=, an =<ExtendedData>= value, the
    geometry -- and an added element goes where =PlacemarkType='s sequence
    puts it. An edited geometry keeps its element's other children where it
    can: a Point or line string takes new coordinates in place, and a track
    edited to the same vertex count keeps its =<when>= series. A feature with
    no native joins the document's first container, in its KML prefix.
    Reordering moves a feature only among the features beside it: it is not
    carried past content the IR does not hold.
  - *Measured*: =hand_hostile.kml= and the =gx:Track= probe come back from
    =kml -> kml= as the same XML; the registry's =kml= and =kmz= hops compare
    every native equal. =Format::same_format_losses='s KML row lost its three
    entries (styles, folders/overlays/models, timestamps/altitude modes) and
    now names only what the XML layer normalises.
  - *Warnings moved to the write* (=convert::kml_write_warnings=): a =<Model>=
    or a track's per-vertex data when the write cannot give the model back --
    another format, a version change, a layered =.kmz= -- and a track an edit
    gave another vertex count. A *version change* is built from the IR alone
    until K5, and says so.
  - *Cost, on a 35 MB, 200,000-Placemark file*: a read takes 546 MB and 0.30 s
    (534 MB and 0.27 s before); =kml -> fgb= 560 MB, less than before, since
    =main.rs= releases natives the target's writer will not read; =kml -> kml=
    812 MB (626 MB), because it now carries the document. The first version
    held 3.5 KB per feature -- =collect= reusing the parse tree's buffers in
    place -- and built two trees; both are fixed and commented where they
    were.
  - /The model stays crate-private/ (=KmlNative='s =document=,
    =KmlFeatureNative='s contents): whether it is public like the other
    natives' contents was left until after K5 (2026-10-23), and is D-K16:
    it stays private.
  ***Step 2 built 2026-10-24: the rest of the projection.*** One function,
  =project::project=, still says what a feature is, and the writer still
  re-projects to find what an edit changed; it now reads a =Context= -- the
  document's =<Schema>=s, which stay in the skeleton -- and the properties come
  in a fixed order: =name=, =description=, time, =icon=, the altitude members,
  then =<ExtendedData>=.
  - *Overlays (D-K14).* =<GroundOverlay>= and =<PhotoOverlay>= are features
    beside =<Placemark>= (=project::is_projected=); =<ScreenOverlay>= stays in
    the skeleton. A ground overlay's footprint is its =<LatLonQuad>= (either
    spelling) as written, else its =<LatLonBox>= turned on the ground --
    longitude offsets scaled by cos(centre latitude), turned
    counter-clockwise, scaled back -- and an unturned box is its edges with
    no arithmetic. The test is § MEASURED IN A RENDERER's own table: the 4°×2°
    box at 60°N turned 45° lands on all four ground-plane corners. A missing
    edge takes 2.3's default; 2.2's puts =north= at 180°, which is not a
    latitude. /On write/: a footprint that is still a turned box goes back
    into its =<LatLonBox>=, an edge the edit did not move keeping its
    spelling; one that is a quadrilateral but no box becomes =<LatLonQuad>=,
    =<gx:LatLonQuad>= in 2.2, declared on itself; an overlay already given as
    a quad stays one. The inverse rounds to 10 decimal places of a degree --
    a hundredth of a millimetre -- because turning there and back gives
    =13.000000000000002=. *A geometry an overlay cannot hold* -- a triangle, a
    hole, a line -- makes the feature a Placemark, its =icon= in
    =<ExtendedData>=, and =drop_warnings= says so; D-K14 did not rule this
    case.
  - *Time (D-K15).* =timestamp=, =begin=, =end= as the source's text; a column
    is declared =DateTime= when it has a value and every value is a whole
    =xsd:dateTime=. On write the properties rebuild =<TimeStamp>= or
    =<TimeSpan>=, keeping the stored primitive's =id= when the kind is the
    same; a stamp wins over a span, and a value that is no KML time
    (=dateTime=, =date=, =gYearMonth=, =gYear=) goes to =<ExtendedData>=.
    =Format::recast_column= knows the three keys, so a time column into KML is
    not reported as recast to text.
  - *=<Schema>= (D-K9).* A =<SimpleData>= is typed by the =<SimpleField>= its
    =<SchemaData schemaUrl="#id">= names: =int=/=uint=/=short=/=ushort= to
    integers in range, =float=/=double= to finite floats, =bool= from
    =true=/=false=/=1=/=0=. A value that is not of its type stays its text --
    kept, not refused or guessed at -- and empty text in a typed field is
    null. Each field is a =FieldDecl= (=int= → =Int32=, =short= → =Int16=,
    =float= → =Float32=, ...); a name two schemas type differently is declared
    by neither, and a schema in another document is not read.
    =Format::carries_column_schema= answers =true= for KML and KMZ, and the
    writer emits one =<Schema>= for the columns a collection declares, with
    =<SchemaData>= per feature. KML has eight field types, so =Int8=/=UInt8=
    widen to =short=/=ushort=, and =Int64=, =UInt64=, =Json=, =DateTime=,
    =Date= and =Binary= are written =string= -- six recasts, warned, and
    pinned in =every_declared_type_survives_or_is_admitted=. KML declares a
    type and nothing else, so =schema_drop_warning= now reports a width,
    precision or constraint bound for KML on its own. An unedited typed value
    keeps its spelling (=1.50= in a =double=): the reconcile compares values
    as the projection reads them.
  - *Altitude modes (D-K12).* =altitudeMode=, =seaFloorAltitudeMode=, =extrude=
    and =tessellate= project as their text, where the source has the element;
    across a =<MultiGeometry>= a member projects when every member stating it
    states the same, and one they disagree on stays in the model. On write a
    member is set on every carrier that can hold it -- =<tessellate>= only on
    line-like geometry -- and a value the element does not admit goes to
    =<ExtendedData>=. The two modes are one choice in the schema, so setting
    one removes the other; a sea-floor mode is =<gx:altitudeMode>= in 2.2.
    *The collection is EPSG:9707* when every leaf with a Z is =absolute= -- a
    track inheriting its multi-track's mode, an absent mode =clampToGround= --
    and =Crs::Wgs84= otherwise. 9707 is carried *by code alone*: geosetta has
    no registry and invents no definition (=crs.rs=), so a GeoParquet or
    Shapefile write of an all-absolute KML asks for one with =--crs=, as any
    bare code does. A KML write of 9707 does not warn; a GeoJSON write says
    the heights move from EGM96 to the ellipsoid. *Warning 3's vertical
    meaning* is =drop_warnings='s =Vertical= cause: a write to another format
    of features whose Z is no EGM96 height.
  - *What the spec text left to this milestone*, decided in the code: a
    property under a member's key is never lost, only moved -- written as the
    element when the value admits it, in =<ExtendedData>= otherwise, and only
    its first occurrence is the member (=kml/place.rs=); a feature built
    fresh for a reconciled document writes =<Data>=, since the document's
    schemas were written for the features it held.
  - *Measured* on the 35 MB, 200,000-Placemark file (peak resident size,
    release build): =kml -> fgb= 587 MB (560 MB at step 1), =kml -> kml= 869 MB
    (812 MB at step 1), the output byte-identical to its input. It measured
    913 MB at first; the same build with the write-side projection skipped
    measured 821 MB, and turning off the new members' projection changed
    nothing, so the cost is the comparison pass's temporaries rather than
    what step 2 projects. Comparing the projection without first cloning each
    feature's properties took 44 MB of it back. No build of step 1 was kept to
    measure beside this one, so the step-1 figures are the ones recorded
    above, not re-measured.
  - *Oracles*: every kind of write -- fresh 2.2 and 2.3, and an edited 2.2 and
    2.3 document with a moved turned box, a quad, a sea-floor mode, a span and
    an icon -- validates against =ogckml22.xsd= (with =kml22gx.xsd=) and
    =ogckml23.xsd= under =xmlschema=, and GDAL LIBKML reads the fresh 2.2
    output's typed =double= as =Real=, its =timestamp= as =DateTime= and its
    =gx:altitudeMode= as =altitudeMode=.
- *K5 -- writers*: the lowering to 2.2 first, since it is the default (D-K2),
  then 2.3 (D-K10). One hostile fixture
  per version; the D-K5 round trip over each; XSD validation of every write.
  =Format::Kml='s three =same_format_losses= entries go.
  /Lowering is a reorder as well as a respelling./ =ogckml23.xsd= declares 79
  =<all>= groups and =ogckml22.xsd= none, so 2.3 admits children in any order
  where 2.2 fixes one. A valid 2.3 document lowered by respelling alone can be
  invalid 2.2: =hand_hostile.kml= is valid 2.3 and invalid 2.2 for exactly this
  reason. The 2.2 writer emits children in =ogckml22.xsd='s sequence, and
  D-K5's spelling provenance does not extend to order on a version change.
  ***The lowering to 2.2 is built, 2026-10-28.*** A 2.3 read written with
  =--kml-version 2.2= is reconciled into its own document as a same-version
  run is, and the result lowered (=kml/lower.rs=); a write from another
  format was already 2.2 and is unchanged.
  - *The order is generated, not transcribed*:
    =tests/fixtures/gen_kml22_order.py= reads =ogckml22.xsd= and
    =kml22gx.xsd= and emits, per parent and spelling, each child's slot in
    the type's sequence, flattened through base types, with every element
    that substitutes for an abstract group -- which is how =gx:Track= reaches
    a Placemark's geometry slot and =gx:altitudeMode= a Point's mode slot.
    Children are stably sorted by slot. *The schema's order is not the one a
    reader guesses*: =gx:altitudeOffset= and =gx:horizFov= sit in their
    parent's extension groups, which come /before/ the parent's own members,
    and =gx:balloonVisibility= comes after =<ExtendedData>= and before a
    Placemark's geometry.
  - *Spelling is keyed on the parent* (§ WHAT THE SCHEMAS SAY): the spelling a
    child has is kept where 2.2 admits it there, else the one 2.2 admits.
    =<TimeStamp>= stays =kml:= on a feature and becomes =gx:= in a view;
    =<value>= stays =kml:= in =<Data>= and becomes =gx:= in
    =<SimpleArrayData>=. A track's =<when>=, =<gx:coord>= and =<gx:angles>=
    come out grouped by the same sort. =gx:= is declared once, on the root,
    reusing a binding the source already has.
  - *Foreign content*: what the schemas name -- =atom:author=,
    =xal:AddressDetails=, a =gx:= element 2.3 did not adopt -- takes its slot,
    its prefix resolved through the declarations in scope; anything else moves
    with the element before it. Comments move with the element they precede.
  - *What 2.2 has no place for*, measured by setting every parent/child pair
    =ogckml23.xsd= admits against the generated table: a geometry in
    =<Create>= or =<Delete>=, a =<LatLonBox>= or =<LatLonQuad>= in a
    =<Region>=, a =<LatLonAltBox>= on a ground overlay, and the =uom=
    attribute. Every 2.3 /element/ has a 2.2 or =gx:= spelling. These are
    dropped and named in D-K7's warning 2; =<Region>='s box could instead be
    written as the =<LatLonAltBox>= it equals when unturned, which is not yet
    done.
  - *Warnings (D-K7)*: warning 1 counts each respelling
    (=Track→gx:Track ×3=), warning 2 each loss; a run that changes only the
    stamp says nothing. Both are counted before the write over the document as
    read (=lower::survey=), so an edit that removes a respelled element still
    counts it. The lowering carries the model, so =drop_warnings= no longer
    reports a =<Model>= or a track's per-vertex data on a 2.3 → 2.2 write.
  - *Fixture*: =tests/fixtures/hand_hostile_2_3.kml=, valid 2.3 under
    =xmlschema=, every adopted element in its 2.3 spelling, children in orders
    2.2 rejects. =tests/same_format.rs= writes each version's hostile fixture
    as 2.2 and compares the features; the model's round-trip test covers it
    too.
  - *Oracles, 2026-10-28*: the lowered fixture, the same written as =.kmz=,
    and the same after =--sort-hilbert= validate under =xmllint= against
    =ogckml22.xsd= with =kml22gx.xsd=; the fixture written back as 2.3 still
    validates under =xmlschema=.
  - *The oracle is in the tree, 2026-10-28*: =tests/kml_schemas.rs=,
    =#[ignore]=d, reads =GEOSETTA_KML_SCHEMAS=, copies the schemas into a
    directory of its own with each =import= pointed at the local copy (the
    published ones import by URL, and the validators run =--nonet=), and
    validates fourteen writes: from GeoJSON and FlatGeobuf in each version;
    =sample.kml=, =duckdb_geoms.kml= and the 2.3 fixture in their own version,
    as read and edited; the 2.3 fixture lowered as read, edited and
    Hilbert-sorted; and a 2.2 source as 2.3. =GEOSETTA_KML_PYTHON= names the
    Python holding =xmlschema=. A missing schema, validator or module fails
    the run by name. *Its first run caught a K4 bug*: an edit adding a
    property to a feature whose values are in =<SchemaData>= appended the new
    =<Data>= after it, which 2.2 rejects; it now goes after the last =<Data>=,
    else before the first =<SchemaData>=.
  - /Not a gap after all/: a document holding both =<Metadata>= and
    =<ExtendedData>=, or both =<Snippet>= and =<snippet>=, is invalid 2.2,
    where each pair is one choice -- and invalid 2.3 too, where each pair
    substitutes for one =AbstractExtendedDataGroup= or =AbstractSnippetGroup=.
    No valid source holds both, so neither transform merges them.
  ***The raising to 2.3 is built, 2026-10-28.*** A 2.2 read written with
  =--kml-version 2.3= is reconciled into its own document and raised
  (=kml/raise.rs=). Nothing is reordered: 2.3's 79 content models are all
  =<all>= groups, and the generator asserts the schema has no =<sequence>=.
  - *Adopted =gx:= elements move into the KML namespace* (D-K10) where 2.3
    admits that element in that parent, from a table
    =tests/fixtures/gen_kml23_children.py= generates from =ogckml23.xsd=. Where
    it does not, the element stays =gx:=, which 2.3's =defaultOpenContent=
    admits anywhere: the =gx:= schema puts =altitudeOffset= on every geometry
    and 2.3 on line strings and rings only, so a =gx:altitudeOffset= on a
    Point is carried rather than respelled into something invalid.
    =every_2_2_placement_is_a_2_3_placement= checks the rest: every other
    child 2.2 admits, 2.3 admits too, so a raise never drops.
  - *=<Snippet>= → =<snippet>=, =<Metadata>= → =<ExtendedData>=* (§ VERSION
    TRANSFORMS), each only when nothing is lost: =<snippet>= is a plain
    string, so a =<Snippet>= with a =maxLines= other than its default, or any
    other attribute, stays; =<Metadata>= becomes =<ExtendedData>= when it
    holds only =<Data>=, =<SchemaData>= and other namespaces' elements. What
    stays is deprecated and still 2.3. Neither is projected, so the IR does not
    see the rename.
  - *The root*: =version="2.3"=, OGC's namespace -- Google's pre-OGC
    namespace rebound to it wherever declared, keeping each element's prefix
    -- and 2.3's schema where =xsi:schemaLocation= named 2.2's.
  - *Warning 1 (D-K7)* counts each respelling and rename:
    =kml: input is KML 2.2; written as KML 2.3 (gx:Track→Track, gx:coord→coord ×2)=.
    D-K7's warning 2 has nothing to report on the way up.
  - *What it retired*: =version_change_warnings='s "built from the feature
    model alone" message, and =drop_warnings='s version parameter -- every
    version change gives the model back, so a =<Model>= or a track's
    per-vertex data is never lost to one.
  - *Measured*: =tests/same_format.rs= writes each version's hostile fixture as
    each version and compares the features, and lowers the 2.3 fixture and
    raises it back to a document with no =gx:= left in it. Under the schema
    oracle, =sample.kml=, =duckdb_geoms.kml=, =hand_hostile.kml= (as read and
    edited) and the lowered 2.3 fixture all raise to valid 2.3.
    =hand_hostile.kml= is invalid 2.2 only in its order, which 2.3 does not
    fix, so raising it repairs it.
