** WHERE THIS ARISES, WHICH IS EXACTLY ONE CONFIGURATION
=main.rs= reads the output file when it exists and hands it to
=write_layers=, which keeps its layers and merges the incoming ones over by
name. So the question needs *two* containers, and there are only two:

#+begin_src text
  geosetta a.gpkg out.gpkg     out.gpkg exists   -> TWO containers, this plan
  geosetta a.gpkg new.gpkg     out does not      -> existing = None, no question
  geosetta a.gpkg -            stdout            -> never "existing", no question
  geosetta a.gpkg a.gpkg       same file         -> refused (same-format-output D4)
#+end_src

*It cannot be dodged by removing the append.* A =.gpkg= is multi-layer, and
accumulating layers into one file by repeated invocation is how you build one;
=README.md= documents it and =run_geopackage_write= implements it deliberately.

*And it is not on the edit loop's path*, which is why it can be scoped
separately from the carrying work rather than inside it. A loop writes to a
fresh path or replaces one -- and since the same-file guard landed, never to its
own input.

** THE ASYMMETRY THAT IS ALREADY THERE
Worth stating first, because it is the thing being made consistent rather than
a new problem:

| destination's… | today |
|----------------+-------|
| *layers* | *survive*, except where an incoming layer replaces one by name |
| *everything else* | *destroyed* -- defect 3, applied to the destination |

=run_geopackage_write= already warns about the second, at its *second*
=container_drop_warnings= call. So "source wins vs destination wins" is not a
question about whether the destination's content survives today. It does not.

** THE QUESTION IS NARROWER AND HARDER THAN "WHICH WINS"
Where names do not collide, every candidate rule keeps both sides. The rule
only decides *collisions* -- and collisions are the **common case, not the rare
one**. Any two =ogr2ogr=-produced GeoPackages both hold =gpkg_metadata=,
=gpkg_metadata_reference= and =gpkg_extensions=.

*** The four rules, and why none of them is right
| rule | for | against |
|------+-----+---------|
| *source wins* | consistent with layers; =gpkg -> gpkg= into a fresh file carries exactly the source | on append, silently discards the destination's rows -- backwards for the file being accumulated |
| *destination wins* | right for append: the accumulating file keeps its history | wrong for the edit loop; inconsistent with layers |
| *source only* (destination's dropped, as today) | no regression, smallest change, edit loop fully served | leaves defect 3 half-fixed, two behaviours to explain |
| *refuse on collision* | never silently wrong | fires on the ordinary path, which is the noise bar =same-format-fidelity.org= § THE RULE forbids |

***For several of these tables neither side should win.*** =gpkg_metadata= is a
*set of records*; two files' worth is two files' worth. The honest operation is
a **merge**, and the rest of this plan is what a merge actually costs.

*** ***=ge_tce= does not make a set either, and it fails on the ordinary path***
§ 3 filed the NULL trap as a =gdcc_ntv= peculiarity and listed =ge_tce= among
the keys that work. Measured, *three of the four =UNIQUE= keys on mergeable
registry tables have a nullable key column*, and SQLite treats NULLs as
distinct under =UNIQUE=:

| key | nullable member | makes a set? |
|-----+-----------------+--------------|
| =ge_tce= | =table_name= *and* =column_name= | *no* |
| =gdcc_ntv= | =value= | *no* |
| =gdc_tn= | =name= | *no* |
| =pk_gdc= | -- | yes |

**And every table-scoped extension registration has =column_name= NULL.**
=INSERT OR IGNORE=-ing one plain =ogr2ogr= file's =gpkg_extensions= into
another's deduped *nothing*: 3 + 3 -> 6, the =gpkg_metadata= and
=gpkg_metadata_reference= registration rows doubled, =integrity_check=
reporting =ok=.

That is this plan's own archetype -- "any two =ogr2ogr= GeoPackages both hold
=gpkg_metadata=" -- breaking on the most ordinary input there is. *GDAL gets it
right because it checks before inserting. It cannot be leaning on the index,
because the index does not hold.*

/=gdcc_ntv= reproduced on real GDAL output too, and with a refinement:/ a
self-merge of a field-domain file went 4 rows -> 5, duplicating the
=price_range= row. The neighbouring =_zoning_dom_domain_description= row
deduped correctly -- its =value= is the empty *string*, not NULL. So the trap
is =constraint_type = 'range'= specifically, not "constraints with no value".

***The consequence lands on § 6, not § 3.*** The written "same row" contract is
load-bearing for *three* tables rather than one, and getting the key right
substitutes for none of it: the database will not dedupe on any of them.

*** One difference in =gpkg_metadata='s DDL, which bears on § 2
GDAL writes =id INTEGER CONSTRAINT m_pk PRIMARY KEY ASC NOT NULL=; the pinned

the ids collide from 1 either way -- § 2's renumbering is needed against both.

What differs is the bookkeeping: **a GDAL-written =gpkg_metadata= has no

** WHAT THE STANDARD CAN AND CANNOT SETTLE HERE
/Written 2026-08-23, after reading the normative text for § 6 rule 3 and the
tile contract. It belongs at the top of this plan rather than inside a
requirement, because the next person will reasonably ask "what does the spec
say about this collision" and deserves the structural answer before spending an
hour finding it out./

***The GeoPackage standard constrains file state, not operations.*** It defines
what a conformant =.gpkg= contains; it has **no notion of append, merge, or
two files at all**. So it can settle what a row *is* and it cannot settle what
to do when two of them disagree.

| question | can the standard answer it? |
|----------+-----------------------------|
| what makes two rows the same record (§ 6) | *often yes* -- a declared =UNIQUE= or primary key is normative |
| may this crate rely on the index enforcing that | *sometimes no* -- see the tiles WARNING below |
| what to do when identity matches and content differs (D4, D5) | **no, and structurally so** |
| whether a value must be preserved across a rewrite (rule 3) | **no** -- and where it is silent, the silence is sometimes deliberate |

*So D4 and D5 rest on this plan's own arguments and always will.* Reading more
specification will not move them, and § THE ORACLE RULE's fourth row -- "what
does the format *require*?" -- simply has no entry for "what should a merge
do". /Two decisions were checked against the text before this was written, and
both came back silent./

**Where it does bite, it bites hard**, and § 6 has both instances: the tile
identity key is normative (Requirement 54), and the =gpkg_metadata_reference=
timestamp's *lack* of defined semantics is itself informative, because the
neighbouring =gpkg_contents.last_change= has them.

*** 4. Index rebuild -- ***BUILT 2026-10-13; D10's reversal is spent***
/=reconcile::merge_tiles= builds each autoindex from the merged rows with
=sqlite::autoindex_records=, after =sqlite::autoindex_key_columns= reads the
DDL for what each one keys on. **The parser is new and had no other caller** --
a carried index needs no key, which is exactly why D10 was cheap./

***The measurement below held, and the collations were never needed.*** No
producer emits an index this crate struggles with, so =compare_values='s
=BINARY=-only scope stands; =sqlite_constraints.gpkg='s =COLLATE NOCASE= is
hand-built and remains § 5's refusal case rather than a gap. A key carrying
=COLLATE= (other than =BINARY=) or =DESC= is **refused**, not approximated.

*The guard that is not obvious, and a mutation survived without it.* The parse
yields a count of implicit indexes, and the carried =autoindexes= were read
from the source's own b-trees -- **two independent answers to one question**.
Where they disagree the parse did not understand the table, and building
anyway writes either a fabricated index (=handoff.org= entry 20) or a declared
constraint with no b-tree (entry 15). The two halves of the same defect, and
this tree has shipped one of them. /The distinguishing input had to be built:
in every fixture the two numbers agree./

*And one property rather than a defect:* a built index is **not byte-equal** to
a carried one over identical rows. =encode_record= writes every integer as an
8-byte serial type where SQLite picks the narrowest that fits, so the records
are wider. Valid -- every index this crate has ever built is encoded that way
and =integrity_check= has always passed -- but it means a merged pyramid's
index bytes are this crate's, not SQLite's.

/The requirement as filed follows./

**** the requirement as filed
[[file:same-format-fidelity.org][same-format-fidelity.org]] D10 says a carried
table's index is *carried verbatim*, and the whole reason that is cheap is that
**an index on disk is already sorted**: an in-order read yields records that
re-pack into fresh pages without ever comparing two keys.

*A merged table's rows are in neither source's order.* Its indexes cannot be
re-packed; they have to be **built** -- which needs SQLite's comparison
semantics: the NULL < INT/REAL < TEXT < BLOB type ordering *plus* the
=BINARY=/=NOCASE=/=RTRIM= collations. That is precisely the machinery D10
scoped out, and =sqlite_constraints.gpkg= already carries a
=UNIQUE COLLATE NOCASE= to pin the case.

**So this is not an increment on M3b's carrying work. It reopens the decision
that work is built on**, and it should be reopened deliberately rather than as
a side effect of picking a collision rule.

***Measured 2026-08-23, and the cost is a fraction of the paragraph above.***
D10 is genuinely reopened -- every mergeable table carries an index, so there
is no version of this that avoids construction. But *no real producer emits an
index this crate would struggle to build*: across six GDAL files and the spec
fixture, every index is an autoindex on =BINARY= ascending key columns. The
collations are the expensive half of the sentence above and **nothing needs
them**. =sqlite_constraints.gpkg='s =COLLATE NOCASE= is hand-built, and it
remains the right fixture for § 5's refusal rather than for the general path.
See § THE MEASUREMENT.

*** 5. Refusal where a merge is undecidable -- ***BUILT 2026-10-13***
/Six refusals now, and two of them are ones this plan did not predict:/

| collision | where | grounds |
|-----------+-------+---------|
| a same-named *user table* | =reconcile::merge_tables= | D5 |
| two same-named pyramids that are **not the same pyramid** -- differing DDL, CRS, tile matrix set or matrix | =reconcile::merge_tiles= | two declarations, or two tiling schemes, have no union; under different matrices =(z, x, y)= does not even name the same ground |
| the same =(z, x, y)= carrying different bytes | =reconcile::merge_tiles= | **D4**, and it fires only on a true overlap |
| a pyramid whose index key the parse cannot honour, or whose DDL and file disagree on how many indexes it has | =reconcile::merge_tiles= | § 4 -- the parse did not understand the table, and building anyway writes entry 15 or entry 20 |
| a source object naming the other side's object of the *other kind* | =reconcile::refuse_cross_kind_collisions= | =gpkg_contents.table_name= is a primary key |
| the same =constraint_name= + =constraint_type= defining different things | =writer::schema_extension_tables= | this section's second bullet |

***And a fifth that belongs to no merge.*** Two *feature layers* sharing a
=gpkg_contents.identifier= produced a database =integrity_check= reports as
=non-unique entry in index sqlite_autoindex_gpkg_contents_2=. The carried
pyramid and carried dataset arms of =writer::gpkg_contents= had enforced
Requirement 13 since 2026-08-24; **the layers had never been checked against
each other**, because a single source cannot hold the collision -- its own
=UNIQUE= forbade it -- and an append composes two sources. =ogr2ogr -nln= copies
the identifier verbatim when it renames a layer, so the input is what a real
producer hands you, and =ogr2ogr -update -append= refuses the same case and
terminates the translation.

/Measured 2026-10-13; =handoff.org= § BUGS FOUND has both entries./

*/The requirement as filed./*

Some collisions have no correct answer and must be *reported*, not resolved:
- a same-named user table with **different DDL** -- no union exists;
- the same =constraint_name= naming different constraints;
- the same =(table_name, column_name, extension_name)= with a different
  =definition= or =scope=.

Per =same-format-fidelity.org= § A refusal honours the rule, a refusal is not a
silent loss and is therefore an acceptable answer. It is only unacceptable when
it fires on the *ordinary* path, which is why § 3's dedup has to work: without
it, every ordinary append would land here.

*** 6. A written contract for "the same row" -- ***WRITTEN 2026-08-23; IMPLEMENTED 2026-10-13***
Two =gpkg_metadata= rows with identical content and different ids are one
record; the same id with different content is two. That judgement has to be
stated per table, because §§ 2 and 3 both depend on it and neither can be
implemented until it exists.

***Written 2026-08-23, and it is load-bearing for three tables rather than
one.*** § THE MEASUREMENT killed the shortcut this requirement was competing
with: the =UNIQUE= key cannot be leaned on to dedupe for any table but
=gpkg_data_columns=, so identity has to be *stated* rather than delegated to
the database. What follows is that statement.

**** The three rules that decide every table
1. ***A surrogate id is allocation, not identity.*** =gpkg_metadata.id= and a
   tile table's =id= exist to be pointed at, not to say what a row *is*. Two
   rows differing only in a surrogate id are one record; this is what makes
   § 2's renumbering safe rather than destructive.
2. ***NULL equals NULL.*** Not SQLite's rule under =UNIQUE=, which is the
   entire content of § 3's trap, so it has to be said here or the trap is
   re-entered at every call site. Identity comparison treats two NULLs in the
   same column as equal and a NULL as unequal to every non-NULL.
3. ***A write-time stamp is provenance, not identity.***
   =gpkg_metadata_reference.timestamp= defaults to =strftime('now')=, so two
   files describing the same reference *always* disagree on it -- /measured:
   two independently built =ogr2ogr= files stamped the same logical reference
   two minutes apart./ Including it in identity would mean nothing ever
   dedupes. **That argument stands on its own and needs no oracle.**

   /GDAL corroborates it, and the corroboration is narrower than it first
   looked, so it is worth stating exactly./ =ogr2ogr -update -append= of a
   *new layer* rewrote the destination's **pre-existing**
   =gpkg_metadata_reference= row to the append time, though nothing about that
   row had changed. It is *not* a refresh on every write: appending features
   into an *existing* layer left the stamp untouched, and so did a read-only
   =ogrinfo=. What triggers it is a new metadata record, at which point GDAL
   rewrites the whole table.

   /An earlier draft of this rule said "rewrote **both** timestamps", which
   was true of the file and useless as evidence: the second row was newly
   created, so its stamp being the append time says nothing. One row carried
   the finding. Corrected on re-measurement, 2026-08-23./

   *The conditional happens to land in scope* -- a container merge is the
   layer-set-grows case -- but GDAL is the oracle for what occurs, not for
   what is right, so the standard was read rather than inferred from it.

   ***The specification constrains the format and is silent on the
   semantics.*** /Read 2026-08-23 at pinned commit =fe83fdd=,
   =spec/core/annexes/extension_metadata.adoc=./ The column description is
   "Timestamp value in ISO 8601 format as defined by the strftime function
   =%Y-%m-%dT%H:%M:%fZ= format string applied to the current time", and
   **Requirement 100** is the only SHALL that reaches it: /"Every
   =gpkg_metadata_reference= table row timestamp column value SHALL be in a
   DATETIME format as per r5."/ Requirement 5 is about *data types*. The
   abstract test suite agrees -- test case
   =/extensions/metadata/metadata_reference/timestamp= reads /"Fail if format
   of returned value does not match"/.

   So there is no requirement that the value denote a particular event, none
   to update it when anything changes, and none to preserve it. **Both
   behaviours produce conformant files**, and the column being =NOT NULL= with
   a DEFAULT means an =INSERT= supplying a value is entirely regular.

   *The contrast inside the same standard is the useful part.*
   =gpkg_contents.last_change= is described as **"timestamp of last change to
   content"** -- explicit semantics -- and carries an identically shaped,
   format-only SHALL. The standard gave one of its two DATETIME columns a
   meaning and did not give the other one. /That is an argument from silence
   and should be weighted as one/, but it cuts toward preservation: GDAL's
   rewrite treats =timestamp= as though it were a =last_change=, which is
   precisely the definition the standard declined to write.

   **Keep the destination's stamp on a dedup.** The record existed and the
   append did not create it -- and the standard leaves the choice open rather
   than making it for us.

**** The contract, table by table
| table | two rows are the same record when | on a conflict |
|-------+-----------------------------------+---------------|
| =gpkg_extensions= | =(table_name, column_name, extension_name)= match, NULLs equal | differing =definition= or =scope= -> *refuse* (§ 5) |
| =gpkg_metadata= | =(md_scope, md_standard_uri, mime_type, metadata)= match -- *=id= excluded* | none possible: different content is a different record |
| =gpkg_metadata_reference= | =(reference_scope, table_name, column_name, row_id_value)= match *and* the **mapped** =md_file_id= / =md_parent_id= match -- =timestamp= excluded | none possible: a different mapped parent is a different reference |
| =gpkg_data_columns= | =(table_name, column_name)= match -- =pk_gdc=, the one key that is sound | any other column differs -> *refuse* (§ 5) |
| =gpkg_data_column_constraints= | *depends on =constraint_type=* -- see below | differing =min=/=max=/inclusive flags/=description= -> *refuse* (§ 5) |
| =gpkg_contents= | =table_name= matches | differing =data_type= -> *refuse*; the rest follows the layer merge |
| =gpkg_geometry_columns= | =(table_name, column_name)= match | follows its layer; it is not merged independently |
| a tile table | =(zoom_level, tile_column, tile_row)= match -- *=id= excluded*; see the note below | differing =tile_data= -> **D4, open** |
| a user table | *no general answer* -- and per **D5** none is invented: a same-named user table is **refused** | see D5, and § 5 for the differing-DDL case |

***=gpkg_data_column_constraints= is the one whose identity is type-dependent***,
and saying so is the honest resolution of § 3's NULL trap rather than a
workaround for it:

| =constraint_type= | identity |
|-------------------+----------|
| =enum=, =glob= | =(constraint_name, constraint_type, value)= |
| =range= | =(constraint_name, constraint_type)= -- =value= is NULL *by definition*, and the standard admits one range row per constraint name, so it carries no information to key on |

*The trap and the contract are the same fact seen twice.* =gdcc_ntv= includes
=value= because it must cover =enum=, where the value is the row's whole point;
a =range= row has none, so the index cannot separate two of them and identity
must not try to.

***A tile table's identity is normative; its index is not.*** /Read 2026-08-23,
=spec/core/2b_tiles.adoc= at =fe83fdd=./ **Requirement 54** says every tile
pyramid user data table /"SHALL be structured consistently with"/ the table
definition and the example SQL, and that definition marks =zoom_level=,
=tile_column= and =tile_row= as **UK** -- so =(z, x, y)= is the declared unique
key, and the contract row above rests on the standard rather than on GDAL's
practice. The =id= is required to be an INTEGER primary key acting as a rowid
alias, which is exactly why § 6 rule 1 excludes it from identity.

*But the enforcement is explicitly not required*, and this is a WARNING in the
standard's own words: /"Though this standard does not technically mandate the
use of an indexing mechanism in a tiles table, the lack of such an index, e.g.,
a =UNIQUE= clause as in the example, is likely to significantly degrade the
performance of queries."/ The example SQL carrying the =UNIQUE= is labelled
**Informative**.

Two consequences, both concrete. A conformant tile table **may have no index at
all**, so nothing here may *require* one -- which also means D2's
index-building obligation is conditional on the source having declared one.
And the dedup may not lean on the index even when it is there, which is the
same conclusion § 3 reached for the registry tables by a different route.

**** What is not merged at all, because it is derived
Stated here so that "merge every table" is not read into the contract:

- =gpkg_ogr_contents= -- a row-count cache. *Recomputed* from what is actually
  written. /Its misclassification in defect 3's warning is M3b's to fix./
- =gpkg_spatial_ref_sys= -- recomputed by =resolve_srs= from the merged layer
  set, which is exactly why § 1 exists.
- the R*Tree shadow tables -- derived, rebuilt (=same-format-fidelity.org= D10).
- =sqlite_sequence= -- recomputed from the merged table's ids per § 2, *not*
  carried, which is the inversion that requirement records.

**** The order the contract forces, which §§ 2 and 3 cannot choose freely
=gpkg_metadata= identity excludes =id=, and =gpkg_metadata_reference= identity
*includes* the mapped =md_file_id=. So the two cannot be deduped in either
order:

#+begin_src text
  1. dedupe gpkg_metadata by content     -> yields an id map per side
  2. apply the map to gpkg_metadata_reference's md_file_id / md_parent_id
  3. dedupe gpkg_metadata_reference on the mapped values
  4. recompute sqlite_sequence from the merged ids
#+end_src

*Step 2 sits between the two dedups*, which is the thing an implementation
will get wrong if it treats § 3 as one pass over all tables. /This is also why
§ 2 and § 3 were filed as separate requirements and are not separable in
practice./

** WHAT § 3 LEFT BEHIND -- /2026-10-13, and it was closed the same day/
***Written when § 3 shipped and step 5 was still open; kept because what it got
wrong is the useful part.*** It called step 5 "the one thing left" and "a
feature rather than a prerequisite", and both were true -- it was built hours
later, which is the one prediction here that reads oddly in hindsight rather
than wrongly.

*What it got right and is worth not relearning:* **step 4 did not need
building.** § 2 names three obligations -- renumber one side's
=gpkg_metadata.id=, rewrite =md_file_id= / =md_parent_id= behind it, and
recompute =sqlite_sequence= rather than carry it. The first two shipped with
§ 3 because § 6's forced order left no way to do the dedup *without* them, and
the third needed no work at all: =writer::metadata_tables= had computed that

***What it got wrong, and the correction is step 5's.*** It said the

carried table and wrong once its ids move -- "applies to a **carried user

reachable case". **A merged tile pyramid is that case**, and step 5 made it
reachable within the day: its rowids move, so its mark is recomputed from the

declared unreachable because the only path to it was currently closed. The

*** D2 -- **MERGE.** Build the index; do not refuse.

*** D4 -- **REFUSE.** Decided 2026-08-23.
/Decided by the project owner, on the recommendation below and after the two
alternatives were given a fair hearing. The entry as filed follows, unchanged./

**The scope is narrower than "a tile collision", and that is why refusing is
affordable.** A set-union on =(z, x, y)= merges two pyramids covering
*adjacent* extents with no collision at all -- different coordinates, nothing
to decide. D4 fires only on a **true overlap with different bytes**: one
coordinate, two images.

*What it costs, stated plainly rather than minimised:* re-tiling the same
extent with newer imagery, by appending a second pyramid under the same table
name, is refused. That is a real workflow and the answer to it is to write a
fresh file, not to have the tool choose an image.

*Why refusing beats "source wins, per tile", which was the live alternative:*
the per-tile rule serves that workflow, and it pays for it by silently
discarding the destination's image at **every** overlap -- which is precisely
the place a user would want to be told. Per
=same-format-fidelity.org= § A refusal honours the rule, a refusal is not a
silent loss; a discarded tile is.

*And why not the layer rule:* treating a same-named tile table as a whole-table
replacement would be consistent with =write_layers='s upsert-by-name and is the
cleanest story, but it reopens **D8**, which classified a tile pyramid as
*independent container content* rather than as a layer. Reversing that to
resolve a collision that fires only on genuine overlap is a large change bought
for a small case.

**** the entry as filed -- OPEN: a tile collision on =(z, x, y)= with different =tile_data=
/Raised 2026-08-23 by § 6's contract, which settles every other table and
cannot settle this one./ Two containers each holding a tile table of the same
name, with a tile at the same =(zoom_level, tile_column, tile_row)= and
different bytes. Identical bytes dedupe under § 6 rule 1 and raise nothing.

*There is no union.* A tile coordinate holds one image; two images at one
coordinate is not a set with two members, it is a disagreement. So the
candidates are refuse, source wins, or destination wins -- and the last two
both destroy an image without saying which.

**Recommendation: refuse**, per § 5. The argument that it stays off the
ordinary path is the specific one: appending a *different* raster layer creates
a *differently named* tile table, which collides with nothing. Reaching this
case means two pyramids that were built separately and given the same name,
which is a genuine ambiguity rather than an ordinary append.

*The standard strengthens this without deciding it.* Requirement 54 makes
=(zoom_level, tile_column, tile_row)= the table's declared unique key (§ 6),
so keeping both rows would emit a table inconsistent with its own definition --
which removes "hold both" from the candidates and leaves refuse, source wins
and destination wins. Choosing among *those three* is still ours: per § WHAT
THE STANDARD CAN AND CANNOT SETTLE HERE, the text has nothing to say about what
a merge should do.

/A second-order note for whoever implements the refusal: a conformant tile
table may carry no =UNIQUE= index at all, so the collision has to be detected
by comparing rows rather than by an insert failing./

/Not decided here: whether the refusal names the first colliding tile or counts
them. Naming one is more useful and cheaper./

*** D5 -- **REFUSE.** Decided 2026-08-23, after being decided the other way and reopened.
/Decided by the project owner. It was first answered "merge on a declared key",
then reopened by the owner when it emerged that the options had been put
without the filed recommendation attached -- and re-argued, at which point a
hazard turned up that neither option had accounted for. **The reversal was the
right call and the reason is the hazard, not the process.** The entry as filed

**** The hazard that decided it -- an unchecked reference the tools cannot see
=gpkg_metadata_reference.row_id_value= is normatively /"the ROWID of a row in
the SQLite table or view identified by the =table_name= column value"/
(=spec/core/annexes/extension_metadata.adoc= at =fe83fdd=). **The DDL declares
no foreign key on it** -- =crmr_mfi_fk= and =crmr_mpi_fk= are the only two, and
both point at =gpkg_metadata(id)=.

So merging a user table renumbers its rowids, and every row-scoped metadata
reference into that table becomes silently wrong. =foreign_key_check= cannot
see it, because there is no key to check. =PRAGMA integrity_check= cannot see
it, because the database is not malformed -- it is merely *lying*.

***That is the same class as =handoff.org= § BUGS FOUND entry 15 and the
=sqlite_sequence= gap*** -- a file every verification ritual in this tree
reports green on. This project has been caught by that class twice in a
week, and the second time only because someone measured a case they had
reasoned about. **Refusing makes it structurally impossible** rather than
guarded against.

***** THE SCOPE OF THIS HAZARD IS WIDER THAN THIS SECTION SAYS -- 2026-08-25
/Correction to the paragraph above, not to the decision below. D5 stands./

"Merging a user table renumbers its rowids" is true and it is not the only
place renumbering happens. **This writer renumbers feature ids on the plain
one-container path as well** -- =writer.rs= assigns =(i + 1)= per row, so a
source holding fids =1, 9, 40= writes out =1, 2, 3=, measured 2026-08-25 and
filed as =handoff.org= § BUGS FOUND entry 19. So the unchecked reference this
section describes is *already live in shipped behaviour*, on the path this plan
treats as the safe one.

Two consequences, and neither reverses D5. First, the argument for refusing is
**stronger** than filed: the hazard is not a cost the merge introduces, it is
one the merge would compound. Second, and this is the part a reader of this
section would have got wrong -- *the one-container path was not safe either*.

***The one-container half is now closed*** (decision 27, 2026-08-25): feature
ids are carried, so a plain =gpkg -> gpkg= run no longer renumbers and no
row-scoped reference is invalidated by it. **The merge half is untouched and is
what D5 governs** -- merging two containers renumbers by necessity, because two
files' ids collide.

/The general lesson survives the fix: the hazard depends on **renumbering**,
and merging is only where it was standing when someone noticed. When §§ 3--5
are built, the =row_id_value= guard belongs wherever a rowid changes, not
wherever a merge happens./

**** Why refusing is affordable here, where D2 rejected the same move
D2 threw out "refuse for indexed tables" because it fired on **every ordinary
append**. That objection does not reach D5, and the reason is specific:
=write_layers= already upserts *feature layers* by name, so the tables D5
governs are the **non-layer** ones -- =side_notes= and its kind. No collision
on one of those has been demonstrated at all, and any two =ogr2ogr= GeoPackages
colliding on =gpkg_metadata= is a *measured* fact. The two cases are not
comparable in frequency, so the same rule is noisy in one and silent in the
other.

**** What is being given up, stated rather than minimised
A table declaring =UNIQUE (sku)= has said exactly what a duplicate is, and this
rule refuses it anyway. That is real information discarded, and the coherence
argument for using it is good: § 6 rule 1 already says a surrogate id is
allocation rather than identity, an =INTEGER PRIMARY KEY= rowid alias *is* a
surrogate, so "declared no identity" falls out of an existing rule instead of
being a special case for user tables. **That argument is not refuted -- it is
outweighed**, and only because of the hazard above.

***Reopen this when a real case appears, and reopen it into a specific shape:***
merge on the declared key, **plus** an explicit guard that refuses when any
=gpkg_metadata_reference= row with =reference_scope= of ='row'= or ='row/col'=
targets the table. That is one query, it closes the hazard, and it is the
version to build the day someone produces a colliding non-layer user table with
a declared key. /Filed as the shape rather than left to be rediscovered,
because the guard is the part that is silent if it is forgotten./

**** the entry as filed -- OPEN: a same-named user table whose DDL *matches*
/Raised 2026-08-23 by § 6, same reason./ § 5 already refuses a same-named user
table with **different** DDL, on the grounds that no union exists. Identical
DDL is a different case: a union is *expressible*. Whether it is *correct* is
the question, and § 6 rule 1 cannot answer it -- the rule says a surrogate id
is allocation rather than identity, and for a user table this crate has no way
to know whether the primary key is a surrogate or carries meaning.

**Recommendation: refuse initially, and revisit if a real case turns up.** Two
supports, and the second is the one that makes it cheap:

- *A user table has no declared identity*, so every merge rule is a guess about
  someone else's schema. Refusing says so; merging on rowid quietly asserts
  that rowids from two files are comparable, which is false in general.
- **It does not reach the ordinary path, because a feature layer never gets
  here.** =write_layers= already upserts layers by name, so the user tables
  this decision governs are the *non-layer* ones -- =side_notes= and its kind.
  Two containers colliding on one of those is rare in a way that two containers
  colliding on =gpkg_metadata= is not.

/The reason to file it rather than fold it into § 5: the refusal is being
recommended from the absence of evidence, not from a measurement. If a real
dataset turns up where a same-DDL user table is appended repeatedly, that is
the case that should reopen it./
